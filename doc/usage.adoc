Générateur de SBOM (Software Bill of Materials) à partir d'une liste mixte de paquets ou d'une image OCI.
Prend en charge les types d'entrée *RPM*, *Python wheel*, *archives tar/zip*, *paquets Debian*, *archives Java* (`.jar`), *requirements.txt*, *modules Go* (go.sum/go.mod), *paquets npm/yarn* (package-lock.json/yarn.lock), *paquets Maven* (pom.xml), *paquets Dart/Flutter* (pubspec.lock/pubspec.yaml) et *images OCI* (via syft, trivy, skopeo ou cdxgen). `--input` accepte aussi un dossier, scanné récursivement pour tous ces types.
Prend en charge les formats de sortie *CycloneDX 1.6/1.7*, *SPDX 2.3*, *SPDX 3.0 JSON-LD*, *JSON personnalisé*, *Markdown*, *AsciiDoc*, *HTML interactif* et *CSV*.

== Installation

=== Option 1 — Exécution directe avec Dart

[source,bash]
----
cd sbom_generator
dart pub get          # télécharge les dépendances (package args)
dart run bin/sbom_generator.dart --help
----

=== Option 2 — Compilation en binaire natif (recommandé)

[source,bash]
----
dart compile exe bin/sbom_generator.dart -o sbom_generator
./sbom_generator --help
----

Le binaire `sbom_generator` est autonome, aucun SDK Dart requis pour l'exécuter.

== Syntaxe

....
sbom_generator -i <fichier> [options]
sbom_generator -I <image-oci> [options]
sbom_generator -i <fichier> -I <image-oci> [options]
sbom_generator --binary <fichier> [options]
sbom_generator diff <sbom-a> <sbom-b> [--json] [--output <fichier>]
sbom_generator merge <sbom1> <sbom2> ... -o <sortie> [-n <nom>]
sbom_generator convert -i <sbom-source> -f <format> -o <sortie>
sbom_generator licenses -i <sbom-source> -o <licences.adoc>
sbom_generator validate <sbom1> [<sbom2> ...]
sbom_generator scan --sbom <fichier> [options]
sbom_generator cra --sbom <fichier> [options]
....

|—
|—

|`--rpm-dir <dossier>`
|`-d`
|—

|`--concurrency <N>`
|`-c`
|`4`
|Nombre de paquets traités simultanément (`0` = illimité)

|`--license-map <fichier>`
|`-l`
|—
|Fichier de substitution de licences (`nom: SPDX-expression` par ligne)

|`--deny-license <motif>`
|—
|—
|Refuser les composants dont la licence correspond au motif SPDX (correspondance partielle,

|`--sdk-version <sdk>=<ver>`
|—
|—
|Vraie version d'un SDK Dart/Flutter (répétable —

`creationInfo.creators` (SPDX 2.3), éléments `Tool` (SPDX 3.0). C'est ainsi

|`--flutter-root <dir>`

|`--tlp <classification>`
|—
|—

|`--patent-map <fichier>`
|—
|—

|`--min-quality-score <score>`

== Format du fichier d'entrée

Un fichier texte, *une référence par ligne*. Les types peuvent être mélangés
librement dans le même fichier.

=== Types de références acceptées

[cols="2,2,2", options="header"]
|===
|Type |Exemple |Mécanisme

|Nom de paquet RPM installé
|`bash`
|`rpm -q bash`

|NEVRA complet
|`bash-5.1.8-6.el9.x86_64`
|`rpm -q bash-5.1.8-6.el9.x86_64`

|Fichier `.rpm` local
|`/mnt/repo/bash-5.1.8.rpm`
|`rpm -qp /mnt/repo/bash-5.1.8.rpm`

|Wheel Python `.whl`
|`/opt/wheels/requests-2.28.0-py3-none-any.whl`
|`python3 zipfile` (extraction METADATA)

|Archive tar `.tar.gz` / `.tgz` / `.tar`
|`/opt/src/mariadb-11.4.8.tar.gz`
|`python3 tarfile` → PURL `pkg:pypi/…` ou `pkg:generic/…`

|Archive ZIP `.zip`
|`/opt/src/mylib-1.0.zip`
|`python3 zipfile` → PURL `pkg:pypi/…` ou `pkg:generic/…`

|Paquet Debian `.deb`
|`/opt/pkgs/libssl3_3.0.1_amd64.deb`
|`dpkg-deb -f`

|Archive Java `.jar`
|`/opt/libs/my-lib-1.2.3.jar`
|`pom.properties` embarqué, sinon `META-INF/MANIFEST.MF`, sinon nom de
fichier ; PURL `pkg:maven/…`. Un jar « shaded »/uber-jar embarquant des
dépendances relocalisées (chacune avec son propre `pom.properties`) produit
un composant par dépendance, en plus du jar lui-même.

|Fichier `requirements.txt`
|`/opt/project/requirements.txt`
|Parseur pur Dart (PEP 508 simplifié)

|Modules Go (`go.sum`)
|`/opt/myapp/go.sum`
|Parseur pur Dart — extrait module et version ; PURL `pkg:golang/…`

|Modules Go (`go.mod`)
|`/opt/myapp/go.mod`
|Parseur pur Dart — extraits des directives `require` ; PURL `pkg:golang/…`

|Paquets npm (`package-lock.json`)
|`/opt/myapp/package-lock.json`
|Parseur pur Dart — lockfileVersion 1, 2 et 3 ; PURL `pkg:npm/…`

|Paquets yarn (`yarn.lock`)
|`/opt/myapp/yarn.lock`
|Parseur pur Dart — yarn v1 classique et yarn v2+ Berry ; PURL `pkg:npm/…`

|Dépendances Maven (`pom.xml`)
|`/opt/myapp/pom.xml`
|Parseur pur Dart — scope compile/provided, hors test et dependencyManagement ; PURL `pkg:maven/…`

|Lockfile Dart/Flutter (`pubspec.lock`)
|`/opt/flutterapp/pubspec.lock`
|Parseur pur Dart — versions résolues + fermeture transitive, toutes sources (hosted/git/path/sdk), hors `direct dev` ; PURL `pkg:pub/…`. Paquets `source: sdk` sans version (voir `--sdk-version`). Licences lues depuis le cache pub (voir `--pub-cache` / `--flutter-root`)

|Manifeste Dart/Flutter (`pubspec.yaml`)
|`/opt/flutterapp/pubspec.yaml`
|Parseur pur Dart — section `dependencies:` seulement (hors `dev_dependencies:`) ; PURL `pkg:pub/…`
|===

=== Règles de syntaxe

* Les lignes vides sont ignorées.
* Les lignes commençant par `#` sont des commentaires et sont ignorées.
* Les paquets identiques (même `bomRef`) sont automatiquement dédupliqués.

=== Raccourci : passer directement une archive unique

`--input` accepte aussi directement le chemin d'une archive ou d'un paquet
unique (`.zip`, `.tar`, `.tar.gz`, `.tgz`, `.whl`, `.deb`, `.rpm`, `.jar`), ou
d'un manifeste unique reconnu par son nom exact (`requirements.txt`, `go.sum`,
`go.mod`, `package-lock.json`, `yarn.lock`, `pom.xml`, `pubspec.lock`,
`pubspec.yaml`), sans passer par un fichier liste intermédiaire :

[source,shell]
----
sbom_generator -i /opt/3PP/myapp-2.0.0-linux-amd64.zip -o sbom
sbom_generator -i /opt/libs/my-lib-1.2.3.jar -o sbom
sbom_generator -i /opt/flutterapp/pubspec.lock -o sbom
----

Pour tout autre chemin de fichier, `--input` reste interprété comme un
fichier liste (une référence par ligne, voir ci-dessus).

=== Raccourci : passer directement un dossier

Si `--input` pointe vers un **dossier**, celui-ci est scanné récursivement
(liens symboliques ignorés) à la recherche de tous les types de fichiers du
tableau ci-dessus : `.rpm`, `.deb`, `.whl`, `.jar`, `.zip`,
`.tar`/`.tar.gz`/`.tgz`, ainsi que les manifestes reconnus par leur nom exact
(`requirements.txt`, `pom.xml`, `go.sum`, `go.mod`, `package-lock.json`,
`yarn.lock`, `pubspec.lock`, `pubspec.yaml`). Si `pubspec.lock` et
`pubspec.yaml` coexistent dans un même dossier, seul le `.lock` est retenu.
Un `.txt` qui ne s'appelle pas exactement `requirements.txt`
n'est donc pas retenu, contrairement au fichier liste où n'importe quel
`.txt` (hors `.whl`) est traité comme un fichier de requirements.

[source,shell]
----
sbom_generator -i /opt/app/libs -o sbom
----

Les noms de paquets RPM nus (ex. `bash`, sans chemin ni extension) ne
peuvent pas être découverts ainsi : ce ne sont pas des fichiers. Utilisez un
fichier liste ou `--rpm-dir` pour ce cas.

=== Générer la liste depuis un système installé

[source,bash]
----
# Tous les paquets RPM installés
rpm -qa > packages.txt

# Paquets d'un groupe spécifique
rpm -qa --queryformat '%{NAME}\n' | grep ^python > python_pkgs.txt

# Fichiers RPM d'un répertoire ISO/dépôt monté
find /mnt/BaseOS/Packages -name '*.rpm' > rpm_files.txt
----

== Exemples d'utilisation

=== Génération CycloneDX (défaut)

[source,bash]
----
./sbom_generator -i packages.txt -o sbom.cdx.json
----

=== SPDX 2.3 avec nom personnalisé

[source,bash]
----
./sbom_generator -i packages.txt -f spdx -n "Mon Application" -o sbom.spdx.json
----

=== SPDX 3.0 JSON-LD

[source,bash]
----
./sbom_generator -i packages.txt -f spdx3 -o sbom.spdx3.jsonld
----

=== JSON détaillé avec mode verbeux

[source,bash]
----
./sbom_generator -i packages.txt -f json -n "Système RHEL 9" -o sbom.json -v
----

=== Fichiers RPM depuis un dépôt monté

[source,bash]
----
find /mnt/BaseOS/Packages -name '*.rpm' > liste.txt
find /mnt/AppStream/Packages -name '*.rpm' >> liste.txt
./sbom_generator -i liste.txt -f cyclonedx -n "RHEL 9 BaseOS+AppStream" -o rhel9.cdx.json
----

=== Multi-format en un seul passage

[source,bash]
----
./sbom_generator -i packages.txt -f cyclonedx,spdx,markdown -o sbom
# Génère : sbom.cdx.json + sbom.spdx.json + sbom.md
----

=== Traitement parallèle et override de licences

[source,bash]
----
# 8 paquets en parallèle + substitution de licences
./sbom_generator -i packages.txt -c 8 -l overrides.txt -o sbom.cdx.json
----

=== Résolution de noms RPM depuis un dossier local

[source,bash]
----
# Les noms nus (bash, glibc…) sont résolus dans /mnt/repo au lieu de rpm -q
./sbom_generator -i packages.txt -d /mnt/repo -o sbom.cdx.json
----

=== Analyse d'une image OCI (via syft, défaut)

[source,bash]
----
./sbom_generator -I nginx:latest -f cyclonedx -n "nginx" -o nginx.cdx.json
----

Avec les backends `syft`, `trivy` et `cdxgen` (pas `skopeo`), le SBOM
CycloneDX/SPDX généré inclut un composant dédié pour l'OS de base de l'image
— nécessaire
pour qu'un outil comme Trivy (`trivy sbom`), rescanné plus tard sur ce
fichier, évalue aussi les CVE des paquets système (RPM/DEB/APK), pas
seulement celles des paquets applicatifs. Sans ce composant, ces CVE
seraient silencieusement absentes du résultat.

NOTE: À l'inverse, il est normal qu'un SBOM généré avec le backend `syft`
fasse remonter, une fois passé dans `trivy sbom`, *quelques* CVE Java en
plus que `trivy image` sur la même image directement — ce n'est pas un
faux positif du SBOM, mais une sous-détection de l'analyseur de jars
intégré à Trivy. Vérifié sur une image RHEL 9.6/Keycloak : 3 CVE HIGH
(`micrometer-core`, `postgresql`) trouvées via le SBOM mais absentes de
`trivy image` en direct, alors que les deux scans portent sur la même
image. Cause : Trivy identifie un jar Maven via `pom.properties`, puis
`MANIFEST.MF`, puis un lookup par hash SHA-1 dans sa base
`trivy-java-db` (indexée depuis Maven Central) ; les jars concernés sont
des rebuilds internes Red Hat (`.redhat-000xx`) sans `pom.properties` et
absents de Maven Central, donc les trois méthodes échouent et Trivy
abandonne silencieusement le paquet — aucun avertissement. Syft, lui, a
un fallback supplémentaire : il sait parser le nom de fichier
`<groupId>.<artifactId>-<version>.jar`, la convention utilisée par le
packaging Quarkus « fast-jar » (répertoire `lib/main/`) de cette image,
et détecte donc ces paquets là où l'analyseur intégré de Trivy échoue.

=== Analyse d'une archive tar exportée avec docker save

Les formats `.tar`, `.tar.gz` et `.tgz` sont détectés automatiquement.

[source,bash]
----
./sbom_generator -I ./ubuntu.tar --oci-tool trivy -f spdx -o ubuntu.spdx.json

# Archive compressée (docker save ubuntu | gzip > ubuntu.tar.gz)
./sbom_generator -I ./ubuntu.tar.gz --oci-tool syft -f cyclonedx -o ubuntu.cdx.json
----

=== Analyse d'un OCI layout directory via skopeo

[source,bash]
----
./sbom_generator -I ./oci_layout/ --oci-tool skopeo -o sbom.cdx.json
----

=== Analyse via cdxgen (OWASP CycloneDX Generator)

`cdxgen` produit un SBOM CycloneDX complet de l'image ; le générateur ne
retient que les composants porteurs d'un PURL d'écosystème réel
(`pkg:deb`, `pkg:rpm`, `pkg:apk`, `pkg:pypi`, `pkg:npm`, `pkg:golang`,
`pkg:maven`…). L'inventaire fichier par fichier (`pkg:generic/…` de type
`file`), les actifs cryptographiques et les dépôts APT émis par cdxgen sont
écartés, pour un résultat cohérent avec `syft`/`trivy`. L'OS de base est
reconstitué depuis le qualifiant `distro=` des PURL système (cdxgen n'émet
pas de composant `operating-system` dédié).

[source,bash]
----
./sbom_generator -I nginx:latest --oci-tool cdxgen -o nginx.cdx.json
----

NOTE: `cdxgen` est distribué via npm (`npm install -g @cyclonedx/cdxgen`) et
requiert Node.js. Registre distant, archive tar et OCI layout directory sont
tous acceptés.

[[sec-binaire-statique]]
=== Analyse d'un binaire lié statiquement (`--binary`)

[source,bash]
----
./sbom_generator --binary /usr/local/bin/mon-app -o app.cdx.json
----

`--binary <fichier>` est une variante explicite d'`--image <fichier>` :
`--image` accepte n'importe quel chemin, et quand ce n'est ni une archive
tar ni un répertoire OCI layout, syft détecte lui-même qu'un chemin local
existant n'est pas une référence d'image et l'analyse directement comme
fichier — c'est ce mécanisme qui permet de lire les dépendances embarquées
dans un binaire autonome, sans registre ni conteneur. `--binary` **force
`--oci-tool syft`** (seul backend supporté ici) et refuse toute combinaison
avec `--oci-tool trivy|skopeo|cdxgen` ou avec `--image`.

[IMPORTANT]
====
Portée réelle, à connaître avant de s'y fier pour un rapport de conformité :

* *Go* (lié statiquement ou non) — la liste complète des modules + versions
  est lue depuis les métadonnées `buildinfo` embarquées dans le binaire
  (celles que `go version -m` affiche), via le `go-module-binary-cataloger`
  de syft. Fonctionne même sur un exécutable strippé, tant que le build n'a
  pas explicitement supprimé cette section.
* *Autres binaires* (Rust, C/C++ liés statiquement…) — syft applique un
  classifieur générique qui reconnaît, par empreinte de chaîne de version,
  un catalogue *fixe* de bibliothèques open source connues (OpenSSL, zlib,
  sqlite, busybox…). Ce n'est pas une extraction arbitraire des dépendances
  liées — seules les bibliothèques du catalogue sont détectées.
* Une bibliothèque liée statiquement sans signature reconnue ni métadonnée
  embarquée (C/C++ « fait maison », Rust sans `cargo-auditable`) *ne peut
  pas* être retrouvée après coup — il faudrait tracer les dépendances au
  moment du build (ex. embarquer un JSON de dépendances comme le fait
  `cargo-auditable` pour Rust).
====

=== Analyse de vulnérabilités (`scan`)

Interroge un ou plusieurs scanners externes sur un SBOM déjà généré, avec un
filtrage optionnel par date de publication ou de modification des CVE.

[cols="2,1,3", options="header"]
|===
|Option |Défaut |Description

|`--sbom <fichier>` / `-s`
|_(obligatoire)_
|Fichier SBOM à analyser (`.cdx.json`, `.spdx.json`…)

|`--scanner <valeur>` / `-S`
|`grype`
|`grype`, `osv`, `trivy`, ou `all` pour les trois

|`--cve-after <AAAA-MM-JJ>`
|—
|N'affiche que les CVE publiées/modifiées après cette date

|`--cve-before <AAAA-MM-JJ>`
|—
|N'affiche que les CVE publiées/modifiées avant cette date

|`--cve-date-field <valeur>`
|`published`
|Champ de date utilisé pour le filtre : `published`, `modified`, ou `latest`

|`--include-undated`
|désactivé
|Inclut les CVE sans date connue dans les résultats filtrés

|`--enrich` / `--no-enrich`
|activé
|Enrichit chaque CVE avec les signaux d'exploitabilité (CISA KEV, EPSS, PoC
public, sous-score CVSS). `--no-enrich` (ou `SBOMGEN_OFFLINE=1`) : aucune
requête réseau — seuls les champs déjà fournis par les scanners (Grype
expose nativement KEV + EPSS) et le cache local sont utilisés.

|`--no-poc`
|—
|Ne pas interroger la source PoC tierce (poc-in-github). KEV, EPSS et la
maturité `E:` du vecteur CVSS restent renseignés.

|`--enrich-timeout <s>`
|`8`
|Délai maximal, en secondes, par requête d'enrichissement.

|`--only-kev`
|—
|Ne garde que les CVE présentes au catalogue CISA KEV.

|`--epss-min <x>`
|—
|Ne garde que les CVE dont le score EPSS est ≥ `x` (entre 0 et 1).

|`--sort <valeur>`
|`severity`
|Ordre d'affichage console : `severity` (pire sévérité d'abord) ou `risk`
(KEV, puis EPSS décroissant, puis sévérité).

|`--format <valeur>` / `-f`
|`text`
|`text` (console colorée), `sarif` (SARIF 2.1.0), ou `markdown` / `asciidoc` /
`pdf` (rapport de synthèse inter-scanners — résumé global, répartition par
sévérité pour chaque scanner, matrice de présence CVE × scanner). `pdf` =
`asciidoc` + conversion via `asciidoctor-pdf` (si absent, le `.adoc` est
conservé à côté).

|`--output <fichier>` / `-o`
|—
|Fichier de sortie. Requis pour `markdown` / `asciidoc` / `pdf` ; pour
`sarif`, écrit sur stdout si omis.

|`--color <valeur>`
|`auto`
|Coloration ANSI des alertes Critical/High listées sur stdout par les
formats rapport : `auto` (couleur si terminal + `NO_COLOR` non défini),
`always`, `never`.
|===

[source,bash]
----
# Toutes les CVE grype (scanner par défaut)
./sbom_generator scan --sbom sbom.cdx.json

# Toutes les CVE grype publiées depuis 2024
./sbom_generator scan --sbom sbom.cdx.json --cve-after 2024-01-01

# CVE OSV-Scanner entre deux dates
./sbom_generator scan --sbom sbom.cdx.json --scanner osv \
  --cve-after 2023-06-01 --cve-before 2024-01-01

# Les trois scanners, champ "dernière modification", CVE sans date incluses
./sbom_generator scan --sbom sbom.cdx.json --scanner all \
  --cve-date-field modified --cve-after 2023-01-01 --include-undated

# Export SARIF (intégration GitHub Code Scanning) vers un fichier
./sbom_generator scan --sbom sbom.cdx.json --scanner all \
  --format sarif --output resultats.sarif

# Rapport de synthèse PDF (Grype + OSV-Scanner + Trivy)
./sbom_generator scan --sbom sbom.cdx.json --scanner all \
  --format pdf --output scan-report.pdf

# Uniquement les CVE activement exploitées (CISA KEV), triées par risque
./sbom_generator scan --sbom sbom.cdx.json --scanner all --only-kev --sort risk

# Prioriser : CVE avec une probabilité d'exploitation EPSS ≥ 10 %
./sbom_generator scan --sbom sbom.cdx.json --epss-min 0.1

# Hors-ligne (CI sans accès réseau) : signaux via Grype + cache seulement
./sbom_generator scan --sbom sbom.cdx.json --no-enrich
----

Les résultats `--format text` sont triés par sévérité décroissante
(`Critical` → `Unknown`) et affichés en tableau texte, un par scanner
interrogé. En `--format sarif`, un `run` SARIF est produit par scanner
interrogé, avec une règle par identifiant de vulnérabilité. L'échec d'un
scanner (binaire absent, sortie JSON illisible) n'empêche pas les autres
scanners demandés (`--scanner all`) de s'exécuter.

Grype est lancé avec les mêmes options que l'onglet Grype de l'interface
graphique — notamment `--add-cpes-if-none` (Grype synthétise un CPE pour les
composants qui n'en ont pas, sinon il ne matche que par PURL) et `--by-cve`
(identifiant CVE plutôt que GHSA). `scan` et la GUI rapportent donc les mêmes
CVE sur un même SBOM.

Les formats `markdown`, `asciidoc` et `pdf` produisent un *rapport de
synthèse* dans le fichier `--output` : résumé global (scanners exécutés,
nombre de CVE uniques tous scanners confondus, total brut), répartition par
sévérité pour chaque scanner, puis une matrice « CVE × scanner » (✓/—) triée
par sévérité — les identifiants distro-préfixés d'OSV-Scanner
(`DEBIAN-CVE-…`) sont ramenés à la forme nue avant la comparaison. Ces
formats retournent le code `0` dès qu'un rapport est produit, quel que soit
le nombre de CVE (le code `1` reste réservé à `text` / `sarif`). C'est ce
que `scripts/build-dist.sh` utilise pour joindre un PDF de synthèse à côté de
l'archive de distribution.

Une section *« Notes par CVE »* suit la matrice quand c'est pertinent : pour
chaque CVE où Grype ne voit *aucun correctif* pour la distribution installée
(état `won't fix` / `not fixed`, repris du statut `<no-dsa>` du Debian
Security Tracker) alors qu'OSV-Scanner ou Trivy annoncent une version
corrigée, une note précise que cette version est généralement le correctif
porté dans les branches _unstable_ / _testing_ de la distribution — pas une
mise à jour installable sur la release stable. Cette divergence est une
source de confusion fréquente : les deux scanners ont raison, ils ne parlent
simplement pas de la même chose.

En plus du fichier, ces trois formats *listent sur stdout chaque CVE
Critical (en rouge) et High (en orange)*, une ligne par CVE unique
(dédupliquée entre scanners), avec le paquet concerné et les scanners qui
l'ont vue, puis un décompte. `--color auto` (défaut) colore seulement si
stdout est un terminal et `NO_COLOR` non défini ; `--color always` force la
couleur (utile derrière un pipe — `build-dist.sh` l'active quand le terminal
du build le permet), `--color never` n'émet que les préfixes `[CRITICAL]` /
`[HIGH]`.

Codes de retour (`--format text` / `sarif`) : `0` = aucune CVE dans la plage
demandée (tous scanners confondus), `1` = au moins une CVE trouvée, ou erreur
de scanner. Les formats rapport (`markdown` / `asciidoc` / `pdf`) renvoient
`0` dès qu'un rapport est écrit ; `1` seulement si `--output` manque ou si
aucun scanner n'a produit de résultat.

=== Exploitabilité et exploitation active

La sévérité (CVSS) dit la gravité *potentielle* d'une faille, pas si un
attaquant peut ou va s'en servir. `scan` complète donc chaque CVE avec quatre
signaux de priorisation :

[cols="1,3", options="header"]
|===
|Signal |Ce qu'il indique

|*CISA KEV*
|La CVE est au catalogue _Known Exploited Vulnerabilities_ de la CISA :
exploitation active *confirmée* dans la nature. Le rapport reprend la date
d'ajout, l'échéance de remédiation et l'éventuel usage par un rançongiciel.

|*EPSS*
|Score _Exploit Prediction Scoring System_ (FIRST.org), 0 à 1 : probabilité
que la CVE soit exploitée dans les 30 jours, avec son percentile (rang
relatif parmi toutes les CVE).

|*PoC / exploit public*
|Un exploit est réellement disponible : dépôt(s) GitHub recensé(s) par
`poc-in-github`, ou maturité `E:` (au moins _Proof-of-Concept_) du vecteur
CVSS quand un CNA la publie.

|*Exploitabilité CVSS*
|Sous-score d'exploitabilité du vecteur (0 à 3,9) : combine vecteur d'attaque
(AV), complexité (AC), privilèges (PR) et interaction (UI). Calculé
localement, sans réseau.
|===

Sources : Grype fournit déjà KEV, EPSS et le vecteur CVSS dans sa base — les
requêtes réseau ne servent qu'à enrichir les CVE vues uniquement par
OSV-Scanner / Trivy et à récupérer le signal PoC. Les réponses sont mises en
cache 24 h sous `~/.cache/sbom-generator/` ; en cas de coupure réseau, le
cache (même périmé) prend le relais. `--no-enrich` (ou `SBOMGEN_OFFLINE=1`)
désactive tout appel réseau.

En `--format text`, trois colonnes s'ajoutent au tableau : `KEV` (✓/—),
`EPSS` (score + percentile), `PoC` (`✓n` = _n_ dépôts, `✓` = maturité CVSS,
`—` = aucun, `?` = inconnu). Les alertes Critical/High des formats rapport
portent les marqueurs `[KEV]`, `EPSS <score>` et `[PoC]`. Le rapport de
synthèse gagne une section *« Exploitabilité et exploitation active »* : liste
des CVE KEV avec dates, puis un tableau *« Priorisation par risque »* trié par
KEV, puis EPSS, puis sévérité. En `--format sarif`, chaque résultat porte les
propriétés `kev`, `epss`, `epssPercentile`, `poc` et `cvssExploitability`, et
`security-severity` passe à `9.5` pour une CVE KEV (priorisation GitHub Code
Scanning).

`--only-kev` et `--epss-min` restreignent la sortie (tous formats) ;
`--sort risk` réordonne l'affichage console.

=== Rapport de conformité Cyber Resilience Act (`cra`)

Produit un rapport de conformité au Règlement (UE) 2024/2847 (*Cyber
Resilience Act*) à partir d'un SBOM et, optionnellement, d'une analyse de
vulnérabilités.

[IMPORTANT]
====
Le rapport ne couvre que les exigences *vérifiables automatiquement* :

* *format et complétude du SBOM* — format d'usage courant lisible par machine
  et couverture des dépendances (Annexe I §2 point 1) ; champs de données par
  composant (BSI TR-03183-2 : nom, version, fournisseur, identifiant unique
  PURL/CPE, empreinte, licence) ; éléments minimaux NTIA 2021 ;
* *gestion des vulnérabilités* — inventaire des vulnérabilités connues
  (point 1) et disponibilité des correctifs (point 2) ;
* *vulnérabilités activement exploitées* — toute CVE au catalogue CISA KEV est
  signalée comme déclenchant l'obligation de notification à l'ENISA et au CSIRT
  coordinateur *sous 24 h* (art. 14).

Les autres obligations du CRA (mécanisme de diffusion sécurisé des mises à
jour, politique de divulgation coordonnée effective, conception sûre par
défaut, tests réguliers, notifications réglementaires, déclaration UE de
conformité) *relèvent du fabricant* et sont seulement listées. **Ce document
n'est pas une déclaration de conformité.**
====

[cols="2,1,3", options="header"]
|===
|Option |Défaut |Description

|`--sbom <fichier>` / `-s` |_(obligatoire)_ |SBOM à évaluer (CycloneDX ou SPDX JSON)
|`--config <cra.yaml>` / `-c` |`./cra.yaml` si présent |Métadonnées fabricant / produit (voir ci-dessous)
|`--manufacturer` / `--product` / `--product-version` |— |Surchargent le fichier de config
|`--support-until <AAAA-MM-JJ>` |— |Date de fin de la période de support (art. 13 §8)
|`--vuln-contact <e-mail\|URL>` |— |Adresse de signalement des vulnérabilités (Annexe I §2 point 6)
|`--cvd-policy-url <URL>` |— |Politique de divulgation coordonnée (point 5)
|`--scan` / `--no-scan` |activé |Lancer une analyse de vulnérabilités pour évaluer l'inventaire et les correctifs
|`--scanner <grype\|osv\|trivy\|all>` |`grype` |Scanner(s) à utiliser avec `--scan`
|`--enrich` / `--no-enrich` |activé |Enrichissement CISA KEV / EPSS (réseau)
|`--format <pdf\|asciidoc\|json>` / `-f` |`pdf` |Format de sortie
|`--output <fichier>` / `-o` |— |Requis pour `pdf` / `asciidoc` ; `json` sur stdout si omis
|===

[source,bash]
----
# Rapport PDF, métadonnées depuis cra.yaml, analyse Grype
./sbom_generator cra --sbom sbom.cdx.json --config cra.yaml -o rapport-cra.pdf

# Rapport JSON machine-lisible sans analyse de vulnérabilités
./sbom_generator cra --sbom sbom.cdx.json --no-scan --format json

# Métadonnées en ligne de commande
./sbom_generator cra --sbom sbom.cdx.json --manufacturer "ACME Corp" \
  --product WidgetOS --product-version 3.2.1 -o rapport-cra.pdf
----

Fichier `cra.yaml` (toutes les clés sont facultatives, `clé: valeur` par
ligne, `#` pour un commentaire) :

[source,yaml]
----
manufacturer: "ACME Corp"
product: "WidgetOS"
product_version: "3.2.1"
support_until: "2030-12-31"
vulnerability_contact: "security@acme.example"

----

À défaut de valeur fournie, `cra` tente de déduire le fabricant et le produit
de `metadata.component` / `metadata.supplier` du SBOM.

Le PDF suit la même charte que le rapport `scan` (page de garde, résumé
exécutif chiffré, verdict). Codes de retour : `0` = conforme ou conforme avec
réserves sur le périmètre vérifié, `2` = non conforme (au moins un point
bloquant : format non lisible par machine, champ obligatoire manquant,
vulnérabilité sans correctif, CVE activement exploitée).

=== Pourquoi les scanners ne trouvent pas les mêmes CVE

Avec `--scanner all`, il est normal qu'une bonne partie des CVE ne soient
signalées que par un seul des trois outils. Sur une même image (RHEL 9.6,
Keycloak) analysée directement par Grype et par Trivy, une comparaison
brute des identifiants ne fait ressortir que 72 CVE communes sur ~210
identifiants uniques de chaque côté — un écart qui a deux causes :

* *Nomenclature d'identifiant différente (cause principale)* — sur les
  paquets Java (JAR/Maven), Grype nomme ses trouvailles avec l'identifiant
  GitHub Security Advisory (`GHSA-xxxx-xxxx-xxxx`, sa source principale
  pour cet écosystème) tandis que Trivy préfère le CVE correspondant. C'est
  la même vulnérabilité sous deux noms différents. Sur cette image, l'accord
  brut n'était que de 2 CVE Java sur ~135 de chaque côté ; une fois les
  `GHSA-*` de Grype résolus vers leur CVE lié (champ
  `relatedVulnerabilities` de la sortie JSON de Grype), l'accord monte à
  132/135 (~98 %). Sur les paquets RPM (base OS), où les deux outils
  utilisent nativement l'identifiant CVE, l'accord était déjà direct à
  ~94 % (70 CVE communes sur ~75 de chaque côté).
* *Écarts réels résiduels* — Grype (base Anchore) et Trivy (`trivy-db`)
  republient leurs bases de vulnérabilités à des rythmes et depuis des
  sources pas parfaitement identiques (NVD, GHSA, OVAL/CSAF Red Hat…). Un
  CVE tout juste publié, ou pas encore mappé au CPE exact d'un paquet, peut
  apparaître chez l'un avant l'autre.

Aucun des deux scanners n'est « la » vérité : `--scanner all` sert
précisément à obtenir l'union des trois plutôt que de se fier à un seul.

=== Empreintes cryptographiques des composants

`sbom_generator` renseigne l'empreinte d'un composant **sans requête
réseau**, quand la source la fournit :

* `integrity` des lockfiles npm (`package-lock.json`) et yarn v1
  (`yarn.lock`), et `sha256` de `pubspec.lock` ;
* champ `Digest` de Trivy et digests d'artefact de Syft (ex. SHA-1 des JAR)
  lors de l'analyse d'une image OCI (`--image`) ;
* empreintes des composants produits par cdxgen ;
* SHA-256 + SHA-512 calculés localement pour un fichier `.rpm` / `.deb` /
  `.jar` / `.whl` passé directement en entrée ;
* `%{SIGMD5}` (empreinte `MD5`) pour un paquet RPM *installé* interrogé par
  nom — le « pkgid » RPM (MD5 de l'en-tête + payload), seule identité de
  contenu disponible quand il n'y a pas de fichier.

Seuls les condensats hexadécimaux d'un artefact/paquet réel sont retenus
(les formats dérivés — dirhash Go `h1:`, checksum APK `Q1…` — sont écartés).
Le condensat de l'*en-tête* RPM (`%{SHA256HEADER}`) est exposé comme
propriété `rpm:header-sha256` et non comme empreinte d'artefact.

L'empreinte est écrite dans `hashes` (CycloneDX), `checksums` (SPDX 2.3) et
`verifiedUsing` (SPDX 3.0). *Pour un SBOM issu d'une image OCI, la plupart
des paquets système restent sans empreinte* : ni Syft ni Trivy ne
reconstruisent systématiquement leur `Digest` (contrairement au chemin
« liste de RPM » qui interroge `%{SIGMD5}` directement).

=== Fournisseur (`supplier`) des composants

Le champ fournisseur est repris de la source quand elle le porte :

[cols="2,3", options="header"]
|===
|Source |Champ

|RPM |`%{VENDOR}`
|Debian `.deb` |`Maintainer:`
|Image OCI |`Vendor` (rpm) / `maintainer` (dpkg, apk) / `author` (selon le backend)
|Wheel Python |`Author-email`, sinon `Author` / `Maintainer` du `METADATA` (souvent absent)
|Maven (`pom.xml`, `.jar`) |`groupId` (namespace, à défaut d'éditeur explicite)
|npm (`package-lock.json`) |champ `author` du `package.json` de chaque paquet dans `node_modules` — **le lockfile ne le contient pas** ; l'arbre `node_modules` doit être présent
|`go.sum`/`go.mod`, `requirements.txt`, `yarn.lock`, `pubspec.lock` |_(aucun — ces formats ne portent pas d'éditeur)_
|===

Quand la source ne fournit rien, `--supplier "<nom>"` donne une valeur de
repli (elle n'écrase **jamais** un fournisseur détecté). Utile quand tu
génères le SBOM d'un produit dont tu es l'éditeur.

En SPDX 2.3, un fournisseur inconnu est écrit `NOASSERTION` (valeur explicite
demandée par la spéc, prise en compte par les éléments minimaux NTIA et
`sbomqs`) plutôt qu'omis. En CycloneDX, les clés `supplier` / `publisher`
sont simplement absentes. Le champ `supplier` est *obligatoire* dans
BSI TR-03183-2 (rapport `cra`).

[source,bash]
----
# SBOM d'une app Node dont l'éditeur est « ACME Corp »
./sbom_generator -i package-lock.json --supplier "ACME Corp" -f spdx -o sbom.spdx.json
----

=== Dépendances

Les dépendances sont résolues *au sein de la liste fournie* :

* `rpm -q --requires <pkg>` → liste des capabilities requises
* `rpm -q --provides <pkg>` → liste des capabilities fournies
* Résolution : si le paquet A requiert une capability que le paquet B fournit, une relation `A → B` est ajoutée
* Les dépendances externes (`glibc`, `systemd`…) non présentes dans la liste apparaissent dans les propriétés `rpm:requires` mais pas dans `dependsOn`

== Formats de sortie en détail

=== CycloneDX 1.6 / 1.7 (`cyclonedx`)

Structure JSON (1.6, par défaut) :

....
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.6",
  "metadata": { timestamp, tools, authors, supplier, lifecycles, licenses, component },
  "components": [ { type, bom-ref, name, version, purl, cpe, hashes, licenses,
                     supplier, externalReferences, properties } ],
  "dependencies": [ { ref, dependsOn[] } ],
  "compositions": [ { aggregate, assemblies[], dependencies[] } ]
}
....

Chaque `dependencies[].dependsOn` contient les `bom-ref` des paquets dont dépend le composant.
L'entrée racine liste tous les composants du SBOM.

Avec `--cyclonedx-version 1.7`, des champs supplémentaires apparaissent selon les options
fournies (absents du schéma 1.6, donc n'apparaissent jamais en 1.6) :

* `metadata.distributionConstraints.tlp` — via `--tlp`
* `citations[]` racine, attribuant `/components` à l'outil source — automatique dès que
  `--image` est utilisé (attribution à `--oci-tool`)
* `components[].patentAssertions[]` + `definitions.patents[]` — via `--patent-map`

[[patent-map]]
==== Déclarations de brevets (`--patent-map`)

Fichier texte, une déclaration par ligne :

....
package_name: numéro_brevet|juridiction|statut_légal|type_assertion
openssl: US1234567|US|granted|license
....

* `juridiction` : code WIPO ST.3 à 2 lettres (`US`, `EP`, `JP`…)
* `statut_légal` : `pending`, `granted`, `revoked`, `expired`, `lapsed`, `withdrawn`,
  `abandoned`, `suspended`, `reinstated`, `opposed`, `terminated`, `invalidated`, `in-force`
* `type_assertion` : `ownership`, `license`, `third-party-claim`, `standards-inclusion`,
  `prior-art`, `exclusive-rights`, `non-assertion`, `research-or-evaluation`

=== SPDX 2.3 (`spdx`)

Structure JSON :

....
{
  "spdxVersion": "SPDX-2.3",
  "creationInfo": { created, creators },
  "packages": [ { SPDXID, name, versionInfo, downloadLocation, licenseConcluded,
                   licenseDeclared, copyrightText, externalRefs, annotations } ],
  "relationships": [ { spdxElementId, relationshipType, relatedSpdxElement } ]
}
....

Types de relations : `DESCRIBES` (document → paquets) et `DEPENDS_ON` (dépendances résolues).

=== SPDX 3.0 JSON-LD (`spdx3`)

Structure JSON-LD :

....
{
  "@context": "https://spdx.org/rdf/3.0.0/spdx-context.jsonld",
  "@graph": [
    { type: "SpdxDocument", profileConformance: ["core","software"], … },
    { type: "CreationInfo", specVersion: "3.0.0", … },
    { type: "Tool", … },
    { type: "Organization", … },         ← un par fournisseur unique
    { type: "software:Package", … },     ← un par paquet RPM
    { type: "Relationship", relationshipType: "describes", … },
    { type: "Relationship", relationshipType: "dependsOn", … }
  ]
}
....

=== JSON personnalisé (`json`)

Inclut toutes les métadonnées RPM brutes (`requires`, `provides`) ainsi que les
dépendances résolues en noms lisibles. Idéal pour du scripting ou de l'intégration
personnalisée.

== Dépannage

=== `rpm: command not found`

Installez le paquet `rpm` :

[source,bash]
----
# Fedora/RHEL
sudo dnf install rpm

# Debian/Ubuntu
sudo apt install rpm
----

=== `python3 not found — required to read .whl, tar, and zip archives`

Installez Python 3 :

[source,bash]
----
# Fedora/RHEL
sudo dnf install python3

# Debian/Ubuntu
sudo apt install python3
----

=== `dpkg-deb not found — required to read .deb files`

Installez `dpkg` :

[source,bash]
----
# Fedora/RHEL
sudo dnf install dpkg

# Debian/Ubuntu
sudo apt install dpkg
----

=== `unzip not found — required to read .jar files`

Installez `unzip` :

[source,bash]
----
# Fedora/RHEL
sudo dnf install unzip

# Debian/Ubuntu
sudo apt install unzip
----

=== `Warning: cannot query "pkg"`

Le paquet n'est pas installé ou le fichier `.rpm` est inaccessible.
Vérifiez avec `rpm -q <paquet>` ou `rpm -qp <fichier.rpm>`.

=== Doublons dans la liste d'entrée

Si le même paquet (même NEVRA) apparaît plusieurs fois (par ex. présent dans BaseOS
et AppStream), il n'est inclus qu'une seule fois dans le SBOM. Un message
`($N doublon(s) supprimé(s))` l'indique.

=== `syft / trivy / skopeo / cdxgen: command not found`

L'outil OCI demandé n'est pas installé ou n'est pas dans le PATH.

Installez l'outil via son script officiel ou le gestionnaire de paquets du système
(`cdxgen` : `npm install -g @cyclonedx/cdxgen`, requiert Node.js).
Vérifiez avec `which syft`, `which trivy`, `which skopeo` ou `which cdxgen`.

=== `Échec de l'analyse OCI : …`

Si l'analyse OCI échoue (image inaccessible, registre privé, permissions réseau) :

* Vérifiez que la référence est accessible : `docker pull <image>` ou `skopeo inspect docker://<image>`
* Pour un registre privé, authentifiez-vous au préalable : `docker login`, `skopeo login`
* Pour une archive locale, vérifiez que le fichier existe : `ls -lh /path/image.tar` (les formats `.tar`, `.tar.gz` et `.tgz` sont supportés)

=== Fichier SBOM très volumineux

Les propriétés `rpm:requires` peuvent représenter 50 à 150 entrées par paquet.
Sur 779 paquets, le fichier CycloneDX peut atteindre 3 Mo. C'est normal.

Les images OCI peuvent contenir plusieurs centaines de paquets (images de base
Ubuntu : ~100, images applicatives complexes : 300–800).
