Tous les générateurs travaillent sur `List<Package>` — la classe abstraite
commune à `RpmPackage`, `WheelPackage`, `DebPackage` et `OciPackage`.
`WheelPackage` est également réutilisé pour Go, npm, yarn, Maven et
Dart/Flutter (`packageType='pub'`) via le champ `packageType`.

== `lib/models.dart` — Hiérarchie de types

=== Classe abstraite `Package`

Interface commune à tous les types de paquets. Tous les générateurs et
`buildDependencies` travaillent exclusivement avec cette interface.

[source,dart]
----
abstract class Package {
  // Champs communs
  String get name;
  String get version;
  String get license;
  String get url;
  String get summary;
  String get vendor;
  String get arch;
  String get sourceRef;
  List<PackageHash> get hashes;   // empreintes de l'artefact (souvent vide)
  List<String> get requires;
  List<String> get provides;

  // Identifiants calculés
  String get fullVersion;   // version affichable
  String get purl;          // Package URL (purl-spec)
  String get bomRef;        // identifiant CycloneDX unique
  String get spdxId;        // identifiant SPDX (SPDXRef-…)
  String get packageType;   // 'rpm' | 'pypi' | 'source' | 'deb'
}
----

La fonction utilitaire de bibliothèque `_safeId(String s)` remplace tout
caractère hors `[a-zA-Z0-9._-]` par `-`. Elle est utilisée dans les
implémentations de `bomRef` et `spdxId` de tous les types de paquets.

=== Empreintes cryptographiques — `PackageHash` et `lib/hash_utils.dart`

`PackageHash(alg, content)` : `alg` au format CycloneDX (`SHA-256`,
`SHA-512`, `SHA-1`, `MD5`, `SHA3-256`…), `content` hexadécimal minuscule.
`lib/hash_utils.dart` centralise la collecte et n'accepte **que le condensat
hexadécimal d'un artefact réel** (bonne longueur pour l'algorithme) :

* `normalizeHashAlg` / `packageHash` — liste blanche d'algorithmes,
  validation hex ; rejette `h1`, `Q1…`, `sha224`, valeurs tronquées ;
* `packageHashFromDigestString` — `"<algo>:<hex>"` (champ `Digest` de Trivy) ;
* `packageHashFromSri` — Subresource Integrity `"sha512-<base64>"`
  (npm/yarn) → hexadécimal ;
* `hashesFromSyftMetadata` — `metadata.archiveDigests` / `digests` / `digest`
  d'un artefact Syft ;
* `hashesFromCycloneDx` — tableau `hashes` d'un composant cdxgen ;
* `hashLocalFile` — SHA-256 + SHA-512 d'un fichier local (`package:crypto`) ;
* `spdx2Alg` / `spdx3Alg` — conversion des libellés vers `SHA256` /
  `sha256` / `sha3_256`.

Populé par : `npm_parser`, `yarn_parser` (v1), `pubspec_parser`,
`deb_parser` / `jar_parser` / `wheel_parser` (entrée fichier directe),
`rpm_parser` (fichier `.rpm` → SHA-256/512 ; paquet installé → `%{SIGMD5}`
en `MD5`), `oci_parser` (chemins Syft, Trivy, cdxgen). `RpmPackage` porte en
plus `headerSha256` (`%{SHA256HEADER}` — hash de l'*en-tête* RPM, pas du
fichier `.rpm`), émis en propriété/annotation `rpm:header-sha256`.

Émis par les trois générateurs (CycloneDX `hashes`, SPDX 2.3 `checksums`,
SPDX 3.0 `verifiedUsing`) et relu par `sbom_reader` lors d'un `convert`.

NOTE: Pour un SBOM issu d'une *image OCI*, la plupart des paquets système
restent sans empreinte (installés dans l'image, pas d'artefact à hacher ;
ni Syft ni Trivy ne reconstruisent systématiquement le `Digest`). Le chemin
« liste de RPM » interroge `%{SIGMD5}` directement et couvre donc tous les
paquets installés.

|`SPDXRef-golang-`

|`'npm'`
|`package-lock.json` ou `yarn.lock` (via `NpmParser` / `YarnParser`)
|`pkg:npm/<name>@<ver>`

|`'pub'`

|OCI / lockfiles Rust
|`pkg:cargo/<name>@<ver>`
|`pkg-src-`

Le nom Python est normalisé selon PEP 503 dans le PURL (`_normalizePyName` :
minuscules, `[-_.]+ → -`).

[NOTE]
====
Les chemins de modules Go contiennent des `/` qui *ne doivent pas* être
encodés en `%2F` dans un PURL (spec PURL Go). Le getter `purl` de `WheelPackage`
gère ce cas spécialement : `pkg:golang/$gn@$v` (sans `Uri.encodeComponent`).
====

Le champ `arch` contient le platform tag du wheel (ex. `any`, `linux_x86_64`)
ou l'architecture détectée depuis le nom de fichier pour les archives génériques.

== `lib/rpm_parser.dart` — Interrogation RPM

=== Constante `_queryFormat`

[source,dart]
----
static const _queryFormat =
    r'%{NAME}|%{VERSION}|%{RELEASE}|%{ARCH}|%{EPOCH}|%{LICENSE}|%{VENDOR}|%{URL}|%{BUILDTIME}|%{SHA256HEADER}|%{SOURCERPM}|%{SIGMD5}|%{SUMMARY}\n';
----

`SUMMARY` est en dernier car il peut contenir des `|`. Le parser rejoint tous
les fragments ≥ index 12 en cas de split excédentaire.

Empreintes :

* `%{SHA256HEADER}` → `RpmPackage.headerSha256`, émis en propriété
  `rpm:header-sha256` (hash de l'*en-tête*, pas du fichier) ;
* `packageRef` = fichier `.rpm` → `hashLocalFile` : SHA-256 + SHA-512 du
  fichier ;
* sinon (paquet installé) → `%{SIGMD5}` (« pkgid » RPM : MD5 en-tête +
  payload), validé par `packageHash('MD5', …)` → empreinte `MD5`.

=== `parsePackage(String packageRef)`

Les trois appels `rpm` sont lancés en *parallèle* via `Future.wait` :

[source,dart]
----
final results = await Future.wait([
  Process.run('rpm', [qFlag, '--queryformat', _queryFormat, packageRef]),
  Process.run('rpm', [qFlag, '--requires', packageRef]),
  Process.run('rpm', [qFlag, '--provides', packageRef]),
]);
----

. `rpm -q[p] --queryformat ...` → 13 champs de métadonnées
. `rpm -q[p] --requires` → liste des capabilities requises (parsée par `_parseCapabilities`)
. `rpm -q[p] --provides` → liste des capabilities fournies (parsée par `_parseCapabilities`)

Retourne `null` avec un avertissement sur `stderr` si le premier appel échoue.

=== `_parseCapabilities(ProcessResult result)` _(nouveau)_

Méthode synchrone remplaçant l'ancien `_queryCapabilities` asynchrone.
Prend un `ProcessResult` déjà disponible et retourne `List<String>` (vide si `exitCode != 0`).

=== `buildDependencies(List<Package> packages)`

Accepte une liste mixte RPM + Python. L'algorithme fonctionne en deux passes.

*Passe 1 — construction de `providesMap`*

....
providesMap : capability name → bomRef
....

Pour chaque paquet : le `name` du paquet + chaque entrée de `provides` sont
ajoutés. Les paquets Python incluent leur nom normalisé dans `provides`, ce qui
permet la résolution intra-Python.

*Passe 2 — résolution des `requires`*

Chaque entrée de `requires` est normalisée via `_capabilityName()` puis cherchée
dans `providesMap`. Une dépendance n'est ajoutée que si la cible est dans la
liste (`knownRefs`).

=== `_capabilityName(String capability)`

[source,dart]
----
return capability.split(RegExp(r'\s+[<>=!]'))[0].trim();
----

[cols="2,1", options="header"]
|===
|Entrée |Sortie

|`bash >= 4.1`
|`bash`

|`python3dist(lxml) >= 3.0`
|`python3dist(lxml)`

|`libc.so.6(GLIBC_2.17)(64bit)`
|`libc.so.6(GLIBC_2.17)(64bit)`

|`/bin/sh`
|`/bin/sh`

|`requests` (Python, déjà normalisé)

== `lib/wheel_parser.dart` — Lecture des wheels Python

=== Fonctionnement

Le wheel est un ZIP contenant un répertoire `{name}-{version}.dist-info/METADATA`.
La classe utilise `python3 zipfile` pour extraire ce fichier sans dézipper l'archive
entière.

[source,python]
----
z = zipfile.ZipFile(sys.argv[1])
name = next(x for x in z.namelist() if x.endswith('/METADATA'))
sys.stdout.buffer.write(z.read(name))
----

=== `parseWheelFile(String path)`

Appelle python3, récupère le texte METADATA, délègue à `_buildPackage()`.

=== `parseMetadataText(String sourceRef, String text, {String packageType})`

*Point d'extension public* utilisé par `TarParser` pour réutiliser le parseur
RFC 822 sans dupliquer le code. Permet de construire un `WheelPackage` depuis
un texte déjà extrait.

=== Parsing RFC 822 (`_parseRfc822`)

Retourne `Map<String, List<String>>` : clé en minuscules → liste de valeurs.
Les lignes de continuation (indent) sont concaténées.

=== Extraction des champs clés

[cols="1,1,2", options="header"]
|===
|Champ METADATA |Priorité |Fallback

|License
|`License-Expression` (PEP 639)
|`License` → classifiers `License :: OSI Approved :: …`

|URL
|`Project-URL: Homepage, …`
|`Home-page`

|Vendor
|`Author-email` (strip `<addr>`)
|`Author` → `Maintainer`

|Arch
|dernier segment `-` avant `.whl`
|`any`

|Requires
|`Requires-Dist` (strip contraintes et markers)
|—
|===

`WheelPackage.provides = [normalizedName]` (nom normalisé PEP 503).

== `lib/tar_parser.dart` — Lecture des archives tar

=== Script Python embarqué

Le script est exécuté via `python3 -c` et retourne un objet JSON sur stdout :

[source,json]
----
{"type": "python", "content": "<texte RFC 822>"}
----

ou

[source,json]
----
{"type": "generic", "licenseFile": "LICENSE", "license": "<2 KB du fichier>"}
----

*Logique de détection* (dans cet ordre) :

. Cherche `*.dist-info/METADATA` ou `**/PKG-INFO` → type `python`
. Cherche `LICENSE`, `COPYING`, `LICENSE-*`, `LICENCE`, `COPYING.*` à profondeur ≤ 2
  → type `generic` avec le contenu du premier fichier trouvé (trié par profondeur puis longueur)

=== Cas Python sdist

Si `type == 'python'` : délègue à `WheelParser().parseMetadataText(path, content)`
→ retourne un `WheelPackage` avec `packageType='pypi'`.

=== Cas archive générique

Si `type == 'generic'` : délègue à `buildGenericArchivePackage()` (depuis `archive_helpers.dart`) :

. Analyse le nom de fichier via `parseArchiveFilename()`
. Identifie la licence via `identifyArchiveLicense()`
. Retourne un `WheelPackage` avec `packageType='source'`

[NOTE]
====
Ces fonctions sont désormais dans `lib/archive_helpers.dart` (partagées avec
`ZipParser`). La logique est identique à l'ancienne implémentation privée de `TarParser`.
====

=== Parsing du nom de fichier (`parseArchiveFilename` dans archive_helpers)

*Algorithme :*

. Supprimer l'extension (`.tar.gz`, `.tgz`, `.tar`)
. Découper sur `-`
. Trouver l'index du premier segment correspondant à `^\d+\.\d+` (version sémantique)
. *Nom* = segments avant la version, moins les mots-clés plateforme
. *Version* = le segment version
. *Arch* = premier segment reconnu comme architecture

*Mots-clés filtrés du nom* (`_isPlatformSegment`) :

* OS : `linux`, `windows`, `darwin`, `macos`, `win`, `osx`
* Arch : `x86_64`, `x64`, `amd64`, `arm64`, `aarch64`, `i386`, `i686`
* Divers : `systemd`, `community`, `enterprise`
* Distros (regex) : `rhel8`, `rhel88`, `el9`, `fc40`, `centos7`, `ubuntu22`, …

=== Identification de licence (`identifyArchiveLicense` dans archive_helpers)

Travaille sur les 2 000 premiers caractères du fichier de licence.
Utilise deux zones :

* *`title`* (300 premiers chars) pour les familles GPL/LGPL — évite le faux positif :
  GPL-2.0 mentionne « GNU Library General Public License » dans son corps, mais
  pas dans son titre.
* *`lower`* (2 000 chars) pour Apache, MIT, SSPL, MPL, etc.

Licences reconnues : `SSPL-1.0`, `Apache-2.0`, `Apache-1.1`, `GPL-2.0-only`,
`GPL-3.0-only`, `LGPL-2.0-only`, `LGPL-2.1-only`, `LGPL-3.0-only`, `MPL-2.0`,
`MPL-1.1`, `MIT`, `ISC`, `BSD-2-Clause`, `BSD-3-Clause`, `EPL-2.0`, `EPL-1.0`,
`CDDL-1.0`.

[WARNING]
====
Le texte GPL-2.0 contient « use the GNU Library General Public License instead »
dans la section « How to Apply ». Vérifier uniquement le titre (300 premiers chars)
empêche ce faux positif LGPL.
====

== `lib/license_normalizer.dart` — Normalisation SPDX centralisée

Factorisation de la logique de normalisation des licences qui était auparavant
enfouie dans `cyclonedx_generator.dart`. Désormais importé par les trois
générateurs (CycloneDX 1.6, SPDX 2.3, SPDX 3.0).

=== `LicenseNormalizer` (méthodes toutes `static`)

[cols="2,1,2", options="header"]
|===
|Méthode |Retour |Usage

|`toSpdxExpression(String raw)`
|`String`
|Expression SPDX pour SPDX 2.3 / 3.0

|`toCycloneDxLicenses(String raw)`
|`List<Map<String, dynamic>>`
|Structure `licenses[]` CycloneDX 1.6
|===

=== Algorithme commun

. Cas vide / `(none)` → retourne vide
. Normalisation des opérateurs booléens (`and` → `AND`, `or` → `OR`, `with` → `WITH`)
  avec regex lookbehind/lookahead `\S` pour protéger les tokens collés
  (`GPL-2.0-or-later` non altéré)
. Détection d'expression composée (présence de `AND`/`OR`/`WITH` entourés d'espaces)
. Résolution token par token dans `_sortedEntries` (tri longueur décroissante →
  évite les matches courts avant les longs)
. Choix du champ CycloneDX : `expression` (composé) ; sinon `id` **si et
  seulement si** le token figure dans `kSpdxLicenseIds` (`lib/spdx_license_ids.dart`)
  ou est une cible vérifiée de `_rpmToSpdx` ; sinon `name`. `LicenseRef-*` va
  toujours en `name` (hors énumération SPDX du schéma CycloneDX).

[WARNING]
====
Ne jamais rétablir l'ancienne heuristique « le token contient un tiret+chiffre
→ `id` » : elle faisait passer en `license.id` les raccourcis `debian/copyright`
(`GFDL-NIV-1.3`, `BSD-3-clause-Berkeley`, `GPL-2.0-only+-with-link-exception`…),
produisant un SBOM CycloneDX rejeté par la validation de schéma (id hors
énumération SPDX). Le champ `id` est désormais gardé par
`_isSpdxLicenseId()` → `isSpdxLicenseId()` (appartenance exacte, sensible à la
casse, à `kSpdxLicenseIds`).
====

`lib/spdx_license_ids.dart` est un instantané figé de la SPDX License List 3.x
(identifiants licences + exceptions). Un id réellement SPDX absent de
l'instantané dégrade proprement en `name` / `LicenseRef-…` (toujours
schéma-valide) — la liste est donc volontairement large sans viser
l'exhaustivité. `curl` en est retiré exprès : `debian/copyright` l'emploie
comme nom vague, on le garde en texte libre.

[TIP]
====
`_sortedEntries` est `static final` — calculé une seule fois au chargement de la
classe. L'ancien code retriait la table à chaque appel de `_normaliseExpressionTokens`.
====

== `lib/jar_parser.dart` — Coordonnées Maven d'un `.jar` autonome

Contrairement à `MavenParser` (qui lit un manifeste `pom.xml`), `JarParser` extrait les
coordonnées Maven directement d'une archive `.jar` binaire, en miroir de la logique déjà
utilisée pour le scan d'images OCI dans `oci_parser.dart` (`_parseMavenJars` ci-dessous),
mais retourne des `WheelPackage(packageType: 'maven')` (comme `maven_parser.dart`) plutôt
que des `OciPackage` — pas de notion d'`imageRef` pour un fichier local.

*Un `.jar` peut produire plusieurs paquets.* Un jar « shaded »/uber-jar (ex.
`netty-common-*.jar`) peut embarquer, en plus de son propre `pom.properties`, celui d'une
ou plusieurs dépendances relocalisées (ex. `org.jctools:jctools-core`). `parseJarFile`
retourne donc une *liste* : le jar lui-même en premier élément (si son identité a pu être
déterminée), suivi d'un élément par dépendance embarquée détectée — même comportement que
syft, qui liste séparément chaque `pom.properties` trouvé (avec un `virtualPath` du type
`/netty-common-*.jar:org.jctools:jctools-core`).

=== `JarParser`

[source,dart]
----
class JarParser {
  Future<List<WheelPackage>> parseJarFile(String path) async { … }
  Future<List<(String, String, String)>> _readAllPomProperties(String path) async { … }
  Future<(String, String, String)?> _readSinglePomProperties(String path, String entryPath) async { … }
  Future<String?> _groupIdFromManifest(String path) async { … }
  bool _looksLikeGroupId(String s) => s.contains('.') && s == s.toLowerCase() && !s.contains(' ');
}
----

=== Résolution de l'identité propre + des dépendances embarquées

. `_readAllPomProperties` liste *tous* les
  `META-INF/maven/<groupId>/<artifactId>/pom.properties` présents dans
  l'archive (`unzip -l` puis un `unzip -p <jar> <chemin exact>` *par entrée*,
  jamais un glob concaténant plusieurs blocs — voir bug ci-dessous) et
  retourne un `(groupId, artifactId, version)` par entrée exploitable.
. Parmi ces entrées, celle dont l'`artifactId` correspond au nom de fichier
  du jar (préfixe avant le premier `-<chiffre>`) est l'identité *propre* du
  jar ; s'il n'y a qu'une seule entrée au total, elle est prise par défaut.
  Toutes les *autres* entrées deviennent des paquets supplémentaires
  (dépendances relocalisées).
. Si aucune entrée ne correspond au nom de fichier (jar ambigu, plusieurs
  `pom.properties` sans correspondance claire), l'identité propre retombe sur
  la convention de nom `<groupId>.<artifactId>-<version>.jar` (Quarkus/Red
  Hat), puis sur `META-INF/MANIFEST.MF` (`Bundle-SymbolicName`,
  `Implementation-Vendor-Id`, `Implementation-Title`,
  `Automatic-Module-Name`, dans cet ordre — première occurrence de chaque
  clé conservée, repliement de ligne RFC 822 géré, valeur retenue seulement
  si `_looksLikeGroupId` l'accepte : au moins un point, entièrement en
  minuscules — rejette par ex. `javafx.baseEmpty`).
+
*Découvert par comparaison avec syft sur un jeu réel de 207 jars* : ce
comportement le reproduit exactement pour la quasi-totalité des cas testés
(ex. `caffeine` → `com.github.ben-manes.caffeine` via `Bundle-SymbolicName`,
`commons-httpclient` → `org.apache` via `Implementation-Vendor-Id`
prioritaire sur `Implementation-Title`). Les entrées `pom.properties` déjà
identifiées comme dépendances embarquées restent remontées même dans ce cas.
. Si le manifeste ne donne rien d'exploitable non plus, `groupId` reprend la
  valeur d'`artifactId` (`pkg:maven/<artifactId>/<artifactId>@<version>`) —
  dégradé mais *non abandonné*.
. Liste vide (+ avertissement `stderr`) seulement si ni identité propre ni
  dépendance embarquée n'ont pu être déterminées (aucun `pom.properties`
  exploitable et aucun suffixe de version reconnaissable dans le nom de
  fichier).

*Bug corrigé, découvert sur un jar réel* (`netty-common-4.1.100.Final.jar`) :
lire le `pom.properties` via un glob large
(`META-INF/maven/*/*/pom.properties`) sans discrimination concatène le
contenu de toutes les entrées trouvées, et un parsing clé=valeur naïf se
fait écraser par le second bloc — le jar `netty-common` ressortait avec
l'identité `jctools-core` ! Même cause sur `woodstox-core-6.5.1.jar`
(embarque `isorelax` et `net.java.dev.msv:xsdlib`). Lire chaque entrée
*individuellement* (étape 1 ci-dessus) élimine complètement le risque de
mélange, tout en permettant de les remonter correctement comme paquets
séparés plutôt que de choisir arbitrairement laquelle garder.

=== `_knownGroupIdOverrides` — correspondances curées (Spring Framework)

Certaines bibliothèques très répandues (les modules « core » de Spring Framework :
`spring-core`, `spring-beans`, `spring-webmvc`, …) n'exposent leur vrai groupId
(`org.springframework`) nulle part dans le jar lui-même — ni `pom.properties`, ni un champ
manifeste fiable : seul un `Automatic-Module-Name` du type `spring.core` est présent, qui
passe `_looksLikeGroupId` (point, minuscules) mais est un nom de module JPMS, pas le
groupId Maven réel.

*Conséquence concrète, pas seulement cosmétique* : un scanner de vulnérabilités (grype…)
associe les CVE aux vraies coordonnées Maven. Avec `pkg:maven/spring.core/spring-core@…`
au lieu de `pkg:maven/org.springframework/spring-core@…`, aucune correspondance n'est
trouvée — des CVE réelles et non corrigées (ex. CVE-2025-41249, CVE-2024-38820,
CVE-2025-22233, toutes sur `org.springframework:spring-core`) restaient invisibles.
Détecté en comparant un scan de vulnérabilités sur nos SBOM vs ceux de syft.

`_knownGroupIdOverrides` (`Map<String artifactId, String groupId>`) est vérifiée *avant*
l'heuristique manifeste — elle doit gagner face à une valeur de manifeste trompeuse.
Volontairement limitée aux ~22 modules officiels de Spring Framework (liste stable,
groupId `org.springframework` uniquement) : ce n'est pas une tentative de répliquer un
dictionnaire CPE complet comme celui de syft, seulement de combler ce trou précis, à
impact sécurité direct. Spring Data/Integration/Retry/Security n'y figurent pas : leur
manifeste expose déjà le vrai groupId via `Implementation-Vendor-Id`.

Requiert `unzip` dans le PATH (vérification dans `bin/sbom_generator.dart`,
`hasJar` → `unzip -v`).

[[sec-syft-binary]]
==== Analyse d'un binaire autonome (`OciRefType.binary`, voir `--binary`)

`syft <chemin> --output json` fonctionne sur un binaire autonome parce que
*syft détecte lui-même* qu'un argument correspondant à un fichier local
existant est une source *fichier* (pas une image à résoudre/pull), et lui
applique ses catalogueurs de binaires :

* *Go* — `go-module-binary-cataloger` lit les métadonnées `buildinfo`
  embarquées dans l'exécutable (celles de `go version -m`) et retrouve la
  liste complète des modules + versions, que le binaire soit lié
  statiquement ou non, même strippé (tant que le build n'a pas
  explicitement supprimé cette section).
* *Autres langages* — seul le classifieur générique de syft s'applique : il
  reconnaît, par empreinte de chaîne de version, un catalogue *fixe* de
  bibliothèques open source connues (OpenSSL, zlib, sqlite, busybox…).

Aucun code de `sbom_generator` n'implémente cette extraction — c'est
entièrement délégué à syft ; `_parseSyft` ne fait ici que transmettre le
chemin tel quel. Une bibliothèque liée statiquement sans signature connue
ni métadonnée embarquée (C/C++ « fait maison », Rust sans
`cargo-auditable`) n'est pas récupérable après coup.

Les licences syft sont des objets `{spdxExpression, value}` — `spdxExpression`
est préféré si non vide, sinon `value`. Plusieurs licences sont jointes par
`' AND '`.

`vendor`, `arch`, `summary` et `url` du composant sont lus via
`_firstNonEmpty(metadata, [...])` : les catalogueurs syft n'emploient pas la
même casse selon l'écosystème (dpkg/apk exposent `architecture` / `maintainer`
en minuscules, rpm `arch` / `vendor`). Le mainteneur dpkg/apk sert de
`supplier` du composant à défaut d'un champ `vendor` rpm — sans lui, le SBOM
n'a aucun fournisseur de composant (métrique `comp_with_supplier` de sbomqs).

[[sec-syft-source-pkg]]
==== Paquets source (`_syftSourcePackage`)

OSV.dev indexe les avis Debian/Ubuntu par paquet *source* (`zlib`, `perl`,
`sqlite3`), pas par paquet binaire (`zlib1g`, `perl-base`, `libsqlite3-0`).
syft ne catalogue que le binaire, en y ajoutant un qualifiant PURL
`upstream=<source>` — qu'OSV-Scanner (scalibr) ne sait pas exploiter : sur un
SBOM syft brut, OSV-Scanner ne matche donc quasiment aucun paquet système
(19 CVE sur `haproxy:3.4.4`, contre 58 avec un SBOM cdxgen).

`_parseSyft` émet donc, en plus des binaires, un composant par paquet source
distinct : `_syftSourcePackage()` lit `metadata.source` / `metadata.sourceVersion`
de l'artefact, dérive le PURL source du PURL binaire normalisé (remplacement
du nom et de la version, suppression de `upstream=`), et déduplique par nom
de source. Un source n'est pas émis si un composant porte déjà ce nom (cas
`perl` binaire + `perl-base`, tous deux de source `perl`).

Corollaire : `_syftArtifactToPackage` retire `upstream=` du PURL du binaire
dès que `metadata.source` diffère du nom. Sinon Grype résoudrait binaire→source
*et* matcherait le composant source explicite → même CVE comptée deux fois
(224 correspondances brutes au lieu de 80, 68 CVE en double). cdxgen, qui
n'émet pas `upstream=`, ne double-compte pas — on s'aligne dessus. L'ensemble
des CVE *uniques* rapportées par Grype est identique avant/après (vérifié) :
seul le sur-comptage d'une CVE sur chaque binaire d'un même source disparaît.

[[sec-syft-debian-purl]]
==== Normalisation du qualifiant `distro` Debian (`_normalizeSyftSystemPurl`)

Pour Debian, syft renseigne le qualifiant `distro` des PURL système et le
champ racine `distro.versionID` avec la *point release* lue dans
`/etc/debian_version` (ex. `debian-13.6`), et non le majeur `13` porté par
`VERSION_ID` d'`/etc/os-release`. Grype tolère cette forme (il ne retient que
le majeur), mais OSV-Scanner en mode « scan de SBOM » (scalibr) ne rattache un
`pkg:deb/debian/...` à l'écosystème `Debian:13` que si `distro` vaut
`debian-<majeur>` **ou** si `distro_name` porte un nom de code connu — avec
`debian-13.6` il ne trouve *silencieusement* rien (0 CVE, sans erreur).

`_normalizeSyftSystemPurl()` ramène donc `distro=debian-X.Y` à
`distro=debian-X` et ajoute `distro_name=<codename>` (repris de
`distro.versionCodename` fourni par syft), s'alignant sur ce que produit
cdxgen. `_syftDistroToOsInfo()` applique la même troncature au majeur pour le
composant `operating-system`. Traitement limité à `id == debian` : pour
alpine (`3.20.3`), rhel (`9.6`)… le mineur porte une information et reste
intact. Vérifié sur `haproxy:3.4.4` (Debian 13.6) : sans le correctif
OSV-Scanner remontait 0 CVE là où Grype en voyait 163 (toutes `wont-fix` /
`not-fixed`, sans version corrigée) ; avec, les trois scanners se recoupent.

=== Backend Trivy (`_parseTrivy`)

Lit `Results[].Type` (ex. `debian`, `centos`, `pip`) et le normalise via
`_normalizeTrivyType()` vers les écosystèmes de `packageType` (`deb`, `rpm`,
`pypi`, etc.). Le PURL est lu depuis `Identifier.PURL` (trivy ≥ 0.38).

`trivy image` (le seul mode invoqué ici) ne supporte pas l'analyse d'un
binaire autonome — passer un `OciRefType.binary` à ce backend transmettrait
le chemin tel quel (branche `registry`/`binary` du `switch`) et échouerait
côté trivy. C'est pourquoi `--binary` (voir <<sec-option-binary>>) rejette
tout `--oci-tool` autre que `syft`.

[[sec-osinfo-oci-parser]]
=== `OsInfo` — OS de base (`_syftDistroToOsInfo` / `_trivyMetadataToOsInfo` / `_cdxgenOsInfo`)

`OciParser` extrait l'OS de base de l'image (voir la classe `OsInfo` sous
<<sec-models>>) pour permettre à
`CycloneDxGenerator`/`SpdxGenerator`/`Spdx3Generator` de générer un
composant `operating-system` dédié dans le SBOM. Sans lui, un consommateur
comme Trivy en mode `trivy sbom` ignore silencieusement toute la classe de
vulnérabilités « os-pkgs » (paquets système RPM/DEB/APK), même si chaque
paquet porte déjà `distro=...` dans son propre purl — voir le CHANGELOG
pour le détail de ce bug, découvert sur une image Keycloak réelle (101 CVE
`os-pkgs` manquantes sur 253 quand le SBOM était utilisé au lieu de l'image
directe).

Deux exigences non documentées de Trivy, isolées empiriquement par
bissection sur un SBOM réel (cf. `pkg/fanal/analyzer/os/release/release.go`
du dépôt aquasecurity/trivy, fonction `idToOSFamily`, pour la table de
référence) :

* Le champ `name`/`id` du composant OS doit suivre la taxonomie interne de
  Trivy (`redhat`, `oracle`, `alma`…), pas l'`id` `/etc/os-release` que syft
  expose tel quel (`rhel`, `ol`, `almalinux`…). `_toTrivyOsFamily()` traduit
  via la table `_trivyOsFamilyById` ; les identifiants absents (`debian`,
  `ubuntu`…) sont déjà identiques à la famille Trivy attendue et passent
  inchangés. Le backend trivy n'a pas besoin de cette traduction :
  `Metadata.OS.Family` est déjà dans la taxonomie interne de Trivy.
* Côté SPDX 2.3, le `SPDXID` du paquet OS doit être préfixé
  `SPDXRef-OperatingSystem-` (pas `SPDXRef-Package-`) pour que Trivy le
  reconnaisse — `primaryPackagePurpose: "OPERATING-SYSTEM"` seul ne suffit
  pas, vérifié empiriquement (voir <<sec-spdx-generator>>).

`os: null` quand syft/trivy n'ont détecté aucune base OS (image `scratch`
ou distroless), ou pour le backend skopeo (jamais couvert, voir ci-dessus).

Le backend cdxgen n'émet pas de composant `operating-system` : `_cdxgenOsInfo()`
reconstitue l'`OsInfo` depuis le qualifiant `distro=` d'un PURL de paquet
système (ex. `pkg:deb/debian/adduser@3.134?...&distro=debian-12` →
`id: debian, version: 12`), en séparant la version au dernier `-` et en
appliquant `_toTrivyOsFamily()` à l'identifiant. `os: null` si aucun paquet
système ne porte de qualifiant `distro` (image sans base OS reconnue).

=== Backend cdxgen (`_parseCdxgen`)

`cdxgen --type docker` accepte les trois `OciRefType` (référence registre,
archive `.tar` via chemin absolu, répertoire OCI layout). Le BOM CycloneDX
est lu sur `stdout` (`--output -`) puis normalisé :

* `_cdxgenComponentToPackage()` écarte les composants de type `file`,
  `cryptographic-asset`, `data`, `operating-system`, `container`, `platform`,
  puis exige un PURL dont le préfixe d'écosystème figure dans
  `_cdxgenPurlEcosystem` (`deb`, `rpm`, `apk`, `pypi`, `npm`, `golang`,
  `maven`, `gem`, `cargo`, `nuget`, `composer`, `pub`, `hex`, `conan`,
  `swift`). Les composants `pkg:generic` (inventaire fichier par fichier de
  cdxgen, dépôts APT) sont donc rejetés.
* Le PURL de cdxgen est repris tel quel dans `purlOverride` (il inclut
  `distro=`/`arch=`, nécessaires à grype).
* Pour un composant `pkg:maven`, `group` + `name` sont recombinés en
  `groupId:artifactId` (convention interne de `WheelPackage`/`OciPackage`).
* Licences au format CycloneDX (`[{expression}]` ou `[{license:{id|name}}]`).

=== Backend Skopeo (`_parseSkopeo`)

*Phases :*

. `skopeo copy <src> oci:<tmpDir>:image` (sauf si `ociLayout` déjà présent)
. `_extractOciLayers()` : lit `index.json` → premier manifest → liste des
  layers → `tar --extract` séquentiel dans `rootfs/`
. Détection de la base de paquets installée :
  ** `var/lib/dpkg/status` → `_parseDpkgStatus()` (RFC 822 ligne par ligne)
  ** `var/lib/rpm` → `_parseRpmRoot()` (`rpm --root <dir> -qa --queryformat …`)
  ** `lib/apk/db/installed` → `_parseApkInstalled()` (format clé:valeur APK)
. Détection des packages applicatifs dans le rootfs :
  ** `_parseMavenJars(rootDir)` : cherche `*.jar` dans tout le rootfs, extrait
     `META-INF/maven/*/*/pom.properties` via `unzip -p`, reconstruit le PURL
     `pkg:maven/<groupId>/<artifactId>@<version>`. Fallback : parsing du nom de
     fichier avec la convention Quarkus/Red Hat (`<groupId>.<artifactId>-<ver>.jar`).
     Déduplication par `groupId:artifactId:version`.
  ** `_parsePythonPackages(rootDir)` : cherche `*.dist-info/METADATA` et
     `*.egg-info/PKG-INFO` via `find`, parse les en-têtes RFC 822 jusqu'à la
     première ligne vide. Champs extraits : `Name`, `Version`, `Summary`,
     `License`, `Home-page`. PURL `pkg:pypi/<name>@<version>`.
  ** `_parseNpmPackages(rootDir)` : cherche `node_modules/*/package.json`
     (premier niveau uniquement, ignore les `node_modules` imbriqués). Saute les
     paquets avec `"private": true`. PURL `pkg:npm/<name>@<version>`.
. Suppression du répertoire temporaire (`chmod -R u+rwX` avant `rm -rf`
  pour les fichiers avec permissions restrictives dans certains layers)

[NOTE]
====
Seuls les paquets au statut `installed` dans `dpkg/status` sont inclus.
Les entrées `gpg-pubkey` du registre RPM sont ignorées.
Les 44 paquets que syft trouve en plus que skopeo (pour Keycloak 26) proviennent
de la lecture du `MANIFEST.MF` par syft, qui produit des groupIds heuristiques
non standard (`common/`, `jrt-fs/`, etc.). Ce gap est documenté et accepté.

== `lib/image_layers.dart` — Analyse par couche (`--per-layer`)

Produit, pour une image de conteneur, le *delta* de chaque couche (composants
ajoutés, modifiés, supprimés) et les annotations que les générateurs
ajoutent au SBOM global et aux SBOM de couche. Indépendant du backend :
l'analyse d'un état du rootfs est injectée (`scan`), et l'attribution par
métadonnées est fournie par `OciParser`.

=== Modèle

[cols="1,3",options="header"]
|===
|Type |Rôle

|`ImageLayer`
|couche : `index` (1 = base), `diffId` (`sha256:…` du tar non compressé), `blobPath` (tar sur disque, mode rootfs), `createdBy`/`created` (`history[]` de la config, entrées `empty_layer` ignorées)

|`LayerDelta`
|`added`, `modified` (`PackageChange = (before, after)`), `removed` ; `packages` = composants décrits par le SBOM de la couche ; `map(f)` pour appliquer surcharges de licence / fournisseur

|`LayerAnalysis`
|`mode`, `layers`, `deltas` ; `origins()` → `bomRef` → `LayerOrigin` (couche d'introduction, couches de modification) pour l'état final

|`LayerSummary`
|résumé d'une couche (compteurs, `fileBase`, `documentUuid`) — sérialisé en JSON dans le SBOM global

|`LayerAnnotations`
|ce que reçoivent les générateurs (paramètre `layers:` de chaque `generate`/`writeToFile`) : `forLayer` (couche décrite, changement par `bomRef`, version précédente, supprimés, lien vers le global) ou `forGlobal` (couche d'origine par `bomRef`, résumé des couches). `documentUuid` fixe le numéro de série CycloneDX / l'espace de noms SPDX, pour les liens croisés
|===

=== Lecture des couches

- `readDockerArchiveLayers(dir)` : archive `docker save`/`podman save`
  extraite (`manifest.json` → `Config` + `Layers[]`).
- `readOciLayoutLayers(dir)` : `index.json` → (index imbriqué, manifeste
  `linux/amd64` de préférence) → config + `layers[]` (`blobs/sha256/…`).
- Sans `diff_ids` exploitables, le digest est déduit du nom de fichier.

=== Mode `rootfs` : `analyzeRootfsLayers`

Pour chaque couche : `tar -xf` dans un répertoire temporaire (compression
détectée par tar ; entrées non créables sans privilèges ignorées),
`chmod -R u+rwX`, puis *`mergeLayerDir`* sur le rootfs cumulé, puis
`scan(rootDir)` et `diffPackages(previous, current)`.

`mergeLayerDir` applique la sémantique overlayfs : `.wh.<nom>` supprime
l'entrée inférieure, `.wh..wh..opq` vide le répertoire, un répertoire
fusionne récursivement, toute autre entrée remplace. Les entrées sont
*déplacées* (`rename`) et la descente ne passe *jamais* par un lien
symbolique — contrairement à des `tar -x` successifs dans le même répertoire
(le backend `skopeo` historique), une couche malveillante (`x -> /` puis
`x/…`) ne peut rien écrire hors du rootfs (cas couvert par
`test/unit/image_layers_test.dart`).

`diffPackages` rapproche d'abord par `bomRef` (composant présent des deux
côtés : « modifié » si PURL, licence, fournisseur ou empreintes diffèrent),
puis les restes par identité logique `type|nom|arch` quand elle est
univoque des deux côtés — une montée de version devient « modifiée » plutôt
que suppression + ajout. Plusieurs versions d'un même nom (`node_modules`
imbriqués) ne sont pas appariées.

=== Mode `metadata` : `metadataLayerAnalysis`

Répartit les paquets de l'analyse habituelle selon `layerOf` (`bomRef` →
index de couche) fourni par `OciParser.layerAttribution` ; seuls les ajouts
sont connus. Un paquet sans couche connue ne figure dans aucun SBOM de
couche (avertissement console).

=== Algorithme de comparaison

. `_indexComponents()` détecte le format de chaque fichier indépendamment

== `lib/sbom_merger.dart` — Fusion de SBOMs

=== `SbomMerger`

[source,dart]
----
class SbomMerger {
  Map<String, dynamic> merge(
    List<Map<String, dynamic>> sboms, {
    String? documentName,
  });
}
----

`merge()` est une méthode d'instance (pas statique). Elle détecte le format
du **premier** SBOM fourni (`spdxVersion` présent → `_mergeSpdx()`, sinon
`_mergeCycloneDx()`) et fusionne tous les fichiers selon cette même
structure ; le document résultant est produit dans ce même format.

=== Algorithme de fusion — CycloneDX (`_mergeCycloneDx`)

. Premier SBOM comme base (préserve `metadata`).
. Parcours de tous les SBOMs suivants :
  - Déduplication des `components` par `purl` (puis par `bom-ref` si PURL absent).
  - Déduplication des `dependencies` par `ref`.
  - Déduplication des `citations` et `definitions.patents` (CycloneDX 1.7) par `bom-ref`.
. Nouveau `serialNumber` UUID v4 généré via `_generateUuid()`.
. `documentName` écrase `metadata.component.name` si fourni.

=== Algorithme de fusion — SPDX 2.3 (`_mergeSpdx`)

. Premier SBOM comme base (préserve `dataLicense`, `creationInfo.licenseListVersion`).
. Déduplication des `packages` par PURL (`externalRefs[referenceType=purl]`), puis par `SPDXID`.
. Déduplication des `relationships` par triple `(spdxElementId, relationshipType, relatedSpdxElement)`.
. Nouveau `documentNamespace` généré via `_generateUuid()`.
. `documentName` écrase `name` si fourni.

[NOTE]
====
Les fichiers source doivent tous être dans le même format que le premier
fichier fourni (CycloneDX ou SPDX 2.3) ; un fichier dans un format différent
n'est pas rejeté explicitement — il produit simplement une fusion
incomplète, faute de validation croisée des formats. Le format SPDX 3.0
(JSON-LD) n'est pas pris en charge en entrée pour `merge`.

Les `SPDXID` des documents source sont conservés tels quels dans les
`relationships` fusionnées ; pour les SBOM générés par cet outil ils sont
déterministes (nom+version via `Package.spdxId`), donc stables entre
documents — une collision reste théoriquement possible si un document
externe réutilise un `SPDXID` générique pour un autre paquet.
====

== `lib/license_report_generator.dart` — Rapport de licences (sous-commande `licenses`)

=== `LicenseReportGenerator`

[source,dart]
----
class LicenseReportGenerator {
  Future<void> writeToFile(
    List<Package> packages,
    String outputPath, {
    String? documentName,
  });
}
----

Regroupe les paquets par `pkg.license` **exacte** — la chaîne telle que
présente dans le SBOM source, y compris les expressions composées
(`A AND B AND …`, fréquentes sur les paquets Debian/RPM dont toutes les
licences trouvées dans les sources sont concaténées) — et écrit un rapport
AsciiDoc en quatre parties : résumé chiffré, avertissement copyleft, section
détaillée par licence, section des paquets sans licence détectée.

=== Classification copyleft

`_classify(license)` applique une heuristique par sous-chaîne sur
l'expression entière (insensible à la casse) :

[cols="2,3", options="header"]
|===
|Catégorie |Condition

|`strongCopyleft`
|contient `AGPL`, ou `GPL` non précédé d'une lettre — regex `(?<![A-Z])GPL`, pour ne pas confondre avec `LGPL`

|`weakCopyleft`
|contient `LGPL`, `MPL`, `EPL`, `CDDL`, `CPL` ou `EUPL`

|`permissive`
|aucun des marqueurs ci-dessus

|`unknown`
|chaîne vide
|===

Cette classification s'applique sur l'expression **entière** : une expression
composée contenant un seul token copyleft (ex. `BSD-3-Clause AND
GPL-2.0-only AND MIT`) classe tout le groupe en copyleft — ce comportement
est voulu, la présence d'un composant copyleft dans le mélange suffit à
déclencher l'avertissement.

[NOTE]
====
`_copyleftTokens(license, target)` découpe une expression composée sur
`AND`/`OR` et ne retient que les tokens dont la classification *individuelle*
correspond à `target`. Cette étape sert uniquement à construire la liste
d'identifiants de l'avertissement en tête de rapport — le regroupement par
section garde toujours l'expression complète telle que déclarée.

Sans cette étape, un SBOM Debian réel (licences systématiquement
concaténées) produit un avertissement listant des dizaines de chaînes
composées entières, illisibles, plutôt que les identifiants copyleft
individuels réellement en cause. Constaté en testant la commande sur un SBOM
Trivy de 157 paquets nginx/Debian : sans le découpage, l'avertissement
tenait sur une seule ligne de plusieurs milliers de caractères.
====

La classification copyleft est une heuristique de repérage destinée à
attirer l'attention, pas une analyse juridique.

class RequirementsParser {

=== Lignes ignorées

* Vides ou commençant par `#`

Tous les parseurs produisant N paquets depuis un seul fichier (cardinalité 1:N)

[source,dart]
----
for (final ref in packageRefs) {
  if (_isRequirements(ref)) {
    preloadedPackages.addAll(reqParser.parseFile(ref));
  } else if (_isGoSum(ref)) {
    preloadedPackages.addAll(goParser.parseGoSum(ref));
  } else if (_isGoMod(ref)) {
    preloadedPackages.addAll(goParser.parseGoMod(ref));
  } else if (_isPackageLock(ref)) {
    preloadedPackages.addAll(npmParser.parsePackageLock(ref));
  } else if (_isYarnLock(ref)) {
    preloadedPackages.addAll(yarnParser.parseYarnLock(ref));
  } else if (_isPomXml(ref)) {
    preloadedPackages.addAll(mavenParser.parsePomXml(ref));
  } else if (_isPubspecLock(ref)) {
    preloadedPackages.addAll(pubspecParser.parsePubspecLock(ref));
  } else if (_isPubspecYaml(ref)) {
    preloadedPackages.addAll(pubspecParser.parsePubspecYaml(ref));
  } else {
    filteredRefs.add(ref);
  }
}
// … boucle Future.wait sur filteredRefs …
packages.addAll(preloadedPackages);
----

Helpers de détection :

[source,dart]
----
bool _isRequirements(String r) => r.endsWith('.txt') && !r.endsWith('.whl');
bool _isGoSum(String r)        => r.endsWith('go.sum');
bool _isGoMod(String r)        => r.endsWith('go.mod');
bool _isPackageLock(String r)  => r.endsWith('package-lock.json');
bool _isYarnLock(String r)     => r.endsWith('yarn.lock');
bool _isPomXml(String r)       => r.endsWith('pom.xml');
bool _isPubspecLock(String r)  => r.endsWith('pubspec.lock');
bool _isPubspecYaml(String r)  => r.endsWith('pubspec.yaml');
----

== `lib/go_parser.dart` — Modules Go

Parseur pur Dart pour `go.sum` et `go.mod`. Utilise `WheelPackage` avec
`packageType: 'golang'`.

=== `parseGoSum(String path)`

Format `go.sum` : une ligne `module version hash` ou `module version/go.mod hash`.

[source,text]
----
github.com/gorilla/mux v1.8.1 h1:TnC2...
github.com/gorilla/mux v1.8.1/go.mod h1:dvbg...
----

Traitement :
. Ignore les lignes vides ou commençant par `#`
. Ignore les lignes dont le deuxième champ se termine par `/go.mod` (doublon de checksum)
. Extrait `module` et `version` (préfixe `v` retiré)
. Déduplication par clé `module@version` (évite le doublon entre les deux lignes d'un module)
. Nom = chemin module brut en minuscules (slashes conservés pour PURL)

=== `parseGoMod(String path)`

Format `go.mod` : directives `require` individuelles ou en bloc.

[source,text]
----
require (
    github.com/gorilla/mux v1.8.1
    golang.org/x/net v0.17.0  // indirect
)
require github.com/pkg/errors v0.9.1
----

Traitement :
. Détecte les blocs `require (…)` et les directives `require x v` isolées
. Retire les commentaires `// indirect` et tout ce qui suit `//`
. Préfixe `v` retiré de la version
. Les versions `v0.0.0-yyyymmdd-commit` (pseudo-versions) sont conservées telles quelles

== `lib/npm_parser.dart` — Paquets npm

Parseur pur Dart pour `package-lock.json` (lockfileVersion 1, 2 et 3).

=== Détection de version

[source,dart]
----
final v = json['lockfileVersion'];
if (v == 1) return _parseDependenciesField(json);
return _parsePackagesField(json);   // v2 et v3
----

=== `_parsePackagesField` (v2/v3)

Clé `packages` → map `{ "node_modules/pkg": { version, license, integrity, … } }`.

. Ignore la clé vide `""` (racine du projet)
. `_stripNodeModulesPrefix` : segment après le *dernier* `node_modules/`
  (gère les chemins imbriqués `node_modules/a/node_modules/b`)
. `_extractLicense(raw)` : gère `String | List` (certains packages déclarent
  plusieurs licences sous forme de tableau `[{ "type": "MIT" }]`)
. `integrity` (SRI `sha512-<base64>`) → `hashes` via `packageHashFromSri`

==== Fournisseur (`_authorFromPackageJson`)

Le lockfile npm ne porte **aucun auteur**. `_parsePackagesField` résout
`<dossier du lockfile>/<clé node_modules>/package.json` et lit `author`
(sinon 1^er^ `contributors[]` / `maintainers[]`) ; `_personName` normalise
un objet `{name}` ou une chaîne `"Nom <email> (url)"` → `"Nom"`.
Best-effort : arbre `node_modules` absent (lockfile committé sans
`npm install`) → chaîne vide, sans erreur. Non appliqué au chemin v1
(pas de chemin d'installation fiable).

=== `_parseDependenciesField` (v1)

Clé `dependencies` → map récursive (dépendances imbriquées).

. Traitement récursif : pour chaque package, ses propres `dependencies` sont
  aussi parsés (dépendances imbriquées de npm v1)
. Chaque paquet a `version` et `resolved` au plus haut niveau

=== `_parseClassic` (yarn v1)

Format : blocs `"pkg@^1.0.0":` suivis de lignes indentées.

[source,text]
----
"lodash@^4.17.21":
  version "4.17.21"
  resolved "https://registry.yarnpkg.com/..."
----

. Détecte les lignes d'en-tête (non indentées, se terminant par `:`)
. Extrait `name` via `_nameFromHeader()` qui gère les scopes `@scope/pkg`,
  préfixes `@npm:`, `@patch:`, et en-têtes multi-spécifications séparées par `, `
. Regroupe les champs `version`, `resolved` dans `_YarnBlock`
. Déduplique par `name@version`

=== `_parseBerry` (yarn v2+)

Format : blocs `"pkg@npm:^1.0.0":` avec syntaxe YAML-like sans guillemets.

[source,text]
----
"lodash@npm:^4.17.21":
  version: 4.17.21
  resolution: "lodash@npm:4.17.21"
----

. Même logique de blocs que classique
. La clé `version:` n'a pas de guillemets (contrairement à yarn v1)
. `__metadata:` est ignoré (bloc de métadonnées Berry)

== `lib/maven_parser.dart` — Dépendances Maven

=== Pré-nettoyage

Avant extraction, les sections confondantes sont retirées du XML :

[source,dart]

. `_extractFirst(xml, 'groupId')` et `_extractFirst(xml, 'artifactId')` via regex
. Version extraite via `_extractFirst(xml, 'version')` (vide si variable `${…}`)
. Scope `test` ou `system` → ignoré
. Name stocké comme `groupId:artifactId` (séparateur `:` pour la reconstruction PURL)

=== PURL Maven

Le getter `WheelPackage.purl` gère le type `'maven'` spécifiquement :

[source,dart]

== `lib/pubspec_parser.dart` — Paquets Dart/Flutter

Parseur *pur Dart* (sans dépendance `yaml`) pour `pubspec.lock` et
`pubspec.yaml`. Retourne `List<WheelPackage>` avec `packageType: 'pub'`
(PURL `pkg:pub/<name>@<ver>`).

=== `parsePubspecLock(String path, {Map<String,String> sdkVersions})`

Lecture ligne à ligne du bloc `packages:` (indentation stable à 2 espaces
générée par `pub`). Pour chaque paquet :

* `dependency:` — `direct dev` → **exclu**. Les transitives tirées uniquement
  par une dépendance de dev ne sont pas distinguables dans le lockfile : elles
  restent incluses.
* `source:` — `hosted` | `git` | `path` | `sdk` : toutes retenues.
* `description.name` (hosted) → nom du paquet ; sinon la clé du bloc.
* `source: sdk` — le nom est **toujours la clé** (`flutter`, `sky_engine`,
  `flutter_web_plugins`…). Le `description:` scalaire (`description: flutter`)
  nomme le SDK, pas le paquet : l'utiliser comme nom collait tous ces paquets
  sur `flutter` puis les dédupliquait (régression corrigée). Il ne sert plus
  qu'à choisir la clé dans `sdkVersions`.
* `version:` — version résolue ; pour `source: sdk`, `pub` écrit toujours
  `"0.0.0"` (aucune vraie version pour un paquet livré dans le SDK) → **version
  vide** (`pkg:pub/flutter`), sauf si `sdkVersions` fournit la vraie version
  (`{'flutter': '3.47.2'}` → tous les paquets `description: flutter` héritent de
  `3.47.2`). Alimenté par `--sdk-version <sdk>=<ver>` côté CLI.

`--sdk-version` a un **second effet**, indépendant du parsing pubspec : la map
`sdkVersions` est passée à `CycloneDxGenerator` / `SpdxGenerator` /
`Spdx3Generator` (paramètre `sdkTools`) qui ajoutent chaque SDK à la toolchain
du document — `metadata.tools.components[]` (`type: platform`,
`bom-ref: tool-sdk-<nom>`) en CycloneDX, `creationInfo.creators`
(`Tool: <nom>-<version>`) en SPDX 2.3, un élément `Tool` référencé par
`createdBy` en SPDX 3.0. C'est le seul endroit où la version du SDK **dart**
apparaît (il n'a pas d'entrée paquet dans un lockfile Flutter).

==== Licences (`--pub-cache` / `--flutter-root`)

`pubspec.lock` ne porte aucune licence. `_resolveLicense()` localise le
fichier `LICENSE` du paquet *résolu* sur disque et l'identifie via
`identifyArchiveLicense()` (`archive_helpers.dart`) :

[cols="1,3", options="header"]
|===
|`source:` |Répertoire cherché

|`hosted`
|`<pubCache>/hosted/<hôte>/<nom>-<version>/` (hôte déduit de `description.url`,
`pub.dev` par défaut)

|`git`
|`<pubCache>/git/<nom>-<resolved-ref>[/<description.path>]/`

|`path`
|`<description.path>` résolu depuis le dossier du `pubspec.lock`

|`sdk`
|`<flutterRoot>/packages/<nom>/`, puis `<flutterRoot>/bin/cache/pkg/<nom>/`,
puis `<flutterRoot>/LICENSE` (repli — `flutter_web_plugins` n'a pas de LICENSE
propre)
|===

Noms de fichier testés : `LICENSE`, `LICENSE.md`, `LICENSE.txt`, `LICENCE`,
`COPYING`, `license`. Un fichier absent ou non identifiable → licence vide, pas
d'erreur. `pubCache` est auto-détecté côté CLI (`$PUB_CACHE`, sinon
`~/.pub-cache` s'il existe) ; `--pub-cache ""` le neutralise.

NOTE: `identifyArchiveLicense()` reconnaît désormais le texte BSD-3-Clause
canonique (« Redistribution and use in source and binary forms… / endorse or
promote products derived ») même sans le mot « BSD » — c'est le `LICENSE` de la
quasi-totalité des paquets pub (rédigés par Google).
* `description.sha256` (hosted) → `WheelPackage.hashes` (`PackageHash('SHA-256', …)`).
* `description.url` → homepage (`https://pub.dev/packages/<name>` pour
  pub.dev, `<registre>/packages/<name>` pour un registre privé, l'URL du dépôt
  pour `git`).

=== `parsePubspecYaml(String path, {Map<String,String> sdkVersions})`

Lit uniquement la section `dependencies:` (la section `dev_dependencies:` et
`dependency_overrides:` sont ignorées). Approche à `flush()` : chaque bloc de
dépendance est bufferisé pour repérer une ligne imbriquée `sdk: <x>` (dépendance
SDK) avant émission — sa version vient alors de `sdkVersions[<x>]` si fournie,
sinon vide. Une contrainte simple est réduite à une version unique quand c'est
univoque (`^1.2.3`, `1.2.3`, `>=1.2.3` → `1.2.3`) ; une plage
(`>=1.0.0 <2.0.0`) ou `any` donne une version vide.

=== Priorité lock / yaml

Dans un scan de dossier, si `pubspec.lock` et `pubspec.yaml` coexistent au
même endroit, `bin/sbom_generator.dart` ne retient que le `.lock` (versions
résolues + fermeture transitive). En fichier liste, les deux sont honorés tels
que listés.

== `lib/sbom_reader.dart` — Lecteur SBOM

Relit un fichier SBOM JSON existant et reconstruit une `List<Package>`.
Utilisé par les sous-commandes `convert` et `licenses`.

=== `SbomFormat` enum

[source,dart]
----
enum SbomFormat { cyclonedx, spdx2, spdx3, unknown }
----

=== Détection de format

[source,dart]
----
static SbomFormat detectFormat(Map<String, dynamic> json) {
  if (json['bomFormat'] == 'CycloneDX')    return SbomFormat.cyclonedx;
  if (json.containsKey('spdxVersion'))     return SbomFormat.spdx2;
  if (json.containsKey('@context') && json.containsKey('@graph'))
                                           return SbomFormat.spdx3;
  return SbomFormat.unknown;
}
----

=== Méthode `read(json)`

Dispatche selon le format :

* *CycloneDX* : lit `json['components']` → `List<Map>` → `_cdxComponent(c)` pour chaque élément
* *SPDX 2.3* : lit `json['packages']` → `_spdx2Package(p)` pour chaque élément
* *SPDX 3.0* : lit `json['@graph']` → filtre les nodes de type `software:Package`
  (`_isSpdx3Package` tolère aussi `software_Package`) → `_spdx3Package(node)`,
  qui lit les champs `software:`-préfixés (`software:packageVersion`,
  `software:downloadLocation`)

Chaque extracteur renseigne : `name`, `version`, `purl`, `license`, `vendor`,
`url`, `hashes` (`hashes` / `checksums` / `verifiedUsing` selon le format), et
infère le `packageType` via `_purlToType(purl)`.

== `bin/sbom_generator.dart` — Point d'entrée

=== Option `--input` / `-i` — fichier liste, archive unique, ou dossier

Historiquement, `--input` devait toujours pointer vers un fichier liste
(texte, une référence par ligne). Passer directement une archive binaire
(`.zip` notamment) faisait planter `File.readAsLines()` avec une
`FileSystemException` de décodage UTF-8 peu explicite. `--input` accepte
désormais trois formes, résolues par trois branches mutuellement exclusives :

[source,dart]
----
bool _isSingleArchiveInput(String path) =>
    path.endsWith('.zip') ||
    _isTar(path) ||
    path.endsWith('.whl') ||
    path.endsWith('.deb') ||
    path.endsWith('.rpm') ||
    _isJar(path);

if (inputPath != null) {
  if (await FileSystemEntity.isDirectory(inputPath)) {
    // Scan récursif : tout fichier matché par _isSupportedPackageFile()
    // devient un packageRef.
    final found = <String>[];
    await for (final entity
        in Directory(inputPath).list(recursive: true, followLinks: false)) {
      if (entity is File && _isSupportedPackageFile(entity.path)) {
        found.add(entity.path);
      }
    }
    found.sort();
    // Si pubspec.lock et pubspec.yaml coexistent au même endroit, on ne
    // garde que le .lock (versions résolues + fermeture transitive).
    packageRefs = found;
  } else if (_isSingleArchiveInput(inputPath) ||
      _isSupportedPackageFile(inputPath)) {
    // Archive/paquet/manifeste unique (nom exact pour les manifestes) :
    // pubspec.lock, requirements.txt, go.sum, pom.xml…
    packageRefs = [inputPath];
  } else {
    try {
      lines = await File(inputPath).readAsLines();
    } on FileSystemException {
      _err('… message explicite …');
      exit(1);
    }
    // … découpage en packageRefs …
  }
}
----

Pour tout chemin restant (branche fichier liste), la lecture ligne par ligne
reste protégée par un `try/catch` : toute `FileSystemException` (fichier
binaire non reconnu, encodage invalide) produit un message d'erreur
actionnable au lieu d'une stack trace brute.

`_isSupportedPackageFile()` est volontairement plus stricte que le fichier
liste pour les manifestes : elle exige un nom de fichier *exact*
(`requirements.txt`, `pom.xml`, `go.sum`, `go.mod`, `package-lock.json`,
`yarn.lock`, `pubspec.lock`, `pubspec.yaml`) plutôt qu'une extension générique
(`*.txt` par ex.), pour éviter
qu'un `README.txt` ou un `notes.txt` traînant dans l'arborescence scannée soit
pris à tort pour un fichier de requirements. Le fichier liste, lui, continue
d'accepter n'importe quel `.txt` (hors `.whl`) via `_isRequirements()` — la
tolérance y est acceptable car l'utilisateur a explicitement tapé le chemin.

Les noms de paquets RPM nus (ex. `bash`) ne sont jamais découverts par le
scan de dossier : ce ne sont pas des fichiers sur disque. `--rpm-dir` reste
le mécanisme dédié pour résoudre ce cas.

`FileSystemEntity.type()` remplace l'ancien `File(inputPath).exists()` pour
la vérification d'existence initiale, car ce dernier renvoie `false` pour un
chemin de dossier (uniquement vrai pour les fichiers), ce qui aurait fait
échouer `--input <dossier>` avec « Input file not found ».

=== Option `--rpm-dir` / `-d`

Permet de résoudre les noms RPM nus (sans `/` ni extension) vers des fichiers
`.rpm` locaux au lieu d'interroger la base de données des paquets installés.

*Indexation au démarrage* (une seule fois) :

[source,dart]
----
final rpmExactIndex = <String, String>{};       // stem → chemin absolu
final rpmNameIndex  = <String, List<String>>{}; // nom paquet → [chemins triés]

await for (final entity in dir.list(recursive: true, followLinks: false)) {
  if (entity is File && entity.path.endsWith('.rpm')) {
    final stem = entity.path.split('/').last.replaceAll(RegExp(r'\.rpm$'), '');
    rpmExactIndex[stem] = entity.path;
    final name = RegExp(r'^(.+?)-\d').firstMatch(stem)?.group(1) ?? stem;
    rpmNameIndex.putIfAbsent(name, () => []).add(entity.path);
  }
}
for (final paths in rpmNameIndex.values) paths.sort();
----

* *`rpmExactIndex`* : clé = stem complet (ex. `bash-5.1.8-6.el9.x86_64`),
  valeur = chemin. Couvre les correspondances NEVRA exactes.
* *`rpmNameIndex`* : clé = nom de paquet extrait par `^(.+?)-\d` (ex. `bash`),
  valeur = liste triée de chemins. Couvre les noms courts.

*Résolution dans la boucle* :

[source,dart]
----
if (rpmDir != null && !ref.contains('/') && !ref.endsWith('.whl') && !_isTar(ref)) {
  final resolved = rpmExactIndex[ref] ?? rpmNameIndex[ref]?.first;
  if (resolved != null) ref = resolved;
  // Si plusieurs fichiers correspondent au nom : avertissement + premier alphabétique
}
----

Si aucune correspondance n'est trouvée dans le dossier, `rpm -q` est utilisé
normalement (fallback transparent). Les références `.whl`, archives tar/zip,
`.deb` et `.jar` ne sont jamais concernées, même si `--rpm-dir` est spécifié.

* *Formats multiples* (`-f cyclonedx,spdx,markdown`) : `--output` est traité comme
  un *chemin de base* ; l'extension appropriée est ajoutée automatiquement par
  `_formatExtension()` / `_basePath()`

[cols="1,1", options="header"]
|===
|Format |Extension ajoutée

|`cyclonedx`
|`.cdx.json`

|`spdx`
|`.spdx.json`

|`spdx3`
|`.spdx3.jsonld`

|`json`
|`.custom.json`

|`markdown`
|`.md`

|`asciidoc`
|`.adoc`

|`html`
|`.html`

|`csv`
|`.csv`

`_basePath(output)` retire les extensions connues du nom passé à `--output`

|Champ de date utilisé pour le filtre : `published`, `modified`, ou `latest`
(la plus récente des deux)

|`--include-undated`
|désactivé
|Inclut les CVE sans date connue dans les résultats filtrés (exclues par
défaut dès qu'un filtre `--cve-after`/`--cve-before` est actif)

|`--format <valeur>` / `-f`
|`text`
|`text`, `sarif`, ou `markdown` / `asciidoc` / `pdf` (rapport de synthèse
inter-scanners — voir `_reportScanFormats`)

|`--output <fichier>` / `-o`
|—
|Fichier de sortie. Obligatoire pour `markdown` / `asciidoc` / `pdf` ; pour
`sarif`, stdout si omis

|`--enrich` / `--no-enrich`
|activé
|Enrichissement exploitabilité (KEV / EPSS / PoC / CVSS). `--no-enrich` ou
`SBOMGEN_OFFLINE=1` → aucune requête réseau

|`--no-poc`
|—
|Coupe la seule source tierce (poc-in-github) ; KEV / EPSS / maturité `E:`
restent renseignés

|`--enrich-timeout <s>`
|`8`
|Délai maximal par requête réseau d'enrichissement

|`--only-kev` / `--epss-min <x>`
|—
|Filtres de priorisation appliqués après enrichissement, tous formats

|`--sort <valeur>`
|`severity`
|Ordre d'affichage console : `severity` ou `risk` (KEV → EPSS → sévérité)
|===

Codes de retour : `text` / `sarif` gardent le contrat historique (`1` si au
moins une CVE, ou erreur de scanner). Les formats rapport retournent `0` dès
qu'un rapport est écrit (peu importe le nombre de CVE), `1` seulement si
`--output` manque ou si aucun scanner n'a produit de résultat — pour qu'un
appelant comme `build-dist.sh` sous `set -e` ne casse pas le build à la
moindre CVE.

Architecture interne :

[cols="1,3", options="header"]
|===
|Fonction |Rôle

|`_runScan()`
|Parse les arguments via `ArgParser`, orchestre les scanners demandés

|`_runScanner()`
|Dispatch vers `_runGrype()`, `_runOsv()`, `_runTrivy()`

|`_runGrype()` / `_runOsv()` / `_runTrivy()`
|Lance le scanner via `Process.run()` (capture `ProcessException` si le
binaire est introuvable → message explicite sur stderr, pas de crash),
parse le JSON propre à chaque outil, retourne une liste normalisée
`{id, severity, package, published, modified}`. La bannière `── Nom ──`
n'est imprimée que si `--format text` (silencieuse en `sarif` pour ne pas
polluer la sortie JSON)

|`_filterByDate()`
|Applique `after` / `before` / `includeUndated` sur le champ de date choisi

|`_enrichFindings()`
|Après tous les scanners, avant les filtres : rassemble les identifiants
(normalisés via `_normalizeCveId`) + une `CveSeed` par CVE (vecteur CVSS,
et pour Grype KEV/EPSS natifs), appelle `VulnEnricher.enrich()`
(`lib/vuln_enrichment.dart`), puis injecte l'`ExploitInfo` obtenu dans
chaque finding (`v['exploit']`). Best-effort : toute exception laisse
`ExploitInfo.empty`. Retourne la map id → `ExploitInfo` pour le rapport

|`_filterByExploit()`
|Applique `--only-kev` / `--epss-min` sur des findings déjà enrichis

|`_cvssFromGrype/Osv/Trivy()`
|Extraient `(vecteur CVSS, score de base)` du JSON propre à chaque scanner
(`vulnerability.cvss[]`, `severity[].score`, `CVSS.<src>.V3Vector`)

|`_printScanResults()`
|Trie par sévérité décroissante (`Critical` → `Unknown`), ou par risque si
`--sort risk`, et affiche un tableau texte par scanner — colonnes
`KEV` / `EPSS` / `PoC` en plus (`--format text`)

|`_buildSarifReport()`
|Construit un rapport SARIF 2.1.0 (un `run` par scanner interrogé, une
`rule` déduite par identifiant de vulnérabilité, `level` via `_sarifLevel()`,
`security-severity` via `_sarifSecurityScore()` — relevé à `9.5` si KEV).
Chaque `result` et `rule` porte les propriétés `kev` / `epss` /
`epssPercentile` / `poc` / `cvssExploitability` — `--format sarif`

|`_writeScanReport()`
|`--format markdown` / `asciidoc` / `pdf` : reçoit le `ScanReportGenerator`
(`lib/scan_report_generator.dart`) et écrit le fichier. Pour `pdf`, écrit
d'abord un `.adoc` à côté puis appelle `renderAsciiDocToPdf()` (shell-out
`asciidoctor-pdf` avec `_kPdfThemeYaml`, `extends: default-sans` — page de
garde, résumé exécutif chiffré + verdict, pied de page paginé, badges de
sévérité francisés ; copie synchronisée du thème de
`gui/lib/widgets/pdf_report.dart`) ; `ProcessException` ou code ≠ 0 →
conserve le `.adoc`, avertit, mais ne fait pas échouer la commande

|`_printSeverityAlerts()`
|Avant l'écriture du fichier (formats rapport uniquement) : liste sur stdout
`ScanReportGenerator.alerts()` — une ligne par CVE unique Critical (rouge
`\e[1;31m`) / High (orange `\e[38;5;208m`), avec paquet + scanners, les
marqueurs `[KEV]` / `EPSS <score>` / `[PoC]`, puis un décompte (dont le
nombre de CVE KEV). `--color auto` (défaut) = `stdout.hasTerminal && !NO_COLOR` ;
`always` / `never` forcent. Best-effort, sans effet sur le code de retour

|`_scannerVersion()`
|Version courte `x.y.z` d'un scanner (best-effort, pour l'entête « Outils »
du rapport)

|`_printScanUsage()`
|Affiche l'aide de la sous-commande avec exemples
|===

`ScanReportGenerator` (`lib/scan_report_generator.dart`) est pur (aucun I/O
hors `renderAsciiDocToPdf`) : `toMarkdown()` / `toAsciiDoc()` prennent la
`Map<String, List<…>?>` par scanner (`null` = non exécuté, `[]` = exécuté
sans résultat) et produisent résumé global + répartition par sévérité +
matrice CVE × scanner. `alerts({keep})` renvoie les `ScanAlert` (CVE unique,
pire sévérité, paquet, scanners) au-dessus d'un seuil — consommé par
`_printSeverityAlerts` côté CLI. Les identifiants distro-préfixés
d'OSV-Scanner (`DEBIAN-CVE-…`) sont normalisés (`_distroPrefixedCveRe`) avant
tout comptage/comparaison, comme dans le tableau de bord de la GUI.

`cveNotes()` renvoie une `Map<String,String>` id → note, rendue en section
« Notes par CVE » sous la matrice : une entrée par CVE que Grype signale
sans correctif exploitable (`fixState` ≠ `fixed` et `fixedVersions` vide)
alors qu'OSV-Scanner ou Trivy portent une version corrigée. Les runners
(`_runGrype` / `_runOsv` / `_runTrivy`) alimentent ça en ajoutant à chaque
finding `fixState` + `fixedVersions` (Grype `vulnerability.fix`), les
événements `fixed` des plages `affected[].ranges[]` (OSV), et `FixedVersion`
scindé (Trivy). Objectif : expliciter que la version corrigée d'un avis de
distribution est en général celle d'`unstable`/`testing`, pas une mise à jour
disponible pour la release stable installée — cf. `usage.adoc`, section
« Pourquoi les scanners ne trouvent pas les mêmes CVE ».

==== Enrichissement exploitabilité (`lib/vuln_enrichment.dart`)

`VulnEnricher.enrich(ids, {seed})` renvoie une `Map<String, ExploitInfo>`
(id normalisé → signaux). C'est, avec `renderAsciiDocToPdf`, le seul point
d'I/O du paquet : requêtes HTTP `dart:io` (aucune dépendance ajoutée) et un
cache disque sous `~/.cache/sbom-generator/` (`kev.json`, `epss.json`,
`poc.json`), TTL 24 h.

[cols="1,3", options="header"]
|===
|Signal |Source & stratégie

|CISA KEV
|Grype (`vulnerability.knownExploited`, via `seed`) + flux
`known_exploited_vulnerabilities.json` (une requête, couvre OSV/Trivy).
Réseau KO → cache, même périmé ; sinon map vide

|EPSS
|Grype (`vulnerability.epss`, via `seed`) + API FIRST
`api.first.org/data/v1/epss?cve=…` par lots de 100. Cache par CVE

|PoC public
|API `poc-in-github.motikan2010.net` (pool de 6, `enablePoc`) **+** maturité
`E:` du vecteur CVSS (`parseCvssVector`, ≥ _Proof-of-Concept_)

|Exploitabilité CVSS
|`parseCvssVector()` — pur, `8.22 × AV × AC × PR × UI` pour un vecteur v3.x ;
`null` sinon (v2/v4 : seule la maturité `E:` est extraite)
|===

`enableNetwork == false` (`--no-enrich` / `SBOMGEN_OFFLINE=1`) : lecture du
cache seul, jamais de requête. `ExploitInfo.riskScore(severity)` fournit la
clé de tri « priorisation par risque » (KEV pèse 1000, EPSS 0–100, sévérité
0–4). Les URL des sources et le répertoire de cache sont injectables
(constructeur) pour les tests — cf. `test/unit/vuln_enrichment_test.dart`
(serveur `HttpServer` local).

`ScanReportGenerator` reçoit cette map via `exploitById` (défaut `const {}`
= sections omises) : compteurs KEV/EPSS/PoC dans le résumé, section
« Exploitabilité et exploitation active » (liste KEV + tableau
« Priorisation par risque ») en Markdown comme en AsciiDoc.

[source,dart]
----
Future<List<Map<String, dynamic>>?> _runGrype(String sbomFile, {bool quiet = false}) async {
  final ProcessResult result;
  try {
    result = await Process.run('grype', [
      sbomFile, '--output', 'json',
      '--platform', 'linux', '--add-cpes-if-none', '--by-cve',
    ]);
  } on ProcessException catch (e) {
    stderr.writeln('grype: introuvable (${e.message}). ...');
    return null;
  }
  // exitCode > 1 → erreur ; sinon parse data['matches'][].{vulnerability, artifact}
}
----

Les options Grype sont alignées sur le lanceur de la GUI
(`gui/lib/services/grype_runner.dart`) : sans `--add-cpes-if-none`, Grype ne
matche que par PURL et rate les CVE indexées par CPE (ex. le pseudo-paquet
`flutter` d'un `pubspec.lock`, qui n'a pas de PURL exploitable) — c'est la
cause d'un écart constaté entre `scan` et l'onglet Grype sur un même SBOM.
`--by-cve` fait rapporter l'ID CVE plutôt que GHSA, condition nécessaire pour
aligner les identifiants avec OSV-Scanner/Trivy dans la matrice
inter-scanners. `--platform linux` est sans effet sur une entrée SBOM (gardé
pour parité). OSV-Scanner (`--format json --sbom`) et Trivy
(`sbom --format json --quiet`) sont déjà invoqués comme la GUI.

Chaque scanner a son propre format JSON (`matches[]` pour grype,
`results[].packages[].vulnerabilities[]` pour osv-scanner,
`Results[].Vulnerabilities[]` pour trivy) ; `_runGrype`/`_runOsv`/`_runTrivy`
absorbent cette hétérogénéité et retournent la même structure normalisée.

L'échec d'un scanner (binaire absent, JSON illisible) n'empêche pas les
autres scanners demandés (`--scanner all`) de s'exécuter.

Codes de retour : `0` si aucune vulnérabilité dans la plage demandée (tous
scanners confondus), `1` si au moins une trouvée ou en cas d'erreur de scanner.

Voir `doc/usage.adoc` pour des exemples d'utilisation complets.

=== Sous-commande `cra` — rapport de conformité Cyber Resilience Act _(nouveau)_

`_runCra(args)` (dispatché sur `arguments.first == 'cra'`) produit un rapport
de conformité au *Règlement (UE) 2024/2847* restreint au **sous-ensemble
d'exigences automatiquement vérifiables** à partir d'un SBOM. Le rapport
délimite explicitement son périmètre et **n'est pas une déclaration de
conformité** — les exigences non vérifiables sont seulement listées comme
« relevant du fabricant ».

Toute la logique est dans `lib/cra_report.dart` (pur, aucun I/O sauf le PDF).
`_runCra` se limite à l'orchestration :

. parse les arguments, valide `--sbom`, `SbomReader.loadJson` (rejette un
  format inconnu) ;
. métadonnées : `CraMetadata` des flags CLI `.merge(` config `cra.yaml` `)`,
  la config étant `--config` ou `./cra.yaml` s'il existe ; les trous restants
  sont comblés depuis `metadata.component` / `metadata.supplier` du SBOM ;
. si `--scan` : boucle `_runScanner` sur `--scanner` (défaut `grype`) puis
  `_enrichFindings(... poc: false, quiet: true)` ;
. `Process.run('sbomqs', ['score', '--basic', sbom])` best-effort ;
. construit `CraReportGenerator` et sérialise : `json` → stdout ou `-o`
  (exit 2 si verdict `fail`) ; `asciidoc` / `pdf` → écrit le `.adoc` puis
  `renderAsciiDocToPdf` ;
. `stdout` : `Verdict (périmètre vérifié) : …` + `exit(verdict == fail ? 2 : 0)`.

Check-list croisée sur quatre référentiels : **BSI TR-03183-2** (champs de
données par composant : nom, version, fournisseur, identifiant unique
PURL/CPE, empreinte, licence, relations de dépendance), **CRA Annexe I §2**
(inventaire des vulnérabilités connues, disponibilité des correctifs),
**NTIA 2021** (sept éléments minimaux), **CRA art. 14** (toute CVE au
catalogue CISA KEV → notification ENISA sous 24 h).

[cols="1,3", options="header"]
|===
|Membre de `cra_report.dart` |Rôle

|`CraMetadata`
|`merge(other)` (this prioritaire) ; `parseConfig(text)` — `cra.yaml` plat
(`clé: valeur` par ligne, `#` commentaire, clés FR + EN)

|`CraStatus` `{ ok, partial, fail, na }`
|extension `.badge` (rôle AsciiDoc) et `.json` (`name`)

|`_FieldCheck`
|couverture d'un champ BSI (`covered`/`total`, `offenders`, `ratio`, `status`)

|`CraReportGenerator`
|`fieldChecks`, `dependencyStatus`, `ntiaElements`, `_cves` (dédupliqués par
ID normalisé), `sevCount()`, `cvesWithoutFix`, `kevCves`, `blockers`,
`verdict`, `verdictSentence` ; sorties `toAsciiDoc()`, `toJson()` (schéma
`sbom-generator/cra-report/1`, `regulation` `EU 2024/2847`), `toJsonString()`
|===

Verdict : `blockers` non vide → `fail` (exit 2) ; sinon `partial` si un champ
est partiel ou si aucun scan n'a été lancé ; sinon `ok`. Points bloquants :
format non lisible par machine, champ BSI obligatoire manquant, CVE sans
correctif disponible, CVE au catalogue CISA KEV.

Le PDF réutilise le thème asciidoctor-pdf du rapport `scan`
(`renderAsciiDocToPdf` ré-exporté). La GUI
(`gui/lib/widgets/cra_panel.dart`, onglet « Conformité CRA ») ne porte pas
cette logique : elle exécute `sbom-generator cra --format json` via
`Process.run` et affiche le JSON.

Tests : `test/unit/cra_report_test.dart` (`parseConfig`, `merge`,
`CraReportGenerator` sur CDX complet / CDX minimal / avec KEV / SPDX 2.3),
`test/integration/cra_test.dart` (`@TestOn('posix')`, CLI réelle `--no-scan`),
`gui/test/cra_panel_test.dart` (rendu du formulaire).

=== Options CI/CD _(nouveau)_

*`--deny-license <motif>`* (multi-option, répétable) : après génération,
`PolicyChecker.checkDenyLicenses()` est appelé. Les violations sont listées
sur stderr. Code retour `2` si au moins une violation.

*`--min-quality-score <score>`* : après génération, `PolicyChecker.runSbomqs()`

*`--sign`* : après génération et vérification des politiques, `_signWithCosign(path)`

La boucle de résolution de dépendances est skippée si le format est `html`

Fichier de substitution de licences : une ligne `nom_paquet: SPDX-expression`

Parsé par `_parseLicenseMap(String path)` → `Map<String, String>`.

=== Option `--supplier` _(nouveau)_

Valeur de repli pour le fournisseur des composants dont la source ne porte
aucun éditeur (lockfiles Go/npm/yarn/pip/pub, `requirements.txt`).
`_applySupplierFallback(packages, supplier)` applique `copyWith(vendor: …)`
**uniquement** aux paquets dont `vendor` est vide — n'écrase jamais un
fournisseur détecté (`%{VENDOR}` RPM, `Maintainer` Debian, `groupId` Maven,
`Author-email` wheel, `author` du `package.json` npm). Appliqué après
`--license-map` sur la génération, et après `reader.read()` sur `convert`.

Alias explicite pour `--image <fichier>` quand la cible est un binaire

[[sec-option-per-layer]]
=== Options `--per-layer` / `--layer-mode`

Validation (après celle de `--oci-tool`) :

- `--layer-mode` sans `--per-layer` → erreur ;
- `--per-layer` avec `--binary` ou un `--image` de type `OciRefType.binary`
  → erreur (« un binaire autonome n'a pas de couches ») ;
- `--layer-mode metadata` avec un backend hors `metadataLayerTools`
  (`syft`, `trivy`) → erreur ; sans `--layer-mode`, le mode vaut `metadata`
  pour syft/trivy et `rootfs` sinon (message console) ;
- mode `rootfs` sur une référence de registre avec un autre backend que
  skopeo : `skopeo` doit être disponible (copie locale des couches).

Déroulement : l'analyse par couche suit l'analyse OCI habituelle (le SBOM
global reste celui d'une exécution sans `--per-layer`, annoté). Les
surcharges `--license-map` / `--supplier` sont appliquées aux composants des
couches via `LayerAnalysis.map`. La boucle de génération est factorisée dans
une fonction locale `writeAll(pkgs, deps, pathFor, layers:, label:)`,
appelée pour le global puis pour chaque couche. Les UUID de document sont
tirés *avant* toute écriture (liens croisés global ↔ couches), ce qui
permet d'écrire le *global en premier* : c'est le premier
`SBOM written → …` de la sortie, celui que les onglets de la GUI ouvrent par
défaut. Fichiers de couche : `layerFileBase(_basePath(outputPath), layer,
total)` + `_formatExtension(fmt)`, soit `<base>.layer-NN-<digest12><ext>`.
Les dépendances d'une couche sont résolues sur ses seuls composants. `--sign`
signe aussi le premier format de chaque couche ; `--min-quality-score` ne
porte que sur le global.

=== Rapport d'erreurs structuré _(nouveau)_

Les packages dont le parser retourne `null` sont désormais *tracés par ref*
(pas seulement comptés). À la fin du traitement, un rapport est émis sur `stderr` :

....
⚠  2 paquet(s) ignoré(s) :
   • openssl-libs
   • mypkg-1.0-1.el9.x86_64.rpm
....

Implémentation : la boucle `Future.wait` utilise l'index `i` pour corréler
`rawResults[i]` → `mainRefs[i]` dans `failedRefs`. Les messages d'erreur détaillés
des parsers restent émis sur `stderr` au fil de l'eau.

=== Option `--concurrency` / `-c` _(nouveau)_

Contrôle le nombre de tâches traitées simultanément (défaut : `4`, `0` = illimité).
Implémenté via la classe `_Semaphore` :

[source,dart]
----
class _Semaphore {
  _Semaphore(int count) : _count = count;
  int _count;
  final _waiters = <Completer<void>>[];
  Future<void> acquire() async {
    if (_count > 0) { _count--; return; }
    final waiter = Completer<void>();
    _waiters.add(waiter);
    await waiter.future;
  }
  void release() {
    if (_waiters.isNotEmpty) _waiters.removeAt(0).complete();
    else _count++;
  }
}
----

La boucle principale est remplacée par :

[source,dart]
----
final sem = _Semaphore(concurrencyN == 0 ? mainRefs.length : concurrencyN);
final rawResults = await Future.wait(
  List<Future<Package?>>.generate(mainRefs.length, (i) async {
    await sem.acquire();
    try {
      return await _processRef(mainRefs[i], …);
    } finally { sem.release(); }
  }),
);
----

[NOTE]
====
`Future.wait(List.generate(...))` préserve l'ordre : `rawResults[i]` correspond
à `mainRefs[i]`.
====

=== Déduplication

[source,dart]
----
final seenRefs = <String>{};
for (final pkg in packages) {
  if (seenRefs.add(pkg.bomRef)) uniquePackages.add(pkg);

----

`bomRef` est distinct par type : `pkg-<name>-…` (RPM), `pkg-pypi-<name>-…`

=== Résolution des dépendances

Skippée si *tous* les formats demandés sont `markdown` ou `asciidoc` (inutile
et coûteuse pour ces formats tabulaires qui n'exposent pas les dépendances).

=== `_printProgress()`

Affiche une barre de progression ANSI sur la ligne courante (écrasée à chaque
appel via `\r` + `\x1B[K`). La barre est composée de 32 cellules `█` (remplies)
et `░` (vides), suivies du compteur `current/total` et du pourcentage :

[source,text]
----

Le libellé est tronqué à gauche si le nom dépasse la largeur disponible.

=== Signature mise à jour

----

  String? documentName, String? author, String? organization,
  String specVersion = '1.6',              // '1.6' ou '1.7'
  String? tlp,                             // distributionConstraints.tlp (1.7)
  String? citationSource,                  // citations[] attributedTo (1.7)

  OsInfo? osInfo,                          // composant operating-system (--image)

----

=== Support CycloneDX 1.7

Le schéma JSON 1.6 a `additionalProperties: false` partout : les champs propres à 1.7
(`citations`, `definitions.patents`, `components[].patentAssertions`,
`metadata.distributionConstraints`) ne sont donc *jamais* émis en 1.6, et `generate()`
lève une `ArgumentError` si `tlp`/`citationSource`/`patentsByPackageName` sont fournis sans
`specVersion: '1.7'`. `CycloneDxGenerator.supportedSpecVersions` et
`.validTlpClassifications` exposent les valeurs valides pour la CLI.

`PatentAssertion` (patentNumber, jurisdiction, legalStatus, assertionType) est validée
avant génération (regex ST.3 pour `jurisdiction`, enums CycloneDX pour le reste). Chaque
brevet référencé est dédupliqué dans `definitions.patents[]` par `bom-ref`
(`patent-<numéro normalisé>`) ; le composant correspondant reçoit une entrée
`patentAssertions[]` pointant vers ce `bom-ref`. Point notable : le champ `asserter` doit
être désambiguïsé avec un `url: []` vide, sinon le schéma le valide simultanément comme
`organizationalEntity` *et* `organizationalContact` et le `oneOf` strict échoue.

La citation (`--image` + `--cyclonedx-version 1.7`) attribue `/components` au `bom-ref`
de l'outil OCI utilisé (`--oci-tool`), ajouté comme second `tools.components[]` dans les
métadonnées.

=== Champ `group` (composants Maven)

`WheelPackage(packageType: 'maven')` stocke les coordonnées Maven sous la forme
`"groupId:artifactId"` dans `Package.name` (convention interne partagée par
`maven_parser.dart`, `jar_parser.dart`, `oci_parser.dart`). `_packageToComponent` sépare ce
`name` en deux champs CycloneDX dédiés — `group: groupId` et `name: artifactId` — au lieu
de laisser le groupId concaténé dans `name`, pour suivre la convention CycloneDX standard
(champ `group` prévu exactement pour ça) et se rapprocher de ce qu'émettent syft/trivy.
`Package.name` lui-même n'est pas modifié : les autres générateurs (SPDX, Markdown, CSV…)
continuent d'afficher `"groupId:artifactId"` tel quel.

Corollaire côté lecture : `sbom_reader.dart` (`_cdxComponent`) recombine `group` + `name`
en `"groupId:artifactId"` dès qu'un composant a `packageType == 'maven'` et un champ
`group` non vide — sinon le groupId serait silencieusement perdu en relisant un document
CycloneDX généré ainsi (`convert`, `merge`, GUI…).

== `lib/spdx_generator.dart` — Générateur SPDX 2.3

Signature : `List<Package>`, plus `osInfo` (`OsInfo?`, optionnel — voir
<<sec-osinfo-oci-parser>>). Normalisation via `LicenseNormalizer.toSpdxExpression()`.
Annotation type-aware :

[source,dart]
----
String _annotationComment(Package pkg) {
  if (pkg is RpmPackage)
    return 'arch=${pkg.arch}; epoch=${pkg.epoch}; release=${pkg.release}…';
  if (pkg is WheelPackage)
    return '${pkg.packageType == "pypi" ? "pypi" : "source"}:platform=${pkg.arch}';
  if (pkg is DebPackage)
    return 'deb:arch=${pkg.arch}';
}
----

Quand `osInfo` est fourni, `_osToSpdx()` ajoute un paquet
`primaryPackagePurpose: "OPERATING-SYSTEM"` avec une relation `DESCRIBES`
depuis `SPDXRef-DOCUMENT`. Le `SPDXID` de ce paquet est préfixé
`SPDXRef-OperatingSystem-` (et non `SPDXRef-Package-` comme les autres) —
c'est ce préfixe précis que Trivy reconnaît pour la classe "os-pkgs" en
mode `trivy sbom` ; `primaryPackagePurpose` seul ne suffit pas (vérifié
empiriquement, voir <<sec-osinfo-oci-parser>>).

`package.supplier` est **toujours émis** : `Organization: <vendor>` si connu,
sinon `NOASSERTION` — la spéc SPDX 2.3 demande la valeur explicite quand le
fournisseur est inconnu (plutôt que d'omettre le champ), et c'est ce
qu'attendent les éléments minimaux NTIA et `sbomqs`. Idem pour le paquet OS.
`checksums` est émis depuis `pkg.hashes` (`spdx2Alg` : `SHA-256` → `SHA256`).

== `lib/spdx3_generator.dart` — Générateur SPDX 3.0 JSON-LD

Signature : `List<Package>`, plus `osInfo` (`OsInfo?`, optionnel). Normalisation via `LicenseNormalizer.toSpdxExpression()`.
Même logique d'annotation que SPDX 2.3 (branche `DebPackage` incluse).
`_buildVendorElements` crée un nœud `Organization` par valeur unique de `pkg.vendor`
(fonctionne pour tous les types).

Quand `osInfo` est fourni, `_osToElement()` ajoute un élément
`software:Package` avec `software:primaryPurpose: "operatingSystem"`,
inclus dans `rootElement` du `SpdxDocument` et dans la relation `describes`.
Représentation correcte selon la spec SPDX 3.0, mais *Trivy ne sait pas lire
de SBOM SPDX 3.0 JSON-LD du tout* (`trivy sbom` échoue avec `SBOM decode
error: unknown scanning is not yet supported`, indépendamment de ce
composant) — limitation de Trivy, sans rapport avec `sbom_generator`.

== Flux de données — exemples concrets

=== RPM : `bash` depuis un fichier .rpm

....
1. Détection : .rpm → RpmParser.parsePackage()
2. rpm -qp --queryformat '…' → "bash|5.1.8|6.el9|x86_64|(none)|GPL-3.0-or-later|…"
3. RpmPackage : bomRef="pkg-bash-5.1.8-6.el9-x86_64", purl="pkg:rpm/bash@5.1.8-6.el9?arch=x86_64"
4. LicenseNormalizer.toCycloneDxLicenses("GPL-3.0-or-later")
   → normalised = "GPL-3.0-or-later" (pas d'opérateur booléen)
   → mapped = "GPL-3.0-or-later" (dans kSpdxLicenseIds → id)
   → {"license": {"id": "GPL-3.0-or-later"}}
....

=== Python wheel : `requests-2.28.2-py3-none-any.whl`

....
1. Détection : .whl → WheelParser.parseWheelFile()
2. python3 zipfile → requests-2.28.2.dist-info/METADATA
3. _parseRfc822() → {name: "requests", version: "2.28.2", license: "Apache-2.0", …}
4. _platformFromFilename() → "any" (dernier segment avant .whl)
5. WheelPackage : packageType='pypi', bomRef="pkg-pypi-requests-2.28.2"
                  purl="pkg:pypi/requests@2.28.2"
....

=== Archive générique : `mariadb-11.4.8-linux-systemd-x86_64.tar.gz`

....
1. Détection : .tar.gz → TarParser.parseTarFile()
2. python3 tarfile : pas de PKG-INFO → type='generic'
   fichier COPYING trouvé → 2 KB extraits
3. _parseFilename() :
   segments=[mariadb, 11.4.8, linux, systemd, x86_64]
   versionIdx=1 ("11.4.8" ≅ ^\d+\.\d+)
   filtrage plateforme : linux, systemd, x86_64 retirés
   → name="mariadb", version="11.4.8", arch="x86_64"
4. _identifyLicense(COPYING) :
   title[:300] contient "GNU GENERAL PUBLIC LICENSE" + "Version 2"
   → "GPL-2.0-only"
5. WheelPackage : packageType='source', purl="pkg:generic/mariadb@11.4.8"
....

=== Python sdist : `Django-4.2.1.tar.gz`

....
1. Détection : .tar.gz → TarParser.parseTarFile()
2. python3 tarfile : PKG-INFO trouvé → type='python', contenu RFC 822
3. Délégation à WheelParser.parseMetadataText(path, content)
4. WheelPackage : packageType='pypi', purl="pkg:pypi/django@4.2.1"
....

=== Paquet Debian : `libssl3_3.0.1-1_amd64.deb`

....
1. Détection : .deb → DebParser.parseDebFile()
2. dpkg-deb -f → control RFC 822 : "Package: libssl3\nVersion: 3.0.1-1\n..."
3. _parseControl() → {Package: libssl3, Version: 3.0.1-1, Architecture: amd64, …}
4. _parseDependsList("libc6 (>= 2.17), libgcc-s1") → ["libc6", "libgcc-s1"]
5. DebPackage : bomRef="pkg-deb-libssl3-3.0.1-1-amd64",
               purl="pkg:deb/libssl3@3.0.1-1?arch=amd64"
....

=== Requirements.txt : `/opt/reqs/requirements.txt`

....
1. Détection : .txt → pré-expansion RequirementsParser (avant la boucle concurrente)
2. Lecture ligne par ligne : "requests==2.28.0\nnumpy>=1.24\nflask\n"
3. _parseLine("requests==2.28.0") → WheelPackage(name="requests", version="2.28.0",
                                                  packageType="pypi")
4. _parseLine("flask") → WheelPackage(name="flask", version="", packageType="pypi")
5. Résultats ajoutés à preloadedPackages (puis packages après boucle principale)
....

=== Image OCI : `nginx:latest` via syft

....
1. Détection OCI : --image nginx:latest (OciRefType.registry)
2. Process.run('syft', ['nginx:latest', '--output', 'json'])
3. _parseSyft() parcourt artifacts[] :
   ex. {name: "bash", version: "5.1.8", type: "rpm", purl: "pkg:rpm/rhel/bash@5.1.8",
        licenses: [{spdxExpression: "GPL-3.0-or-later"}], metadata: {Arch: "x86_64"}}
4. OciPackage(name="bash", version="5.1.8", packageType="rpm",
              purlOverride="pkg:rpm/rhel/bash@5.1.8",
              bomRef="pkg-oci-rpm-bash-5.1.8")
5. Résultats ajoutés à ociPackages → fusionnés dans packages avant déduplication
....

== Pièges et décisions de conception

=== 1. Séparateur `|` dans SUMMARY (RPM)

`SUMMARY` peut contenir des `|`. Il est placé en dernier dans `_queryFormat`
et les fragments ≥ index 12 sont rejoints.

=== 2. Doublons de bomRef (RPM)

Même NEVRA dans plusieurs dépôts → même `bomRef` → interdit par CycloneDX.
La déduplication dans `main()` supprime le deuxième exemplaire.

=== 3. `LicenseRef-*` dans CycloneDX

`license.id` est validé contre la liste SPDX officielle. `LicenseRef-*` n'en
fait pas partie (dans le schéma embarqué de sbomqs v2.0.6). Utiliser
`{"license": {"name": "…"}}` à la place.

=== 4. Champ `acknowledgement` (CycloneDX 1.6.1)

Ajouté après la version du schéma embarqué dans sbomqs. Son utilisation cause
une erreur de validation. Ne pas l'utiliser.

=== 5. `_capabilityName` et les modules Python RPM

`split(RegExp(r'[\s(]'))` tronquerait `python3dist(lxml)` en `python3dist`,
créant de faux positifs. Le split sur `\s+[<>=!]` préserve les parenthèses.

=== 6. Faux positif GPL → LGPL dans la détection de licence

Le texte GPL-2.0 mentionne « GNU Library General Public License » dans sa
section « How to Apply ». La détection LGPL ne porte que sur les 300 premiers
caractères (titre du document), pas sur le corps complet.

=== 7. Dépendances Python intra-liste

La résolution fonctionne si les noms sont normalisés de manière cohérente
(PEP 503). `WheelPackage.provides` contient le nom normalisé ; `Requires-Dist`
est aussi normalisé au parsing. `buildDependencies` ajoute de plus `pkg.name`
brut à `providesMap`, couvrant les deux formes.

=== 8. Requirements.txt : cardinalité 1:N

Un fichier `.txt` unique peut produire N paquets. La boucle concurrente modélise
`Future<Package?>` (1 ref → 0 ou 1 résultat), incompatible avec la cardinalité
1:N. Solution : pré-expansion des `.txt` avant la boucle dans `preloadedPackages`.

=== 9. Champ `License` absent dans de nombreux `.deb`

Le standard Debian ne rend pas le champ `License` obligatoire dans
`DEBIAN/control`. `DebPackage.license` sera souvent vide, ce qui donne
`NOASSERTION` dans SPDX et une liste `licenses` vide dans CycloneDX —
comportement conforme, non une erreur.

=== 10. Ordre préservé par `Future.wait(List.generate(...))`

`Future.wait` garantit que le résultat à l'index `i` correspond à l'entrée `i`.
L'ordre d'apparition dans le SBOM final est donc identique à l'ordre du fichier
d'entrée, malgré le traitement concurrent.

entrées sont lancées simultanément.

=== Limites connues

* *Pas de résolution transitive* : seules les dépendances entre paquets présents
  dans la liste sont incluses.
* *CPE approximatifs* : valides syntaxiquement, peuvent différer des entrées NVD
  officielles.
* *Licences archive heuristiques* : la détection depuis les fichiers LICENSE/COPYING
  est basée sur des patterns textuels, non sur une analyse exhaustive.
* *Champ License absent dans les `.deb`* : la plupart des paquets Debian n'incluent
  pas de champ `License` dans leur `control` — `DebPackage.license` sera vide, ce
  qui produit `NOASSERTION` dans SPDX.
* *Pas de vérification d'existence des fichiers* : si un chemin `.whl`, `.tar.gz`,
  `.zip` ou `.deb` n'existe pas, le subprocess échoue et le paquet est compté comme
  échec.
* *Licences absentes dans les images OCI (skopeo)* : `_parseDpkgStatus` ne lit pas
  les fichiers `copyright` ; `_parseRpmRoot` ne dispose que des champs `%{LICENSE}`
  du registre RPM — même lacune qu'avec `DebPackage`.
* *Analyse OCI non parallélisée* : l'appel `OciParser.parseImage()` est séquentiel
  et bloquant ; `--concurrency` ne s'applique qu'aux entrées de `--input`.
