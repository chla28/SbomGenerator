== Introduction

=== What is an SBOM?

An *SBOM* (Software Bill of Materials) is a structured file listing all the
components of a piece of software: packages, libraries, versions, licenses.
It plays the role of a bill of materials, in the industrial sense of the term.

The most widespread formats are:

* *CycloneDX* (JSON, recommended by OWASP and ANSSI)
* *SPDX* (ISO/IEC 5962:2021 standard, adopted by the Linux Foundation)

=== What is Grype?

*Grype* (Anchore) is an open-source CVE vulnerability scanner.
It analyzes an SBOM file and compares it with vulnerability databases
(NVD, GitHub Security Advisories…) to identify the affected packages and
their severity level.

Severity levels (from most critical to most benign):

[cols="1,1,3", options="header"]
|===
|Level |Color in the UI |Meaning

|Critical
|Dark red
|Immediate exploitation, maximum impact (RCE, privilege escalation…)

|High
|Red-orange
|Significant impact, likely exploitation

|Medium
|Orange
|Exploitable under particular conditions

|Low
|Green
|Limited impact, hard to exploit

|Negligible
|Grey
|Theoretical impact, generally not exploitable in practice (Grype only)
|===

NOTE: The databases used by OSV-Scanner sometimes use the label `MODERATE`
(GitHub Advisory, npm) instead of `MEDIUM`. The application unifies them
automatically: any `MODERATE` severity is displayed as `Medium` in the table
and the filters.

=== About the tool

*SBOM Generator GUI* is a Linux desktop graphical interface that orchestrates
command-line tools:

* `sbom-generator`: generates SBOM files from a list of packages or an OCI image
* `grype`: analyzes the generated SBOMs to detect CVE vulnerabilities (Anchore)
* `osv-scanner`: analyzes SBOMs to detect CVE vulnerabilities (Google)
* `trivy`: analyzes SBOMs to detect CVE vulnerabilities (Aqua Security)
* `sbomqs`: computes an SBOM quality score (optional)
* `asciidoctor-pdf`: converts the AsciiDoc report to PDF (optional)

The interface lets you configure the options, follow the execution in real
time, access the produced files, preview them, and run a vulnerability
analysis without ever opening a terminal.

For each run, the *equivalent command line* is displayed in the interface —
under the *▶ Generate the SBOM* button and as the first entry of the progress
log.

Settings are *automatically saved* between sessions.

*Left panel — Configuration*: setting of all the options before launching.
Fixed width (390 px). Settings are restored automatically at each start. The
equivalent CLI command is displayed under the *▶ Generate the SBOM* button and
is updated in real time.

*Right panel — Results*: fourteen tabs — Progress (with log export and
summary), Results (files + sbomqs score), Dashboard (multi-scanner CVE
synthesis), Grype, OSV-Scanner and Trivy (CVE analyses), CRA Compliance
(Cyber Resilience Act compliance report), SBOM Quality (sbomqs +
sbom-scorecard), SBOM Tree (exploration of the SBOM components), SBOM
Comparison (diff of two SBOMs), SBOM Merge (combines several SBOMs into one),
SBOM Licenses (visualization of the SBOM licenses and compliance report in
AsciiDoc, Markdown, HTML, CSV or JSON), SBOM Viewer (interactive exploration
of an external SBOM file) and Preview (preview of the SBOM content).

The *❓* button in the title bar opens this user manual directly in the
application (table of contents on the left, selected chapter on the right) —
not to be confused with the smaller ❓ icons present on each field/section,
which display a short tooltip on hover instead of opening the full manual.
The search field at the top of the table of contents filters the chapters by
title *and* by content as you type; an excerpt of the passage found is
displayed under the title of the matching chapter.

The *🌙 / ☀* button in the title bar switches between dark and light mode.
The *🎨* button opens the theme color picker. Both preferences are saved.

The *文A* button (interface language) offers *System*, *Français* and
*English*. *System* follows the language of the workstation, falling back to
French if it is not supported. The choice applies immediately and is saved.
The language is also forwarded to the `sbom-generator` CLI launched by the
GUI (via `SBOM_LANG`), so the messages of the Progress tab follow it.

NOTE: The interface, the exported reports (AsciiDoc/PDF), the CLI messages and
this manual are available in French and English. Machine-read contents (SBOM
files, `Error:` / `Warning:` prefixes, JSON keys) are never translated.

== Configuration panel

=== Input section

==== Input file (`--input`)

Path to the file containing the list of packages to analyze.
The 📂 button to the right of the field offers a menu:

[cols="2,3"]
|===
|*Filtered type (.lst .txt)* |Only shows files with the usual extensions
|*All files* |Shows all the files of the directory
|===

TIP: You can also *drag and drop* a file from your file manager (Nautilus,
Thunar…) directly onto this field. A blue outline indicates that the drop is
accepted.

The file must contain *one item per line*. The accepted types are:

[cols="2,3", options="header"]
|===
|Type |Line format

|Installed RPM package
|`bash` or `bash-5.1.8-6.el9.x86_64`

|Local RPM file
|`/path/to/package.rpm`

|Python wheel (`.whl`)
|`/path/to/package-1.0-py3-none-any.whl`

|Tar archive
|`/path/to/pkg.tar.gz` or `.tgz`

|Zip archive
|`/path/to/archive.zip`

|Debian package (`.deb`)
|`/path/to/package.deb`

|Python dependencies
|`/path/to/requirements.txt`

|Java archive (`.jar`)
|`/path/to/lib-1.2.3.jar`

|Manifest / lockfile
|`go.sum`, `go.mod`, `package-lock.json`, `yarn.lock`, `pom.xml`,
`pubspec.lock`, `pubspec.yaml`
|===

A single input file may contain lines of different types. A path pointing
directly to an archive or to a single manifest (rather than to a list file) is
also accepted; a directory is scanned recursively for all these types. For
Dart/Flutter, `pubspec.lock` provides the resolved versions and the complete
transitive closure (development dependencies are excluded); `pubspec.yaml`
only provides the direct dependencies of the `dependencies:` section.

NOTE: The *Packages to analyze* field becomes optional if an *OCI image* is
specified in the next section.

IMPORTANT: The *Packages to analyze* and *OCI image* fields are mutually
exclusive in the interface: filling in one (typing, drag and drop, or
file/directory picker) automatically empties the other. To combine both
sources in a single analysis, use the command line (`--input` and `--image`
together).

=== OCI image section

==== OCI image (`--image`)

Reference of an OCI image to analyze. Three formats are accepted:

[cols="2,3,2", options="header"]
|===
|Format |Description |Example

|Registry
|Docker Hub image or private registry
|`nginx:latest`

|Tar archive
|`docker save` or `skopeo copy docker-archive:` export (.tar, .tar.gz, .tgz)
|`/path/ubuntu.tar`, `/path/image.tar.gz`

|OCI layout
|Directory containing `index.json`
|`/path/oci_dir/`
|===

The 📂 button to the right of the field opens a context menu:

* *Tar archive (.tar / .tar.gz / .tgz)* — file picker filtered on these three extensions
* *OCI layout directory* — directory picker

For registry images, type the reference manually.

If the field is empty, the OCI analysis is disabled.

==== OCI tool (`--oci-tool`)

Only visible when the *OCI image* field is filled in. Select the analysis
backend:

[cols="1,2,2", options="header"]
|===
|Tool |Description |Requirements

|Syft (default)
|Anchore Syft — all package types (deb, rpm, apk, pypi, npm, go, java…)
|`syft` in the PATH

|Trivy
|Aqua Trivy — all package types
|`trivy` in the PATH

|Skopeo
|Manual layer extraction — dpkg, RPM and APK only
|`skopeo` and `tar` in the PATH

|cdxgen
|OWASP CycloneDX Generator — all package types; the produced SBOM is
filtered to the components carrying a real ecosystem PURL
|`cdxgen` in the PATH (requires Node.js)
|===

[[sec-depth]]
==== Descent depth (`--depth`)

Under the input field, the *Depth* selector lets you descend into the objects
contained in the input: for example the jars of an RPM, the packages and jars
of a `.tar.gz` / `.zip` archive, the jars of a fat jar, as well as the
manifests found (`package-lock.json`, `go.sum`, `pom.xml`…).

[cols="1,3"]
|===
|*0 — object only* |Default behavior: the input is not opened
|*1 level, 2, 3* |Descends N levels (1 = direct objects of the input, 2 = what these contain…)
|*Unlimited* |All levels (capped at 10)
|===

The generated SBOM merges the object and everything it contains: each nested
component carries its location (`sbom_generator:nested:location`) and its
depth, and the dependency graph links the container to its content. As soon
as the depth is greater than 0, the *One SBOM per nested object* checkbox
additionally writes one SBOM per jar/package/archive
(`<output>.nested-NN-<object>.<ext>`); these files appear in the list of
produced files, after the global SBOM. Unchecking the box adds
`--no-nested-files`.

NOTE: The depth only applies to a *file / folder* input (not to an image or a
binary). The extraction is size-bounded and requires `python3`; analyzing a
nested `.rpm` requires `rpm`.

[[sec-per-layer]]
==== One SBOM per layer (`--per-layer`)

Checkbox visible under the OCI backend, only for an *OCI image* (a standalone
binary has no layers). Once checked, the generation produces, in addition to
the global SBOM, one SBOM per image layer in each checked format:
`<output>.layer-NN-<digest>.<ext>` (e.g. `sbom.layer-02-b676b687f0f5.cdx.json`).

The SBOM of a layer describes its *delta*: the components added or modified
by the layer, with the removed components listed separately; its root
component carries the build instruction (`RUN …`, `COPY …`) and the digest of
the layer. The global SBOM indicates, for each component, the layer that
introduced it.

The method selector (`--layer-mode`) offers:

[cols="1,3",options="header"]
|===
|Method |Principle

|Metadata (default)
|Originating layer reported by Syft or Trivy. Fast; only *additions* are
known. Unavailable with Skopeo and cdxgen.

|Rootfs
|Layers are applied one by one and the image is re-analyzed after each one:
additions, *modifications* (version bumps…) and *removals*. One analysis per
layer, hence slower. The only possible mode with Skopeo and cdxgen (reminder
displayed under the selector). For a registry image, `skopeo` must be
installed.
|===

Layer SBOMs can be browsed from the *SBOM Tree* and *SBOM Viewer* tabs (see
<<sec-nav-couches>>). The global SBOM is always the first file produced: it is
the one that the other tabs (Preview, scanners, Quality, CRA…) select by
default.

==== Standalone binary (`--binary`)

Separate field, under a second “OR” separator: local executable to analyze
directly (not a container image) — for example a statically linked Go binary.
The 📂 button opens a simple file picker (no extension filter, a binary often
has none).

Mutually exclusive with *Packages to analyze* and *OCI image*: filling in this
field automatically empties the other two, and conversely.

Systematically forces the Syft backend (the *OCI tool* selector is not
displayed for this field) — it is the only backend able to exploit the
metadata embedded in a standalone binary:

* *Go* (statically linked or not): the complete list of modules + versions
  is read from the `buildinfo` metadata embedded in the executable, even if
  stripped.
* *Other languages* (Rust, static C/C++…): only a *fixed* catalog of
  well-known open-source libraries (OpenSSL, zlib, sqlite, busybox…) is
  detected through a version-string fingerprint — not an arbitrary
  extraction of the linked dependencies.
* A statically linked library with no recognized signature nor embedded
  metadata (home-made C/C++, Rust without `cargo-auditable`) cannot be
  recovered afterwards.

=== Output section

==== Base path (`--output`)

Prefix of the generated files, without extension.
Example: `sbom` will produce `sbom.cdx.json`, `sbom.spdx.json`, etc.
A relative path is resolved from the current directory at launch time.

A preview of the expected file names is displayed as soon as the field is
filled in.

==== Formats (`--format`)

Check one or more formats. At least one format must be selected.

[cols="2,2,3", options="header"]
|===
|Format |Produced extension |Typical use

|CycloneDX 1.6
|`.cdx.json`
|Vulnerability analysis with grype, OWASP tools

|SPDX 2.3
|`.spdx.json`
|Legal compliance, OpenChain tools

|SPDX 3.0 JSON-LD
|`.spdx3.jsonld`
|Linked ecosystems (RDF/ontology)

|Custom JSON
|`.custom.json`
|Integration into internal pipelines

|Markdown
|`.md`
|Documentation directly readable on GitHub/GitLab

|AsciiDoc
|`.adoc`
|Rich technical report (tables, styles)

|HTML
|`.html`
|Standalone interactive report (filterable and sortable, charts by ecosystem/license)

|CSV
|`.csv`
|Import into a spreadsheet or a data-processing pipeline
|===

==== PDF option (AsciiDoc only)

When the *AsciiDoc* format is checked, an additional option appears:
*Convert to PDF (asciidoctor-pdf)*. If enabled, the `asciidoctor-pdf` tool is
launched automatically after the `.adoc` is generated.

An optional field lets you specify the destination path of the PDF.
Without a value, the PDF is created in the same folder as the `.adoc`, with
the same base name.

=== Options section

==== SBOM document name (`--name`)

Label that will appear in the SBOM metadata
(`metadata.component.name` field in CycloneDX).
Example: `My Application 2.1.0`.
Leave empty to use the name of the input file.

==== Local RPM directory (`--rpm-dir`)

Folder containing additional `.rpm` files to include in the analysis.
Useful to enrich the metadata resolution (exact version, license)
when the packages are not installed on the current machine.

==== License override (`--license-map`)

Text file used to correct or specify the licenses of some packages.
The button on the right offers the same options as the input file field:
filtered type (`.txt`, `.yaml`) or all files.
Format: one rule per line: `package-name: SPDX-expression`

Example:
----
openssl: OpenSSL
my-internal-lib: LicenseRef-PROPRIETARY
----

==== Concurrency (`--concurrency`)

Number of packages processed in parallel. The slider goes from *0*
(unlimited) to *16*. The default value is *4*.

* Increase it if your machine has many cores and a good network connection.
* Decrease it (1 = sequential) in case of rate-limiting errors on the repositories.
* The value 0 processes all the packages simultaneously — to be used with
  caution on large lists.

==== Verbose mode (`--verbose`)

Displays additional information in the *Progress* tab: resolution tools used,
processing statistics, details of each package found.

==== sbomqs quality score

When this option is checked, `sbomqs score` is run automatically on the first
generated JSON SBOM file (`*.cdx.json` or `*.spdx.json`).
The result is displayed in the *Results* tab under the file list.

If `sbomqs` is not installed, the option is silently ignored.

NOTE: See <<_installing_sbomqs_optional>> for the installation.

=== Settings persistence

All the settings of the *Options* section — selected formats, base path, RPM
directory, license file, concurrency level, verbose mode, PDF generation,
sbomqs score — are *automatically saved* after each generation and *restored*
at the next application start.

The saved settings *do not include* the input file (too tied to a particular
context) nor the PDF path.

be recalled in one click to switch quickly between several typical
configurations (e.g. “RHEL 9 production”, “Python audit”, “Minimal CI/CD”).

=== Command preview

Under the *▶ Generate the SBOM* button, the shell command line equivalent to
the current configuration is permanently displayed:

----
  $ sbom-generator --input /home/user/packages.lst \
    --output /home/user/sbom --format cyclonedx spdx
----

This preview is updated at each field change. A 📋 button copies the command
to the clipboard to replay it from a terminal or integrate it into a CI/CD
script.

=== Starting and stopping the generation

Click *▶ Generate the SBOM* to start.
The button turns into *■ Stop generation* during execution.
Clicking Stop sends an interrupt signal to the process.

=== Post-generation summary

At the end of a successful generation, a summary card is displayed at the
bottom of the tab:

* number of analyzed packages
* number of generated SBOM files
* number of warnings (in orange if > 0)

The card outline is green on success with no warning, orange otherwise.

[[sec-source-scan]]
=== Selecting the source to analyze

A *SBOM file / Container image / Package / archive* toggle at the top of the
panel lets you choose what grype analyzes. This choice, as well as the
associated field, is shared by the three scan tabs (Grype, OSV-Scanner,
Trivy) — see also <<sec-onglet-trivy-source>> and <<sec-onglet-osv-source>>.

*SBOM file* (default mode): the field is automatically pre-filled with the
last SBOM file generated in the current session, giving priority to the
formats recognized by grype: `.cdx.json` (CycloneDX) then `.spdx.json`
(SPDX). You can type a path manually or click *Choose* to browse the file
system. The `.json` and `.jsonld` formats are offered in the picker.

NOTE: Grype analyzes the content of the file, not its extension.
A CycloneDX file renamed `.json` is recognized correctly.

*Container image*: the field accepts three forms of reference, all supported
by grype with no syntax distinction on the application side:

* a *registry* reference, e.g. `nginx:latest`, `ghcr.io/org/app:tag` — the
  image is fetched through the local Docker configuration (`docker login`)
  if the registry is private, with no dedicated credentials field in the
  application;
* an *archive* exported by `docker save` (or an OCI archive), through the
  dedicated button (extensions `.tar`, `.tar.gz`, `.tgz`);
* an *OCI layout directory* (produced for example by `skopeo copy`), through
  the second dedicated button.

An optional *Platform* field appears in image mode, to force the target
platform on a multi-architecture image (e.g. `linux/arm64`). Left empty, grype
automatically detects the most suitable platform.

[[sec-scan-paquet]]
*Package / archive*: a local file — `.rpm`, `.deb`, `.tar` / `.tar.gz` /
`.tgz`, `.zip`, `.jar` / `.war` / `.ear`, `.whl` — is analyzed directly,
without going through an SBOM file. The application first runs
`sbom-generator --input <file> --depth N` (see <<sec-depth>>) in a temporary
directory, then the scanner analyzes the produced CycloneDX SBOM, exactly
like an SBOM file: the three tabs (Grype, OSV-Scanner, Trivy) therefore
receive the same components. The *Depth* selector (0 — object only, 1 to 3
levels, Unlimited) chooses how far to descend into the contained objects (jars
of an RPM, packages of an archive…). The generated SBOM is reused by the tabs
as long as the file and the depth do not change. The header of the exported
reports indicates “package <name> (depth N)”.

NOTE: CVEs are displayed per vulnerable package (`name@version`). To know
which nested object contains it, use the *sbom-generator scan --package
equivalent* command of the *CLI Command* button (`OBJECT` column).

[[sec-cli-commande]]
=== Command line (*CLI Command* button)

The *CLI Command* button, next to the analyze button (shared by the three scan
tabs), opens a popup with the commands matching the current settings of the
tab, each with a *Copy* button:

* *Command run by the tab* — the exact `grype` / `osv-scanner` / `trivy` line,
  with all the options of the tab (built by the same code as the execution).
  With the *Per layer* option (see <<sec-scan-couches>>), the sequence
  actually launched: generation of the per-layer SBOM set
  (`sbom-generator --image … --per-layer`), then the scan of the image
  (*Attribution*) or a `for f in …; do …; done` loop over the layer SBOMs
  (*Each layer*). The application's temporary directory is replaced by
  `/tmp/sbom-couches`.
* *sbom-generator scan equivalent* — the command of the project's CLI that
  produces the same kind of analysis: target (`--sbom` or `--image`),
  `--scanner`, per-layer options (`--per-layer --layer-scan …
  --layer-mode …`), the tab's date filter (`--cve-after`, `--cve-before`,
  `--cve-date-field`, `--include-undated`) and offline enrichment
  (`--no-enrich`). A remark points out the options of the tab with no
  equivalent (template, `--fail-on`, `--only-fixed`, Trivy severities,
  configuration files…) and reminds that with `--image`, `sbom-generator scan`
  analyzes the SBOM generated by syft and not the image directly.

With the *Package / archive* source, the popup additionally displays the SBOM
generation (`sbom-generator --input … --depth N`, SBOM written to
`/tmp/sbom-paquet/`) before the scanner command, and the equivalent is
`sbom-generator scan --package … --depth N`.

As long as the target is not filled in, it appears as `<sbom.cdx.json>`,
`<image>` or `<package>`.

[[sec-scan-couches]]
=== Per-layer analysis (“Container image” source)

In *Container image* mode, the *Per layer* checkbox (shared by the three scan
tabs) attributes each vulnerability to the *layer* of the image that brings
the vulnerable package. The application first generates, through
`sbom-generator --image … --per-layer` (syft backend), a global SBOM and one
SBOM per layer in a temporary directory; this set is reused by the three tabs
as long as the image and the computation do not change.

[cols="1,3,3",options="header"]
|===
|Method |Principle |What you see

|Attribution (default)
|A single scan of the image, as without the option; each vulnerability is
attached to the originating layer of its package. Trivy and OSV-Scanner
report this layer themselves (`Layer.DiffID`, `image_origin_details`), used
first; otherwise, the package is looked up in the global SBOM.
|The CVEs of the final image, by the layer that introduced them.

|Each layer
|The SBOM of each layer is scanned separately (one scan per layer); the
outputs are merged.
|In addition, the CVEs of a version introduced by a layer then replaced
higher up (with the *Rootfs* computation). A CVE may appear in several
layers.
|===

The second selector chooses the layer computation: *Metadata* (originating
layer reported by syft — fast, additions only) or *Rootfs* (layers applied one
by one and re-analyzed — additions, modifications, removals; slower). During
the analysis, a status line indicates the current step (preparing the SBOMs,
layer i/N…); the *Stop* button also interrupts the generation and the
remaining scans.

In the *Table view* (see <<sec-vue-table>>):

* a *LAYER* column shows the layer(s) of each vulnerability (`?` if the
  package is absent from the image SBOM — a banner shows the number); the
  tooltip recalls the digest and the build instruction;
* the *All layers / Layer N (n)* menu filters on one layer;
* the *Group by layer* button (layers icon) groups the list under one header
  per layer — digest, build instruction and counters per severity;
* the CSV and AsciiDoc + PDF exports add a *Layer(s)* column and, for the PDF,
  an *Image layers* section.

The *Dashboard* reuses this information (see <<sec-dashboard-couches>>).

NOTE: In *Each layer* mode, OSV-Scanner analyzes SBOMs and not the image: it
then finds few or no CVEs on system packages (see
<<sec-pourquoi-ecarts-scanners>>) — prefer *Attribution* with this tool.

=== Scan options

==== `--platform linux`

Forces grype to consider the target platform as Linux when resolving
vulnerabilities, in *SBOM file* mode only. Recommended for SBOMs coming from
RPM or DEB package lists.

Uncheck this option if you analyze an SBOM coming from another system (macOS
libraries…).

NOTE: This checkbox has no effect in *Container image* mode: it is ignored in
favor of the *Platform* field described above (`linux` alone, without
architecture, is moreover rejected by grype on a multi-platform image).

==== `--add-cpes-if-none`

Grype uses *CPE* (Common Platform Enumeration) identifiers to match packages
with CVE entries. If a package of the SBOM has no declared CPE, this option
asks grype to generate one automatically from the package name and version.

Recommended: reduces false negatives on SBOMs produced without CPEs (which is
the case of most SBOMs generated by `sbom-generator`).

==== `--by-cve`

Without this option, grype groups the results by *GHSA* identifier (GitHub
Security Advisory) when available. With this option, each result is presented
under its main *CVE* identifier, which is more universal and recognized by
vulnerability management tools.

Recommended for interoperability with ticketing tools (Jira, defect trackers,
etc.) or internal vulnerability repositories.

==== `--distro rhel:<version>`

Specifies the target Linux distribution. Without this option, grype tries to
deduce it from the SBOM, which may fail or produce imprecise matches.

RHEL versions available in the menu: *7*, *8*, *9*, *10*. Select *(none)* to
let grype detect the distribution automatically.

NOTE: Choosing the wrong version may cause false positives (vulnerabilities
not applicable because already fixed by the RHEL backport) or false negatives.
Check the exact version of your system with `cat /etc/redhat-release`.

==== `--fail-on <severity>`

Controls the exit code of grype. With this option, grype returns an error
(non-zero) code if at least one vulnerability of the given level or higher is
detected. Useful in CI/CD.

Example: `--fail-on high` makes the analysis fail if a *High* or *Critical*
vulnerability is found.

The result banner in the UI reflects this exit code: red background if grype
returned an error, green otherwise.

==== `--only-fixed`

Only shows the vulnerabilities for which a fixed version is available. Lets
you focus on the immediately actionable items.

=== Output template (`-t`)

The *Template (-t)* field lets you generate a custom output (CSV, HTML, text)
through a Go template file.

The field is pre-filled with `./grype_csv.tmpl`. If this file does not exist
at launch time, the template output is ignored without error.

Example of a Go template for a CSV:

----
"CVE","Package","Installed version","Fixed version","Severity"
{{- range .Matches}}
"{{.Vulnerability.ID}}","{{.Artifact.Name}}","{{.Artifact.Version}}","{{fixedIn .Vulnerability}}","{{.Vulnerability.Severity}}"
{{- end}}
----

The produced output is displayed in the *Template* tab (see
<<sec-vue-template,Template view>>) and can be copied to the clipboard.

NOTE: Grype is launched in a single pass that simultaneously produces the JSON
output (for the Table view) and the template output (through a temporary
file).

=== Configuration file (`grype.yaml`)

Path to a grype configuration file in YAML format. Lets you define ignore
rules, custom databases, proxies, etc.

This parameter is optional. Leave the field empty to use the default grype
configuration (`~/.grype.yaml` if it exists).

Official documentation: https://github.com/anchore/grype#configuration

==== Table view

[[sec-vue-table]]
The Table view shows a search/sort toolbar, the severity filters, then the
list of vulnerabilities:

----
  [ Search...                            ] [⬇]
  Filter : [Critical (1)] [High (2)] [Medium (2)] [Low (0)]  [Show all]

  ┌────────────┬──────────────────┬──────────────────┬───────────────┬──────┐
  │ SEVERITY ↕ │ PACKAGE ↕        │ VERSION ↕        │ CVE/ID ↕      │ TYPE │
  ├────────────┼──────────────────┼──────────────────┼───────────────┼──────┤
  │ CRITICAL   │ openssl          │ 1.1.1k → 1.1.1l  │ CVE-2021-3711 │ rpm  │
  │ HIGH       │ bash             │ 5.0.17  (no fix) │ CVE-2021-3489 │ rpm  │
  │ MEDIUM     │ zlib             │ 1.2.11  → 1.2.12 │ CVE-2022-37434│ rpm  │
  └────────────┴──────────────────┴──────────────────┴───────────────┴──────┘
----

*Merging of visual duplicates*: the same component can be detected at several
distinct locations in the analyzed image/SBOM — for example a library present
both as a standalone jar and shaded (embedded) in another jar — with exactly
the same severity, the same CVE, the same package and the same version. Grype
and Trivy then rightly report two distinct results, but visually identical in
this table (no column shows the file path). These rows are therefore merged
into a single one, with a *×N* badge next to the CVE identifier — hover it to
see the real number of locations. This merging applies to the summary banner,
the severity counters and the exports (see below); only the *JSON* view
(<<sec-vue-json,JSON view>>) remains faithful to the full, unmerged output of
the tool.

*Search*: the search field filters in real time on the package name, the CVE
identifier, the version or the type.

*Sort*: click a column header (SEVERITY, PACKAGE, VERSION, CVE/ID) to sort in
ascending order, click again to reverse. The ↑↓ arrow indicates the active
column and sort direction. By default, results are sorted by decreasing
severity (Critical first).

*CSV export*: the ⬇ (download) button exports the current filtered list
(taking into account the search, the severity filters, and already merged —
see above) to a `.csv` file in RFC 4180 format. Columns: Severity, CVE/ID,
Package, Installed version, Fixed version, Type, Locations (number of merged
occurrences, `1` if the component is present in a single place only).

*AsciiDoc + PDF export*: the ⬥ button (next to the CSV export) exports the
filtered list into a polished report: *cover page* (title, date, analyzed
target, version), *executive summary* — a figures box “Critical / High /
CISA KEV / Total” and a one-sentence verdict (“Immediate action required” if
KEV CVEs are present, etc.) — severity distribution bar, *Tools* section
(versions detected through `<tool> --version` at export time, hence always
up to date), then the detailed table. The `.adoc` file is then converted to
PDF through `asciidoctor-pdf`; if the tool is missing, the `.adoc` is still
produced and a message says so. The output location is chosen through a
dialog box.

The PDF uses a sober layout: sans-serif font, slate-blue palette, dark table
headers, colored severity badges (labels in the report language: CRITICAL /
HIGH / MEDIUM / LOW), footer with report title and “Page X / Y” pagination.
The *dashboard* report (export button of its summary card) follows the same
style and adds a *“CVE details”* section.

*Severity filters*: click one or more badges to only display the
vulnerabilities of the matching level. The *Show all* button clears the active
filters. Only the badges matching severities present in the results are
displayed.

*Date filter*: a time-filtering bar sits above the table. It lets you display
only the CVEs published or modified in a given date range:

----
  📅 CVE date: [Published] [Modified] [Most recent]
     After: [2024-01-01 ×]   Before: [2024-12-31 ×]
     [✓] Undated    [Apply to other tabs]
----

* *Date field*: three-value selector — *Published* (initial publication date
  of the CVE), *Modified* (last update), *Most recent* (the later of the two
  available dates).
* *After / Before*: clickable chips opening a calendar. An × clears each bound
  independently.
* *Undated*: checkbox to include the CVEs whose selected date field is absent
  or not filled in in the scanner data. By default, these CVEs are excluded
  when a filter is active.
* *Apply to other tabs*: copies the current filter to the two other CVE tabs
  (OSV-Scanner and Trivy). The analyses themselves are not re-run; only the
  display is filtered.

NOTE: The date filter is applied as post-processing on the JSON returned by
Grype. It is independent of the Grype command-line options and can be combined
with the severity filters and the text search.

Columns:

* *Severity badge*: colored label (CRITICAL / HIGH / MEDIUM / LOW / NEGLIGIBLE)
* *Package*: name of the affected package in bold
* *Versions*: installed version, and fixed version if available (after `→`).
  The `(won't fix)` mention indicates that the maintainer does not plan a fix.
* *CVE*: vulnerability identifier
* *Type*: package type (`rpm`, `python`, `deb`…)

*Clicking a row expands it* and shows the <<sec-cve-detail,full CVE detail>>:
package and versions, severity and dates as reported by the scanner, detailed
exploitability (KEV, EPSS, CVSS, PoC) and reference buttons (NVD, CVE.org,
osv.dev, CISA KEV). The detail panel contains a *copy the identifier* button.
Clicking the row again collapses it.

==== Exploitability and active exploitation

[[sec-exploitabilite]]
After each scan, the application enriches the CVEs found with four
prioritization signals, displayed as chips under each row and as sortable
*KEV* / *EPSS* columns:

* *KEV* (red chip 🔥) — the CVE is in the *CISA Known Exploited
  Vulnerabilities* catalog: active exploitation confirmed in the wild. The
  hover tooltip gives the date added and any use by ransomware.
* *EPSS* — *Exploit Prediction Scoring System* score (FIRST.org), from 0 to 1:
  probability of exploitation within 30 days, with its percentile.
* *PoC* — a public exploit is recorded (GitHub repositories via
  `poc-in-github`, or the `E:` maturity of the CVSS vector).
* *expl.* — exploitability sub-score of the CVSS vector (AV/AC/PR/UI), from 0
  to 3.9, computed locally.

Grype already provides KEV, EPSS and the CVSS vector in its database: for the
Grype tab, only the PoC signal requires a network request. For OSV-Scanner and
Trivy, the KEV/EPSS enrichment is done online. Responses are cached for 24 h in
`~/.cache/sbom-generator/` (shared with the command line).

*CISA KEV filter*: a *CISA KEV (N)* chip appears next to the severity filters
as soon as an exploited CVE is present — click it to display only these CVEs.
The *KEV* sort puts the catalog CVEs first; the *EPSS* sort orders by
decreasing probability.

*Online / offline toggle*: the ☁ icon in the table toolbar enables or cuts the
network enrichment requests. The choice is remembered (like the theme) and
shared by the three scan tabs. Offline, only the data provided by Grype and
the local cache are used.

The CSV and AsciiDoc/PDF exports gain the *KEV*, *EPSS* and *PoC* columns when
the enrichment has produced results; the *dashboard* marks the KEV/high-EPSS
CVEs in its cross-scanner comparison and brings them to the top.

osv-scanner --format json --sbom /path/to/sbom.cdx.json

osv-scanner scan image --format json nginx:latest

normal, not an error); a code greater than 1 indicates an error.

== CRA Compliance tab — Cyber Resilience Act

The *CRA Compliance* tab produces a compliance report with *Regulation (EU)
2024/2847* (Cyber Resilience Act) from an SBOM. It drives the
`sbom-generator cra` subcommand (the binary configured in the settings) and
displays its result.

[IMPORTANT]
====
The report only covers the CRA requirements that can be *verified
automatically* from an SBOM and a known-vulnerability analysis:

* *SBOM format and completeness* — commonly used machine-readable format,
  dependency coverage (Annex I §2 point 1), data fields per component (BSI
  TR-03183-2: name, version, supplier, unique PURL/CPE identifier, hash,
  license), NTIA 2021 minimum elements;
* *vulnerability management* — inventory of known vulnerabilities and
  availability of fixes (Annex I §2 points 1-2);
* *actively exploited vulnerabilities* — any CVE in the CISA KEV catalog is
  flagged as triggering the obligation to notify ENISA *within 24 h*
  (art. 14).

The other CRA obligations (secure distribution of updates, effective
coordinated disclosure policy, secure-by-default design, regular testing,
regulatory notifications, EU declaration of conformity) are the manufacturer's
responsibility and are only listed. *This report is not a declaration of
conformity.*
====

=== Filling in the form

*SBOM file to assess*: pre-filled with the first generated SBOM
(`.cdx.json` / `.spdx.json`, otherwise `.json`). The *Choose* button opens a
file picker.

*Product metadata (optional)*: collapsible section — Manufacturer, Product,
Product version, End of support (`YYYY-MM-DD`), Vulnerability reporting
contact, URL of the coordinated disclosure policy. The *Load a cra.yaml*
button imports these values from a file (`key: value` per line). The fields
entered here take precedence over the file; missing values are deduced from
the `metadata.component` of the SBOM.

*Scan for known vulnerabilities*: checked by default. Runs a scanner (*Grype*
by default, or OSV-Scanner / Trivy / all three) to assess the vulnerability
inventory and the availability of fixes, with CISA KEV / EPSS enrichment.
Unchecked, the report is limited to the SBOM analysis and states that
vulnerability management could not be attested.

=== Running and exporting

*Assess*: runs the analysis and displays the result under the form:

* *verdict banner* — Compliant / Partial / Non-compliant on the verified
  scope, with the summary sentence;
* *four indicators* — compliant SBOM fields, NTIA elements, vulnerabilities
  without a fix, actively exploited CVEs (KEV);
* *blocking items* — list of the reasons for non-compliance, if any;
* *table of SBOM data fields* (BSI TR-03183-2) with coverage and status per
  field;
* reminder of the SBOM format, the number of components and dependency
  relationships, and the vulnerability count.

*Export the PDF report*: regenerates the complete report as a PDF (cover
page, executive summary, product identification, detailed SBOM analysis,
vulnerability management, manufacturer requirements, conclusion) and saves it
at the chosen location. The PDF conversion requires `asciidoctor-pdf`.

A *Non-compliant* report is not an error: it lists the points to fix. Blocking
reasons: non-machine-readable format, insufficiently filled mandatory field,
vulnerability without an available fix, CVE in the CISA KEV catalog.

[[sec-pourquoi-ecarts-scanners]]
=== Why Grype, OSV-Scanner and Trivy do not find the same CVEs

It is normal — and expected — that a good part of the rows of the
cross-scanner table are isolated (seen by a single tool). On the same Keycloak
image (RHEL 9.6, ~450 MB) analyzed directly by Grype and by Trivy, a raw
comparison of identifiers only shows 72 common CVEs out of ~210 unique
identifiers on each side — a gap with two quite distinct causes:

* *Different identifier naming (main cause, not a real detection gap)* — on
  Java packages (JAR/Maven), Grype names its findings with the *GitHub
  Security Advisory* identifier (`GHSA-xxxx-xxxx-xxxx`, its main source for
  this ecosystem) while Trivy prefers the matching *CVE* identifier. It is the
  same vulnerability under two different names — Grype moreover lists the
  related CVE in its `relatedVulnerabilities` field. On this same image, the
  two tools seemed to agree on only 2 Java CVEs out of ~135 on each side; once
  Grype's `GHSA-*` are resolved to their related CVE, the agreement rises to
  132/135 (~98 %). On RPM packages (OS base), where both tools natively use
  the CVE identifier, the agreement was already direct at ~94 % (70 common
  CVEs out of ~75 on each side).
* *Another different naming, this one normalized automatically* — on Debian
  packages, OSV-Scanner names some of its advisories `DEBIAN-CVE-xxxx-xxxxx`
  (Debian Security Tracker origin) where Grype and Trivy report the matching
  bare CVE identifier. Unlike the GHSA↔CVE case above, the Dashboard's
  comparison table resolves this prefix automatically (see
  <<sec-dashboard-export>>) — on a real Debian image, this reduced the number
  of rows of the cross-scanner comparison from 200 to 106 (nearly half were
  only this naming duplicate).
* *Residual real gaps (freshness and coverage of the databases)* — Grype
  (Anchore database) and Trivy (`trivy-db`) republish their vulnerability
  databases at paces and from sources that are not perfectly identical (NVD,
  GHSA, Red Hat OVAL/CSAF…). A just-published CVE, or one not yet mapped to
  the exact CPE of a package, may appear in one before the other. The version
  matching rules (affected bounds, RPM epoch) and the retained severity score
  (NVD CVSS vs vendor vs distro) may also differ slightly from one engine to
  another.
* *Grype and Trivy do not have the same exhaustiveness on Debian OS
  packages* — on a real Debian image (79 packages), Grype reported 207 matches
  versus only 27 for Trivy, on the same SBOM. This is nevertheless not a
  problem of CPE false positives: both tools do use their dedicated distro
  matcher (`dpkg-matcher` on the Grype side). The gap comes from the
  completeness of the data taken in — Grype reports the whole Debian Security
  Tracker, including the advisories marked `<no-dsa>` (minor bug that Debian
  chose never to fix) and the CVEs with no known fixed version, where Trivy
  only reports a more restricted subset. Checked on
  `security-tracker.debian.org`: a CVE cited only by Grype (`CVE-2026-19499`
  on `glibc`/trixie) is indeed listed there as “vulnerable” with the note
  `<no-dsa> (Minor issue)` — Grype therefore rightly reports it (“won't fix”
  state), Trivy simply omits it. Neither is wrong: Trivy is more conservative
  (CVEs with a settled status), Grype more exhaustive but noisier.

Neither scanner is “the” truth: each has its own database and its own matching
granularity. That is precisely the purpose of this tab — seeing the union of
the three scanners rather than relying on a single one to maximize detection
coverage.

A gap may also appear with a *single* scanner depending on whether it is given
an SBOM or the image directly — typically in the Trivy tab (see
<<sec-onglet-trivy-source>>) between the *SBOM file* (`trivy sbom`) and
*Container image* (`trivy image`) modes. On this same Keycloak image,
`trivy sbom` on an SBOM generated with the `syft` backend found 3 HIGH CVEs
(`micrometer-core`, `postgresql`) absent from a direct `trivy image`: the jar
analyzer built into Trivy identifies a jar through `pom.properties`, then
`MANIFEST.MF`, then a SHA-1 lookup in its `trivy-java-db` database (indexed
from Maven Central) — and silently drops the package if all three fail, which
happens for internally rebuilt jars (e.g. `.redhat-000xx`) without
`pom.properties` and absent from Maven Central. The syft cataloger, for its
part, can recover these packages by parsing the file name
`<groupId>.<artifactId>-<version>.jar` (convention of the Quarkus “fast-jar”
packaging of this image). Here again, the SBOM does not invent CVEs: it is
`trivy image` that misses a few that `trivy sbom` finds thanks to syft's more
complete detection.

The same kind of gap existed for OSV-Scanner, but far more drastically: on
distribution packages, giving it a syft SBOM brought the result down to almost
*zero* CVEs, whereas scanning the image directly finds hundreds. Two causes,
both fixed at the source by `sbom_generator` (syft backend):

* *`distro` qualifier* — OSV-Scanner only links a `pkg:deb/debian/...` to the
  `Debian:13` ecosystem if `distro` is `debian-<major>` or if `distro_name`
  carries a known codename. syft fills in the *point release*
  (`distro=debian-13.6`, read from `/etc/debian_version`), which is not
  recognized. Fixed: `debian-13.6` → `debian-13` + `distro_name=trixie`.
* *Binary vs source package* — OSV.dev indexes Debian advisories by *source*
  package (`zlib`, `perl`), not binary (`zlib1g`, `perl-base`). syft only
  lists the binary (with `upstream=`), which OSV-Scanner does not use. Fixed:
  one component per distinct source package is added (like cdxgen), and
  `upstream=` is removed from the binary so that Grype does not count the CVE
  twice.

On `haproxy:3.4.4` (Debian 13.6), the syft SBOM thus goes from ~0 to 58
OSV-Scanner CVEs (parity with the cdxgen SBOM), cross-checked by the three
scanners instead of Grype alone.

Two limits remain:

* the other families of distribution packages (Alpine, RPM/RHEL) — OSV.dev
  indexes them poorly or not at all in “SBOM scan” mode;
* `osv-scanner scan image`, which does its own extraction without PURLs,
  remains more exhaustive on the base OS. For maximum OS coverage with this
  tool, scan the image directly.

=== AsciiDoc + PDF export

The ⬥ button (PDF icon, in the global synthesis card) exports a report
reproducing the whole displayed view:

* the global summary (scanners run, unique CVEs);
* the *Tools* section: version of sbom_generator_gui and version of each
  scanner run (detected through `<tool> --version` at export time, hence
  always up to date even if the tool was updated since the last scan —
  “unavailable” if the tool is no longer in the `PATH`);
* for each scanner: its severity distribution with a colored bar (or “Not
  run” / “No vulnerability detected” as appropriate);
* the complete cross-scanner comparison table (severity, CVE/ID, presence per
  tool, and KEV / EPSS columns if the enrichment ran), in the *same order as
  displayed on screen*, with the distro-prefixed CVEs already normalized (see
  <<sec-pourquoi-ecarts-scanners>>);
* a *“CVE details”* section: one block per CVE retained by the report's
  severity threshold (all with “All”; CISA KEV catalog CVEs are always
  included) — with package, versions, severity and dates per scanner, and all
  the exploitability information (KEV, EPSS, CVSS, PoC, links). It reproduces
  the content of the expandable detail panel on screen.

Unlike the Grype/OSV-Scanner/Trivy tabs, there is only one synthesis view
here — no individually filtered rows to export, but the active sort column of
the cross-scanner table is respected.

*Report severity level*: the menu to the left of the export button
(*Critical*, *≥ High*, *≥ Medium*, *All* — *All* by default) limits the whole
report to the CVEs of that level or above: executive summary, distribution per
scanner, image layers, cross-scanner comparison and detail. The choice is
remembered from one session to another; the on-screen display is not
filtered.

* A CVE is retained according to its *worst* severity, all scanners combined:
  a CVE that is High for Grype and Medium for Trivy appears in a “≥ High”
  report with both scanners, so that the comparison stays fair.
* The *CISA KEV* catalog CVEs (actively exploited) are always included,
  whatever their severity.
* The filtered report states it at the top (chosen level, number of retained
  CVEs out of the total) and the proposed file name carries the level
  (`vulnerability-report-high.adoc`).

The button stays disabled as long as no scanner has been run. Once the `.adoc`
file is written (location chosen through a dialog box), the conversion to PDF
through `asciidoctor-pdf` is attempted automatically; if the tool is not
installed, the `.adoc` file is still produced and a message says so — same
behavior as the export of the scan tabs (see <<sec-vue-table>>). The PDF
reuses the Dashboard colors (severity badges, distribution bar, blue headers)
— see <<sec-vue-table>> for the theme detail.

NOTE: The Dashboard is updated automatically every time an analysis is run in
a scanner tab. No additional action is required.

The *SBOM Merge* tab combines several SBOM files into a single document,

=== Selecting the files to merge

Two ways to fill the list:

* *➕ Add files…*: opens a two-entry menu — *.json / .jsonld* (filters the
  picker on these extensions) or *All files* (no filter, for SBOMs whose
  extension is not `.json`, e.g. `.cdx`, `.spdx`, `bom`, or with no
  extension). Multiple selection is possible in both cases. The content must

* *📂 Generated files*: menu listing the SBOM files produced during the

  Constraints below).

Each file in the list can be removed individually through the *✕* button. The

* *Output file*: path of the produced merged document (default value:

* *Document name* (optional): if filled in, replaces the document name in the

The *🔀 Merge* button launches `sbom-generator merge` with the selected files.
The command output (log) is displayed under the fields, followed by a result
banner:

* *✔ Merge succeeded → <file>* (green) on success.
* *✘ Merge failed (code N)* (red) on failure — check the displayed log for the

All the selected files must be in the same format (that of the first file in
the list): CycloneDX or SPDX 2.3. The output format follows that of the first
file. The SPDX 3.0 (JSON-LD) format is not supported as merge input.

== `scan` subcommand — CVE analysis from the command line

The `scan` subcommand runs the same CVE analyses as the GUI directly from the
terminal, with built-in date filtering. It does not require a graphical
interface.

[source,bash]
----
sbom-generator scan --sbom <file.cdx.json> [options]
----

=== Options

[cols="2,1,3", options="header"]
|===
|Option |Default |Description

|`--sbom <path>` (or `-s`)
|_required_
|SBOM file to analyze (CycloneDX, SPDX…)

|`--scanner <name>` (or `-S`)
|`grype`
|Scanner to use: `grype`, `osv`, `trivy`, or `all` (the three)

|`--cve-after <YYYY-MM-DD>`
|_none_
|Only show the CVEs whose date is after this value (inclusive)

|`--cve-before <YYYY-MM-DD>`
|_none_
|Only show the CVEs whose date is before this value (inclusive, end of day)

|`--cve-date-field <field>`
|`published`
|Date field used: `published`, `modified`, or `latest` (the more recent of
the two)

|`--include-undated`
|_disabled_
|Include the CVEs whose date field is absent from the scanner data

|`--help` (or `-h`)
|—
|Display the help of the subcommand
|===

=== Exit codes

* *0* — no CVE in the requested range (or no CVE found at all)
* *1* — at least one CVE found in the range, or a scanner error

=== Examples

[source,bash]
----
# All Grype CVEs since January 1st, 2024
sbom-generator scan --sbom sbom.cdx.json --cve-after 2024-01-01

# OSV-Scanner CVEs between two dates
sbom-generator scan --sbom sbom.cdx.json --scanner osv \
  --cve-after 2023-06-01 --cve-before 2024-01-01

# All scanners, modification date, undated CVEs included
sbom-generator scan --sbom sbom.cdx.json --scanner all \
  --cve-date-field modified --cve-after 2023-01-01 --include-undated

# Use in a CI script (returns 1 if recent CVEs are detected)
sbom-generator scan --sbom sbom.cdx.json \
  --cve-after "$(date -d '90 days ago' +%F)" && echo "OK" || echo "Recent CVEs!"
----

=== Output format

For each scanner, the command prints a text table sorted by decreasing
severity:

----
── Grype ──────────────────────────────────────────
  3 CVE(s) found  Filter: field=published  after=2024-01-01

SEVERITY      CVE / ID              PACKAGE
------------  --------------------  ------------------------------------
Critical      CVE-2024-1234         openssl@1.1.1k
High          CVE-2024-5678         bash@5.0.17
Medium        CVE-2024-9012         zlib@1.2.11
----

== Troubleshooting

=== `sbom-generator` not found

*Symptom*: the generation fails immediately with an error such as
`sbom-generator: command not found`.

*Solution*: check that the `sbom-generator` binary is reachable in the PATH:

[source,bash]
----
which sbom-generator
sbom-generator --version
----

If the binary is installed in a non-standard location, put it in a folder of
the PATH or create a symbolic link:

[source,bash]
----
ln -s /path/to/sbom-generator /usr/local/bin/sbom-generator
----

=== `syft` / `skopeo` / `cdxgen` not found

*Symptom*: the generation fails with the message
`syft not found or not working — required for --image.`

*Solution*: install the missing tool and check that it is in the PATH:

[source,bash]
----
# Syft
curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh \
  | sh -s -- -b /usr/local/bin
syft version

# Skopeo (Fedora/RHEL)
sudo dnf install skopeo
skopeo --version

# cdxgen (npm, requires Node.js)
npm install -g @cyclonedx/cdxgen
cdxgen --version
----

=== OCI analysis failure

*Symptom*: `OCI analysis failed: …` in the log.

*Possible causes and solutions:*

* *Unreachable registry image*: check the network connection and the
  authentication (`docker login` or `skopeo login`).
* *Corrupted tar archive or unrecognized format*: regenerate the archive
  with `docker save <image> -o /path/image.tar` (or compressed:
  `docker save <image> | gzip > /path/image.tar.gz`).
  The `.tar`, `.tar.gz` and `.tgz` formats are supported.
* *Invalid OCI layout directory*: check that `index.json` is present at the
  root of the directory.

=== `grype` not found

*Symptom*: the Grype analysis fails with the message
`grype not found. Install it: https://github.com/anchore/grype`.

*Solution*: install grype (see <<_installing_grype>>) and check that it is in
the PATH:

[source,bash]
----
which grype
grype version
----

=== `osv-scanner` not found

*Symptom*: the OSV-Scanner analysis fails with a message such as
`osv-scanner: command not found` or the SBOM file is not found.

*Solution*: check that `osv-scanner` is in the PATH of your graphical session
(not only in the terminal):

[source,bash]
----
which osv-scanner
osv-scanner --version
----

If `osv-scanner` is installed via `go install` in `~/go/bin`, this folder is
often not in the graphical PATH. Add it in `~/.profile`:

[source,bash]
----
export PATH="$HOME/go/bin:$PATH"
----

Then log in again or restart the GUI.

=== `trivy` not found

*Symptom*: the Trivy analysis fails with a message such as
`trivy: command not found`.

*Solution*: check that `trivy` is in the PATH:

[source,bash]
----
which trivy
trivy --version
----

Install it if needed (see <<_installing_trivy_optional>>).

=== The Trivy database is outdated

*Symptom*: Trivy displays a warning about the age of its database.

*Solution*: leave *--skip-db-update* unchecked (default behavior) so that
Trivy updates its database automatically at launch. In an offline
environment, update manually:

[source,bash]
----
trivy image --download-db-only
----

=== No vulnerability detected despite a loaded SBOM

*Possible causes:*

* The selected SBOM file is not a format recognized by grype.
  Grype natively supports CycloneDX JSON (`.cdx.json`) and SPDX JSON
  (`.spdx.json`). The SPDX 3.0 JSON-LD format may require a recent version of
  grype.

* The grype vulnerability database is outdated.
  Grype updates it automatically on first launch,
  but may need a manual update:
+
[source,bash]
----
grype db update
----

* The RHEL version selected in *Distro* does not match the packages of the
  SBOM. Try *(none)* to let grype detect it automatically.

=== License warnings

*Symptom*: `Warning: unknown license for 'package'` lines appear in the
progress.

*Explanation*: `sbom-generator` could not determine the SPDX license of the
package. The SBOM is still generated, with the value `NOASSERTION` for the
license concerned.

*Solution*: use a *license override* file (`--license-map`) to manually
define the license of unrecognized packages.

=== The sbomqs score does not appear

*Possible causes:*

* `sbomqs` is not installed or is not in the PATH.
  Check with `which sbomqs`. If missing, install it
  (see <<_installing_sbomqs_optional>>).

* The *sbomqs quality score* option is not checked in the *Options* section.

* No JSON SBOM file was generated in the current session.
  sbomqs only runs on the `.cdx.json`, `.spdx.json` or `.jsonld` formats.
  Make sure at least one of these formats is selected.

=== The PDF conversion fails

*Symptom*: the message `asciidoctor-pdf not found` appears in the logs
(SBOM generation) or in the confirmation message (AsciiDoc + PDF export of a
Grype/OSV-Scanner/Trivy tab — the `.adoc` file is still produced).

*Solution*: install `asciidoctor-pdf` (see
<<_installing_asciidoctor_pdf_optional>>).

If `asciidoctor-pdf` is installed but not found, make sure the Ruby gems
folder is in the PATH:

[source,bash]
----
gem environment gemdir
# Example: /home/user/.local/share/gem/ruby/3.2.0
export PATH="$HOME/.local/share/gem/ruby/3.2.0/bin:$PATH"
----
