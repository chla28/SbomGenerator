== Introduction

=== Qu'est-ce qu'un SBOM ?

Un *SBOM* (Software Bill of Materials — inventaire logiciel) est un fichier
structuré listant tous les composants d'un logiciel : paquets, bibliothèques,
versions, licences. Il joue le rôle d'une nomenclature, au sens industriel
du terme.

Les formats les plus répandus sont :

* *CycloneDX* (JSON, recommandé par l'OWASP et l'ANSSI)
* *SPDX* (standard ISO/IEC 5962:2021, adopté par la Linux Foundation)

=== Qu'est-ce que Grype ?

*Grype* (Anchore) est un scanner de vulnérabilités CVE open-source.
Il analyse un fichier SBOM et le compare à des bases de données de
vulnérabilités (NVD, GitHub Security Advisories…) pour identifier les
paquets affectés et leur niveau de sévérité.

Niveaux de sévérité (du plus critique au plus bénin) :

[cols="1,1,3", options="header"]
|===
|Niveau |Couleur dans l'UI |Signification

|Critical
|Rouge foncé
|Exploitation immédiate, impact maximal (RCE, élévation de privilèges…)

|High
|Rouge-orange
|Impact important, exploitation probable

|Medium
|Orange
|Exploitable sous conditions particulières

|Low
|Vert
|Impact limité, exploitation difficile

|Negligible
|Gris
|Impact théorique, généralement non exploitable en pratique (Grype uniquement)
|===

NOTE: Les bases de données utilisées par OSV-Scanner emploient parfois le
libellé `MODERATE` (GitHub Advisory, npm) à la place de `MEDIUM`. L'application
les unifie automatiquement : toute sévérité `MODERATE` est affichée comme
`Medium` dans le tableau et les filtres.

=== Présentation de l'outil

*SBOM Generator GUI* est une interface graphique de bureau Linux qui orchestre
des outils en ligne de commande :

* `sbom-generator` : génère des fichiers SBOM depuis une liste de paquets ou une image OCI
* `grype` : analyse les SBOM générés pour détecter les vulnérabilités CVE (Anchore)
* `osv-scanner` : analyse les SBOM pour détecter les vulnérabilités CVE (Google)
* `trivy` : analyse les SBOM pour détecter les vulnérabilités CVE (Aqua Security)
* `sbomqs` : calcule un score de qualité SBOM (optionnel)
* `asciidoctor-pdf` : convertit le rapport AsciiDoc en PDF (optionnel)

L'interface permet de configurer les options, suivre l'exécution en temps réel,
accéder aux fichiers produits, les prévisualiser, et lancer une analyse de
vulnérabilités sans jamais ouvrir un terminal.

Pour chaque lancement, la *ligne de commande équivalente* est affichée dans
l'interface — sous le bouton *▶ Générer le SBOM* et comme première entrée du
journal de progression.

Les paramètres sont *automatiquement sauvegardés* entre les sessions.

[source,bash]

==== Installer osv-scanner (optionnel)

[source,bash]
----
# Script officiel Google
curl -sSfL \
  https://raw.githubusercontent.com/google/osv-scanner/main/scripts/install.sh \
  | sh -s -- -b /usr/local/bin

# Ou via Go (si Go est installé)

----

de votre session graphique (`~/.profile` ou `~/.bash_profile`).

*Panneau gauche — Configuration* : réglage de toutes les options avant

automatiquement à chaque démarrage. La commande CLI équivalente s'affiche

mode clair. Le bouton *🎨* ouvre le sélecteur de couleur de thème.

== Panneau Configuration

=== Section Entrée

==== Fichier d'entrée (`--input`)

Chemin vers le fichier contenant la liste des paquets à analyser.
Le bouton 📂 à droite du champ propose un menu :

[cols="2,3"]
|===
|*Type filtré (.lst, .txt…)* |N'affiche que les fichiers aux extensions courantes
|*Tous les fichiers* |Affiche tous les fichiers du répertoire
|===

TIP: Vous pouvez également *glisser-déposer* un fichier depuis votre gestionnaire
de fichiers (Nautilus, Thunar…) directement sur ce champ. Un liseré bleu indique
que le dépôt est accepté.

Le fichier doit contenir *un élément par ligne*. Les types acceptés sont :

[cols="2,3", options="header"]
|===
|Type |Format de la ligne

|Paquet RPM installé
|`bash` ou `bash-5.1.8-6.el9.x86_64`

|Fichier RPM local
|`/chemin/vers/package.rpm`

|Wheel Python (`.whl`)
|`/chemin/vers/package-1.0-py3-none-any.whl`

|Archive tar
|`/chemin/vers/pkg.tar.gz` ou `.tgz`

|Archive Zip
|`/chemin/vers/archive.zip`

|Paquet Debian (`.deb`)
|`/chemin/vers/package.deb`

|Dépendances Python
|`/chemin/vers/requirements.txt`
|===

Un seul fichier d'entrée peut contenir des lignes de types différents.

NOTE: Le champ *Fichier d'entrée* devient optionnel si une *Image OCI* est
spécifiée dans la section suivante — les deux sources peuvent être combinées.

=== Section Image OCI

==== Image OCI (`--image`)

Référence à une image OCI à analyser. Trois formats sont acceptés :

[cols="2,3,2", options="header"]
|===
|Format |Description |Exemple

|Registre
|Image Docker Hub ou registre privé
|`nginx:latest`

|Archive tar
|Export `docker save` ou `skopeo copy docker-archive:`
|`/path/ubuntu.tar`

|OCI layout
|Répertoire contenant `index.json`
|`/path/oci_dir/`
|===

Le bouton 📂 à droite du champ permet de sélectionner un *répertoire OCI layout*.
Pour les images de registre ou les archives tar, saisissez la référence manuellement.

Si le champ est vide, l'analyse OCI est désactivée.

==== Outil OCI (`--oci-tool`)

Visible uniquement lorsque le champ *Image OCI* est rempli. Sélectionnez le
backend d'analyse :

[cols="1,2,2", options="header"]
|===
|Outil |Description |Prérequis

|Syft (défaut)
|Anchore Syft — tous types de paquets (deb, rpm, apk, pypi, npm, go, java…)
|`syft` dans le PATH

|Trivy
|Aqua Trivy — tous types de paquets
|`trivy` dans le PATH

|Skopeo
|Extraction manuelle des layers — dpkg, RPM et APK uniquement
|`skopeo` et `tar` dans le PATH
|===

=== Section Sortie

==== Chemin de base (`--output`)

Préfixe des fichiers générés, sans extension.
Exemple : `sbom` produira `sbom.cdx.json`, `sbom.spdx.json`, etc.
Un chemin relatif est résolu depuis le répertoire courant au moment du lancement.

Une prévisualisation des noms de fichiers attendus s'affiche dès que
le champ est renseigné.

==== Formats (`--format`)

Cochez un ou plusieurs formats. Au moins un format doit être sélectionné.

[cols="2,2,3", options="header"]
|===
|Format |Extension produite |Usage typique

|CycloneDX 1.6
|`.cdx.json`
|Analyse de vulnérabilités avec grype, outils OWASP

|SPDX 2.3
|`.spdx.json`
|Conformité légale, outils OpenChain

|SPDX 3.0 JSON-LD
|`.spdx3.jsonld`
|Écosystèmes liés (RDF/ontologie)

|JSON personnalisé
|`.custom.json`
|Intégration dans des pipelines internes

|Markdown
|`.md`
|Documentation lisible directement sur GitHub/GitLab

|AsciiDoc
|`.adoc`
|Rapport technique riche (tableaux, styles)
|===

==== Option PDF (AsciiDoc uniquement)

Quand le format *AsciiDoc* est coché, une option supplémentaire apparaît :
*Convertir en PDF (asciidoctor-pdf)*. Si elle est activée, l'outil
`asciidoctor-pdf` est lancé automatiquement après la génération du `.adoc`.

Un champ optionnel permet de spécifier le chemin de destination du PDF.
Sans valeur, le PDF est créé dans le même dossier que le `.adoc`, avec
le même nom de base.

=== Section Options

==== Nom du document SBOM (`--name`)

Libellé qui apparaîtra dans les métadonnées du SBOM
(champ `metadata.component.name` en CycloneDX).
Exemple : `Mon Application 2.1.0`.
Laissez vide pour utiliser le nom du fichier d'entrée.

==== Répertoire RPM local (`--rpm-dir`)

Dossier contenant des fichiers `.rpm` supplémentaires à inclure dans l'analyse.
Utile pour enrichir la résolution de métadonnées (version exacte, licence)
lorsque les paquets ne sont pas installés sur la machine courante.

==== Override de licences (`--license-map`)

Fichier texte permettant de corriger ou préciser les licences de certains paquets.
Le bouton à droite propose les mêmes options que le champ fichier d'entrée :
type filtré (`.txt`, `.yaml`) ou tous les fichiers.
Format : une règle par ligne : `nom-paquet: SPDX-expression`

Exemple :
----
openssl: OpenSSL
my-internal-lib: LicenseRef-PROPRIETARY
----

==== Concurrence (`--concurrency`)

Nombre de paquets traités en parallèle. Le curseur va de *0* (illimité)
à *16*. La valeur par défaut est *4*.

* Augmentez si votre machine a de nombreux cœurs et une bonne connexion réseau.
* Diminuez (1 = séquentiel) en cas d'erreurs de rate-limiting sur les dépôts.
* La valeur 0 traite tous les paquets simultanément — à utiliser avec prudence
  sur de grandes listes.

==== Mode verbeux (`--verbose`)

Affiche dans l'onglet *Progression* des informations supplémentaires :
outils de résolution utilisés, statistiques de traitement, détails de chaque
paquet trouvé.

==== Score qualité sbomqs

Quand cette option est cochée, `sbomqs score` est exécuté automatiquement
sur le premier fichier SBOM JSON généré (`*.cdx.json` ou `*.spdx.json`).
Le résultat s'affiche dans l'onglet *Résultats* sous la liste des fichiers.

Si `sbomqs` n'est pas installé, l'option est ignorée silencieusement.

NOTE: Voir <<_installer_sbomqs_optionnel>> pour l'installation.

=== Persistance des paramètres

Tous les paramètres de la section *Options* — formats sélectionnés, chemin
de base, répertoire RPM, fichier de licences, niveau de concurrence, mode verbeux,
génération PDF, score sbomqs — sont *automatiquement sauvegardés* après chaque
génération et *restaurés* au prochain démarrage de l'application.

Les paramètres sauvegardés *ne comprennent pas* le fichier d'entrée (trop lié
à un contexte particulier) ni le chemin du PDF.

=== Profils de configuration

Un *profil* regroupe tous les paramètres de configuration sous un nom
personnalisé, et peut être rappelé en un clic pour basculer rapidement
entre plusieurs configurations types (ex. : « RHEL 9 production », « Audit
Python », « CI/CD minimal »).

==== Accéder aux profils

Cliquez sur l'icône 🔖 (signets) en haut à droite de l'en-tête du panneau
Configuration.

----
  ┌─ Configuration ────────────────── [🔖] ─┐
  │  ...                                     │
----

==== Fenêtre de gestion des profils

----
  ┌─ Profils de configuration ──────────────────────────────────┐
  │                                                              │
  │  Nom du profil : [ RHEL 9 production      ] [Enregistrer]  │
  │                                                              │
  │  ─────────────────────────────────────────────────────────  │
  │  RHEL 9 production               [Charger] [Supprimer]      │
  │  Audit Python                    [Charger] [Supprimer]      │
  │  CI/CD minimal                   [Charger] [Supprimer]      │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
----

[cols="2,3"]
|===
|*Enregistrer* |Sauvegarde l'état actuel de tous les champs sous le nom saisi
|*Charger* |Applique les valeurs du profil (sauf le fichier d'entrée)
|*Supprimer* |Demande confirmation, puis supprime le profil
|===

NOTE: Le *fichier d'entrée* n'est pas inclus dans les profils — il est
généralement propre à chaque contexte d'utilisation.

TIP: Si un profil du même nom existe déjà, *Enregistrer* le met à jour.

=== Prévisualisation de la commande

Sous le bouton *▶ Générer le SBOM* s'affiche en permanence la ligne de commande
shell équivalente à la configuration actuelle :

----
  $ sbom-generator --input /home/user/paquets.lst \
    --output /home/user/sbom --format cyclonedx spdx
----

Cette prévisualisation se met à jour à chaque modification d'un champ.
Un bouton 📋 permet de copier la commande dans le presse-papiers pour
la rejouer depuis un terminal ou l'intégrer dans un script CI/CD.

=== Lancer et arrêter la génération

Cliquez sur *▶ Générer le SBOM* pour démarrer.
Le bouton se transforme en *■ Arrêter la génération* pendant l'exécution.
Cliquer sur Arrêter envoie un signal d'interruption au processus.

=== Codes couleur du terminal

[cols="2,3", options="header"]
|===
|Couleur |Signification

|Cyan
|Commande shell lancée (première ligne, préfixée par `$`)

|Blanc (défaut)
|Information générale

|Bleu
|Début d'une étape (`Generating`, `Resolving`, `Found`, `Analysés`)

|Orange
|Avertissement (`Warning:`, `⚠`)

|Rouge
|Erreur fatale (`Error:`)

|Vert
|Fichier produit (`SBOM written`, `PDF written`)

|Bleu clair
|Conversion PDF en cours
|===

Le texte du terminal est sélectionnable pour copier-coller des messages d'erreur.

=== Barre de progression

La barre de progression indique le nombre de paquets traités, le pourcentage
et le nom du paquet en cours. Elle apparaît uniquement pendant la génération.

Une fois la génération terminée, l'onglet *Résultats* s'active automatiquement
en cas de succès.

=== Export des logs

Une fois la génération terminée, deux boutons apparaissent en haut du terminal :

[cols="1,3"]
|===
|Copier |Copie l'intégralité des logs dans le presse-papiers
|Enregistrer |Ouvre un dialogue de sauvegarde pour écrire les logs dans un fichier `.log`
|===

=== Résumé post-génération

À la fin d'une génération réussie, une carte de résumé s'affiche en bas de
l'onglet :

* nombre de paquets analysés
* nombre de fichiers SBOM générés
* nombre d'avertissements (en orange si > 0)

Le contour de la carte est vert en cas de succès sans avertissement,
orange sinon.

  │    /home/user/projet/sbom.cdx.json     [📋] [↗]    │
  │    42.3 KB                                          │
  ├─────────────────────────────────────────────────────┤
  │ 📄 sbom.spdx.json                                   │
  │    /home/user/projet/sbom.spdx.json    [📋] [↗]    │

=== Bannière de résultat

* *Fond vert* : génération réussie. Le nombre de fichiers et d'avertissements
  est affiché.
* *Fond rouge* : la génération a échoué. Le message d'erreur est affiché
  directement dans la bannière.

=== Fichiers générés

Chaque fichier est présenté dans une carte avec :

* son nom (en gras, police monospace)
* son chemin complet
* sa taille

Deux boutons sont disponibles à droite de chaque carte :

[cols="1,3"]
|===
|📋 |Copie le chemin complet dans le presse-papiers
|↗ |Ouvre le fichier avec l'application système par défaut (visionneuse JSON, éditeur…)
|===

=== Score sbomqs

Si l'option *Score qualité sbomqs* est cochée et que `sbomqs` est installé,
un bloc indigo s'affiche après la liste des fichiers avec la sortie complète
de `sbomqs score` :

----
  ── Score sbomqs ──────────────────────────────────
  sbomqs score sbom.cdx.json
  Document Name  Format  Spec   Score   Avg
  sbom.cdx.json  cdx     1.6    8.3/10  8.3
----

Le texte est sélectionnable pour copier-coller le score.

=== Avertissements

Les avertissements sont affichés dans un bloc orange replié. Si leur nombre
dépasse 5, un bouton *Voir N de plus…* permet de les afficher tous.
Ces avertissements sont non bloquants : les fichiers SBOM ont bien été générés.

=== Erreur fatale

En cas d'échec (code de retour non nul), le message d'erreur apparaît dans
un bloc rouge sélectionnable pour faciliter le copier-coller.

== Onglet Aperçu — Prévisualisation SBOM

L'onglet *Aperçu (N)* affiche le contenu brut des fichiers SBOM générés
directement dans l'interface, sans avoir à ouvrir un éditeur externe.

----
  ┌─ Fichier : [ sbom.cdx.json ▼ ]                     [📋] ─┐

  │  MEDIUM    zlib 1.2.11              CVE-2022-37434  rpm         │

=== Indicateur de version

En haut du panneau de configuration, l'application affiche la version de
`grype` installée ainsi que l'état de mise à jour, vérifiés en arrière-plan
au démarrage :

* *✔ v0.87.0* (vert) — `grype` est installé et à jour.
* *↑ v0.87.0 → v0.88.1* (orange, cliquable) — une nouvelle version est
  disponible sur GitHub. Cliquez pour ouvrir la page de release dans
  le navigateur.
* *non installé* (rouge) — `grype` n'est pas trouvé dans le PATH.

NOTE: La vérification interroge l'API GitHub. En l'absence de connexion
réseau, seule la version installée est affichée, sans comparaison.

=== Sélection du fichier SBOM

Le champ *Fichier SBOM* est pré-rempli automatiquement avec le dernier fichier
SBOM généré dans la session courante, en priorisant les formats reconnus par
grype : `.cdx.json` (CycloneDX) puis `.spdx.json` (SPDX).

Vous pouvez saisir manuellement un chemin ou cliquer sur *Choisir* pour
parcourir le système de fichiers. Les formats `.json` et `.jsonld` sont
proposés dans le sélecteur.

NOTE: Grype analyse le contenu du fichier, pas son extension.
Un fichier CycloneDX renommé `.json` est reconnu correctement.

=== Options de scan

==== `--platform linux`

Force grype à considérer la plateforme cible comme Linux lors de la
résolution des vulnérabilités. Recommandé pour les SBOM issus de listes
de paquets RPM ou DEB.

Décochez cette option si vous analysez un SBOM issu d'un autre système
(image Docker multi-plateforme, bibliothèques macOS…).

==== `--add-cpes-if-none`

Grype utilise les identifiants *CPE* (Common Platform Enumeration) pour
faire correspondre les paquets aux entrées CVE. Si un paquet du SBOM ne
possède pas de CPE déclaré, cette option demande à grype d'en générer un
automatiquement depuis le nom et la version du paquet.

Recommandé : réduit les faux-négatifs sur des SBOM produits sans CPE
(c'est le cas de la plupart des SBOM générés par `sbom-generator`).

==== `--by-cve`

Sans cette option, grype groupe les résultats par identifiant *GHSA*
(GitHub Security Advisory) quand il est disponible.
Avec cette option, chaque résultat est présenté sous son identifiant
*CVE* principal, plus universel et reconnu par les outils de gestion
des vulnérabilités.

Recommandé pour l'interopérabilité avec des outils de ticketing (Jira,
défauts, etc.) ou des référentiels de vulnérabilités internes.

==== `--distro rhel:<version>`

Précise la distribution Linux cible. Sans cette option, grype tente
de la déduire du SBOM, ce qui peut échouer ou produire des correspondances
imprécises.

Versions RHEL disponibles dans le menu : *7*, *8*, *9*, *10*. Sélectionnez
*(aucune)* pour laisser grype détecter automatiquement la distribution.

NOTE: Choisir la mauvaise version peut engendrer des faux-positifs
(vulnérabilités non applicables car déjà corrigées par le backport RHEL)
ou des faux-négatifs. Vérifiez la version exacte de votre système avec
`cat /etc/redhat-release`.

==== `--fail-on <sévérité>`

Contrôle le code de retour de grype. Avec cette option, grype retourne
un code d'erreur (non nul) si au moins une vulnérabilité du niveau
indiqué ou supérieur est détectée. Utile en CI/CD.

Exemple : `--fail-on high` fait échouer l'analyse si une vulnérabilité
*High* ou *Critical* est trouvée.

La bannière de résultat dans l'UI reflète ce code de retour : fond rouge
si grype a retourné une erreur, fond vert sinon.

==== `--only-fixed`

N'affiche que les vulnérabilités pour lesquelles une version corrigée
est disponible. Permet de se concentrer sur les actions immédiatement
réalisables.

=== Template de sortie (`-t`)

Le champ *Template (-t)* permet de générer une sortie personnalisée
(CSV, HTML, texte) via un fichier template Go.

Le champ est pré-rempli avec `./grype_csv.tmpl`. Si ce fichier n'existe
pas au moment du lancement, la sortie template est ignorée sans erreur.

Exemple de template Go pour un CSV :

----
"CVE","Paquet","Version installée","Version corrigée","Sévérité"
{{- range .Matches}}
"{{.Vulnerability.ID}}","{{.Artifact.Name}}","{{.Artifact.Version}}","{{fixedIn .Vulnerability}}","{{.Vulnerability.Severity}}"
{{- end}}
----

La sortie produite est affichée dans l'onglet *Template* (voir <<sec-vue-template>>)
et peut être copiée dans le presse-papiers.

NOTE: Grype est lancé en une seule passe qui produit simultanément la sortie
JSON (pour la vue Table) et la sortie template (via un fichier temporaire).

=== Fichier de configuration (`grype.yaml`)

Chemin vers un fichier de configuration grype au format YAML.
Permet de définir des règles d'ignorance, des bases de données personnalisées,
des proxies, etc.

Ce paramètre est optionnel. Laissez le champ vide pour utiliser la
configuration grype par défaut (`~/.grype.yaml` si elle existe).

Documentation officielle : https://github.com/anchore/grype#configuration

=== Lancer et arrêter l'analyse

Cliquez sur *Analyser* pour démarrer. Une barre de progression linéaire
s'affiche pendant l'exécution. Le bouton devient *Stop* pour interrompre.

==== Vue Table

[[sec-vue-table]]
La vue Table affiche une barre d'outils de recherche/tri, les filtres par
sévérité, puis la liste des vulnérabilités :

----
  [ Rechercher...                        ] [⬇]
  Filtre : [Critical (1)] [High (2)] [Medium (2)] [Low (0)]  [Tout voir]

  ┌────────────┬──────────────────┬──────────────────┬───────────────┬──────┐
  │ SÉVÉRITÉ ↕ │ PAQUET ↕         │ VERSION ↕        │ CVE/ID ↕      │ TYPE │
  ├────────────┼──────────────────┼──────────────────┼───────────────┼──────┤
  │ CRITICAL   │ openssl          │ 1.1.1k → 1.1.1l  │ CVE-2021-3711 │ rpm  │
  │ HIGH       │ bash             │ 5.0.17  (no fix) │ CVE-2021-3489 │ rpm  │
  │ MEDIUM     │ zlib             │ 1.2.11  → 1.2.12 │ CVE-2022-37434│ rpm  │
  └────────────┴──────────────────┴──────────────────┴───────────────┴──────┘
----

*Recherche* : le champ de recherche filtre en temps réel sur le nom du paquet,
l'identifiant CVE, la version ou le type.

*Tri* : cliquez sur l'en-tête d'une colonne (SÉVÉRITÉ, PAQUET, VERSION, CVE/ID)
pour trier dans l'ordre croissant, cliquez à nouveau pour inverser. La flèche ↑↓
indique la colonne et le sens de tri actifs. Par défaut, les résultats sont triés
par sévérité décroissante (Critical en premier).

*Export CSV* : le bouton ⬇ (téléchargement) exporte la liste filtrée en cours
(tenant compte de la recherche et des filtres sévérité) dans un fichier `.csv`
au format RFC 4180. Colonnes : Sévérité, CVE/ID, Paquet, Version installée,
Version corrigée, Type.

*Filtres par sévérité* : cliquez sur un ou plusieurs badges pour n'afficher que
les vulnérabilités du niveau correspondant. Le bouton *Tout voir* efface les
filtres actifs. Seuls les badges correspondant à des sévérités présentes dans
les résultats sont affichés.

*Filtre par date* : une barre de filtrage temporel se trouve au-dessus de la
table. Elle permet d'afficher uniquement les CVE publiées ou modifiées dans
une plage de dates donnée :

----
  📅 Date CVE : [Publication] [Modification] [La plus récente]
     Après le : [2024-01-01 ×]   Avant le : [2024-12-31 ×]
     [✓] Sans date    [Propager aux autres onglets]
----

* *Champ de date* : sélecteur à trois valeurs — *Publication* (date initiale
  de publication du CVE), *Modification* (dernière mise à jour), *La plus
  récente* (la plus tardive des deux dates disponibles).
* *Après le / Avant le* : chips cliquables ouvrant un calendrier. Un ×
  permet d'effacer chaque borne indépendamment.
* *Sans date* : case à cocher pour inclure les CVE dont le champ de date
  sélectionné est absent ou non renseigné dans les données du scanner. Par
  défaut, ces CVE sont exclues lorsqu'un filtre est actif.
* *Propager aux autres onglets* : copie le filtre en cours vers les deux
  autres onglets CVE (OSV-Scanner et Trivy). Les analyses elles-mêmes ne
  sont pas relancées ; seul l'affichage est filtré.

NOTE: Le filtre par date s'applique en post-traitement sur le JSON retourné
par Grype. Il est indépendant des options de ligne de commande Grype et
cumulable avec les filtres par sévérité et par recherche textuelle.

Colonnes :

* *Badge de sévérité* : libellé coloré (CRITICAL / HIGH / MEDIUM / LOW / NEGLIGIBLE)
* *Paquet* : nom du paquet concerné en gras
* *Versions* : version installée, et version corrigée si disponible (après `→`).
  La mention `(won't fix)` indique que le mainteneur ne prévoit pas de correction.
* *CVE* : identifiant cliquable — un clic copie l'identifiant dans le presse-papiers
* *Type* : type de paquet (`rpm`, `python`, `deb`…)

[[sec-vue-json]]

inspecter le détail d'une vulnérabilité (CVSS, références, métadonnées…).

Le bouton 📋 en haut à droite copie l'intégralité du JSON dans le presse-papiers.

==== Vue Template

[[sec-vue-template]]

pas encore été lancée.

Le bouton 📋 copie la sortie dans le presse-papiers.

== Sous-commande `scan` — Analyse CVE en ligne de commande

La sous-commande `scan` permet d'exécuter les mêmes analyses CVE que le GUI
directement depuis le terminal, avec filtrage par date intégré. Elle ne
nécessite pas d'interface graphique.

[source,bash]
----
sbom-generator scan --sbom <fichier.cdx.json> [options]
----

=== Options

[cols="2,1,3", options="header"]
|===
|Option |Défaut |Description

|`--sbom <chemin>` (ou `-s`)
|_obligatoire_
|Fichier SBOM à analyser (CycloneDX, SPDX…)

|`--scanner <nom>` (ou `-S`)
|`grype`
|Scanner à utiliser : `grype`, `osv`, `trivy`, ou `all` (les trois)

|`--cve-after <YYYY-MM-DD>`
|_aucun_
|N'afficher que les CVE dont la date est postérieure à cette valeur (inclusive)

|`--cve-before <YYYY-MM-DD>`
|_aucun_
|N'afficher que les CVE dont la date est antérieure à cette valeur (inclusive,
fin de journée)

|`--cve-date-field <champ>`
|`published`
|Champ de date utilisé : `published`, `modified`, ou `latest` (la plus récente
des deux)

|`--include-undated`
|_désactivé_
|Inclure les CVE dont le champ de date est absent des données du scanner

|`--help` (ou `-h`)
|—
|Afficher l'aide de la sous-commande
|===

=== Codes de retour

* *0* — aucune CVE dans la plage demandée (ou aucune CVE trouvée du tout)
* *1* — au moins une CVE trouvée dans la plage, ou erreur d'un scanner

=== Exemples

[source,bash]
----
# Toutes les CVE Grype depuis le 1er janvier 2024
sbom-generator scan --sbom sbom.cdx.json --cve-after 2024-01-01

# CVE OSV-Scanner entre deux dates
sbom-generator scan --sbom sbom.cdx.json --scanner osv \
  --cve-after 2023-06-01 --cve-before 2024-01-01

# Tous les scanners, date de modification, CVE sans date incluses
sbom-generator scan --sbom sbom.cdx.json --scanner all \
  --cve-date-field modified --cve-after 2023-01-01 --include-undated

# Utiliser dans un script CI (retour 1 si CVE récentes détectées)
sbom-generator scan --sbom sbom.cdx.json \
  --cve-after "$(date -d '90 days ago' +%F)" && echo "OK" || echo "CVE récentes !"
----

La commande affiche pour chaque scanner une table textuelle triée par
sévérité décroissante :

----
── Grype ──────────────────────────────────────────
  3 CVE(s) trouvée(s)  Filtre : champ=published  après=2024-01-01

SÉVÉRITÉ      CVE / ID              PAQUET
------------  --------------------  ------------------------------------
Critical      CVE-2024-1234         openssl@1.1.1k
High          CVE-2024-5678         bash@5.0.17

== Problèmes courants

=== `sbom-generator` introuvable

*Symptôme* : la génération échoue immédiatement avec une erreur du type
`sbom-generator: commande introuvable`.

*Solution* : vérifiez que le binaire `sbom-generator` est accessible dans le PATH :

[source,bash]
----
which sbom-generator
sbom-generator --version
----

Si le binaire est installé à un emplacement non standard, placez-le dans
un dossier du PATH ou créez un lien symbolique :

[source,bash]
----
ln -s /chemin/vers/sbom-generator /usr/local/bin/sbom-generator
----

=== `syft` / `skopeo` introuvable

*Symptôme* : la génération échoue avec le message
`syft introuvable ou non fonctionnel — requis pour --image.`

*Solution* : installez l'outil manquant et vérifiez qu'il est dans le PATH :

[source,bash]
----
# Syft
curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh \
  | sh -s -- -b /usr/local/bin
syft version

# Skopeo (Fedora/RHEL)
sudo dnf install skopeo
skopeo --version
----

=== Échec de l'analyse OCI

*Symptôme* : `Échec de l'analyse OCI : …` dans le journal.

*Causes possibles et solutions :*

* *Image de registre inaccessible* : vérifiez la connexion réseau et
  l'authentification (`docker login` ou `skopeo login`).
* *Archive tar corrompue ou format non reconnu* : regénérez l'archive
  avec `docker save <image> -o /path/image.tar`.
* *Répertoire OCI layout invalide* : vérifiez que `index.json` est présent
  à la racine du répertoire.

=== `grype` introuvable

*Symptôme* : l'analyse Grype échoue avec le message
`grype introuvable. Installez-le : https://github.com/anchore/grype`.

*Solution* : installez grype (voir <<_installer_grype>>) et vérifiez qu'il
est dans le PATH :

[source,bash]
----
which grype
grype version
----

=== `osv-scanner` introuvable

*Symptôme* : l'analyse OSV-Scanner échoue avec un message du type
`osv-scanner: commande introuvable` ou le fichier SBOM n'est pas trouvé.

*Solution* : vérifiez que `osv-scanner` est dans le PATH de votre session
graphique (pas seulement dans le terminal) :

[source,bash]
----
which osv-scanner
osv-scanner --version
----

Si `osv-scanner` est installé via `go install` dans `~/go/bin`, ce dossier
n'est souvent pas dans le PATH graphique. Ajoutez-le dans `~/.profile` :

[source,bash]
----
export PATH="$HOME/go/bin:$PATH"
----

Puis reconnectez-vous ou relancez le GUI.

=== `trivy` introuvable

*Symptôme* : l'analyse Trivy échoue avec un message du type
`trivy: commande introuvable`.

*Solution* : vérifiez que `trivy` est dans le PATH :

[source,bash]
----
which trivy
trivy --version
----

Installez-le si nécessaire (voir <<_installer_trivy_optionnel>>).

=== La base de données Trivy est obsolète

*Symptôme* : Trivy affiche un avertissement sur l'âge de sa base de données.

*Solution* : laissez *--skip-db-update* décoché (comportement par défaut)
pour que Trivy mette à jour sa base automatiquement au lancement.
En environnement hors-ligne, mettez à jour manuellement :

[source,bash]
----
trivy image --download-db-only
----

=== Aucune vulnérabilité détectée malgré un SBOM chargé

*Causes possibles :*

* Le fichier SBOM sélectionné n'est pas un format reconnu par grype.
  Grype supporte nativement CycloneDX JSON (`.cdx.json`) et SPDX JSON
  (`.spdx.json`). Le format SPDX 3.0 JSON-LD peut nécessiter une version
  récente de grype.

* La base de données de vulnérabilités grype est obsolète.
  Grype la met à jour automatiquement au premier lancement,
  mais peut avoir besoin d'une mise à jour manuelle :
+
[source,bash]
----
grype db update
----

* La version RHEL sélectionnée dans *Distro* ne correspond pas aux paquets
  du SBOM. Essayez *(aucune)* pour laisser grype détecter automatiquement.

=== Avertissements de licence

*Symptôme* : des lignes `Warning: licence inconnue pour 'paquet'` apparaissent
dans la progression.

*Explication* : `sbom-generator` n'a pas pu déterminer la licence SPDX du
paquet. Le SBOM est généré quand même avec la valeur `NOASSERTION` pour
la licence concernée.

*Solution* : utilisez un fichier *override de licences* (`--license-map`)
pour définir manuellement la licence des paquets non reconnus.

=== Le score sbomqs n'apparaît pas

*Causes possibles :*

* `sbomqs` n'est pas installé ou n'est pas dans le PATH.
  Vérifiez avec `which sbomqs`. Si absent, installez-le
  (voir <<_installer_sbomqs_optionnel>>).

* L'option *Score qualité sbomqs* n'est pas cochée dans la section *Options*.

* Aucun fichier JSON SBOM n'a été généré dans la session courante.
  sbomqs ne s'exécute que sur les formats `.cdx.json`, `.spdx.json` ou `.jsonld`.
  Assurez-vous qu'au moins un de ces formats est sélectionné.

=== La conversion PDF échoue

*Symptôme* : le message `asciidoctor-pdf introuvable` apparaît dans les logs.

*Solution* : installez `asciidoctor-pdf` (voir <<_installer_asciidoctor_pdf_optionnel>>).

Si `asciidoctor-pdf` est installé mais introuvable, assurez-vous que le
dossier des gems Ruby est dans le PATH :

[source,bash]
----
gem environment gemdir
# Exemple : /home/user/.local/share/gem/ruby/3.2.0
export PATH="$HOME/.local/share/gem/ruby/3.2.0/bin:$PATH"
----
