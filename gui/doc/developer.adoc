== Introduction

Ce document décrit l'architecture du GUI Flutter du projet `sbom_generator`.
Il s'adresse à un développeur Dart qui n'a pas encore pratiqué Flutter, ou qui
rejoint le projet sans en connaître l'historique.

Le GUI est une application de bureau Linux (Flutter desktop).
Il n'effectue aucun traitement métier lui-même : il orchestre deux outils
en ligne de commande externes —

* *sbom-generator* : génère les fichiers SBOM
* *grype* : analyse les SBOM générés et détecte les vulnérabilités CVE

=== Installation de Flutter

[source,bash]
----
# Cloner Flutter
git clone https://github.com/flutter/flutter.git ~/flutter
export PATH="$HOME/flutter/bin:$PATH"

# Activer le support bureau Linux
flutter config --enable-linux-desktop

# Vérifier
flutter doctor
----

=== Lancer le GUI en développement

[source,bash]
----
cd gui/

# Télécharger les dépendances
flutter pub get

# Lancer en mode debug (hot-reload disponible)
flutter run -d linux

# Analyser le code (équivalent dart analyze)
flutter analyze

# Exécuter les tests (-j 1 : plus déterministe que le parallélisme par
# défaut sur des machines aux ressources limitées, voir Setup développement)
flutter test -j 1
----

En mode debug, Flutter affiche des assertions dans la console (ex. ListTile dans
ColoredBox). Ces messages sont des _warnings_ inoffensifs, pas des crashes
(voir <<sec-piege-listile>>).

Exécuté automatiquement par `../.github/workflows/ci.yml` (job GUI :
`flutter analyze` puis `flutter test -j 1`) sur chaque push/pull request
vers `main`.

=== Compiler un binaire autonome

[source,bash]
----
flutter build linux --release
# Binaire produit dans :
# build/linux/x64/release/bundle/sbom_generator_gui
----

=== Rôle de chaque fichier

==== `main.dart` — Point d'entrée

`main()` est *async* : il charge la configuration sauvegardée, le thème
et l'index de couleur (`shared_preferences`) avant le premier rendu,
puis passe ces valeurs à `SbomGeneratorApp`.

`SbomGeneratorApp` est un `StatefulWidget` qui :

* gère `ThemeMode _themeMode` (clair / sombre)
* gère `int _themeIndex` (index dans `kAppThemes`)
* expose `_toggleTheme()` et `_onThemeIndexChanged(int)` transmis à `HomeScreen`
* déclare un `theme` (clair) et un `darkTheme` (sombre), tous deux basés
  sur `ColorScheme.fromSeed(seedColor: kAppThemes[_themeIndex].color)`
  avec le bon `brightness`

Quand `_themeIndex` change, `SettingsService.saveThemeColorIndex(index)`
est appelé de façon non bloquante.

==== `home_screen.dart` — Écran principal

`HomeScreen` est un `StatefulWidget` (voir <<sec-flutter-stateful>>) qui :

* reçoit `initialConfig`, `themeMode`, `onThemeToggle`, `themeIndex` et
  `onThemeIndexChanged` depuis `SbomGeneratorApp`
* détient l'état global de la session SBOM : log, fichiers produits, progression,
  code de retour, état d'exécution, sortie sbomqs
* instancie `SbomRunner` ; initialise `_config` depuis `initialConfig`
* écoute le stream de `SbomRunner` et redistribue les événements vers `ResultsPanel`
  via des `setState()`
* déclenche automatiquement la conversion PDF (`asciidoctor-pdf`) après un
  succès si `_config.generatePdf` est vrai
* déclenche `_runSbomqs()` après un succès si `_config.enableSbomqs` est vrai
* sauvegarde la configuration (`SettingsService.saveConfig`) avant chaque
  génération et sur chaque changement de champ (`onChanged` de `ConfigPanel`)
* affiche dans l'`AppBar` : bouton palette 🎨 (`IconButton` → `_showThemePicker`),
  bouton bascule thème 🌙/☀, bouton info

`_startScan()` place comme première entrée de `_logLines` la commande shell
complète via `_config.toCommandLine(SettingsService.cliBinary)`.

`_showThemePicker()` ouvre `_ThemePickerDialog` (dialog inline défini en bas
du fichier). `_ThemePickerDialog` affiche un `Wrap` de `_ThemeSwatch` —
des cercles colorés (`AnimatedContainer`) avec une coche pour le thème actif.

Layout : `Row` avec deux enfants —

[source,text]
----
HomeScreen
├── ConfigPanel    (largeur fixe 390 px)
│     └── SbomConfig (modèle mutable partagé)
└── ResultsPanel   (Expanded — prend le reste)
----

==== `models/sbom_config.dart` — Configuration SBOM

Objet mutable (`SbomConfig`) partagé entre `HomeScreen` et `ConfigPanel`.
Expose `toArgs()` qui construit la liste d'arguments CLI, et
`expectedOutputPaths()` pour la prévisualisation des fichiers avant génération.

`toCommandLine(String binary)` est ajouté pour l'affichage humain :

[source,dart]
----
String toCommandLine(String binary) {
  return [binary, ...toArgs()]
      .map((s) => s.contains(' ') ? '"$s"' : s)
      .join(' ');
}
----

Cette méthode est appelée dans `_startScan()` de `HomeScreen` (première ligne
du log) et dans `_CommandPreview` de `ConfigPanel` (prévisualisation live).

Expose aussi `toJson()` / `SbomConfig.fromJson(Map)` pour la persistance
via `SettingsService`. Les champs *non* persistés (trop contextuels) sont
`inputFile` et `pdfOutputPath`.

Champ ajouté : `bool enableSbomqs` (défaut : `false`) — active l'analyse
qualité automatique après génération.

Champs ajoutés pour OCI :

* `String imageRef` (défaut : `''`) — référence à une image OCI (`--image`) ;
  vide signifie que l'analyse OCI est désactivée.
* `String ociTool` (défaut : `'syft'`) — backend OCI choisi (`--oci-tool`).
  Valeurs : `'syft'`, `'trivy'`, `'skopeo'`, `'cdxgen'`.
* `String binaryPath` (défaut : `''`) — binaire local à analyser directement
  (`--binary`), voir <<sec-binary-field>>.

* `String nestedDepth` (défaut : `'0'`) — profondeur de descente dans les
  objets imbriqués de `--input` (`--depth`) : `'0'`, `'1'`…`'3'` ou `'all'`
  (`allNestedDepths`). `bool nestedFiles` (défaut : `true`) — un SBOM par
  objet imbriqué ; `false` → `--no-nested-files`. `toArgs()` n'émet
  `--depth` (et `--no-nested-files`) que si `inputFile` est renseigné et la
  profondeur ≠ `'0'` ; le CLI refuse `--depth` sans `--input`. Option
  affichée par `_NestedDepthOptions` (`config_panel.dart`), sous le champ
  d'entrée. Les fichiers `*.nested-NN-*` sont repris des lignes
  `SBOM written →` comme les SBOM de couche.
* `bool perLayer` (défaut : `false`) — un SBOM par couche (`--per-layer`),
  voir <<sec-per-layer-option>>.
* `String layerMode` (défaut : `'metadata'`) — méthode mémorisée
  (`--layer-mode`) ; la valeur transmise est `effectiveLayerMode`, qui vaut
  `'rootfs'` pour un backend hors `metadataLayerTools` (`{'syft', 'trivy'}`)
  quel que soit le choix mémorisé (le CLI refuse `metadata` avec skopeo /
  cdxgen).

Ces champs sont inclus dans `toJson()` / `fromJson()` (clés `'imageRef'`,
`'ociTool'`, `'binaryPath'`, `'perLayer'`, `'layerMode'`) et donc persistés
entre sessions. Ils sont chargés par `_loadProfileInto()` dans
`_ProfilesDialog`.

Dans `toArgs()` :

[source,dart]
----
if (binaryPath.isNotEmpty) {
  // --binary est exclusif de --image côté CLI et force --oci-tool syft :
  // ociTool ne s'applique qu'à --image, jamais émis ici.
  args.addAll(['--binary', binaryPath]);
} else if (imageRef.isNotEmpty) {
  args.addAll(['--image', imageRef]);
  args.addAll(['--oci-tool', ociTool]);
  if (perLayer) {
    args.addAll(['--per-layer', '--layer-mode', effectiveLayerMode]);
  }
}
----

`--per-layer` n'est émis qu'avec `--image` : ni `--input` seul ni
`--binary` (un binaire n'a pas de couches).

Constantes exposées :

* `allFormats`, `formatLabels`, `_formatExtensions` — checkboxes de format
  (`formatLabel(fmt, l)` renvoie le libellé affiché, en traduisant `json`)
* `allOciTools` (`['syft', 'trivy', 'skopeo', 'cdxgen']`) — liste des backends OCI
* `ociToolLabels` (`{'syft': 'Syft', 'trivy': 'Trivy', 'skopeo': 'Skopeo',
  'cdxgen': 'cdxgen'}`) — libellés des segments du sélecteur d'outil OCI

const kAppThemes = [

  AppTheme('Violet',  Color(0xFF4A148C)),

  AppTheme('Vert',    Color(0xFF1B5E20)),
  AppTheme('Orange',  Color(0xFFBF360C)),

==== `models/sbom_result.dart` — Modèles de résultat

Contient `OutputFile` (chemin + taille formatée) et `SbomResult` (agrégat de
sortie). `SbomResult` n'est pas utilisé directement dans l'UI — les champs
sont remontés un à un via les événements du stream (voir <<sec-stream>>).

==== `models/cve_date_filter.dart` — Filtre temporel CVE

Modèle immuable partagé entre les trois panneaux scanner (Grype, OSV, Trivy)
et la CLI `scan`.

[source,dart]
----
enum CveDateField { published, modified, latest }

class CveDateFilter {
  final DateTime? after;
  final DateTime? before;
  final CveDateField field;   // champ de date utilisé pour le filtrage
  final bool includeUndated;  // inclure les CVE sans date

  static const CveDateFilter empty = CveDateFilter();
  bool get hasConstraints => after != null || before != null;

  bool matches(DateTime? published, DateTime? modified) { … }
  CveDateFilter copyWith({…}) { … }
}
----

Points notables :

* `hasConstraints` retourne `false` quand `after` et `before` sont tous deux
  nuls — `matches()` court-circuite alors sans calcul.
* `CveDateField.latest` utilise `_latest(a, b)` qui retourne la date la plus
  tardive des deux (gère les cas où l'une est nulle).
* `copyWith()` applique le *sentinel pattern* (`static const Object _sentinel`)
  pour distinguer "paramètre non fourni" de "paramètre explicitement `null`"
  sur les champs `DateTime?` — le pattern `?? this.field` n'étant pas
  utilisable pour effacer une date nullable.
* `CveDateFilter.empty` (constante) est utilisé comme valeur initiale dans
  `ResultsPanel` pour les trois filtres, évitant les vérifications de nullité.

==== `services/sbom_runner.dart` — Exécution SBOM

[[sec-sbom-runner]]
Lance `sbom-generator` via `Process.start()` et expose un
`Stream<SbomEvent>`. Quatre types d'événements (sealed class) :

[cols="1,2", options="header"]
|===
|Événement |Contenu

|`SbomProgressEvent`
|current, total, percent, label — parsés depuis la barre de progression stdout

|`SbomLogEvent`
|line, isError, isWarning — toute ligne de log

|`SbomOutputFileEvent`
|un `OutputFile` parsé depuis `"SBOM written → path (size)"`

|`SbomDoneEvent`
|exitCode
|===

`HomeScreen` écoute ce stream avec `.listen()` et appelle `setState()` à chaque
événement pour mettre à jour l'UI.

Le runner lance le CLI avec l'environnement de langue de l'interface
(`SettingsService.cliEnvironment`, variable `SBOM_LANG`) pour que les messages
du CLI suivent la langue choisie dans la GUI. Les *contrats machine* qu'il
analyse (`SBOM written →`, la barre de progression `] n/m %`, les préfixes
`Error:` / `Warning:` / `⚠` / `   •`) ne sont jamais traduits par le CLI.

==== `services/grype_runner.dart` — Exécution Grype

[[sec-grype-runner]]
Même principe que `sbom_runner.dart`, mais les événements sont différents :

[cols="1,2", options="header"]
|===
|Événement |Contenu

|`GrypeOutputEvent`
|JSON complet de grype (accumulé depuis stdout, émis après exit)

|`GrypeTemplateEvent`
|Contenu du fichier temporaire de sortie template (lu après exit)

|`GrypeDoneEvent`
|exitCode + stderr optionnel
|===

Lorsqu'un fichier template est configuré, grype est lancé avec deux sorties :

[source,bash]
----
grype sbom.cdx.json \
  --output json \
  --output template=/tmp/grype_tmpl_<ts>.txt \
  --template ./grype_csv.tmpl \
  ...
----

La sortie JSON arrive sur stdout (capturée dans `jsonBuf`).
La sortie template est écrite dans un fichier temporaire, lue après exit,
puis supprimée (voir <<sec-piege-tmpl>>).

[[sec-scan-image]]
===== Scan d'image de conteneur (Grype/OSV-Scanner/Trivy)

Les trois panneaux de scan (voir <<sec-vuln-shared>>) offrent une bascule
*Fichier SBOM / Image de conteneur*. Le paramètre `sbomFile` de `run()` a
été renommé `target` dans les trois runners pour refléter ce double usage :
chemin d'un fichier SBOM en mode par défaut, ou référence d'image (registre,
archive locale, répertoire OCI layout) en mode image.

`grype_runner.dart` n'a besoin d'aucune logique de branchement : grype
détecte seul le type de source depuis l'argument positionnel (fichier SBOM,
image de registre, archive `docker save`/OCI, répertoire OCI layout — voir
`grype --help`). Seul un paramètre `platform` (`--platform`, ex.
`linux/arm64`) a été ajouté, prioritaire sur le booléen `platformLinux`
existant :

[source,dart]
----
if (platform != null && platform.isNotEmpty) {
  args.addAll(['--platform', platform]);
} else if (platformLinux) {
  args.addAll(['--platform', 'linux']);
}
----

IMPORTANT: `grype_panel.dart` force `platformLinux: false` lorsque
`sourceKind == ScanSourceKind.image`, quel que soit l'état de la case
`--platform linux`. Cette case n'a d'effet qu'en mode fichier SBOM ; en mode
image, `--platform linux` (sans architecture) est *rejeté* par grype sur une
image multi-plateforme (`no child with platform linux in index`, vérifié en
conditions réelles) — seul le champ dédié doit s'appliquer dans ce mode.

[[sec-package-scan-dev]]
==== Source « Paquet / archive » — `services/package_scan_service.dart`

`ScanSourceKind.package` (3^e^ segment de `ScanSourceToggle`, commun aux trois
onglets) affiche `PackageSourceField` (`vuln_shared.dart`) : champ de chemin,
bouton de sélection et menu de profondeur (`packageScanDepths` : `0`, `1`,
`2`, `3`, `all`). Aucune logique métier côté GUI : `PackageScanService.prepare(
chemin, profondeur)` lance `sbom-generator --input … --depth N
--no-nested-files --format cyclonedx --output <tmp>/package.cdx.json`
(`SettingsService.cliBinary`), met le chemin du SBOM en cache pour la session
(clé : chemin + date de modification + profondeur, donc partagé par les trois
onglets ; un échec n'est pas mis en cache) et lève `PackageScanException`
(code de sortie + stderr) en cas d'échec. `kill()` interrompt la génération.

Dans chaque onglet, `_analyze()` délègue à `_analyzePackage()` pour cette
source : validation du chemin, état « Génération du SBOM du paquet… »
(`_status`), `PackageScanService.prepare`, puis `_launch(sbom, false, libellé)`
— le même corps que pour un fichier SBOM (`_launch` est l'ancienne fin de
`_analyze`). Le libellé de cible (en-tête des rapports) est
`paquet « nom » (profondeur N)`. Le bouton *Arrêter* appelle
`PackageScanService.kill()`.

Popup *CLI Commande* : `_cliSections()` ajoute la génération du SBOM
(`cliPackageSbom`, `/tmp/sbom-paquet/package.cdx.json`) avant les sections
habituelles de `_scanCliSections(sbomTarget:, packageTarget:)` ;
`sbomGeneratorScanArgs(usePackage: true, packageDepth:)` produit
`scan --package <fichier> [--depth N] --scanner …`. La colonne `OBJET` (objet
imbriqué contenant le paquet vulnérable) n'existe que dans la sortie du CLI :
les modèles `GrypeVuln` / `OsvVuln` / `TrivyVuln` ne portent pas l'objet.

==== `services/osv_runner.dart` — Exécution OSV-Scanner

Même architecture que `grype_runner.dart`. Deux types d'événements (sealed class) :

[cols="1,2", options="header"]
|===
|Événement |Contenu

|`OsvOutputEvent`
|JSON complet d'osv-scanner (accumulé depuis stdout, émis après exit)

|`OsvDoneEvent`
|exitCode + stderr optionnel
|===

Particularité : un code de retour *1* indique que des vulnérabilités ont été
trouvées (comportement normal d'osv-scanner), pas une erreur. Seul un code
*supérieur à 1* signale une vraie erreur — ce comportement est partagé par
`scan image` (vérifié en conditions réelles).

En mode fichier SBOM (`useImage: false`, par défaut), la commande lancée
reprend l'ancien style par flags (toujours accepté, bien que marqué
`[DEPRECATED]` dans l'aide d'osv-scanner ≥ 2.x) :

[source,bash]
----
osv-scanner --format json --sbom <target> [--config <configFile>]
----

En mode image (`useImage: true`), seule la sous-commande `scan image`
(introduite dans le CLI v2) sait analyser une image ; l'ancien style ne le
permet pas :

[source,bash]
----
osv-scanner scan image --format json <target>                # registre
osv-scanner scan image --format json --archive <target>       # archive locale
----

Le choix entre les deux se fait via `FileSystemEntity.typeSync(target)` :
un fichier local déclenche `--archive`, sinon `target` est passé tel quel
(référence de registre). *Contrairement à Grype et Trivy, osv-scanner ne
sait pas lire un répertoire OCI layout* (seule une archive tar est
supportée par `--archive`) — c'est pourquoi `osv_panel.dart` passe
`allowOciDir: false` à `ImageRefField` et n'offre pas ce sélecteur.
osv-scanner n'a pas non plus d'option `--platform`.

==== `services/trivy_runner.dart` — Exécution Trivy

Même architecture. Paramètres nommés de `run()` :

[source,dart]
----
Stream<TrivyEvent> run({
  required String target,
  bool useImage = false,
  String? platform,                     // ex. 'linux/arm64', mode image uniquement
  List<String> severities = const [],   // ex. ['CRITICAL', 'HIGH']
  bool ignoreUnfixed = false,
  bool skipDbUpdate = false,
  String? configFile,
})
----

Deux types d'événements :

[cols="1,2", options="header"]
|===
|Événement |Contenu

|`TrivyOutputEvent`
|JSON complet de trivy (accumulé depuis stdout, émis après exit)

|`TrivyDoneEvent`
|exitCode + stderr optionnel
|===

En mode fichier SBOM (`useImage: false`), la sous-commande est `sbom` :

[source,bash]
----
trivy sbom --format json --quiet \
  [--severity CRITICAL,HIGH,...] \
  [--ignore-unfixed] \
  [--skip-db-update] \
  [--config trivy.yaml] \
  <target>
----

En mode image (`useImage: true`), la sous-commande devient `image` et
`--platform` est ajouté si renseigné. `--input` accepte aussi bien une
archive (`docker save`/OCI) qu'un répertoire OCI layout ; une référence de
registre se passe en argument positionnel, comme en mode SBOM :

[source,bash]
----
trivy image --format json --quiet \
  [--severity ...] [--ignore-unfixed] [--skip-db-update] \
  [--config trivy.yaml] [--platform linux/arm64] \
  <target>                    # référence de registre
# ou, si FileSystemEntity.typeSync(target) détecte un chemin local :
trivy image [...] --input <target>   # archive ou répertoire OCI local
----

NOTE: Il est attendu que le mode SBOM (sur un SBOM généré par
`sbom_generator` avec le backend syft) et le mode image de `TrivyRunner`
ne rapportent pas exactement les mêmes CVE Java pour la même image — ce
n'est pas un bug de ce fichier ni de `oci_parser.dart`. L'analyseur de
jars intégré à Trivy identifie un jar via `pom.properties`, puis
`MANIFEST.MF`, puis un lookup SHA-1 dans sa base `trivy-java-db`
(indexée depuis Maven Central), et abandonne silencieusement le paquet si
les trois échouent — ce qui arrive pour des jars rebuilds internes (ex.
Red Hat `.redhat-000xx`) sans `pom.properties` et absents de Maven
Central. Le cataloguer de syft, utilisé pour produire nos SBOM, sait
retrouver ces paquets en parsant le nom de fichier
`<groupId>.<artifactId>-<version>.jar`. Vérifié sur une image
RHEL 9.6/Keycloak : `trivy sbom` trouvait 3 CVE HIGH
(`micrometer-core`, `postgresql`) absentes de `trivy image` en direct.
Voir `user.adoc`, section « Pourquoi Grype, OSV-Scanner et Trivy ne
trouvent pas les mêmes CVE ».

[[sec-enrichissement]]
==== `services/vuln_enrichment.dart` + `scan_enrichment.dart` — enrichissement CVE

La GUI ne dépend pas du paquet racine : `services/vuln_enrichment.dart` est
une **copie synchronisée** de `lib/vuln_enrichment.dart` du CLI (garder les
deux identiques — les corps de classe le sont, seul le commentaire d'en-tête
diffère). Il fournit `VulnEnricher` (CISA KEV via le flux CISA, EPSS via
l'API FIRST, PoC via `poc-in-github.motikan2010.net`, tout en `dart:io
HttpClient`, cache 24 h sous `~/.cache/sbom-generator/` partagé avec le CLI,
repli sur le cache si le réseau échoue), `parseCvssVector()` et les modèles
`CveSeed` / `ExploitInfo`.

`scan_enrichment.dart` fait le pont avec les panneaux :

* `normalizeCveId(id)` — même regex distro que `_normalizeVulnId` du tableau
  de bord ;
* `seedsFromGrypeJson` / `seedsFromOsvJson` / `seedsFromTrivyJson` — extraient
  les *graines* du JSON brut de chaque scanner : vecteur CVSS pour tous, et
  **KEV + EPSS natifs pour Grype** (qui les porte dans sa base — autant de
  requêtes réseau évitées) ;
* `enrichCves(ids, {seed, online})` — instancie `VulnEnricher` et renvoie
  `Map<String, ExploitInfo>`.

Chaque panneau (`grype_panel` / `osv_panel` / `trivy_panel`), après
`dedupeVulns`, appelle `_enrich(rawJson, vulns)` : construit les graines,
appelle `enrichCves` (best-effort, `_enrichRun` garde contre les courses),
`setState(_exploitById)`, puis remonte via `onExploitChanged`. `ResultsPanel`
fusionne les trois maps (`_mergedExploit`, priorité aux entrées portant le
plus de signal) et la passe à `DashboardPanel`. Le bouton `☁` (barre d'outils
de `VulnTableView`) bascule `online` ; le choix est persisté par
`SettingsService.saveScanEnrichOnline()` (clé `scan_enrich_online_v1`, défaut
activé) et partagé par les trois onglets.

[[sec-version-service]]
==== `services/version_service.dart` — Version installée + mise à jour GitHub

Ce fichier regroupe trois éléments indépendants.

*`ToolVersionInfo`* — modèle immuable :

[source,dart]
----
class ToolVersionInfo {
  final String? installed;   // '0.87.0', null = non installé
  final String? latest;      // '0.88.1', null = API inaccessible
  final String? releaseUrl;  // URL page GitHub release
  bool get isInstalled => installed != null;
  bool get hasUpdate { ... } // compare installed < latest (semver)
}
----

*`VersionService`* — trois méthodes statiques asynchrones :

[source,dart]
----
VersionService.checkGrype()   // grype version
VersionService.checkOsv()     // osv-scanner --version
VersionService.checkTrivy()   // trivy --version
----

Chaque appel exécute la commande via `Process.run()`, extrait le premier
motif `\d+\.\d+\.\d+` dans stdout+stderr, puis interroge
`https://api.github.com/repos/<owner>/<repo>/releases/latest` (timeout 5 s)
pour récupérer `tag_name` et `html_url`.

*`ToolVersionBadge`* — widget `StatelessWidget` affiché en haut de
`_ConfigSection` dans chaque panel :

[cols="1,3", options="header"]
|===
|État |Rendu

|`info == null`
|Rien (vérification en cours)

|Non installé
|Icône rouge + « non installé »

|À jour
|Icône verte + « v{installed} »

|Mise à jour disponible
|Icône orange + « v{installed} → v{latest} » (cliquable → release GitHub)
|===

Le badge utilise `url_launcher` pour ouvrir la page de release dans le
navigateur. Il est initialisé dans `initState()` de chaque panel avec
`.then((info) { if (mounted) setState(...) })` pour ne pas bloquer le rendu.

[[sec-settings-service]]
==== `services/settings_service.dart` — Résolution du binaire + persistance

`SettingsService.cliBinary` cherche le binaire `sbom-generator` dans cet ordre :

1. `<exe_dir>/../../bin/sbom-generator` (bundle installé Linux)
2. `<exe_dir>/sbom-generator` (binaire côte-à-côte)
3. `sbom-generator` dans le PATH (fallback développement)

En développement, il suffit que le CLI soit compilé et accessible dans le PATH :

[source,bash]
----
cd ..   # racine du projet
dart compile exe bin/sbom_generator.dart -o build/sbom-generator
export PATH="$PWD/build:$PATH"
----

Le service gère également la *persistance* via `shared_preferences` :

[cols="2,3", options="header"]
|===
|Méthode |Rôle

|`saveConfig(SbomConfig)`
|Sérialise la config en JSON et la stocke sous la clé `sbom_config_v1`

|`loadConfig()`
|Désérialise et retourne un `SbomConfig?` (null si aucune config sauvée)

|`saveTheme(ThemeMode)`
|Stocke `'light'`, `'dark'` ou `'system'` sous la clé `theme_mode`

|`loadTheme()`
|Retourne le `ThemeMode` sauvegardé, ou `ThemeMode.system` par défaut

|`saveThemeColorIndex(int)`
|Stocke l'index du thème de couleur (0-9) sous la clé `theme_color_index`

|`loadThemeColorIndex()`
|Retourne l'index sauvegardé, ou `0` (Indigo) par défaut

|`saveLanguage(String)` / `loadLanguage()`
|Langue de l'interface (`system`, `fr`, `en`), clé `ui_language_v1` ; `system`
par défaut

|`cliLang` / `cliEnvironment`
|Champ statique posé par `main.dart` d'après la locale effective, et
environnement de processus `{SBOM_LANG: cliLang}` qui en est tiré — transmis
par tous les runners au CLI qu'ils lancent

|`saveScanEnrichOnline(bool)` / `loadScanEnrichOnline()`
|Autoriser les requêtes réseau d'enrichissement CVE (clé
`scan_enrich_online_v1`, défaut `true`) — bouton `☁` des onglets de scan

|`listProfiles()`
|Retourne la liste des noms de profils sauvegardés (clé `profile_names_v1`)

|`saveProfile(String name, SbomConfig)`
|Sérialise et stocke le profil sous la clé `profile_v1_<name encodé URI>`

|`loadProfile(String name)`
|Désérialise et retourne le `SbomConfig?` du profil nommé

|`deleteProfile(String name)`
|Supprime le profil et son nom de la liste
|===

La clé `sbom_config_v1` inclut un suffixe de version pour faciliter les
migrations futures (ignorer les clés `v0` obsolètes, ajouter `v2`, etc.).

Les noms de profils sont encodés avec `Uri.encodeComponent()` pour éviter
les collisions entre noms contenant des caractères spéciaux.

==== `widgets/config_panel.dart` — Formulaire de configuration

`ConfigPanel` est un `StatefulWidget` qui :

* expose un formulaire Flutter `Form` + `TextFormField`
* synchronise les champs vers l'objet `SbomConfig` à chaque modification
  (via `_sync()`) et appelle le callback optionnel `widget.onChanged?.()`
* déclenche le lancement via `widget.onRun()` (callback vers `HomeScreen`)
* génère dynamiquement les checkboxes de format depuis la liste `allFormats`
* encapsule le champ *Fichier d'entrée* dans un `DropTarget` (package
  `desktop_drop`) pour accepter les glisser-déposer de fichiers depuis le
  gestionnaire de fichiers système — un booléen `_isDragging` déclenche un
  `AnimatedContainer` avec liseré bleu
* propose la checkbox *Score qualité sbomqs* (pilote `SbomConfig.enableSbomqs`)
* expose un bouton 🔖 dans l'en-tête pour la gestion des profils nommés

Tous les textes visibles viennent des fichiers ARB (clés `cfg…`) : `build()`
lit `final l = context.l10n;` et les sous-widgets privés font de même dans
leur propre `build()`.

Le paramètre `VoidCallback? onChanged` est appelé après chaque modification
d'un champ (texte via `_sync()`, booléens directement dans leur `setState`).
`HomeScreen` l'utilise pour déclencher `SettingsService.saveConfig()` sans
attendre le prochain lancement.

*Profils de configuration* : l'en-tête du panneau est un `Row` avec le titre
à gauche et un `IconButton(Icons.bookmarks_outlined)` à droite. Ce bouton
appelle `_showProfilesDialog(context)` qui ouvre `_ProfilesDialog`.

`_ProfilesDialog` est un `StatefulWidget` défini en fin de fichier :

* au `initState()`, charge la liste de profils via `SettingsService.listProfiles()`
* affiche un `TextField` + bouton *Enregistrer* : appelle `_sync()` pour
  s'assurer que `widget.config` est à jour, puis `SettingsService.saveProfile()`
* pour chaque profil existant : bouton *Charger* (appelle `_loadProfileInto`)
  et bouton *Supprimer* (dialog de confirmation, puis `SettingsService.deleteProfile()`)

`_loadProfileInto(SbomConfig loaded)` copie tous les champs du profil dans les
`TextEditingController` existants et appelle `_sync()` + `widget.onChanged?.call()`.
Le champ `inputFile` est intentionnellement exclu du chargement.

*Filtre de type de fichier* : le widget interne `_FileField` accepte
deux callbacks optionnels — `onPick` (sélection standard filtrée) et
`onPickAll` (tous les fichiers). Quand les deux sont fournis, l'icône 📂
est remplacée par un `PopupMenuButton<bool>` qui propose :

* *Type filtré (extensions)* — appelle `onPick`
* *Tous les fichiers* — appelle `onPickAll`

*Section Image OCI* : insérée entre le champ fichier d'entrée et la section
Sortie. Elle comprend deux éléments :

. *Champ Image OCI* — `_imageCtrl` / `TextEditingController` lié à `c.imageRef`.
  Le bouton 📂 à droite ouvre un `PopupMenuButton` avec deux options :
  `_pickFile(extensions: ['tar', 'gz', 'tgz'])` pour les archives compressées
  ou non, et `_pickDir()` pour les répertoires OCI layout.
  Le type `registry` est toujours saisi manuellement.
. *Sélecteur d'outil OCI* — `_OciToolSelector` (widget privé) affiché uniquement
  si `c.imageRef.isNotEmpty`. `SegmentedButton` à quatre segments (`syft`,
  `trivy`, `skopeo`, `cdxgen`) qui met à jour `c.ociTool` via `setState`.

[[sec-binary-field]]
*Champ Binaire autonome* (`--binary`, sous un second séparateur « OU ») :
`_BinaryField` (widget privé, calqué sur `_OciImageField` mais avec un
sélecteur de fichier simple — pas de `PopupMenuButton` tar/dossier, un
binaire n'a généralement pas d'extension reconnaissable) lié à `_binaryCtrl`
/ `c.binaryPath`. Contrairement au champ Image OCI, il n'affiche *jamais* le
sélecteur `_OciToolSelector` : `--binary` force `--oci-tool syft` côté CLI,
donc `ociTool` n'a pas de sens ici. Un simple texte informatif (« Backend :
syft (forcé)… ») s'affiche à la place quand `c.binaryPath.isNotEmpty`.

La validation du champ fichier d'entrée (`--input`) est assouplie : l'erreur
"Requis" ne s'affiche que si `imageRef` *et* `binaryPath` sont vides tous
les deux :

[source,dart]
----
validator: (v) => (v == null || v.trim().isEmpty) &&
    _imageCtrl.text.trim().isEmpty &&
    _binaryCtrl.text.trim().isEmpty
        ? l.cfgInputRequired   // « Requis (ou spécifiez une image OCI / un binaire) »
        : null,
----

*Exclusivité mutuelle à trois* : `_inputCtrl`, `_imageCtrl` et `_binaryCtrl`
sont mutuellement exclusifs dans l'UI — remplir l'un vide les deux autres,
afin d'éviter toute ambiguïté sur la source réellement utilisée (le CLI,
lui, sait combiner `--input` et `--image`, mais rejette explicitement
`--binary` combiné à `--image`). Chaque point d'entrée qui modifie un des
trois champs vide les deux autres avant d'appeler `_sync()` :

* `onChanged` des trois `TextFormField` (saisie manuelle)
* `onDragDone` du `DropTarget` (glisser-déposer sur le champ fichier d'entrée)
* `_pickFile()` / `_pickDir()` — le paramètre optionnel, initialement
  `TextEditingController? clears`, est devenu
  `List<TextEditingController>? clears` pour pouvoir vider les *deux* autres
  champs en une seule liste (également utilisés par `rpm-dir`,
  `license-map`, etc., qui passent toujours une liste vide ou omettent le
  paramètre) :
+
[source,dart]
----
Future<void> _pickFile(TextEditingController ctrl,
    {String? title, List<String>? extensions,
    List<TextEditingController>? clears}) async {
  …
  ctrl.text = r.files.single.path!;
  for (final other in clears ?? const <TextEditingController>[]) {
    other.clear();
  }
  _sync();
  setState(() {});
}
----

[[sec-per-layer-option]]
*Option Un SBOM par couche* (`--per-layer`) : `_PerLayerOptions` (widget
privé), affiché sous `_OciToolSelector` donc uniquement quand
`c.imageRef.isNotEmpty`. Une `Checkbox` liée à `c.perLayer` ; une fois
cochée, un `SegmentedButton` *Métadonnées / Rootfs* lié à `c.layerMode`,
dont la sélection affichée est `c.effectiveLayerMode`. Le segment
*Métadonnées* est désactivé (`enabled: false`) pour un backend hors
`metadataLayerTools`, avec un rappel « Mode rootfs forcé » en dessous.

*Prévisualisation de la commande* : le widget `_CommandPreview` est inséré
entre le bouton *▶ Générer le SBOM* et la fin du formulaire. Il lit
`config.toCommandLine(SettingsService.cliBinary)` à chaque `build()` (donc
se met à jour à chaque `setState` existant) et l'affiche sur fond sombre
avec un bouton 📋 copie.

==== `widgets/osv_panel.dart` — Onglet OSV-Scanner

`OsvPanel` est un `StatefulWidget` autonome avec `AutomaticKeepAliveClientMixin`
(état préservé lors de la navigation entre onglets). Il reçoit
`List<OutputFile> outputFiles` et pré-sélectionne automatiquement le premier
fichier SBOM via `didUpdateWidget`.

Paramètres :

* `List<OutputFile> outputFiles` — liste des fichiers SBOM générés
* `void Function(List<OsvVuln>)? onVulnsChanged` — callback déclenché après
  chaque analyse réussie ; `ResultsPanel` l'utilise pour alimenter `DashboardPanel`
* `CveDateFilter dateFilter` — filtre temporel courant, transmis depuis `ResultsPanel`
* `void Function(CveDateFilter)? onDateFilterChanged` — callback à chaque modification
* `void Function(CveDateFilter)? onPropagate` — copie le filtre vers Grype et Trivy

Structure interne :

* `_ConfigSection` — `ToolVersionBadge` (voir <<sec-version-service>>) +
  `ScanSourceToggle` (voir <<sec-vuln-shared>>) qui bascule entre le champ
  "Fichier SBOM" et `ImageRefField(allowOciDir: false)`, puis "Config toml"
  (avec `SplitPickButton`)
* Bannière de résultat (vert / jaune / orange / rouge selon sévérités)
* `TabController` à 2 onglets internes : *Vulnérabilités* et *JSON brut*

`_OsvPanelState` appelle `VersionService.checkOsv()` dans `initState()`,
identique au pattern Grype. `_sourceKind` (`ScanSourceKind`, voir
<<sec-scan-image>>) détermine si `_analyze()` appelle `_runner.run()` avec
`useImage: false` (fichier `_fileCtrl`) ou `useImage: true` (référence
`_imageCtrl`) ; en mode image, la validation d'existence locale
(`File(target).existsSync()`) n'est appliquée que si `looksLikeLocalPath(target)`
est vrai, pour ne pas rejeter une référence de registre comme `nginx:latest`.

L'onglet Vulnérabilités affiche `VulnTableView<OsvVuln>` (voir <<sec-vuln-shared>>
pour le composant partagé) instancié avec `toolName: 'OSV-Scanner'`,
`csvHeader`/`csvRow` propres aux colonnes OSV, `extraColumnHeader:
'ÉCOSYSTÈME'`.

`OsvVuln` est un modèle de données parsé depuis le JSON OSV :
`results[].packages[].vulnerabilities[]`. La sévérité est extraite depuis
`database_specific.severity` ou calculée depuis les scores CVSS v2/v3.
La version corrigée est lue depuis `affected[].ranges[].events[].fixed`.
Les champs de date :

* `publishedDate` (`DateTime?`) — depuis `v['published']` (ISO 8601 → UTC)
* `modifiedDate` (`DateTime?`) — depuis `v['modified']`

La méthode statique `_normalizeSeverity(String s)` normalise les libellés
de sévérité hétérogènes retournés par les différentes bases de données OSV :

[cols="1,1", options="header"]
|===
|Valeur brute (exemples) |Valeur normalisée

|`CRITICAL`
|`Critical`

|`HIGH`
|`High`

|`MEDIUM`, `MODERATE` (GitHub Advisory, npm)
|`Medium`

|`LOW`, `NONE`
|`Low`

|Tout autre valeur
|`Unknown`
|===

Sans cette normalisation, `MODERATE` apparaissait tel quel dans le tableau
et les chips de filtrage par sévérité étaient absentes (clé introuvable dans
`_severityOrder` en titre case).

==== `widgets/cra_panel.dart` — Onglet Conformité CRA

`CraPanel` (`StatefulWidget`) pilote la sous-commande CLI
`sbom-generator cra` — rapport de conformité *Cyber Resilience Act*
(Règlement (UE) 2024/2847), périmètre vérifiable automatiquement uniquement.
Comme les autres panneaux qui dépendent du binaire, il **ne porte pas** la
logique d'analyse (celle-ci vit dans `lib/cra_report.dart` côté CLI) : il
construit une ligne de commande et exécute
`Process.run(SettingsService.cliBinary, [...])`.

Paramètre : `List<OutputFile> outputFiles` — la liste des SBOM générés, pour
pré-remplir le champ « Fichier SBOM » (`.cdx.json` / `.spdx.json` en
priorité, sinon `.json` ; jamais un `.pdf`).

État de `_CraPanelState` : sept `TextEditingController` (SBOM + six
métadonnées produit), `String? _configPath` (fichier `cra.yaml`), `bool
_scan` (défaut `true`), `String _scanner` (défaut `grype`), plus
`_running` / `_error` / `Map<String, dynamic>? _result`.

* `_run()` — `cra --sbom <p> --format json` (+ `--scan`/`--no-scan`,
  `--scanner`, `_metaArgs()`). Le JSON est lu sur `stdout` *même si*
  `exitCode == 2` (rapport non conforme) ; seul un `stdout` ne commençant
  pas par `{` est traité comme une erreur. Les clés JSON sont stables et
  jamais traduites (y compris les clés NTIA et l'`id` des `fieldChecks`) : le
  panneau traduit les libellés affichés à partir de ces identifiants.
* `_exportPdf()` — `FilePicker.saveFile` puis `cra ... --format pdf -o
  <path>` ; `exitCode` 0 ou 2 = succès (fichier écrit).
* `_metaArgs()` — n'ajoute `--manufacturer` / `--product` /
  `--product-version` / `--support-until` / `--vuln-contact` /
  `--cvd-policy-url` que pour les champs non vides, plus `--config` si un
  `cra.yaml` est chargé.

`_CraResultView` (privé) rend le JSON : bandeau de verdict
(`verdict` / `verdictSentence`), quatre tuiles KPI (`sbom.fieldChecks`
« ok », `ntiaMinimumElements` « ok » / 7, `vulnerabilities.withoutFix`,
`vulnerabilities.activelyExploited`), liste `blockers`, `Table` des
`fieldChecks` (champ / couverture / statut), rappel format + composants +
relations de dépendance.

Test : `test/cra_panel_test.dart` (rendu du formulaire, auto-remplissage du
SBOM, présence des boutons, dépliage des métadonnées).

`QualityPanel` est un `StatefulWidget` autonome avec `AutomaticKeepAliveClientMixin`.
Il lance deux outils en parallèle via `Future.wait` :

|Outil |Commande

|`sbomqs`

==== `widgets/dashboard_panel.dart` — Onglet Tableau de bord

`DashboardPanel` est un `StatefulWidget`. Il reçoit les résultats des trois
scanners en paramètre (valeur `null` = scanner pas encore exécuté), plus la
map `exploitById` fusionnée par `ResultsPanel` depuis les trois onglets :

[source,dart]
----
class DashboardPanel extends StatefulWidget {
  final List<GrypeVuln>? grypeVulns;
  final List<OsvVuln>?  osvVulns;
  final List<TrivyVuln>? trivyVulns;
  final Map<String, ExploitInfo> exploitById;
}
----

Ces listes sont stockées dans l'état de `ResultsPanel` et transmises ici.
`_DashboardPanelState` ne tient que l'état de tri de la comparaison
inter-scanners (`_CrossSort? _crossSort`, `bool _crossSortAsc`) ; le reste est
calculé à chaque `build()`.

Structure :

* `_GlobalSummary` — bandeau : nombre de scanners exécutés, nombre de CVE
  *uniques* tous scanners confondus (`allIds.length`, union complète — voir
  ci-dessous), et le bouton d'export AsciiDoc + PDF (`onExport`, `null` tant
  qu'aucun scanner n'a tourné)
* `_ScannerCard` × 3 — une carte par scanner avec `_SeverityBar` (barres
  empilées `Expanded(flex: N)` colorées) et `_SevRow` (un rang par sévérité)
* `_CrossScannerSection` (`StatefulWidget`, tient le `Set<String> _expanded`) —
  liste complète des CVE vues par *au moins un* scanner (pas seulement celles
  communes à plusieurs — c'est justement en gardant les CVE isolées qu'on
  repère les écarts de détection entre scanners). Colonnes triables via
  `SortHeader` : SÉV. / CVE-ID / (KEV / EPSS si enrichissement) / Grype ✓ /
  OSV ✓ / Trivy ✓ + chevron. Le tri est appliqué par la fonction pure
  `_sortCrossRows(rows, _CrossSort, asc, exploitById)` (colonnes `severity`,
  `cveId`, `grype`/`osv`/`trivy` = présence d'abord, `kev` = priorisation
  risque KEV→EPSS→sévérité, `epss` = score) — **partagée avec l'export** pour
  que le PDF reflète l'ordre affiché. Défaut : `kev` si enrichissement, sinon
  `severity`. Une CVE vue par un seul scanner (`isIsolated`) porte un marqueur
  ambre. Cliquer une ligne déplie un `CveDetailPanel` construit par
  `_crossCveDetail(id, …)` (agrège les vues des 3 scanners + `ExploitInfo`).

Toutes les entrées sont affichées via un `for` loop dans un `Column` ; le défilement
est assuré par le `SingleChildScrollView` qui enveloppe l'ensemble du `DashboardPanel`.

NOTE: `DashboardPanel` ne lance aucun processus externe pour les scans
eux-mêmes — c'est un widget de visualisation pure qui consomme les données
déjà parsées par les autres panels. Il lance en revanche `asciidoctor-pdf`
pour la conversion PDF de son propre export (voir ci-dessous).

NOTE: Un nombre élevé de lignes `isIsolated` n'est pas le signe d'un bug
dans un des runners — c'est un comportement attendu des outils externes.
Sur l'écosystème Java, Grype identifie ses trouvailles par `GHSA-*`
(GitHub Security Advisories, sa source principale pour ce langage) alors
que Trivy préfère l'identifiant CVE correspondant : `_crossScannerRows`
compare des chaînes brutes (`vulnerability.id` / `VulnerabilityID`), donc
la même vulnérabilité sous deux alias apparaît comme deux lignes isolées
distinctes plutôt qu'une seule ligne partagée. Le reste de l'écart
(quelques CVE de chaque côté même après résolution des alias) vient de la
fraîcheur/couverture des bases de vulnérabilités respectives (Anchore DB
pour Grype, `trivy-db` pour Trivy) — voir l'explication utilisateur
détaillée avec chiffres réels dans `user.adoc`, section « Pourquoi Grype,
OSV-Scanner et Trivy ne trouvent pas les mêmes CVE ». Aucune résolution
d'alias GHSA↔CVE n'est effectuée côté GUI :
le tableau reflète fidèlement le vocabulaire de chaque scanner.

`_crossScannerRows` normalise en revanche un autre cas de nomenclature :
OSV-Scanner préfixe certains de ses avis Debian par l'origine
(`DEBIAN-CVE-2026-13221`) là où Grype/Trivy rapportent le CVE nu
(`CVE-2026-13221`). `_normalizeVulnId(id)` — `RegExp(r'^[A-Z]+-(CVE-\d{4}-\d+)$')`
appliquée à chaque ID avant construction des sets/maps `grypeIds`/`osvIds`/
`trivyIds` (et au calcul de `allIds` dans `DashboardPanel.build()`) — réduit
`PREFIXE-CVE-xxxx-xxxxx` à `CVE-xxxx-xxxxx`. Motif générique plutôt qu'une
liste de préfixes en dur : couvre aussi UBUNTU-/ALPINE-/etc. si un scanner
les produit. Vérifié empiriquement sur une image Debian réelle : 90 des 95
ID `DEBIAN-CVE-xxxx` d'OSV-Scanner correspondaient à un ID Grype et 94 à un
ID Trivy une fois le préfixe retiré — 200 lignes de comparaison avant
normalisation, 106 après.

NOTE: Deux autres écarts, plus sévères que la nomenclature, affectent
spécifiquement les paquets OS (Debian/Alpine/RPM) et expliquent des écarts
de comptage bruts massifs entre scanners que `_normalizeVulnId` ne touche
pas. **OSV-Scanner peut tomber à 0 CVE sur un SBOM alors qu'il en trouve
des centaines sur la même image scannée directement.** Pour Debian, deux
causes, toutes deux corrigées par le backend syft du CLI `sbom-generator`
(que la GUI invoque pour produire les SBOM — la GUI en bénéficie donc) :
(1) le qualifiant `distro` — OSV-Scanner ne rattache un `pkg:deb/debian/...`
à `Debian:<n>` que si `distro` vaut `debian-<majeur>` ou si `distro_name`
porte un nom de code connu, or syft renseigne le *point release*
(`distro=debian-13.6`) ; corrigé en `debian-13` + `distro_name=trixie`.
(2) binaire vs source — OSV.dev indexe les avis Debian par paquet *source*
(`zlib`, `perl`), pas binaire (`zlib1g`, `perl-base`) ; le backend émet donc
un composant par paquet source (comme cdxgen) et retire `upstream=` du
binaire. Voir `../../doc/developer.adoc`, sections « Paquets source » et
« Normalisation du qualifiant `distro` Debian ». Sur `haproxy:3.4.4`,
OSV-Scanner passe de ~19 à 58 CVE Debian. Reste hors de portée : Alpine/RPM
(OSV.dev les indexe mal en mode « scan de SBOM ») et `osv-scanner scan
image` (extraction interne, sans purl) plus exhaustif sur l'OS de base —
sur une image Debian réelle (79 paquets), 233 CVE via `scan image`.
**Grype et Trivy
n'ont par ailleurs pas la même exhaustivité sur les paquets OS Debian**
(207 correspondances Grype contre 27 Trivy sur le même SBOM, alors que les
deux utilisent leur matcher distro dédié — `dpkg-matcher` côté Grype,
donc pas un artefact de matching CPE) : Grype reprend l'intégralité du
Debian Security Tracker y compris les avis `<no-dsa>` (won't-fix) et
`not-fixed`, là où Trivy ne remonte qu'un sous-ensemble plus restreint —
confirmé sur `security-tracker.debian.org` pour `CVE-2026-19499`/`glibc`
(listée « vulnerable », `<no-dsa> (Minor issue)` : présente chez Grype en
`fix.state=wont-fix`, absente chez Trivy). Détail et méthode de
vérification complète dans `user.adoc`, section « Pourquoi Grype,
OSV-Scanner et Trivy ne trouvent pas les mêmes CVE ».

===== Seuil de sévérité du rapport (`ReportSeverityThreshold`)

`enum ReportSeverityThreshold { critical, high, medium, all }` (libellé +

===== `_crossScannerRows` / `_exportDashboard` — export AsciiDoc + PDF

Contrairement à `VulnTableView` (grype/osv/trivy_panel.dart, voir
<<sec-vuln-shared>>), le tableau de bord n'a pas de liste ligne-par-ligne
unique, filtrable/triable, à exporter : c'est une vue composite (résumé +
3 cartes + tableau croisé). L'export reproduit donc l'intégralité de ce qui
est affiché à l'écran plutôt qu'une sélection filtrée.

`_crossScannerRows(grypeVulns, osvVulns, trivyVulns)` — fonction top-level
(pas une méthode de `_CrossScannerSection`) qui calcule l'union triée des
CVE avec leur présence par scanner, sous forme de `typedef _CrossRowData
= ({String id, String severity, bool inGrype, bool inOsv, bool inTrivy})`.
Extraite du corps de `_CrossScannerSection.build()` pour être appelée aussi
par `_exportDashboard`, garantissant que le rapport exporté correspond
exactement au tableau affiché (aucune logique dupliquée entre les deux).

`_exportDashboard(context, {scansRun, uniqueIds, grype, osv, trivy,
crossRows, exploitById, crossSortCol, crossSortAsc})` construit le rapport
AsciiDoc : `== Résumé global`, `== Outils` (voir <<sec-pdf-report>>),
`== Répartition par scanner` (un `=== <Nom>` par scanner avec sa barre
`buildSeverityBarSvg`/`svgImageMacro` et son décompte par sévérité via
`DashboardPanel._countByKey`), `== Comparaison inter-scanners` — `crossRows`
trié par `_sortCrossRows` avec la colonne de tri **active à l'écran**
(`crossSortCol`/`crossSortAsc`), colonnes KEV / EPSS ajoutées si
`exploitById` non vide —, puis `== Détail des CVE` : un bloc
`=== CVE-xxxx` par ligne de la comparaison (déjà filtrée par le seuil du
rapport via `filterForReport`, KEV toujours incluses — pas de second
filtre), rendu par `CveDetail.toAdocRows(adocEscape)`
(<<sec-cve-detail-widget>>). Suit ensuite le même patron que
`_VulnTableViewState._exportAsciiDoc()` : écriture du `.adoc` via
`FilePicker.saveFile`, conversion via `runAsciidoctorPdf`, retour `SnackBar`.

==== `widgets/sbom_diff_panel.dart` — Onglet Comparaison SBOM

`SbomDiffPanel` est un `StatefulWidget` avec `AutomaticKeepAliveClientMixin`.

Les modèles de parsing sont dupliqués depuis `sbom_tree_panel.dart` (privés `_`),
y compris `_spdx3()` pour le SPDX 3.0 JSON-LD. Cette duplication est
intentionnelle : les deux panels peuvent diverger dans leurs besoins de
parsing, et évite une dépendance publique.

Algorithme de comparaison (`_computeDiff`) :

[source,dart]
----
List<_DiffEntry> _computeDiff(_SbomInfo a, _SbomInfo b) {
  // clé = _diffKey(c) : purl sans version (jusqu'au dernier '@') si présent,
  //   sinon "name.toLowerCase():type.toLowerCase()" — alignée sur
  //   SbomDiffer._componentKey() côté CLI (lib/sbom_diff.dart) pour que les
  //   deux comparaisons produisent le même résultat sur un même couple de
  //   fichiers.
  // construit mapA / mapB
  // union des clés → pour chaque clé :
  //   absente de A → added
  //   absente de B → removed
  //   version ou licence différente → changed
  //   sinon → unchanged
  // trie : added/removed/changed avant unchanged, puis par nom
}
----

NOTE: Avant cette clé purl-first, `_computeDiff` indexait par
`name.toLowerCase()` seul, ce qui produisait un résultat différent de la
sous-commande `diff` du CLI (purl-first) sur un renommage de paquet avec
purl identique (faux Ajouté+Supprimé au lieu d'un seul Modifié). Corrigé.
La logique de clé elle-même (`_componentKey`) est couverte côté CLI par
`test/unit/sbom_diff_test.dart` ; aucun test widget dédié côté GUI (voir
<<sec-file-io-tests>>).

Statuts :

[source,dart]
----
enum _Status { added, removed, changed, unchanged }
----

Sous-widgets :

* `_FileSelectorBar` — deux `_FileSlot` (champ + 📂) + bouton *Comparer*
  (actif uniquement si les deux fichiers sont chargés)
* `_SummaryBar` — 4 compteurs colorés (vert ajoutés / rouge supprimés /
  orange modifiés / gris inchangés)
* `_FilterBar` — `_FilterChip2` toggle par statut + champ de recherche ;
  les composants *Inchangés* sont masqués par défaut
* `_DiffHeader` — en-têtes de colonnes
* `_DiffRow` — fond et bordure gauche colorés selon statut ;
  pour les composants modifiés : version et licence affichés avec
  `TextDecoration.lineThrough` (ancienne valeur) + texte vert (nouvelle valeur)

==== `widgets/sbom_merge_panel.dart` — Onglet Fusion SBOM

`SbomMergePanel` est un `StatefulWidget` avec `AutomaticKeepAliveClientMixin`.
Contrairement à `SbomDiffPanel`/`SbomTreePanel`/`SbomViewerPanel`, ce panel
ne parse pas lui-même le contenu des SBOM : il se contente de collecter une
liste de chemins de fichiers et de déléguer la fusion au binaire CLI via

État de `_SbomMergePanelState` :

* `List<String> _inputFiles` — chemins des fichiers à fusionner (ajout via

==== `widgets/sbom_licenses_panel.dart` — Onglet Licences SBOM

`SbomLicensesPanel` est un `StatefulWidget` avec `AutomaticKeepAliveClientMixin`,
construit sur le même modèle que `SbomMergePanel` (<<sec-merge-panel>>) : pas
de parsing local du SBOM, délégation complète à `sbom-generator licenses`
via `SbomRunner`.

Le panneau a deux fonctions :

* *Visualisation* : à la sélection d'un fichier, `_selectFile()` appelle
  `loadLicensesViaCli()` (`licenses -f json -o <fichier temporaire>`, lu puis
  supprimé — la sortie standard mêle progression et journal) et parse le
  résultat en `LicenseReportData` (`models/license_report.dart`). Le paramètre
  `loader` du widget permet de remplacer ce chargement dans les tests. La GUI
  ne classifie rien : catégories copyleft et regroupements viennent du CLI.
  Deux vues (`_View.grouped` : `ExpansionTile` par licence ; `_View.table` :
  lignes triables par colonne), badges par catégorie, filtre texte
  (`LicenseReportData.filter`, insensible à la casse, sur la licence ou le
  paquet).
* *Rapport* (bas de page) : format au choix (`_ReportFormat` : asciidoc,
  markdown, html, csv, json → `-f`). `_setFormat()` adapte l'extension du
  fichier de sortie tant qu'elle correspond à celle du format précédent.

État de `_SbomLicensesPanelState` :

* `String? _inputFile` — chemin du fichier source unique (contrairement à
  `SbomMergePanel`, un seul fichier en entrée, pas de liste)
* `_outputCtrl`, `_nameCtrl` — contrôleurs de texte pour `-o`/`-n`
  (`_outputCtrl` initialisé à `licences.adoc`)
* `_running`, `_exitCode`, `_resultPath`, `_logLines` — même rôle que dans
  `SbomMergePanel`

`_runLicenses()` construit les arguments `['licenses', '-i', _inputFile!,
'-f', format, '-o', outputPath, if (nom) '-n', nom]`. Le bouton *Générer* est actif
uniquement si `_inputFile != null` et `_outputCtrl.text` non vide.

`_sbomFiles` (fichiers proposés dans le menu *Fichiers générés*) filtre
`widget.outputFiles` sur les trois extensions SBOM lisibles par `licenses`
(`.cdx.json`, `.spdx.json`, `.spdx3.jsonld`) — contrairement à
`SbomMergePanel` qui exclut `.spdx3.jsonld` (SPDX 3.0 non supporté en entrée
pour `merge`), `licenses` accepte les trois formats comme `diff`.

==== `models/layer_nav.dart` + `widgets/layer_selector.dart` — SBOM par couche

Navigation dans un jeu produit par `sbom-generator --per-layer` (global
`<base><ext>`, couches `<base>.layer-NN-<digest12><ext>`), partagée par
l'Arborescence et la Visionneuse :

* `LayerNav.discover(path)` — liste le répertoire du fichier, retrouve les
  couches du même jeu (même base, même extension ; pour un global sans
  extension — sortie à format unique nommée sans suffixe — toute extension
  lisible, `.cdx.json` d'abord) et le global depuis une couche. `null` si le
  fichier n'appartient à aucun jeu. Le lien se fait *par le nom*, pas par le
  contenu : il fonctionne pour les trois formats lisibles.
* `LayerDocInfo.fromSbom(json)` — description à afficher : propriétés
  `sbom_generator:layer:*` / `sbom_generator:layers:NNN` du composant racine
  CycloneDX (`layerLabels` : compteurs + instruction par couche,
  `removed`), commentaire du document en SPDX 2.3 / 3.0.
* `readLayerLabels(globalPath)` — relit les libellés depuis le global quand
  on ouvre directement une couche.
* `layerFieldsOf(component)` — champs de couche d'un composant : propriétés
  CycloneDX, `annotations[].comment` (SPDX 2.3) ou `annotation[].statement`
  (SPDX 3.0), motif `sbom_generator:layer:<clé>=<valeur>`. Ces textes sont
  des *contrats machine* écrits par le CLI : ils restent en français et ne
  sont jamais traduits ; la GUI traduit leur affichage à partir des valeurs
  lues.
* `layerColumnLabel` / `layerGroupKey` — libellé de colonne et clé de
  regroupement (`Couche 01`… triables, `Ajoutés` / `Modifiés`).
* `isLayerSbomFile(path)` — exclut les SBOM de couche des sélections
  automatiques.

`LayerSelector` (sans état) : `DropdownButton` *SBOM global / Couche i/N
(digest) + libellé*, lignes de `LayerDocInfo.lines`, badge des supprimés
(info-bulle). Il n'ouvre rien lui-même : il appelle `onOpen(path)`.

Les trois onglets de scan de vulnérabilités affichaient jusqu'à une session

=== `VulnRow` — socle commun aux trois modèles de vulnérabilité

[source,dart]
----
abstract class VulnRow {
  String get id;
  String get severity;
  String get packageName;
  String get installedVersion;
  String get fixedVersion;
  DateTime? get publishedDate;
  DateTime? get modifiedDate;
  int get occurrenceCount;   // 1 = pas de fusion, voir dedupeVulns ci-dessous
}
----

`GrypeVuln`, `OsvVuln` et `TrivyVuln` implémentent chacun cette interface
(`implements VulnRow`) et restent des classes séparées — conservées
distinctes plutôt qu'unifiées en une seule, car `DashboardPanel` et
`ResultsPanel` les consomment avec leur type propre (champs additionnels :
`packageType` pour Grype, `ecosystem` pour OSV, `title` pour Trivy). Chacune
porte aussi `occurrenceCount` (défaut `1`) et une méthode
`withOccurrenceCount(int n)` qui reconstruit l'instance avec un compteur
différent — utilisée uniquement par `dedupeVulns` (ci-dessous).

[[sec-dedupe-vulns]]
=== `dedupeVulns<T extends VulnRow>` — fusion des doublons visuels

[source,dart]
----
List<T> dedupeVulns<T extends VulnRow>(
  List<T> vulns,
  T Function(T first, int count) withOccurrenceCount,
)
----

Un même composant peut être détecté à plusieurs emplacements distincts d'une
image/d'un SBOM — ex. `jackson-databind` présent en jar autonome *et*
reshadé (embarqué) dans un fat jar comme `keycloak-admin-cli-*.jar` — avec
exactement la même sévérité, le même identifiant de vulnérabilité, le même
nom de paquet et la même version installée. `GrypeVuln`/`TrivyVuln` ne
portant pas de champ « chemin », ces deux entrées légitimes et distinctes du
scanner sont, à l'écran, visuellement indiscernables ; sans fusion elles
apparaissent comme des doublons.

`dedupeVulns` regroupe par la clé `(severity, id, packageName,
installedVersion)`, jointes avec un octet NUL (`\u0000`) plutôt qu'un
simple espace pour éviter toute collision si un champ contenait un
espace, et conserve la première occurrence rencontrée, dont
`withOccurrenceCount` reconstruit une copie avec le nombre d'occurrences
fusionnées. L'ordre de première apparition est préservé (`Map` de Dart,
insertion-ordered).

Chaque panneau appelle `dedupeVulns` immédiatement après le parsing JSON,
avant `setState()` :

[source,dart]
----
final raw = GrypeVuln.fromJson(jsonOutput);
final vulns = dedupeVulns(raw, (v, n) => v.withOccurrenceCount(n));
setState(() { _jsonOutput = jsonOutput; _vulns = vulns; });
widget.onVulnsChanged?.call(_vulns);
----

Ce point d'insertion unique suffit à propager la fusion *partout* sans
logique supplémentaire ailleurs : `_vulns.length` (label d'onglet, bannière
de synthèse), les compteurs par sévérité dans `VulnTableView` (calculés sur
`widget.vulns`), les exports CSV/AsciiDoc (`_filtered` dérive de
`widget.vulns`) et `DashboardPanel` (alimenté via `onVulnsChanged`) reçoivent
tous la liste déjà fusionnée. Seule la vue JSON brut (`_jsonOutput`, non
touchée) reste fidèle à la sortie complète et non fusionnée de l'outil —
choix délibéré pour garder un canal de données 100% fidèle à des fins de
débogage.

Le badge *×N* affiché dans `VulnTableView` (à côté de l'identifiant, visible
dès que `occurrenceCount > 1`) porte un tooltip expliquant la fusion.

[[sec-scan-source-widgets]]
=== `ScanSourceToggle` / `ImageRefField` / `looksLikeLocalPath`

Composants partagés par les trois panneaux pour le scan d'image de
conteneur (voir <<sec-scan-image>> côté runners) :

* `enum ScanSourceKind { sbomFile, image }` — état de la bascule, tenu dans
  chaque `_XxxPanelState._sourceKind`.
* `ScanSourceToggle` — `SegmentedButton<ScanSourceKind>` à deux segments
  ("Fichier SBOM" / "Image de conteneur"), style compact.
* `ImageRefField` — champ de saisie de la référence d'image, avec deux
  boutons `IconButton.outlined` : archive locale (`.tar`/`.tar.gz`/`.tgz`,
  toujours proposé) et répertoire OCI layout (proposé seulement si
  `allowOciDir: true`, valeur par défaut ; `osv_panel.dart` passe `false`
  car osv-scanner ne sait pas lire un tel répertoire). Le label du champ
  (`HelpLabel`) et le `hintText` adaptent leur contenu à `allowOciDir`.
* `bool looksLikeLocalPath(String s)` — heuristique (`s.startsWith('/')`,
  `'./'`, `'../'` ou `'~'`) utilisée côté panneaux pour décider si la
  validation d'existence locale (`File(...).existsSync()`) s'applique avant
  de lancer l'analyse ; une référence de registre comme `nginx:latest` ne
  la déclenche pas.

Ces trois éléments ne portent aucune logique de commande : le choix entre
"registre / archive / répertoire OCI" et sa traduction en arguments CLI
reste dans chaque `*_runner.dart` (voir <<sec-scan-image>>), pas ici.

* `LayerScanOptions` — case *Par couche* + `SegmentedButton`
  Rattachement / Chaque couche et Métadonnées / Rootfs, liée à un
  `LayerScanSettings` tenu par chaque panneau (`_layerSettings`), affichée
  sous le champ image. `ScanStatusLine` affiche l'étape en cours sous la
  barre de progression.

* Chaque panneau fournit `_cliSections()` (paramétrage courant, lu au clic)

=== Analyse par couche — `models/layer_scan.dart` + `services/layer_scan_service.dart`

* `LayeredSbomSet.parse(globalPath, json)` — jeu produit par
  `sbom-generator --per-layer` : `layerByPackage` (`nom@version` → couche,
  depuis `sbom_generator:layer:index`), couches (`LayerInfo` : index,
  digest, instruction depuis `sbom_generator:layers:NNN`, chemin du SBOM de
  couche via `LayerNav.discover`). `layerOf(nom, version)` (repli sur le nom
  seul s'il est univoque), `layerOfDigest(digest)` (digest complet, puis
  préfixe court lu dans le nom de fichier).
* `vulnLayerKey(id, paquet, version)` — clé commune aux lignes brutes et
  dédupliquées (`dedupeVulns` fusionne sur les mêmes champs + sévérité) :
  les couches sont portées par une map `LayerScanResult.layersByKey` plutôt
  que par les trois modèles `GrypeVuln` / `OsvVuln` / `TrivyVuln`.
* `mergeGrypeJson` / `mergeOsvJson` / `mergeTrivyJson` — fusion des sorties
  du mode « chaque couche » en un document au format natif (concaténation
  de `matches` / `results` / `Results`) : `fromJson`, la vue JSON et
  l'enrichissement (`seedsFrom…Json`) s'appliquent sans changement.
* `trivyLayerDigests` (`Layer.DiffID`) / `osvLayerDigests`
  (`image_origin_details.index` → `image_metadata.layer_metadata[i].diff_id`)
  — couche native d'une sortie de scan d'image, prioritaire en
  rattachement. Nécessaire pour OSV-Scanner, qui rapporte le paquet
  *source* (`expat`) là où le SBOM porte le binaire (`libexpat`).
* `LayerScanService.prepare(image, layerMode)` — lance le CLI
  (`SettingsService.cliBinary --image … --oci-tool syft --per-layer
  --layer-mode … -f cyclonedx`) dans un répertoire temporaire ; résultat
  mis en cache par (image, mode) pour la session (les trois onglets le
  partagent), un échec n'est pas mis en cache. `kill()` interrompt la
  génération (bouton *Stop*).
* `LayerScanService.run(image, settings, scanOnce, parse, merge,
  nativeDigests?, onStatus?, isCancelled?, prepareSet?)` — orchestre les
  deux méthodes ; chaque panneau fournit `_scanOnce(target, useImage)`
  (son runner consommé jusqu'à l'événement de fin, via `_start`, qui porte
  les options du panneau), son `fromJson` et sa fonction de fusion.
  `prepareSet` remplace `prepare` dans les tests. Le service ne renvoie jamais
  de phrase affichée : il signale une étape typée `LayerScanStep` que
  l'interface traduit.

Chaque panneau (`_analyze`) bascule sur `_analyzeLayered` quand la source
est une image et `_layerSettings.enabled` ; le résultat est remonté par
`onLayerScanChanged` (`null` pour un scan sans couches) à `ResultsPanel`,
qui tient `_layerScans` (clé : nom du scanner) et le passe au tableau de
bord.

=== Export CSV et AsciiDoc + PDF

Deux boutons dans la barre d'outils, tous deux désactivés si `_filtered` est
vide :

* *Export CSV* (`Icons.download_outlined`) — `_exportCsv()` : écrit
  `csvHeader` puis une ligne par élément de `_filtered` via `csvRow`,
  échappement RFC 4180 (`csvEscape`), chemin choisi via
  `FilePicker.saveFile(...)`. `_filtered` dérive de `widget.vulns`, déjà
  fusionné par `dedupeVulns` (voir <<sec-dedupe-vulns>>) : chaque panneau
  ajoute une colonne « Emplacements » à `csvHeader`/`csvRow` reportant
  `v.occurrenceCount`. L'en-tête CSV n'est *pas* traduit (lu par des
  programmes).
* *Export AsciiDoc + PDF* (`Icons.picture_as_pdf_outlined`) — `_exportAsciiDoc()` :
  écrit un rapport AsciiDoc sur `_filtered` (donc après filtres
  sévérité/recherche/date, comme le CSV), dans la langue de l'interface
  (`AppLocalizations l`, transmis aux générateurs) — résumé chiffré (décompte par
  sévérité, chaque libellé passé à `pdfSeverityBadge` + barre
  `buildSeverityBarSvg`/`svgImageMacro`, filtre de date appliqué le cas
  échéant), section `== Outils` (`pdfToolVersionRow('sbom_generator_gui',
  kGuiVersion)` puis `pdfToolVersionRow(widget.toolName,
  await _toolVersionFor(widget.toolName))` — voir <<sec-pdf-report>>) suivi
  d'un tableau détaillé dont les colonnes sont dérivées de
  `csvHeader`/`csvRow` (pas de paramètres AsciiDoc dédiés : le CSV et
  l'AsciiDoc partagent la même description de colonnes ; seule la première
  cellule — la sévérité — passe par `pdfSeverityBadge` au lieu d'`adocEscape`
  brut). Une fois le `.adoc` écrit, tente automatiquement
  `runAsciidoctorPdf(path, pdfPath)` (voir <<sec-pdf-report>>) — silencieux
  si l'outil est absent (`catch` générique, message dans le `SnackBar` de
  résultat) ou en échec (code retour non nul rapporté, `.adoc` conservé) ;
  même philosophie que `HomeScreen._generatePdf()` (conversion PDF du
  rapport SBOM principal, qui elle n'utilise pas le thème coloré — voir
  <<sec-pdf-report>>), en plus compact car il n'y a pas de journal
  persistant à alimenter — tout le retour utilisateur passe par le
  `SnackBar`. `adocEscape(s)` échappe uniquement `|` (ambigu en tête de
  cellule AsciiDoc) — plus simple que `csvEscape` car les valeurs exportées
  (sévérité, CVE, nom de paquet, version) ne contiennent ni retour à la
  ligne ni guillemet à échapper en pratique.

[[sec-pdf-report]]
=== `widgets/pdf_report.dart` — thème et helpers PDF partagés

Habillage visuel commun à `_VulnTableViewState._exportAsciiDoc()`
(ci-dessus) et `_exportDashboard` (<<sec-dashboard-export>>), pour que les
deux exports se ressemblent et ressemblent à l'écran plutôt que de produire
chacun un PDF noir et blanc par défaut :

* `kGuiVersion` — constante de version de la GUI, seul endroit à mettre à
  jour côté GUI lors d'un bump (avec `gui/pubspec.yaml`) ; `home_screen.dart`
  (dialogue « À propos ») s'y réfère aussi, au lieu d'un littéral dupliqué.
* `runAsciidoctorPdf(adocPath, pdfPath)` — écrit le thème YAML
  (`_kPdfThemeYaml`) dans le dossier temp système à chaque appel (contenu
  statique, coût négligeable), puis lance `asciidoctor-pdf` avec
  `-a pdf-theme=<chemin absolu>`. Le thème `extends: default-sans` (variante
  sans-serif fournie par asciidoctor-pdf — aucune police à embarquer) :
  palette bleu-ardoise, en-têtes de tableau foncés, page de garde
  (`:title-page:`), pied de page « `{document-title}` … Page {page-number}
  / {page-count} » avec filet, rôles `sev-*` (badges de sévérité),
  `h1-num` / `h1-num-alert` (chiffres du résumé exécutif),
  `verdict-urgent` / `verdict-watch` / `verdict-ok`.
  *Copie synchronisée* de `_kPdfThemeYaml` de
  `lib/scan_report_generator.dart` (paquet CLI) — garder les deux
  identiques.
* `pdfSeverityBadge(severity, {l})` — rend `[.sev-xxx]#LIBELLÉ#` avec le
  libellé traduit par `frenchSeverityLabel(severity, l: l)` (CRITIQUE /
  ÉLEVÉE / MOYENNE / FAIBLE en français, CRITICAL / HIGH / MEDIUM / LOW en
  anglais ; le nom de la fonction est historique).
  Seuils identiques à `severityFg`/`severityBg` (ce fichier, plus haut).
* `pdfFrenchDate(DateTime, {l})` — date longue dans la langue du rapport
  (« 8 septembre 2026 » / « 8 September 2026 ») pour l'attribut `:revdate:`
  de l'en-tête, sans dépendance `intl`.
* `buildSeverityBarSvg(countsBySeverity)` / `svgImageMacro(svg)` —
  reproduisent `_SeverityBar` (`dashboard_panel.dart`) : segments
  proportionnels Critical/High/Medium/Low/Autre, mêmes couleurs, mêmes
  coins arrondis. Construite en SVG et embarquée en data URI
  (`image::data:image/svg+xml;base64,...[]`) plutôt qu'en cellules de
  tableau à fond coloré : l'attribut AsciiDoc `{set:cellbgcolor:...}`,
  technique documentée pour colorer une cellule, s'est révélé non honoré
  par le thème par défaut d'asciidoctor-pdf 2.3.24 lors des tests — le SVG
  en data URI, lui, ne nécessite aucun fichier temporaire supplémentaire.
* `grypeVersion()` / `osvScannerVersion()` / `trivyVersion()` — lancent
  respectivement `grype version`, `trivy --version`, `osv-scanner --version`
  et extraient le numéro via une regex ancrée en début de ligne (`^Version:`
  pour grype/trivy — qui ancre aussi bien la première ligne non indentée que
  la version, sans capturer les versions de bases indentées qui suivent
  chez trivy —, `^osv-scanner version:` pour osv-scanner). Exécutées au
  moment de l'export, pas au moment du scan : reflète la version réellement
  installée même si l'outil a été mis à jour depuis. Retournent `null`
  (`try`/`catch` générique) si l'outil est absent du `PATH` ou si la sortie
  ne correspond pas au format attendu — les appelants ne doivent alors pas
  afficher la ligne "null", d'où `pdfToolVersionRow(label, version)` qui
  affiche `_indisponible_` en italique dans ce cas.

Tous les textes visibles des rapports viennent des fichiers ARB (clés `pdf*`,
`adoc*`, `rep*`, `dash*`) via un paramètre optionnel `AppLocalizations? l`
(défaut : français, ce qui laisse les tests existants inchangés) ; les exports
déclenchés depuis l'interface passent `context.l10n`.

=== `widgets/help_viewer.dart` — aide en ligne (manuel utilisateur intégré)

`HelpViewerScreen`, ouvert depuis l'icône ❓ de la barre du haut
(`home_screen.dart`), affiche le manuel utilisateur dans l'appli elle-même — `doc/user.adoc` en
français, `doc/user.en.adoc` en anglais — pas seulement l'aide contextuelle courte des icônes ❓ par champ (`HelpIcon`/
`HelpLabel`, `widgets/help_icon.dart`).

**Génération des assets (`tool/generate_help.dart`)** — à relancer
manuellement (`dart run tool/generate_help.dart` depuis `gui/`) après toute
modification de `doc/user.adoc` ou `doc/user.en.adoc` ; ses sorties sont
commitées comme des fichiers générés ordinaires, l'appli elle-même n'exécute
jamais `asciidoctor`. Pour chacun des deux guides (`user.adoc` →
`assets/help/manual/`, `user.en.adoc` → `assets/help/manual_en/`) :

* Rend le guide en HTML unique via `asciidoctor -a icons! -a toc!`
  (`icons!` : labels texte "Note"/"Astuce"… plutôt qu'une police d'icônes
  externe que `flutter_html` ne peut pas charger ; `toc!` : le sommaire est
  reconstruit côté Flutter, pas besoin de celui d'asciidoctor).
* Découpe le HTML avec `package:html` à chaque `<div class="sect1">`
  (asciidoctor enveloppe déjà chaque section `== ` de premier niveau dans
  un tel div, enfant direct de `#content` — pas besoin de redécouper
  manuellement au fil des `<h2>`) → un fichier `<n>.html` par chapitre (22
  actuellement).
* Émet `toc.json` : la liste ordonnée `{title, file}`
  pour le sommaire, et une table `id d'ancre → index de chapitre` construite
  à partir de tous les attributs `id="…"` du HTML (dont les ancres
  `[[sec-xxx]]` du `.adoc`) — permet à un renvoi interne
  (`<<sec-xxx>>`, rendu `<a href="#sec-xxx">`) de faire basculer le lecteur
  sur le bon chapitre au clic, même s'il pointe vers un autre chapitre que
  celui affiché.

Les deux répertoires sont déclarés dans `pubspec.yaml` (`assets:`). À
l'ouverture, `HelpViewerScreen` choisit `manual_en` quand la langue effective
est l'anglais (`appLocale`) et que le répertoire existe, `manual` (français)
sinon. Les ids d'ancre (`sec-…`) sont identiques dans les deux guides.

**Lecteur (`HelpViewerScreen`)** — `Scaffold` avec sommaire (recherche +
`ListView` des titres de chapitres) à gauche et contenu du chapitre
sélectionné à droite, rendu par le paquet `flutter_html` (widgets Flutter
natifs, pas de WebView — `webview_flutter` n'a pas de support desktop Linux
stable, `flutter_html` n'en a besoin d'aucun). Les chapitres (HTML +
texte brut) sont chargés une seule fois au démarrage (`_loadAll`,
`Future.wait`, ~240 Ko au total) plutôt que paresseusement à chaque
sélection : la recherche doit pouvoir scanner le contenu de tous les
chapitres sans aller-retour disque à chaque frappe. `onAnchorTap`
intercepte les clics sur les liens internes : ancre connue dans `toc.json`
→ changement de chapitre (`Navigator` non utilisé, juste un `setState` +
`ScrollController.jumpTo(0)`) ; sinon, ouverture via `url_launcher` (lien
externe). Le style (`_helpStyle`) calque les couleurs du thème Material
courant (`Theme.of(context)`), y compris en mode sombre — même principe que
le thème PDF de `pdf_report.dart` ci-dessus,
en plus simple (pas de fichier de thème séparé, juste une `Map<String, Style>`
passée au widget `Html`).

**Recherche** — un `TextField` en tête de sommaire filtre `_visibleIndices`
(titre *ou* contenu, insensible à la casse) sur le texte brut de chaque
chapitre, extrait du HTML via `package:html` (`html_parser.parse(html)
.documentElement?.text`, plus fiable qu'une regex de nettoyage de balises —
gère correctement les entités comme `&#8217;`). `_snippetFor(i)` construit un
court extrait de contexte autour de la première occurrence de la requête
(±60 caractères, `…` en tête/fin si tronqué), affiché en sous-titre du
`ListTile` du sommaire quand la correspondance vient du contenu plutôt que
du titre. Aucune mise en évidence *dans* le contenu affiché à droite ni
défilement jusqu'à l'occurrence : `flutter_html` ne rend pas de widgets
adressables individuellement (pas de clé par nœud), retrouver et surligner
un passage précis demanderait de reconstruire son propre moteur de rendu —
hors de proportion pour ce que ça apporterait.

NOTE: `flutter_html: ^3.0.0` importe une API interne
(`package:html/src/query_selector.dart`) dont la forme a changé en
`html 0.15.6+` (`Method not found: 'matches'` à la compilation) — `html` est
donc épinglé à `0.15.5` (voir le commentaire dans `pubspec.yaml`). Dépendance
directe (pas seulement transitive via `flutter_html`) : `HelpViewerScreen`
l'utilise aussi directement pour la recherche (`_stripHtml`), et
`tool/generate_help.dart` s'appuie sur la même résolution de version. À
réévaluer si `flutter_html` est mis à jour.

[[sec-l10n]]
== Localisation (FR / EN)

L'interface utilise le mécanisme standard de Flutter (`gen-l10n`) :

* `l10n.yaml` : fichiers ARB dans `lib/l10n/`, *français = langue de
  référence* (`app_fr.arb`, template), classe générée `AppLocalizations`.
* `lib/l10n/app_<langue>.arb` : un fichier par langue ; le français porte
  la description de chaque clé (`@clé.description`) et les paramètres
  (`placeholders`). Pluriels et paramètres en syntaxe ICU
  (`{count, plural, =1{…} other{…}}`) — jamais de concaténation de
  morceaux de phrase ni de « (s) ».
* `lib/l10n/app_localizations*.dart` : code *généré* (par `flutter pub get`
  ou `flutter gen-l10n`), versionné ; ne pas le modifier à la main.
* `lib/l10n/l10n.dart` : `AppLanguage` (`system` / `fr` / `en`, réglage
  mémorisé par `SettingsService.load/saveLanguage`, clé `ui_language_v1`),
  `resolveAppLocale` (langue du système si prise en charge, sinon
  français), l'extension `context.l10n`, la globale `appLocale` (locale
  effective, mise à jour par `main.dart`) et `appL10n()` pour le code sans
  `BuildContext` (services, exports). `context.l10n` retombe sur le français
  hors d'une application localisée : les tests de widgets montés sans
  délégués — la plupart des tests existants — voient donc les textes
  français sans modification.
* `main.dart` branche `localizationsDelegates`, `supportedLocales`,
  `locale` et `localeListResolutionCallback`, et `_applyLanguage` met à jour
  `appLocale` et `SettingsService.cliLang` ; `home_screen.dart` porte le menu
  de langue (clé `language-menu`).

*Ajouter un texte* : clé dans `app_fr.arb` (avec description), traduction
dans `app_en.arb`, `flutter gen-l10n`, puis `context.l10n.maCle` (ou
`l10n.maCle(param)`) dans le widget. Préfixe par zone : `common…`,
`scanSource…`, `vulnTable…`, `dateFilter…`, `layerScan…`, `cliCommand…`,
`cfg…` (panneau de configuration), `dash…`, `pdf…` / `adoc…` / `rep…`
(rapports exportés), `<onglet>…` (`grype…`). Une fonction hors widget reçoit
`AppLocalizations` en paramètre — obligatoire quand elle est appelée depuis un
widget, `{AppLocalizations? l}` optionnel (défaut : français) pour les
exports et modèles testés sans contexte (ex. `equivalentScanNote(l10n, …)`,
`pdfSeverityBadge(sev, l: l)`) ; un service ne produit jamais de phrase
affichée mais une valeur typée que l'interface traduit (ex. `LayerScanStep` →
`layerScanStepLabel`). Dans une méthode `async`, lire `final l = context.l10n;`
en début de méthode, avant le premier `await`.

*Ajouter une langue* : `lib/l10n/app_<code>.arb` avec toutes les clés, puis
une valeur dans `AppLanguage` et son libellé dans le menu.

*Tests* : `test/l10n_test.dart` vérifie que chaque fichier ARB a les mêmes
clés et paramètres que le français, que chaque clé française est
documentée, la résolution de langue, le repli et le menu ;
`test/l10n_grype_test.dart` affiche l'onglet pilote en anglais.

*Ce qui n'est pas traduit* (contrats machine, identiques quelle que soit la
langue) : les lignes du CLI analysées par la GUI (`SBOM written → …`, la
barre de progression `] n/m %`, les préfixes `Error:` / `Warning:` / `⚠` /
`   •`), les propriétés `sbom_generator:*`, les textes embarqués dans les SBOM
(y compris les textes de couches relus par la GUI), les clés JSON, les
en-têtes CSV et le contenu des fichiers lus par d'autres outils. Les messages

== Concepts Flutter pour débutant

[[sec-flutter-stateful]]
=== StatefulWidget vs StatelessWidget

Un `StatelessWidget` est immutable : ses propriétés ne changent pas après
construction. Un `StatefulWidget` possède un objet `State<T>` séparé, qui
peut appeler `setState()` pour déclencher un *rebuild* (re-rendu) du widget.

[source,dart]
----
class MyWidget extends StatefulWidget {
  const MyWidget({super.key});
  @override
  State<MyWidget> createState() => _MyWidgetState();
}

class _MyWidgetState extends State<MyWidget> {
  int _count = 0;

  @override
  Widget build(BuildContext context) {
    return Text('$_count');
  }

  void _increment() {
    setState(() => _count++);   // déclenche un rebuild
  }
}
----

Dans ce projet : `HomeScreen`, `ResultsPanel`, `ConfigPanel` et `GrypePanel`
sont tous des `StatefulWidget`.

[[sec-stream]]
=== Stream et écoute d'événements

Un `Stream<T>` est un flux asynchrone qui émet zéro, une ou plusieurs valeurs
dans le temps, puis se termine.

[source,dart]
----
final stream = SbomRunner().run(args: [...]);

stream.listen(
  (event) {
    // appelé à chaque événement
    setState(() { /* mettre à jour l'UI */ });
  },
  onError: (Object e) { /* erreur */ },
);
----

Côté `SbomRunner`, le stream est produit avec un `StreamController<T>` :

[source,dart]
----
final controller = StreamController<SbomEvent>();
// ... émettre des événements :
controller.add(SbomLogEvent('ligne de log'));
// ... terminer :
controller.close();
return controller.stream;
----

=== TabController

Un `TabController` gère l'onglet actif d'un `TabBar` / `TabBarView`.
Son `length` est fixé à la construction et *ne peut pas être modifié* (voir
<<sec-piege-tabcontroller>>).

Il est créé dans `initState()` et libéré dans `dispose()`.
Le mixin `SingleTickerProviderStateMixin` est nécessaire pour fournir
l'animation (paramètre `vsync`).

[source,dart]
----
class _MyState extends State<My> with SingleTickerProviderStateMixin {
  late final TabController _tabs;

  @override
  void initState() {
    super.initState();
    _tabs = TabController(length: 14, vsync: this);  // ResultsPanel : 14 onglets
  }

  @override
  void dispose() {
    _tabs.dispose();
    super.dispose();
  }
}
----

Pour changer d'onglet par programme : `_tabs.animateTo(index)`.

=== didUpdateWidget

`didUpdateWidget(OldWidget old)` est appelé lorsque le parent reconstruit
le widget avec de nouveaux paramètres. C'est le bon endroit pour réagir à
un changement de prop sans recréer tout l'état :

[source,dart]
----
@override
void didUpdateWidget(GrypePanel old) {
  super.didUpdateWidget(old);
  if (widget.outputFiles != old.outputFiles) {
    _updateAutoFile();   // mettre à jour le champ fichier SBOM
  }
}
----

Architecture interne :

[cols="1,3", options="header"]

== Pièges & décisions techniques

[[sec-keepalive]]
=== Préserver l'état des onglets distants (AutomaticKeepAliveClientMixin)

Par défaut, un `TabBarView` libère les widgets des onglets non visibles pour
économiser la mémoire (comportement `PageView`). Quand l'utilisateur revient
sur un onglet, son `State` est recréé depuis zéro — le fichier sélectionné,
les options et les résultats sont perdus.

La solution est `AutomaticKeepAliveClientMixin` sur le `State` de chaque panel :

[source,dart]
----
class _GrypePanelState extends State<GrypePanel>
    with AutomaticKeepAliveClientMixin {

  @override
  bool get wantKeepAlive => true;  // <1>

  @override
  Widget build(BuildContext context) {
    super.build(context);           // <2>
    // ... reste du build
  }
}
----
<1> Déclarer que cet état doit être conservé
<2> L'appel `super.build()` est obligatoire — il active le mécanisme keep-alive

Ce mixin est appliqué à `_GrypePanelState`, `_OsvPanelState`, `_TrivyPanelState`,
`_QualityPanelState`, `_SbomTreePanelState` et `_SbomDiffPanelState`.

[[sec-piege-osv-severity]]
=== Hétérogénéité des libellés de sévérité OSV

Le JSON retourné par `osv-scanner` peut contenir des valeurs de sévérité
issues de bases de données différentes, sans normalisation :

* NVD/CVE : `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`
* GitHub Security Advisory : `CRITICAL`, `HIGH`, `MODERATE`, `LOW`
* npm Advisory : `CRITICAL`, `HIGH`, `MODERATE`, `LOW`, `INFO`
* PyPI : `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`

Sans traitement, deux problèmes surgissent :

. Les chips de filtrage par sévérité disparaissent car `_severityOrder`
  utilise du titre case (`'Medium'`) mais les clés dans `counts` sont en
  majuscules (`'MODERATE'`, `'MEDIUM'`…) → `counts.containsKey('Medium') = false`.
. Les libellés `'MODERATE'` apparaissent tels quels dans le tableau au lieu
  de `'Medium'`.

La solution est `OsvVuln._normalizeSeverity()`, appliquée à la réception du
JSON (pas à l'affichage), qui mappe toutes les variantes vers les cinq
valeurs canoniques utilisées dans l'application :
`Critical`, `High`, `Medium`, `Low`, `Unknown`.

[[sec-piege-tabcontroller]]
=== TabController.length est fixe

Le `length` d'un `TabController` est immuable après création.
Pour un onglet conditionnel (visible uniquement si une condition est remplie),
deux approches :

* *Onglet toujours présent, contenu conditionnel* : c'est l'approche choisie
  pour l'onglet *Template* de `GrypePanel` — il est toujours là, mais affiche
  un hint si aucun template n'est configuré.
* *Recréer le widget avec une clé* : assigner une `Key` au widget contenant
  le `TabController` et la changer pour forcer la reconstruction complète.
  À éviter si possible car cela réinitialise tout l'état.

[[sec-piege-tmpl]]
=== Fichier temporaire pour la sortie template Grype

Grype ne peut écrire qu'une sortie sur stdout. Quand le mode template est
activé en plus du mode JSON, il faut deux canaux de sortie.

La solution retenue dans `grype_runner.dart` :

. grype est lancé avec `-o json` (stdout) *et* `-o template=/tmp/grype_tmpl_<ts>.txt`
. stdout est capturé dans `jsonBuf` (habituel)
. après l'exit du processus, le fichier temp est lu, son contenu est émis
  via `GrypeTemplateEvent`, puis le fichier est supprimé

[source,dart]
----
// Fichier temp créé avant Process.start()
final tmpFile = File('${Directory.systemTemp.path}/grype_tmpl_${ts}.txt');

// Après exitCode.then(...)
final content = await tmpFile.readAsString();
controller.add(GrypeTemplateEvent(content));
await tmpFile.delete();
----

Si grype ne supporte pas la syntaxe `-o template=<fichier>` (versions < 0.65),
une alternative est de lancer grype deux fois séquentiellement.

[NOTE]
====
Le snippet ci-dessus simplifie un détail important : `tmpFile` est en
réalité `File?` (`null` quand aucun template n'est demandé), déclaré comme
variable locale mutable puis capturé par **deux** closures imbriquées
(`Process.start(...).then((process) { … process.exitCode.then((code) async {
… }); })`). Le vérificateur de types Dart ne promeut pas de manière fiable
une variable mutable capturée à travers plusieurs closures/`await` — un test
`if (tmpFile != null && tmpFile.existsSync())` suffisait pour `.existsSync()`
juste après, mais échouait à la compilation sur `tmpFile.delete()` un peu
plus loin (`tmpFile` retombait à `File?`). Correction : rebinder dans une
variable locale `final` au point d'usage — `final tf = tmpFile; if (tf !=
null && tf.existsSync()) { … tf.delete(); }` — qui reste promue de façon
stable puisqu'elle n'est jamais réassignée.
====

=== Les préfixes machine du CLI ne se traduisent pas

La coloration du journal de `ResultsPanel` et l'analyse de `SbomRunner`
reposent sur des préfixes littéraux des lignes du CLI : `Error:`, `Warning:`,
`⚠`, `   •`, `SBOM written →`, la barre de progression `] n/m %`. Le CLI
(`lib/i18n.dart`, `tr(fr, en)`) traduit le *message* qui suit mais jamais ces
préfixes ; les traduire casserait silencieusement la coloration, le compteur
d'avertissements et la détection des fichiers produits. Il en va de même des
propriétés `sbom_generator:*` et des textes embarqués dans les SBOM, que la
GUI relit.

=== Stream vs Future pour les processus externes

`Process.run()` retourne un `Future<ProcessResult>` — pratique mais bloquant :
on n'a accès à stdout qu'après la fin du processus.

`Process.start()` retourne un `Future<Process>` depuis lequel on accède
aux streams `stdout` et `stderr` en temps réel. C'est obligatoire pour
afficher la progression ligne par ligne dans `SbomRunner`.

Pour `GrypeRunner`, le choix du stream n'est pas pour le temps réel (grype
n'affiche rien d'utile en cours de route) mais pour la cohérence
architecturale et pour pouvoir appeler `kill()` à tout moment.

=== Sélection automatique du fichier SBOM dans GrypePanel

`GrypePanel._updateAutoFile()` est appelé depuis `didUpdateWidget` quand
`outputFiles` change (après une génération réussie).

La garde `_fileCtrl.text.isNotEmpty` est essentielle : sans elle, chaque
nouvelle génération SBOM écraserait une sélection manuelle faite par
l'utilisateur dans le champ "Fichier SBOM" de l'onglet Grype.

La priorité de sélection automatique :

. `.cdx.json` ou `.spdx.json` (formats reconnus par grype nativement)
. `.json` ou `.jsonld` (fallback)

=== unawaited(process.stdin.close())

Après `Process.start()`, le stdin du processus fils reste ouvert.
Certains processus attendent la fermeture de stdin avant de démarrer.
L'appel `process.stdin.close()` retourne un `Future<void>` qu'on ne veut
pas `await`er (on ne veut pas bloquer le stream).

`unawaited()` de `dart:async` marque explicitement ce Future comme
intentionnellement ignoré, ce qui supprime le warning Dart.

[[sec-piege-listile]]
=== Assertions ListTile en mode debug

En mode debug Flutter, un avertissement s'affiche quand un `CheckboxListTile`
ou `ListTile` est enfant d'un `ColoredBox` ou `Container(color: ...)`.
Flutter ne peut pas peindre les effets d'encre (ripple) sur le bon ancêtre.

Ce sont des *assertions* (warnings de dev), pas des erreurs : l'application
fonctionne normalement. Ils disparaissent en mode release.

Pour les supprimer en dev : encapsuler le `ListTile` dans un `Material` :

[source,dart]
----
Material(
  color: Colors.transparent,
  child: CheckboxListTile(...),
)
----

=== SbomConfig est un objet mutable partagé

`SbomConfig` est instancié dans `HomeScreen` (depuis `initialConfig` chargé
par `main()` ou un `SbomConfig()` par défaut) et passé en référence à
`ConfigPanel`. `ConfigPanel` le modifie directement (via `_sync()`) sans
passer par des callbacks de valeur.

C'est un choix délibéré de simplicité : le modèle est toujours cohérent
au moment du lancement (la méthode `_run()` appelle `_sync()` avant
`widget.onRun()`). En contrepartie, `HomeScreen` ne reçoit pas de
notification à chaque frappe clavier, ce qui évite des rebuilds inutiles
du panneau de résultats.

Pour la persistance, `ConfigPanel` appelle le callback `widget.onChanged?.call()`
après chaque modification. `HomeScreen` y connecte `_saveSettings()` qui
appelle `SettingsService.saveConfig(_config)` de façon asynchrone et non bloquante.

=== `setState()` synchrone dans `initState()` (`SbomTreePanel`)

`SbomTreePanel.initState()` appelait directement `_autoLoad(widget.outputFiles)`,
qui invoque `_loadFile()` — une fonction `async` dont la toute première
instruction (avant le premier `await`) est un `setState()`. En Dart, le code
d'une fonction `async` avant le premier `await` s'exécute *de façon
synchrone* dans la pile d'appel de l'appelant : ce `setState()` s'exécutait
donc pendant `initState()`, avant que le widget ait fini de monter.

Corrigé en différant l'appel après le premier frame :

[source,dart]
----
@override
void initState() {
  super.initState();
  WidgetsBinding.instance
      .addPostFrameCallback((_) => _autoLoad(widget.outputFiles));
}
----

C'est le correctif standard pour tout appel à `setState()` déclenché depuis
`initState()`. Ce n'est *pas* la cause du blocage décrit en <<sec-file-io-tests>>
(reproduit même avec ce correctif en place) mais reste une amélioration de
robustesse à part entière.

[[sec-file-io-tests]]
=== `testWidgets` + `dart:io File` réel : blocage observé dans certains environnements

En écrivant des tests widgets pour `SbomTreePanel`/`SbomDiffPanel` qui
écrivent une fixture JSON sur disque (`File(...).writeAsString()`) puis la
font lire par le panel testé, le test se bloquait indéfiniment (jusqu'au
timeout interne de `flutter_test`, ~30 s, suivi d'une erreur secondaire
`Bad state: Cannot close sink while adding stream.` lors du nettoyage forcé).

Diagnostic par répétition avec un test minimal, sans aucun code du projet :
un `testWidgets` qui fait un simple `File(...).writeAsString()` puis
`tester.pumpWidget(...)` bloque déjà, alors que le même code dans un `test`
classique (sans `WidgetTester`) s'exécute instantanément. Le blocage
persiste avec le bac à sable (sandbox) de l'outil de développement désactivé
— ce n'est donc pas un artefact de sandboxing, mais une interaction
spécifique à l'environnement entre `AutomatedTestWidgetsFlutterBinding` et
les I/O fichier réelles.

Conséquence pratique : les tests widgets de ce dépôt évitent toute écriture/
lecture de fichier réel à l'intérieur de `testWidgets` (`sbom_merge_panel_test.dart`,
`sbom_viewer_panel_test.dart` s'en tiennent à un état en mémoire). La
couverture de la logique de parsing SBOM (clé purl, formats CycloneDX/SPDX)
reste donc portée côté CLI (`test/unit/sbom_diff_test.dart`), qui exerce le
même algorithme (`_componentKey`/`_diffKey`) sans dépendance à Flutter.

Si cette contrainte disparaît dans un environnement différent (poste de
développeur standard, CI GitHub Actions), rien n'empêche d'ajouter des tests
widgets équivalents pour `SbomTreePanel`/`SbomDiffPanel`.

=== Deux `rootBundle.loadString` dans le même fichier de test : le second bloque

En écrivant les tests de `HelpViewerScreen` (qui charge
`assets/help/manual/toc.json` via `rootBundle.loadString` dans
`initState`), un second `testWidgets` dans le *même fichier* — chacun
montant sa propre instance du widget — voyait sa future de chargement ne
jamais se résoudre : ni erreur, ni `setState`, un `pump` répété (jusqu'à
4 s) ne changeait rien, et `pumpAndSettle` finissait par expirer (timeout)
plutôt que planter proprement.

Diagnostic par répétition avec un widget minimal, sans aucun code du
projet ni `flutter_html` : un `StatefulWidget` dont `initState` appelle
juste `rootBundle.loadString('assets/…')` reproduit le même blocage dès
qu'il est monté une seconde fois dans deux `testWidgets` du même fichier —
premier test : `pump` de 500 ms suffit ; second test : même après 4 s de
`pump` répétés, la chaîne reste sur son texte "loading" initial. Un défaut
d'isolation du cache d'assets entre tests d'un même fichier dans ce binding
Flutter/test, sans rapport avec `HelpViewerScreen` lui-même.

Conséquence pratique : `help_viewer_test.dart` (chargement + affichage du
premier chapitre) et `help_viewer_navigation_test.dart` (clic sur le
sommaire) sont deux fichiers séparés plutôt que deux `testWidgets` du même
fichier — `package:test` isole chaque fichier dans son propre isolat, ce
qui contourne le problème (vérifié : les deux passent une fois séparés).
