15.1. Per-scanner cards

Each scanner has a card displaying:

  • The distribution by severity (colored stacked bars)

  • The number of vulnerabilities per level

The cards of scanners not yet run display a prompt message.

15.2. Global synthesis

The top banner indicates:

  • The number of scanners that produced results (out of 3)

  • The total number of unique CVEs (union of the identifiers of all the scanners run)

  • The ⬥ AsciiDoc + PDF export button (see AsciiDoc + PDF export)

15.3. Cross-scanner comparison

The table at the bottom lists all the vulnerabilities detected by at least one scanner — not only those common to several: it is precisely by keeping the isolated CVEs (seen by a single scanner while several ran) that detection gaps between tools can be spotted. These isolated rows carry an amber border, a ⚠ icon and a “Seen by a single scanner out of N” tooltip to tell them apart at a glance. A ✓ / — mark indicates presence or absence in each scanner.

Sort: click a column header to sort, click again to reverse (the ↑ / ↓ arrow indicates the active column and direction):

  • SEV. — severity (Critical first);

  • CVE / ID — alphabetical order;

  • Grype / OSV / Trivy — CVEs seen by this scanner first (✓ before —), to isolate in one click what each tool detects alone;

  • KEV and EPSS (columns only present if the enrichment ran, see [sec-exploitabilite]) — CISA catalog CVEs first, or decreasing EPSS score.

By default, rows are ordered by risk prioritization — CISA KEV, then decreasing EPSS, then severity — when the enrichment produced results; by severity alone otherwise. The AsciiDoc / PDF export follows exactly the displayed order.

CVE detail: click a row (the ▾ chevron on the right indicates it) to expand it. A panel then displays, from the data already in memory:

  • the affected package, its installed version and the fixed version, as seen by each scanner;

  • the severity and the publication / modification dates, per scanner — often different from one tool to another;

  • the detailed exploitability: CISA KEV (date added, remediation due date, use by ransomware), EPSS score and its percentile, CVSS exploitability sub-score with the vector and the exploit maturity, public PoC repositories (clickable links);

  • reference buttons opening NVD, CVE.org, osv.dev and — for a CVE of the catalog — CISA KEV in the browser, plus a copy the identifier button.

Clicking the row again collapses the panel. The same detail is available in the Grype / OSV-Scanner / Trivy tabs.

If the list exceeds the available height, the tab’s vertical scrollbar lets you browse everything — scroll down inside the Dashboard tab.

Note
 OSV-Scanner sometimes prefixes a CVE with the origin of the distro advisory (e.g. DEBIAN-CVE-2026-13221 for a Debian package) where Grype and Trivy report the same bare identifier (CVE-2026-13221). The table automatically normalizes this kind of prefix before comparing — the vulnerability therefore appears only once, in its bare CVE form, instead of two distinct rows one of which is wrongly marked “seen by a single scanner”.

15.4. Image layers

When at least one scan tab has analyzed an image with the Per layer option (see Per-layer analysis (“Container image” source)), an Image layers card is displayed: for each layer, its digest, its build instruction and the number of unique CVEs (all scanners combined), including critical and high ones; the method used by each scanner is recalled at the top. The Cross-scanner comparison gains a LAYER(S) column, and the AsciiDoc + PDF export an Image layers section and the same column.

15.5. Remediation

The Remediation section answers "what should I update?". CVEs from every scanner are grouped by installed package; for each package the target version is the smallest one that fixes every fixable CVE (e.g. log4j-core 2.14.1 → 2.17.1 — 5 CVEs fixed). Packages are ranked by risk reduction: severity (critical 10, high 5, medium 2, low 1), +20 if the CVE is actively exploited (CISA KEV), + 10 × EPSS. A package none of whose CVEs has a fix is flagged "no known fix"; unfixable CVEs of a fixable package are shown as remaining. Expand a row to see its CVEs; the Copy and CSV buttons export the plan.

Note
 The target version is a heuristic (numeric version comparison, distribution suffixes ignored): check it with your package manager.

15.6. Sessions, history and trend

At the top of the dashboard:

  • Save session… writes the scan results (scanner lists, KEV/EPSS signals, targets) to a JSON file; Open session… reloads it into the dashboard (per-layer analyses included). VEX statements are saved in the file and applied by sbom-generator report.

  • History: every analysis is kept automatically (one entry per target and per day, 50 at most) in ~/.local/share/sbom-generator-gui/history. You can Open an old analysis, Compare it with the current results, Delete an entry or Clear history.

  • Trend: once a reference session is chosen (Compare), a card shows the new, gone (fixed or no longer detected) and unchanged CVEs since that date, the total before → after and the list of new CVEs. Remove the comparison hides it.

15.7. VEX statements

A VEX (Vulnerability Exploitability eXchange) document says that a CVE does not affect you, or is fixed. In a CVE’s detail (click a row), Declare via VEX… opens a dialog: status (not affected, affected, fixed, under investigation), justification (required for "not affected": component not present, vulnerable code not present, never executed, cannot be controlled by an attacker, inline mitigations), a free explanation and the scope (one package or all). The dashboard’s VEX bar:

  • hides covered CVEs ("not affected" / "fixed") while Hide CVEs covered by a VEX is ticked — the counts, the comparison, the remediation and the report follow;

  • Import a VEX… reads an OpenVEX or CycloneDX VEX document;

  • Export writes the statements as OpenVEX or CycloneDX VEX (usable with sbom-generator scan --vex);

  • Manage lists and deletes statements.

Statements are remembered between application sessions.

15.8. Why Grype, OSV-Scanner and Trivy do not find the same CVEs

It is normal — and expected — that a good part of the rows of the cross-scanner table are isolated (seen by a single tool). On the same Keycloak image (RHEL 9.6, ~450 MB) analyzed directly by Grype and by Trivy, a raw comparison of identifiers only shows 72 common CVEs out of ~210 unique identifiers on each side — a gap with two quite distinct causes:

  • Different identifier naming (main cause, not a real detection gap) — on Java packages (JAR/Maven), Grype names its findings with the GitHub Security Advisory identifier (GHSA-xxxx-xxxx-xxxx, its main source for this ecosystem) while Trivy prefers the matching CVE identifier. It is the same vulnerability under two different names — Grype moreover lists the related CVE in its relatedVulnerabilities field. On this same image, the two tools seemed to agree on only 2 Java CVEs out of ~135 on each side; once Grype’s GHSA-* are resolved to their related CVE, the agreement rises to 132/135 (~98 %). On RPM packages (OS base), where both tools natively use the CVE identifier, the agreement was already direct at ~94 % (70 common CVEs out of ~75 on each side).

  • Another different naming, this one normalized automatically — on Debian packages, OSV-Scanner names some of its advisories DEBIAN-CVE-xxxx-xxxxx (Debian Security Tracker origin) where Grype and Trivy report the matching bare CVE identifier. Unlike the GHSA↔CVE case above, the Dashboard’s comparison table resolves this prefix automatically (see AsciiDoc + PDF export) — on a real Debian image, this reduced the number of rows of the cross-scanner comparison from 200 to 106 (nearly half were only this naming duplicate).

  • Residual real gaps (freshness and coverage of the databases) — Grype (Anchore database) and Trivy (trivy-db) republish their vulnerability databases at paces and from sources that are not perfectly identical (NVD, GHSA, Red Hat OVAL/CSAF…). A just-published CVE, or one not yet mapped to the exact CPE of a package, may appear in one before the other. The version matching rules (affected bounds, RPM epoch) and the retained severity score (NVD CVSS vs vendor vs distro) may also differ slightly from one engine to another.

  • Grype and Trivy do not have the same exhaustiveness on Debian OS packages — on a real Debian image (79 packages), Grype reported 207 matches versus only 27 for Trivy, on the same SBOM. This is nevertheless not a problem of CPE false positives: both tools do use their dedicated distro matcher (dpkg-matcher on the Grype side). The gap comes from the completeness of the data taken in — Grype reports the whole Debian Security Tracker, including the advisories marked <no-dsa> (minor bug that Debian chose never to fix) and the CVEs with no known fixed version, where Trivy only reports a more restricted subset. Checked on security-tracker.debian.org: a CVE cited only by Grype (CVE-2026-19499 on glibc/trixie) is indeed listed there as “vulnerable” with the note <no-dsa> (Minor issue) — Grype therefore rightly reports it (“won’t fix” state), Trivy simply omits it. Neither is wrong: Trivy is more conservative (CVEs with a settled status), Grype more exhaustive but noisier.

Neither scanner is “the” truth: each has its own database and its own matching granularity. That is precisely the purpose of this tab — seeing the union of the three scanners rather than relying on a single one to maximize detection coverage.

A gap may also appear with a single scanner depending on whether it is given an SBOM or the image directly — typically in the Trivy tab (see Selecting the source to analyze) between the SBOM file (trivy sbom) and Container image (trivy image) modes. On this same Keycloak image, trivy sbom on an SBOM generated with the syft backend found 3 HIGH CVEs (micrometer-core, postgresql) absent from a direct trivy image: the jar analyzer built into Trivy identifies a jar through pom.properties, then MANIFEST.MF, then a SHA-1 lookup in its trivy-java-db database (indexed from Maven Central) — and silently drops the package if all three fail, which happens for internally rebuilt jars (e.g. .redhat-000xx) without pom.properties and absent from Maven Central. The syft cataloger, for its part, can recover these packages by parsing the file name <groupId>.<artifactId>-<version>.jar (convention of the Quarkus “fast-jar” packaging of this image). Here again, the SBOM does not invent CVEs: it is trivy image that misses a few that trivy sbom finds thanks to syft’s more complete detection.

The same kind of gap existed for OSV-Scanner, but far more drastically: on distribution packages, giving it a syft SBOM brought the result down to almost zero CVEs, whereas scanning the image directly finds hundreds. Two causes, both fixed at the source by sbom_generator (syft backend):

  • distro qualifier — OSV-Scanner only links a pkg:deb/debian/…​ to the Debian:13 ecosystem if distro is debian-<major> or if distro_name carries a known codename. syft fills in the point release (distro=debian-13.6, read from /etc/debian_version), which is not recognized. Fixed: debian-13.6 → debian-13 + distro_name=trixie.

  • Binary vs source package — OSV.dev indexes Debian advisories by source package (zlib, perl), not binary (zlib1g, perl-base). syft only lists the binary (with upstream=), which OSV-Scanner does not use. Fixed: one component per distinct source package is added (like cdxgen), and upstream= is removed from the binary so that Grype does not count the CVE twice.

On haproxy:3.4.4 (Debian 13.6), the syft SBOM thus goes from ~0 to 58 OSV-Scanner CVEs (parity with the cdxgen SBOM), cross-checked by the three scanners instead of Grype alone.

Two limits remain:

  • the other families of distribution packages (Alpine, RPM/RHEL) — OSV.dev indexes them poorly or not at all in “SBOM scan” mode;

  • osv-scanner scan image, which does its own extraction without PURLs, remains more exhaustive on the base OS. For maximum OS coverage with this tool, scan the image directly.

15.9. AsciiDoc + PDF export

The ⬥ button (PDF icon, in the global summary card) exports the dashboard report. It is produced by the CLI (sbom-generator report) from the displayed results: it is exactly the report of sbom-generator scan --format pdf (see the CLI guide, "Vulnerability report"); the CLI and the GUI share a single generator. The CLI must therefore be installed (it is, with the application).

Content: executive summary (verdict, targets, severity level, VEX), Tools, breakdown per scanner with a severity bar, Image layers (when a per-layer analysis was run), cross-scanner comparison, exploitability (KEV, EPSS, PoC), Remediation (minimal updates per package, ranked by risk reduction), Trend (if a comparison was chosen in the history), VEX (statements and dropped CVEs) and CVE details (one card per CVE: package, versions, scanners, dates, description, exploitation signals, links).

Report severity level: the menu to the left of the export button (Critical, ≥ High, ≥ Medium, All — All by default) limits the whole report to CVEs of that level or above. The choice is remembered between sessions; the on-screen display is not filtered.

  • A CVE is kept according to its worst severity, every scanner: a CVE that is High for Grype and Medium for Trivy appears in a "≥ High" report with both scanners.

  • CVEs in the CISA KEV catalog are always included, whatever their severity.

  • The filtered report says so at the top (level, "N of M unique CVEs") and the suggested file name carries the level (vulnerability-report-high.adoc).

VEX and trend: the report applies the VEX statements while Hide CVEs covered by a VEX is ticked, and includes the Trend section when a reference session is active (the Compare button of the history).

The button stays disabled until a scanner has run. Once the .adoc file is written (location chosen through a dialog), the CLI tries the PDF conversion with asciidoctor-pdf; if the tool is not installed the .adoc file is still produced and a message says so. The same report can be regenerated on the command line from a saved session: sbom-generator report -i session.json -o report.pdf.

Note
 The Dashboard is updated automatically every time an analysis is run in a scanner tab. No additional action is required.
