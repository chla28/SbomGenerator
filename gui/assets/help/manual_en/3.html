4. Configuration panel

4.1. Input section

4.1.1. Input file (--input)

Path to the file containing the list of packages to analyze. The 📂 button to the right of the field offers a menu:

Filtered type (.lst .txt)

Only shows files with the usual extensions

All files

Shows all the files of the directory
Tip
 You can also drag and drop a file from your file manager (Nautilus, Thunar…) directly onto this field. A blue outline indicates that the drop is accepted.

The file must contain one item per line. The accepted types are:

Type Line format

Installed RPM package

bash or bash-5.1.8-6.el9.x86_64

Local RPM file

/path/to/package.rpm

Python wheel (.whl)

/path/to/package-1.0-py3-none-any.whl

Tar archive

/path/to/pkg.tar.gz or .tgz

Zip archive

/path/to/archive.zip

Debian package (.deb)

/path/to/package.deb

Python dependencies

/path/to/requirements.txt

Java archive (.jar)

/path/to/lib-1.2.3.jar

Manifest / lockfile

go.sum, go.mod, package-lock.json, yarn.lock, pom.xml, pubspec.lock, pubspec.yaml

A single input file may contain lines of different types. A path pointing directly to an archive or to a single manifest (rather than to a list file) is also accepted; a directory is scanned recursively for all these types. For Dart/Flutter, pubspec.lock provides the resolved versions and the complete transitive closure (development dependencies are excluded); pubspec.yaml only provides the direct dependencies of the dependencies: section.

Note
 The Packages to analyze field becomes optional if an OCI image is specified in the next section.
Important
 The Packages to analyze and OCI image fields are mutually exclusive in the interface: filling in one (typing, drag and drop, or file/directory picker) automatically empties the other. To combine both sources in a single analysis, use the command line (--input and --image together).

4.2. OCI image section

4.2.1. OCI image (--image)

Reference of an OCI image to analyze. Three formats are accepted:

Format Description Example

Registry

Docker Hub image or private registry

nginx:latest

Tar archive

docker save or skopeo copy docker-archive: export (.tar, .tar.gz, .tgz)

/path/ubuntu.tar, /path/image.tar.gz

OCI layout

Directory containing index.json

/path/oci_dir/

The 📂 button to the right of the field opens a context menu:

  • Tar archive (.tar / .tar.gz / .tgz) — file picker filtered on these three extensions

  • OCI layout directory — directory picker

For registry images, type the reference manually.

If the field is empty, the OCI analysis is disabled.

4.2.2. OCI tool (--oci-tool)

Only visible when the OCI image field is filled in. Select the analysis backend:

Tool Description Requirements

Syft (default)

Anchore Syft — all package types (deb, rpm, apk, pypi, npm, go, java…)

syft in the PATH

Trivy

Aqua Trivy — all package types

trivy in the PATH

Skopeo

Manual layer extraction — dpkg, RPM and APK only

skopeo and tar in the PATH

cdxgen

OWASP CycloneDX Generator — all package types; the produced SBOM is filtered to the components carrying a real ecosystem PURL

cdxgen in the PATH (requires Node.js)

4.2.3. Descent depth (--depth)

Under the input field, the Depth selector lets you descend into the objects contained in the input: for example the jars of an RPM, the packages and jars of a .tar.gz / .zip archive, the jars of a fat jar, as well as the manifests found (package-lock.json, go.sum, pom.xml…).

0 — object only

Default behavior: the input is not opened

1 level, 2, 3

Descends N levels (1 = direct objects of the input, 2 = what these contain…)

Unlimited

All levels (capped at 10)

The generated SBOM merges the object and everything it contains: each nested component carries its location (sbom_generator:nested:location) and its depth, and the dependency graph links the container to its content. As soon as the depth is greater than 0, the One SBOM per nested object checkbox additionally writes one SBOM per jar/package/archive (<output>.nested-NN-<object>.<ext>); these files appear in the list of produced files, after the global SBOM. Unchecking the box adds --no-nested-files.

Note
 The depth only applies to a file / folder input (not to an image or a binary). The extraction is size-bounded and requires python3; analyzing a nested .rpm requires rpm.

4.2.4. One SBOM per layer (--per-layer)

Checkbox visible under the OCI backend, only for an OCI image (a standalone binary has no layers). Once checked, the generation produces, in addition to the global SBOM, one SBOM per image layer in each checked format: <output>.layer-NN-<digest>.<ext> (e.g. sbom.layer-02-b676b687f0f5.cdx.json).

The SBOM of a layer describes its delta: the components added or modified by the layer, with the removed components listed separately; its root component carries the build instruction (RUN …, COPY …) and the digest of the layer. The global SBOM indicates, for each component, the layer that introduced it.

The method selector (--layer-mode) offers:

Method Principle

Metadata (default)

Originating layer reported by Syft or Trivy. Fast; only additions are known. Unavailable with Skopeo and cdxgen.

Rootfs

Layers are applied one by one and the image is re-analyzed after each one: additions, modifications (version bumps…) and removals. One analysis per layer, hence slower. The only possible mode with Skopeo and cdxgen (reminder displayed under the selector). For a registry image, skopeo must be installed.

Layer SBOMs can be browsed from the SBOM Tree and SBOM Viewer tabs (see Per-layer navigation (--per-layer)). The global SBOM is always the first file produced: it is the one that the other tabs (Preview, scanners, Quality, CRA…) select by default.

4.2.5. Standalone binary (--binary)

Separate field, under a second “OR” separator: local executable to analyze directly (not a container image) — for example a statically linked Go binary. The 📂 button opens a simple file picker (no extension filter, a binary often has none).

Mutually exclusive with Packages to analyze and OCI image: filling in this field automatically empties the other two, and conversely.

Systematically forces the Syft backend (the OCI tool selector is not displayed for this field) — it is the only backend able to exploit the metadata embedded in a standalone binary:

  • Go (statically linked or not): the complete list of modules + versions is read from the buildinfo metadata embedded in the executable, even if stripped.

  • Other languages (Rust, static C/C++…): only a fixed catalog of well-known open-source libraries (OpenSSL, zlib, sqlite, busybox…) is detected through a version-string fingerprint — not an arbitrary extraction of the linked dependencies.

  • A statically linked library with no recognized signature nor embedded metadata (home-made C/C++, Rust without cargo-auditable) cannot be recovered afterwards.

4.3. Output section

4.3.1. Base path (--output)

Prefix of the generated files, without extension. Example: sbom will produce sbom.cdx.json, sbom.spdx.json, etc. A relative path is resolved from the current directory at launch time.

A preview of the expected file names is displayed as soon as the field is filled in.

4.3.2. Formats (--format)

Check one or more formats. At least one format must be selected.

Format Produced extension Typical use

.cdx.json

Vulnerability analysis with grype, OWASP tools

.spdx.json

Legal compliance, OpenChain tools

.spdx3.jsonld

Linked ecosystems (RDF/ontology)

.custom.json

Integration into internal pipelines

Documentation directly readable on GitHub/GitLab

Rich technical report (tables, styles)

Standalone interactive report (filterable and sortable, charts by ecosystem/license)

CSV

Import into a spreadsheet or a data-processing pipeline

4.3.3. PDF option (AsciiDoc only)

When the AsciiDoc format is checked, an additional option appears: Convert to PDF (asciidoctor-pdf). If enabled, the asciidoctor-pdf tool is launched automatically after the .adoc is generated.

An optional field lets you specify the destination path of the PDF. Without a value, the PDF is created in the same folder as the .adoc, with the same base name.

4.4. Options section

4.4.1. SBOM document name (--name)

Label that will appear in the SBOM metadata (metadata.component.name field in CycloneDX). Example: My Application 2.1.0. Leave empty to use the name of the input file.

4.4.2. Local RPM directory (--rpm-dir)

Folder containing additional .rpm files to include in the analysis. Useful to enrich the metadata resolution (exact version, license) when the packages are not installed on the current machine.

4.4.3. License override (--license-map)

Text file used to correct or specify the licenses of some packages. The button on the right offers the same options as the input file field: filtered type (.txt, .yaml) or all files. Format: one rule per line: package-name: SPDX-expression

Example:

openssl: OpenSSL
my-internal-lib: LicenseRef-PROPRIETARY

4.4.4. Concurrency (--concurrency)

Number of packages processed in parallel. The slider goes from 0 (unlimited) to 16. The default value is 4.

  • Increase it if your machine has many cores and a good network connection.

  • Decrease it (1 = sequential) in case of rate-limiting errors on the repositories.

  • The value 0 processes all the packages simultaneously — to be used with caution on large lists.

4.4.5. Verbose mode (--verbose)

Displays additional information in the Progress tab: resolution tools used, processing statistics, details of each package found.

4.4.6. sbomqs quality score

When this option is checked, sbomqs score is run automatically on the first generated JSON SBOM file (.cdx.json or .spdx.json). The result is displayed in the Results tab under the file list.

If sbomqs is not installed, the option is silently ignored.

Note
 See Installing sbomqs (optional) for the installation.

4.5. Settings persistence

All the settings of the Options section — selected formats, base path, RPM directory, license file, concurrency level, verbose mode, PDF generation, sbomqs score — are automatically saved after each generation and restored at the next application start.

The saved settings do not include the input file (too tied to a particular context) nor the PDF path.

4.6. Configuration profiles

A profile groups all the configuration settings under a custom name, and can be recalled in one click to switch quickly between several typical configurations (e.g. “RHEL 9 production”, “Python audit”, “Minimal CI/CD”).

4.6.1. Accessing the profiles

Click the 🔖 (bookmarks) icon at the top right of the Configuration panel header.

  ┌─ Configuration ────────────────── [🔖] ─┐
  │  ...                                     │

4.6.2. Profile management window

  ┌─ Configuration profiles ────────────────────────────────────┐
  │                                                              │
  │  Profile name : [ RHEL 9 production       ] [Save]          │
  │                                                              │
  │  ─────────────────────────────────────────────────────────  │
  │  RHEL 9 production               [Load] [Delete]             │
  │  Python audit                    [Load] [Delete]             │
  │  Minimal CI/CD                   [Load] [Delete]             │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘

Save

Saves the current state of all the fields under the entered name

Load

Applies the profile values (except the input file)

Delete

Asks for confirmation, then deletes the profile
Note
 The input file is not included in the profiles — it is generally specific to each usage context.
Tip
 If a profile with the same name already exists, Save updates it.

4.7. Command preview

Under the ▶ Generate the SBOM button, the shell command line equivalent to the current configuration is permanently displayed:

  $ sbom-generator --input /home/user/packages.lst \
    --output /home/user/sbom --format cyclonedx spdx

This preview is updated at each field change. A 📋 button copies the command to the clipboard to replay it from a terminal or integrate it into a CI/CD script.

4.8. Starting and stopping the generation

Click ▶ Generate the SBOM to start. The button turns into ■ Stop generation during execution. Clicking Stop sends an interrupt signal to the process.
