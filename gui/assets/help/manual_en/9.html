10.1. Version indicator

At the top of the configuration panel, the application displays the installed grype version and the update status, checked in the background at startup:

  • ✔ v0.87.0 (green) — grype is installed and up to date.

  • ↑ v0.87.0 → v0.88.1 (orange, clickable) — a new version is available on GitHub. Click to open the release page in the browser.

  • not installed (red) — grype is not found in the PATH.

Note
 The check queries the GitHub API. Without a network connection, only the installed version is displayed, with no comparison.

10.2. Selecting the source to analyze

A SBOM file / Container image / Package / archive toggle at the top of the panel lets you choose what grype analyzes. This choice, as well as the associated field, is shared by the three scan tabs (Grype, OSV-Scanner, Trivy) — see also Selecting the source to analyze and Selecting the source to analyze.

SBOM file (default mode): the field is automatically pre-filled with the last SBOM file generated in the current session, giving priority to the formats recognized by grype: .cdx.json (CycloneDX) then .spdx.json (SPDX). You can type a path manually or click Choose to browse the file system. The .json and .jsonld formats are offered in the picker.

Note
 Grype analyzes the content of the file, not its extension. A CycloneDX file renamed .json is recognized correctly.

Container image: the field accepts three forms of reference, all supported by grype with no syntax distinction on the application side:

  • a registry reference, e.g. nginx:latest, ghcr.io/org/app:tag — the image is fetched through the local Docker configuration (docker login) if the registry is private, with no dedicated credentials field in the application;

  • an archive exported by docker save (or an OCI archive), through the dedicated button (extensions .tar, .tar.gz, .tgz);

  • an OCI layout directory (produced for example by skopeo copy), through the second dedicated button.

An optional Platform field appears in image mode, to force the target platform on a multi-architecture image (e.g. linux/arm64). Left empty, grype automatically detects the most suitable platform.

Package / archive: a local file — .rpm, .deb, .tar / .tar.gz / .tgz, .zip, .jar / .war / .ear, .whl — is analyzed directly, without going through an SBOM file. The application first runs sbom-generator --input <file> --depth N (see Descent depth (--depth)) in a temporary directory, then the scanner analyzes the produced CycloneDX SBOM, exactly like an SBOM file: the three tabs (Grype, OSV-Scanner, Trivy) therefore receive the same components. The Depth selector (0 — object only, 1 to 3 levels, Unlimited) chooses how far to descend into the contained objects (jars of an RPM, packages of an archive…). The generated SBOM is reused by the tabs as long as the file and the depth do not change. The header of the exported reports indicates “package <name> (depth N)”.

Note
 CVEs are displayed per vulnerable package (name@version). To know which nested object contains it, use the sbom-generator scan --package equivalent command of the CLI Command button (OBJECT column).

10.3. Command line (CLI Command button)

The CLI Command button, next to the analyze button (shared by the three scan tabs), opens a popup with the commands matching the current settings of the tab, each with a Copy button:

  • Command run by the tab — the exact grype / osv-scanner / trivy line, with all the options of the tab (built by the same code as the execution). With the Per layer option (see Per-layer analysis (“Container image” source)), the sequence actually launched: generation of the per-layer SBOM set (sbom-generator --image … --per-layer), then the scan of the image (Attribution) or a for f in …; do …; done loop over the layer SBOMs (Each layer). The application’s temporary directory is replaced by /tmp/sbom-couches.

  • sbom-generator scan equivalent — the command of the project’s CLI that produces the same kind of analysis: target (--sbom or --image), --scanner, per-layer options (--per-layer --layer-scan … --layer-mode …), the tab’s date filter (--cve-after, --cve-before, --cve-date-field, --include-undated) and offline enrichment (--no-enrich). A remark points out the options of the tab with no equivalent (template, --fail-on, --only-fixed, Trivy severities, configuration files…) and reminds that with --image, sbom-generator scan analyzes the SBOM generated by syft and not the image directly.

With the Package / archive source, the popup additionally displays the SBOM generation (sbom-generator --input … --depth N, SBOM written to /tmp/sbom-paquet/) before the scanner command, and the equivalent is sbom-generator scan --package … --depth N.

As long as the target is not filled in, it appears as <sbom.cdx.json>, <image> or <package>.

10.4. Per-layer analysis (“Container image” source)

In Container image mode, the Per layer checkbox (shared by the three scan tabs) attributes each vulnerability to the layer of the image that brings the vulnerable package. The application first generates, through sbom-generator --image … --per-layer (syft backend), a global SBOM and one SBOM per layer in a temporary directory; this set is reused by the three tabs as long as the image and the computation do not change.

Method Principle What you see

Attribution (default)

A single scan of the image, as without the option; each vulnerability is attached to the originating layer of its package. Trivy and OSV-Scanner report this layer themselves (Layer.DiffID, image_origin_details), used first; otherwise, the package is looked up in the global SBOM.

The CVEs of the final image, by the layer that introduced them.

Each layer

The SBOM of each layer is scanned separately (one scan per layer); the outputs are merged.

In addition, the CVEs of a version introduced by a layer then replaced higher up (with the Rootfs computation). A CVE may appear in several layers.

The second selector chooses the layer computation: Metadata (originating layer reported by syft — fast, additions only) or Rootfs (layers applied one by one and re-analyzed — additions, modifications, removals; slower). During the analysis, a status line indicates the current step (preparing the SBOMs, layer i/N…); the Stop button also interrupts the generation and the remaining scans.

In the Table view (see [sec-vue-table]):

  • a LAYER column shows the layer(s) of each vulnerability (? if the package is absent from the image SBOM — a banner shows the number); the tooltip recalls the digest and the build instruction;

  • the All layers / Layer N (n) menu filters on one layer;

  • the Group by layer button (layers icon) groups the list under one header per layer — digest, build instruction and counters per severity;

  • the CSV and AsciiDoc + PDF exports add a Layer(s) column and, for the PDF, an Image layers section.

The Dashboard reuses this information (see Image layers).

Note
 In Each layer mode, OSV-Scanner analyzes SBOMs and not the image: it then finds few or no CVEs on system packages (see Remediation) — prefer Attribution with this tool.

10.5. Scan options

10.5.1. --platform linux

Forces grype to consider the target platform as Linux when resolving vulnerabilities, in SBOM file mode only. Recommended for SBOMs coming from RPM or DEB package lists.

Uncheck this option if you analyze an SBOM coming from another system (macOS libraries…).

Note
 This checkbox has no effect in Container image mode: it is ignored in favor of the Platform field described above (linux alone, without architecture, is moreover rejected by grype on a multi-platform image).

10.5.2. --add-cpes-if-none

Grype uses CPE (Common Platform Enumeration) identifiers to match packages with CVE entries. If a package of the SBOM has no declared CPE, this option asks grype to generate one automatically from the package name and version.

Recommended: reduces false negatives on SBOMs produced without CPEs (which is the case of most SBOMs generated by sbom-generator).

10.5.3. --by-cve

Without this option, grype groups the results by GHSA identifier (GitHub Security Advisory) when available. With this option, each result is presented under its main CVE identifier, which is more universal and recognized by vulnerability management tools.

Recommended for interoperability with ticketing tools (Jira, defect trackers, etc.) or internal vulnerability repositories.

10.5.4. --distro rhel:<version>

Specifies the target Linux distribution. Without this option, grype tries to deduce it from the SBOM, which may fail or produce imprecise matches.

RHEL versions available in the menu: 7, 8, 9, 10. Select (none) to let grype detect the distribution automatically.

Note
 Choosing the wrong version may cause false positives (vulnerabilities not applicable because already fixed by the RHEL backport) or false negatives. Check the exact version of your system with cat /etc/redhat-release.

10.5.5. --fail-on <severity>

Controls the exit code of grype. With this option, grype returns an error (non-zero) code if at least one vulnerability of the given level or higher is detected. Useful in CI/CD.

Example: --fail-on high makes the analysis fail if a High or Critical vulnerability is found.

The result banner in the UI reflects this exit code: red background if grype returned an error, green otherwise.

10.5.6. --only-fixed

Only shows the vulnerabilities for which a fixed version is available. Lets you focus on the immediately actionable items.

10.6. Output template (-t)

The Template (-t) field lets you generate a custom output (CSV, HTML, text) through a Go template file.

The field is pre-filled with ./grype_csv.tmpl. If this file does not exist at launch time, the template output is ignored without error.

Example of a Go template for a CSV:

"CVE","Package","Installed version","Fixed version","Severity"
{{- range .Matches}}
"{{.Vulnerability.ID}}","{{.Artifact.Name}}","{{.Artifact.Version}}","{{fixedIn .Vulnerability}}","{{.Vulnerability.Severity}}"
{{- end}}

The produced output is displayed in the Template tab (see Template view) and can be copied to the clipboard.

Note
 Grype is launched in a single pass that simultaneously produces the JSON output (for the Table view) and the template output (through a temporary file).

10.7. Configuration file (grype.yaml)

Path to a grype configuration file in YAML format. Lets you define ignore rules, custom databases, proxies, etc.

This parameter is optional. Leave the field empty to use the default grype configuration (~/.grype.yaml if it exists).

Official documentation: https://github.com/anchore/grype#configuration

10.8. Starting and stopping the analysis

Click Analyze to start. A linear progress bar is displayed during the execution. The button becomes Stop to interrupt.

10.9.2. Table view

The Table view shows a search/sort toolbar, the severity filters, then the list of vulnerabilities:

  [ Search...                            ] [⬇]
  Filter : [Critical (1)] [High (2)] [Medium (2)] [Low (0)]  [Show all]

  ┌────────────┬──────────────────┬──────────────────┬───────────────┬──────┐
  │ SEVERITY ↕ │ PACKAGE ↕        │ VERSION ↕        │ CVE/ID ↕      │ TYPE │
  ├────────────┼──────────────────┼──────────────────┼───────────────┼──────┤
  │ CRITICAL   │ openssl          │ 1.1.1k → 1.1.1l  │ CVE-2021-3711 │ rpm  │
  │ HIGH       │ bash             │ 5.0.17  (no fix) │ CVE-2021-3489 │ rpm  │
  │ MEDIUM     │ zlib             │ 1.2.11  → 1.2.12 │ CVE-2022-37434│ rpm  │
  └────────────┴──────────────────┴──────────────────┴───────────────┴──────┘

Merging of visual duplicates: the same component can be detected at several distinct locations in the analyzed image/SBOM — for example a library present both as a standalone jar and shaded (embedded) in another jar — with exactly the same severity, the same CVE, the same package and the same version. Grype and Trivy then rightly report two distinct results, but visually identical in this table (no column shows the file path). These rows are therefore merged into a single one, with a ×N badge next to the CVE identifier — hover it to see the real number of locations. This merging applies to the summary banner, the severity counters and the exports (see below); only the JSON view (JSON view) remains faithful to the full, unmerged output of the tool.

Search: the search field filters in real time on the package name, the CVE identifier, the version or the type.

Sort: click a column header (SEVERITY, PACKAGE, VERSION, CVE/ID) to sort in ascending order, click again to reverse. The ↑↓ arrow indicates the active column and sort direction. By default, results are sorted by decreasing severity (Critical first).

CSV export: the ⬇ (download) button exports the current filtered list (taking into account the search, the severity filters, and already merged — see above) to a .csv file in RFC 4180 format. Columns: Severity, CVE/ID, Package, Installed version, Fixed version, Type, Locations (number of merged occurrences, 1 if the component is present in a single place only).

AsciiDoc + PDF export: the ⬥ button (next to the CSV export) exports the filtered list into a polished report: cover page (title, date, analyzed target, version), executive summary — a figures box “Critical / High / CISA KEV / Total” and a one-sentence verdict (“Immediate action required” if KEV CVEs are present, etc.) — severity distribution bar, Tools section (versions detected through <tool> --version at export time, hence always up to date), then the detailed table. The .adoc file is then converted to PDF through asciidoctor-pdf; if the tool is missing, the .adoc is still produced and a message says so. The output location is chosen through a dialog box.

The PDF uses a sober layout: sans-serif font, slate-blue palette, dark table headers, colored severity badges (labels in the report language: CRITICAL / HIGH / MEDIUM / LOW), footer with report title and “Page X / Y” pagination. The dashboard report (export button of its summary card) follows the same style and adds a “CVE details” section.

Severity filters: click one or more badges to only display the vulnerabilities of the matching level. The Show all button clears the active filters. Only the badges matching severities present in the results are displayed.

Date filter: a time-filtering bar sits above the table. It lets you display only the CVEs published or modified in a given date range:

  📅 CVE date: [Published] [Modified] [Most recent]
     After: [2024-01-01 ×]   Before: [2024-12-31 ×]
     [✓] Undated    [Apply to other tabs]

  • Date field: three-value selector — Published (initial publication date of the CVE), Modified (last update), Most recent (the later of the two available dates).

  • After / Before: clickable chips opening a calendar. An × clears each bound independently.

  • Undated: checkbox to include the CVEs whose selected date field is absent or not filled in in the scanner data. By default, these CVEs are excluded when a filter is active.

  • Apply to other tabs: copies the current filter to the two other CVE tabs (OSV-Scanner and Trivy). The analyses themselves are not re-run; only the display is filtered.

Note
 The date filter is applied as post-processing on the JSON returned by Grype. It is independent of the Grype command-line options and can be combined with the severity filters and the text search.

Columns:

  • Severity badge: colored label (CRITICAL / HIGH / MEDIUM / LOW / NEGLIGIBLE)

  • Package: name of the affected package in bold

  • Versions: installed version, and fixed version if available (after →). The (won’t fix) mention indicates that the maintainer does not plan a fix.

  • CVE: vulnerability identifier

  • Type: package type (rpm, python, deb…)

Clicking a row expands it and shows the full CVE detail: package and versions, severity and dates as reported by the scanner, detailed exploitability (KEV, EPSS, CVSS, PoC) and reference buttons (NVD, CVE.org, osv.dev, CISA KEV). The detail panel contains a copy the identifier button. Clicking the row again collapses it.

10.9.3. Exploitability and active exploitation

After each scan, the application enriches the CVEs found with four prioritization signals, displayed as chips under each row and as sortable KEV / EPSS columns:

  • KEV (red chip 🔥) — the CVE is in the CISA Known Exploited Vulnerabilities catalog: active exploitation confirmed in the wild. The hover tooltip gives the date added and any use by ransomware.

  • EPSS — Exploit Prediction Scoring System score (FIRST.org), from 0 to 1: probability of exploitation within 30 days, with its percentile.

  • PoC — a public exploit is recorded (GitHub repositories via poc-in-github, or the E: maturity of the CVSS vector).

  • expl. — exploitability sub-score of the CVSS vector (AV/AC/PR/UI), from 0 to 3.9, computed locally.

Grype already provides KEV, EPSS and the CVSS vector in its database: for the Grype tab, only the PoC signal requires a network request. For OSV-Scanner and Trivy, the KEV/EPSS enrichment is done online. Responses are cached for 24 h in ~/.cache/sbom-generator/ (shared with the command line).

CISA KEV filter: a CISA KEV (N) chip appears next to the severity filters as soon as an exploited CVE is present — click it to display only these CVEs. The KEV sort puts the catalog CVEs first; the EPSS sort orders by decreasing probability.

Online / offline toggle: the ☁ icon in the table toolbar enables or cuts the network enrichment requests. The choice is remembered (like the theme) and shared by the three scan tabs. Offline, only the data provided by Grype and the local cache are used.

The CSV and AsciiDoc/PDF exports gain the KEV, EPSS and PoC columns when the enrichment has produced results; the dashboard marks the KEV/high-EPSS CVEs in its cross-scanner comparison and brings them to the top.

10.9.4. JSON view

Displays the raw JSON output of grype, formatted and indented. Useful to inspect the detail of a vulnerability (CVSS, references, metadata…).

The 📋 button at the top right copies the whole JSON to the clipboard.

10.9.5. Template view

Displays the result of the template file generation (CSV or other custom format). Only visible if a template file has been configured in the Template (-t) field.

A hint is displayed if no template is configured or if the analysis has not been run yet.

The 📋 button copies the output to the clipboard.
