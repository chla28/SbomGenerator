12.1. Cartes par scanner

Chaque scanner dispose d’une carte affichant :

  • La répartition par sévérité (barres empilées colorées)

  • Le nombre de vulnérabilités par niveau

Les cartes des scanners non encore exécutés affichent un message d’invite.

12.2. Synthèse globale

Le bandeau supérieur indique :

  • Le nombre de scanners ayant produit des résultats (sur 3)

  • Le nombre total de CVE uniques (union des identifiants de tous les scanners exécutés)

  • Le bouton ⬥ d’export AsciiDoc + PDF (voir Export AsciiDoc + PDF)

12.3. Comparaison inter-scanners

Le tableau en bas liste toutes les vulnérabilités détectées par au moins un scanner — pas seulement celles communes à plusieurs : c’est justement en gardant les CVE isolées (vues par un seul scanner alors que plusieurs ont tourné) qu’on repère les écarts de détection entre outils. Ces lignes isolées portent une bordure ambre, une icône ⚠ et un tooltip « Vu par un seul scanner sur N » pour les distinguer d’un coup d’œil. Les lignes sont triées par sévérité décroissante ; une coche ✓ / — indique la présence ou l’absence dans chaque scanner.

Si la liste dépasse la hauteur disponible, l’ascenseur vertical de l’onglet permet de tout parcourir — faites défiler vers le bas à l’intérieur de l’onglet Tableau de bord.

Note
 OSV-Scanner préfixe parfois un CVE par l’origine de l’avis distro (ex. DEBIAN-CVE-2026-13221 pour un paquet Debian) là où Grype et Trivy rapportent le même identifiant nu (CVE-2026-13221). Le tableau normalise automatiquement ce genre de préfixe avant comparaison — la vulnérabilité n’apparaît donc qu’une seule fois, sous sa forme CVE nue, au lieu de deux lignes distinctes dont une marquée à tort « vue par un seul scanner ».

12.4. Pourquoi Grype, OSV-Scanner et Trivy ne trouvent pas les mêmes CVE

Il est normal — et attendu — qu’une bonne partie des lignes du tableau inter-scanners soient isolées (vues par un seul outil). Sur une même image Keycloak (RHEL 9.6, ~450 Mo) analysée directement par Grype et par Trivy, une comparaison brute des identifiants ne fait ressortir que 72 CVE communes sur ~210 identifiants uniques de chaque côté — un écart qui a deux causes bien distinctes :

  • Nomenclature d’identifiant différente (cause principale, pas un vrai écart de détection) — sur les paquets Java (JAR/Maven), Grype nomme ses trouvailles avec l’identifiant GitHub Security Advisory (GHSA-xxxx-xxxx-xxxx, sa source principale pour cet écosystème) tandis que Trivy préfère l’identifiant CVE correspondant. C’est la même vulnérabilité sous deux noms différents — Grype liste d’ailleurs le CVE lié dans son champ relatedVulnerabilities. Sur cette même image, les deux outils ne semblaient d’accord que sur 2 CVE Java sur ~135 de chaque côté ; une fois les GHSA-* de Grype résolus vers leur CVE lié, l’accord monte à 132/135 (~98 %). Sur les paquets RPM (base OS), où les deux outils utilisent nativement l’identifiant CVE, l’accord était déjà direct à ~94 % (70 CVE communes sur ~75 de chaque côté).

  • Autre nomenclature différente, celle-ci normalisée automatiquement — sur les paquets Debian, OSV-Scanner nomme certains de ses avis DEBIAN-CVE-xxxx-xxxxx (origine Debian Security Tracker) là où Grype et Trivy rapportent l’identifiant CVE nu correspondant. Contrairement au cas GHSA↔CVE ci-dessus, le tableau de comparaison du Tableau de bord résout ce préfixe automatiquement (voir Export AsciiDoc + PDF) — sur une image Debian réelle, cela a réduit le nombre de lignes de la comparaison inter-scanners de 200 à 106 (près de la moitié n’étaient que ce doublon de nomenclature).

  • Écarts réels résiduels (fraîcheur et couverture des bases) — Grype (base Anchore) et Trivy (trivy-db) republient leurs bases de vulnérabilités à des rythmes et depuis des sources pas parfaitement identiques (NVD, GHSA, OVAL/CSAF Red Hat…). Un CVE tout juste publié, ou pas encore mappé au CPE exact d’un paquet, peut apparaître chez l’un avant l’autre. Les règles de correspondance de version (bornes affectées, epoch RPM) et le score de sévérité retenu (CVSS NVD vs fournisseur vs distro) peuvent aussi différer légèrement d’un moteur à l’autre.

  • Grype et Trivy n’ont pas la même exhaustivité sur les paquets OS Debian — sur une image Debian réelle (79 paquets), Grype rapportait 207 correspondances contre seulement 27 pour Trivy, sur le même SBOM. Ce n’est pourtant pas un problème de faux positifs par CPE : les deux outils utilisent bien leur matcher distro dédié (dpkg-matcher côté Grype). L’écart vient de la complétude des données reprises — Grype remonte l’intégralité du Debian Security Tracker, y compris les avis marqués <no-dsa> (bug mineur que Debian a choisi de ne jamais corriger) et les CVE sans version corrigée connue, là où Trivy ne remonte qu’un sous-ensemble plus restreint. Vérification faite sur security-tracker.debian.org : une CVE citée uniquement par Grype (CVE-2026-19499 sur glibc/trixie) y est bien listée « vulnerable » avec la note <no-dsa> (Minor issue) — Grype la rapporte donc à raison (état « won’t fix »), Trivy l’omet simplement. Aucun des deux n’a tort : Trivy est plus conservateur (CVE au statut tranché), Grype plus exhaustif mais plus bruyant.

Aucun des deux scanners n’est « la » vérité : chacun a sa base et sa granularité de correspondance propres. C’est précisément la raison d’être de cet onglet — voir l’union des trois scanners plutôt que se fier à un seul pour maximiser la couverture de détection.

Un écart peut aussi apparaître avec un seul et même scanner selon qu’on lui donne un SBOM ou l’image directement — typiquement dans l’onglet Trivy (voir Sélection de la source à analyser) entre les modes Fichier SBOM (trivy sbom) et Image de conteneur (trivy image). Sur cette même image Keycloak, trivy sbom sur un SBOM généré avec le backend syft trouvait 3 CVE HIGH (micrometer-core, postgresql) absentes de trivy image en direct : l’analyseur de jars intégré à Trivy identifie un jar via pom.properties, puis MANIFEST.MF, puis un lookup SHA-1 dans sa base trivy-java-db (indexée depuis Maven Central) — et abandonne silencieusement le paquet si les trois échouent, ce qui arrive pour des jars rebuilds internes (ex. .redhat-000xx) sans pom.properties et absents de Maven Central. Le cataloguer de syft, lui, sait retrouver ces paquets en parsant le nom de fichier <groupId>.<artifactId>-<version>.jar (convention du packaging Quarkus « fast-jar » de cette image). Là encore, ce n’est pas le SBOM qui invente des CVE : c’est trivy image qui en manque quelques-unes que trivy sbom retrouve grâce à la détection plus complète de syft.

Le même type d’écart existe pour OSV-Scanner, mais de façon bien plus radicale : sur les paquets de distribution (Debian/Alpine/RPM), lui donner un SBOM peut faire tomber le résultat à zéro CVE, alors que scanner l’image directement en trouve des centaines. En cause : osv-scanner scan source --sbom=…​ interroge l’API OSV.dev avec le purl du SBOM tel quel, mais OSV.dev n’indexe les avis Debian que sous une forme purl très spécifique — paquet source, arch=source, nom de code de la distribution (ex. pkg:deb/debian/openssl?arch=source&distro=trixie) — différente du purl standard produit par syft/sbom_generator pour un paquet Debian (pkg:deb/debian/<paquet-binaire>@<version>?arch=amd64&distro=debian-13.6, conforme à la spec purl). Sur l’image Debian réelle citée plus haut, cela donnait 0 CVE via osv-scanner scan source --sbom=, contre 233 via osv-scanner scan image (qui fait sa propre extraction et n’utilise aucun purl). Ce n’est pas un défaut du SBOM généré — le même écart existe avec un SBOM produit par syft seul — mais une limite du mode « scan de SBOM » d’OSV-Scanner pour les paquets de distribution : pour une couverture OS fiable avec cet outil, mieux vaut scanner l’image directement plutôt que passer par un SBOM.

12.5. Export AsciiDoc + PDF

Le bouton ⬥ (icône PDF, dans la carte de synthèse globale) exporte un rapport reprenant l’intégralité de la vue affichée :

  • le résumé global (scanners exécutés, CVE uniques) ;

  • la section Outils : version de sbom_generator_gui et version de chaque scanner exécuté (détectées via <outil> --version au moment de l’export, donc toujours à jour même si l’outil a été mis à jour depuis le dernier scan — « indisponible » si l’outil n’est plus dans le PATH) ;

  • pour chaque scanner : sa répartition par sévérité avec barre colorée (ou « Non exécuté » / « Aucune vulnérabilité détectée » selon le cas) ;

  • le tableau complet de comparaison inter-scanners (sévérité, CVE/ID, présence par outil), avec les CVE préfixés distro déjà normalisés (voir Pourquoi Grype, OSV-Scanner et Trivy ne trouvent pas les mêmes CVE).

Contrairement aux onglets Grype/OSV-Scanner/Trivy, il n’y a ici qu’une seule vue de synthèse — pas de lignes filtrées/triées individuellement à exporter.

Le bouton reste désactivé tant qu’aucun scanner n’a été exécuté. Une fois le fichier .adoc écrit (emplacement choisi via une boîte de dialogue), la conversion en PDF via asciidoctor-pdf est tentée automatiquement ; si l’outil n’est pas installé, le fichier .adoc reste produit et un message l’indique — même comportement que l’export des onglets de scan (voir [sec-vue-table]). Le PDF reprend les couleurs du Tableau de bord (badges de sévérité, barre de répartition, en-têtes bleus) — voir [sec-vue-table] pour le détail du thème.

Note
 Le Tableau de bord se met à jour automatiquement chaque fois qu’une analyse est lancée dans un onglet scanner. Aucune action supplémentaire n’est requise.
