4. Panneau Configuration

4.1. Section Entrée

4.1.1. Fichier d’entrée (--input)

Chemin vers le fichier contenant la liste des paquets à analyser. Le bouton 📂 à droite du champ propose un menu :

Type filtré (.lst, .txt…)

N’affiche que les fichiers aux extensions courantes

Tous les fichiers

Affiche tous les fichiers du répertoire
Tip
 Vous pouvez également glisser-déposer un fichier depuis votre gestionnaire de fichiers (Nautilus, Thunar…) directement sur ce champ. Un liseré bleu indique que le dépôt est accepté.

Le fichier doit contenir un élément par ligne. Les types acceptés sont :

Type Format de la ligne

Paquet RPM installé

bash ou bash-5.1.8-6.el9.x86_64

Fichier RPM local

/chemin/vers/package.rpm

Wheel Python (.whl)

/chemin/vers/package-1.0-py3-none-any.whl

Archive tar

/chemin/vers/pkg.tar.gz ou .tgz

Archive Zip

/chemin/vers/archive.zip

Paquet Debian (.deb)

/chemin/vers/package.deb

Dépendances Python

/chemin/vers/requirements.txt

Archive Java (.jar)

/chemin/vers/lib-1.2.3.jar

Manifeste / lockfile

go.sum, go.mod, package-lock.json, yarn.lock, pom.xml, pubspec.lock, pubspec.yaml

Un seul fichier d’entrée peut contenir des lignes de types différents. Un chemin pointant directement vers une archive ou un manifeste unique (plutôt que vers un fichier liste) est également accepté ; un répertoire est scanné récursivement pour tous ces types. Pour Dart/Flutter, pubspec.lock fournit les versions résolues et la fermeture transitive complète (les dépendances de développement sont exclues) ; pubspec.yaml ne fournit que les dépendances directes de la section dependencies:.

Note
 Le champ Fichier d’entrée devient optionnel si une Image OCI est spécifiée dans la section suivante.
Important
 Les champs Fichier d’entrée et Image OCI sont mutuellement exclusifs dans l’interface : remplir l’un (saisie, glisser-déposer ou sélecteur de fichier/répertoire) vide automatiquement l’autre. Pour combiner les deux sources en une seule analyse, utilisez la ligne de commande (--input et --image ensemble).

4.2. Section Image OCI

4.2.1. Image OCI (--image)

Référence à une image OCI à analyser. Trois formats sont acceptés :

Format Description Exemple

Registre

Image Docker Hub ou registre privé

nginx:latest

Archive tar

Export docker save ou skopeo copy docker-archive: (.tar, .tar.gz, .tgz)

/path/ubuntu.tar, /path/image.tar.gz

OCI layout

Répertoire contenant index.json

/path/oci_dir/

Le bouton 📂 à droite du champ ouvre un menu contextuel :

  • Archive tar (.tar / .tar.gz / .tgz) — sélecteur de fichier filtré sur ces trois extensions

  • Répertoire OCI layout — sélecteur de répertoire

Pour les images de registre, saisissez la référence manuellement.

Si le champ est vide, l’analyse OCI est désactivée.

4.2.2. Outil OCI (--oci-tool)

Visible uniquement lorsque le champ Image OCI est rempli. Sélectionnez le backend d’analyse :

Outil Description Prérequis

Syft (défaut)

Anchore Syft — tous types de paquets (deb, rpm, apk, pypi, npm, go, java…)

syft dans le PATH

Trivy

Aqua Trivy — tous types de paquets

trivy dans le PATH

Skopeo

Extraction manuelle des layers — dpkg, RPM et APK uniquement

skopeo et tar dans le PATH

cdxgen

OWASP CycloneDX Generator — tous types de paquets ; le SBOM produit est filtré aux composants porteurs d’un PURL d’écosystème réel

cdxgen dans le PATH (requiert Node.js)

4.2.3. Un SBOM par couche (--per-layer)

Case à cocher visible sous le backend OCI, uniquement pour une Image OCI (un binaire autonome n’a pas de couches). Une fois cochée, la génération produit, en plus du SBOM global, un SBOM par couche de l’image dans chaque format coché : <sortie>.layer-NN-<digest>.<ext> (ex. sbom.layer-02-b676b687f0f5.cdx.json).

Le SBOM d’une couche décrit son delta : les composants ajoutés ou modifiés par la couche, avec les composants supprimés listés à part ; son composant racine porte l’instruction de build (RUN …, COPY …) et le digest de la couche. Le SBOM global indique, pour chaque composant, la couche qui l’a introduit.

Le sélecteur de méthode (--layer-mode) propose :

Méthode Principe

Métadonnées (défaut)

Couche d’origine indiquée par Syft ou Trivy. Rapide ; seuls les ajouts sont connus. Indisponible avec Skopeo et cdxgen.

Rootfs

Les couches sont appliquées une à une et l’image est réanalysée après chacune : ajouts, modifications (montée de version…) et suppressions. Une analyse par couche, donc plus lent. Seul mode possible avec Skopeo et cdxgen (rappel affiché sous le sélecteur). Pour une image de registre, skopeo doit être installé.

Les SBOM de couche se parcourent depuis les onglets Arborescence SBOM et Visionneuse SBOM (voir Navigation par couche (--per-layer)). Le SBOM global est toujours le premier fichier produit : c’est lui que les autres onglets (Aperçu, scanners, Qualité, CRA…) sélectionnent par défaut.

4.2.4. Binaire autonome (--binary)

Champ séparé, sous un second séparateur « OU » : exécutable local à analyser directement (pas une image de conteneur) — par exemple un binaire Go lié statiquement. Le bouton 📂 ouvre un sélecteur de fichier simple (aucun filtre d’extension, un binaire n’en a souvent pas).

Mutuellement exclusif avec Paquets à analyser et Image OCI : renseigner ce champ vide automatiquement les deux autres, et réciproquement.

Force systématiquement le backend Syft (le sélecteur Outil OCI n’est pas affiché pour ce champ) — c’est le seul backend qui sache exploiter les métadonnées embarquées dans un binaire autonome :

  • Go (lié statiquement ou non) : la liste complète des modules + versions est lue depuis les métadonnées buildinfo embarquées dans l’exécutable, même strippé.

  • Autres langages (Rust, C/C++ statiques…) : seul un catalogue fixe de bibliothèques open source connues (OpenSSL, zlib, sqlite, busybox…) est détecté par empreinte de chaîne de version — pas une extraction arbitraire des dépendances liées.

  • Une bibliothèque liée statiquement sans signature reconnue ni métadonnée embarquée (C/C++ « fait maison », Rust sans cargo-auditable) ne peut pas être retrouvée après coup.

4.3. Section Sortie

4.3.1. Chemin de base (--output)

Préfixe des fichiers générés, sans extension. Exemple : sbom produira sbom.cdx.json, sbom.spdx.json, etc. Un chemin relatif est résolu depuis le répertoire courant au moment du lancement.

Une prévisualisation des noms de fichiers attendus s’affiche dès que le champ est renseigné.

4.3.2. Formats (--format)

Cochez un ou plusieurs formats. Au moins un format doit être sélectionné.

Format Extension produite Usage typique

CycloneDX 1.6

.cdx.json

Analyse de vulnérabilités avec grype, outils OWASP

SPDX 2.3

.spdx.json

Conformité légale, outils OpenChain

SPDX 3.0 JSON-LD

.spdx3.jsonld

Écosystèmes liés (RDF/ontologie)

JSON personnalisé

.custom.json

Intégration dans des pipelines internes

Markdown

.md

Documentation lisible directement sur GitHub/GitLab

AsciiDoc

.adoc

Rapport technique riche (tableaux, styles)

HTML

.html

Rapport interactif autonome (filtrable et triable, graphiques par écosystème/licence)

CSV

.csv

Import dans un tableur ou un pipeline de traitement de données

4.3.3. Option PDF (AsciiDoc uniquement)

Quand le format AsciiDoc est coché, une option supplémentaire apparaît : Convertir en PDF (asciidoctor-pdf). Si elle est activée, l’outil asciidoctor-pdf est lancé automatiquement après la génération du .adoc.

Un champ optionnel permet de spécifier le chemin de destination du PDF. Sans valeur, le PDF est créé dans le même dossier que le .adoc, avec le même nom de base.

4.4. Section Options

4.4.1. Nom du document SBOM (--name)

Libellé qui apparaîtra dans les métadonnées du SBOM (champ metadata.component.name en CycloneDX). Exemple : Mon Application 2.1.0. Laissez vide pour utiliser le nom du fichier d’entrée.

4.4.2. Répertoire RPM local (--rpm-dir)

Dossier contenant des fichiers .rpm supplémentaires à inclure dans l’analyse. Utile pour enrichir la résolution de métadonnées (version exacte, licence) lorsque les paquets ne sont pas installés sur la machine courante.

4.4.3. Override de licences (--license-map)

Fichier texte permettant de corriger ou préciser les licences de certains paquets. Le bouton à droite propose les mêmes options que le champ fichier d’entrée : type filtré (.txt, .yaml) ou tous les fichiers. Format : une règle par ligne : nom-paquet: SPDX-expression

Exemple :

openssl: OpenSSL
my-internal-lib: LicenseRef-PROPRIETARY

4.4.4. Concurrence (--concurrency)

Nombre de paquets traités en parallèle. Le curseur va de 0 (illimité) à 16. La valeur par défaut est 4.

  • Augmentez si votre machine a de nombreux cœurs et une bonne connexion réseau.

  • Diminuez (1 = séquentiel) en cas d’erreurs de rate-limiting sur les dépôts.

  • La valeur 0 traite tous les paquets simultanément — à utiliser avec prudence sur de grandes listes.

4.4.5. Mode verbeux (--verbose)

Affiche dans l’onglet Progression des informations supplémentaires : outils de résolution utilisés, statistiques de traitement, détails de chaque paquet trouvé.

4.4.6. Score qualité sbomqs

Quand cette option est cochée, sbomqs score est exécuté automatiquement sur le premier fichier SBOM JSON généré (.cdx.json ou .spdx.json). Le résultat s’affiche dans l’onglet Résultats sous la liste des fichiers.

Si sbomqs n’est pas installé, l’option est ignorée silencieusement.

Note
 Voir Installer sbomqs (optionnel) pour l’installation.

4.5. Persistance des paramètres

Tous les paramètres de la section Options — formats sélectionnés, chemin de base, répertoire RPM, fichier de licences, niveau de concurrence, mode verbeux, génération PDF, score sbomqs — sont automatiquement sauvegardés après chaque génération et restaurés au prochain démarrage de l’application.

Les paramètres sauvegardés ne comprennent pas le fichier d’entrée (trop lié à un contexte particulier) ni le chemin du PDF.

4.6. Profils de configuration

Un profil regroupe tous les paramètres de configuration sous un nom personnalisé, et peut être rappelé en un clic pour basculer rapidement entre plusieurs configurations types (ex. : « RHEL 9 production », « Audit Python », « CI/CD minimal »).

4.6.1. Accéder aux profils

Cliquez sur l’icône 🔖 (signets) en haut à droite de l’en-tête du panneau Configuration.

  ┌─ Configuration ────────────────── [🔖] ─┐
  │  ...                                     │

4.6.2. Fenêtre de gestion des profils

  ┌─ Profils de configuration ──────────────────────────────────┐
  │                                                              │
  │  Nom du profil : [ RHEL 9 production      ] [Enregistrer]  │
  │                                                              │
  │  ─────────────────────────────────────────────────────────  │
  │  RHEL 9 production               [Charger] [Supprimer]      │
  │  Audit Python                    [Charger] [Supprimer]      │
  │  CI/CD minimal                   [Charger] [Supprimer]      │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘

Enregistrer

Sauvegarde l’état actuel de tous les champs sous le nom saisi

Charger

Applique les valeurs du profil (sauf le fichier d’entrée)

Supprimer

Demande confirmation, puis supprime le profil
Note
 Le fichier d’entrée n’est pas inclus dans les profils — il est généralement propre à chaque contexte d’utilisation.
Tip
 Si un profil du même nom existe déjà, Enregistrer le met à jour.

4.7. Prévisualisation de la commande

Sous le bouton ▶ Générer le SBOM s’affiche en permanence la ligne de commande shell équivalente à la configuration actuelle :

  $ sbom-generator --input /home/user/paquets.lst \
    --output /home/user/sbom --format cyclonedx spdx

Cette prévisualisation se met à jour à chaque modification d’un champ. Un bouton 📋 permet de copier la commande dans le presse-papiers pour la rejouer depuis un terminal ou l’intégrer dans un script CI/CD.

4.8. Lancer et arrêter la génération

Cliquez sur ▶ Générer le SBOM pour démarrer. Le bouton se transforme en ■ Arrêter la génération pendant l’exécution. Cliquer sur Arrêter envoie un signal d’interruption au processus.
