8.1. Indicateur de version

En haut du panneau de configuration, l’application affiche la version de grype installée ainsi que l’état de mise à jour, vérifiés en arrière-plan au démarrage :

  • ✔ v0.87.0 (vert) — grype est installé et à jour.

  • ↑ v0.87.0 → v0.88.1 (orange, cliquable) — une nouvelle version est disponible sur GitHub. Cliquez pour ouvrir la page de release dans le navigateur.

  • non installé (rouge) — grype n’est pas trouvé dans le PATH.

Note
 La vérification interroge l’API GitHub. En l’absence de connexion réseau, seule la version installée est affichée, sans comparaison.

8.2. Sélection de la source à analyser

Une bascule Fichier SBOM / Image de conteneur / Paquet / archive en haut du panneau permet de choisir ce que grype analyse. Ce choix, ainsi que le champ associé, est commun aux trois onglets de scan (Grype, OSV-Scanner, Trivy) — voir aussi Sélection de la source à analyser et Sélection de la source à analyser.

Fichier SBOM (mode par défaut) : le champ est pré-rempli automatiquement avec le dernier fichier SBOM généré dans la session courante, en priorisant les formats reconnus par grype : .cdx.json (CycloneDX) puis .spdx.json (SPDX). Vous pouvez saisir manuellement un chemin ou cliquer sur Choisir pour parcourir le système de fichiers. Les formats .json et .jsonld sont proposés dans le sélecteur.

Note
 Grype analyse le contenu du fichier, pas son extension. Un fichier CycloneDX renommé .json est reconnu correctement.

Image de conteneur : le champ accepte trois formes de référence, toutes prises en charge par grype sans distinction de syntaxe côté application :

  • une référence de registre, ex. nginx:latest, ghcr.io/org/app:tag — l’image est récupérée via la configuration Docker locale (docker login) si le registre est privé, sans champ d’identifiants dédié dans l’application ;

  • une archive exportée par docker save (ou une archive OCI), via le bouton dédié (extensions .tar, .tar.gz, .tgz) ;

  • un répertoire au format OCI layout (produit par exemple par skopeo copy), via le second bouton dédié.

Un champ optionnel Plateforme apparaît en mode image, pour forcer la plateforme cible sur une image multi-architecture (ex. linux/arm64). Laissé vide, grype détecte automatiquement la plateforme la plus adaptée.

Paquet / archive : un fichier local — .rpm, .deb, .tar / .tar.gz / .tgz, .zip, .jar / .war / .ear, .whl — est analysé directement, sans passer par un fichier SBOM. L’application lance d’abord sbom-generator --input <fichier> --depth N (voir Profondeur de descente (--depth)) dans un répertoire temporaire, puis le scanner analyse le SBOM CycloneDX produit, exactement comme un fichier SBOM : les trois onglets (Grype, OSV-Scanner, Trivy) reçoivent donc les mêmes composants. Le sélecteur Profondeur (0 — objet seul, 1 à 3 niveaux, Illimitée) choisit jusqu’où descendre dans les objets contenus (jars d’un RPM, paquets d’une archive…). Le SBOM généré est réutilisé par les onglets tant que le fichier et la profondeur ne changent pas. L’en-tête des rapports exportés indique « paquet <nom> (profondeur N) ».

Note
 Les CVE s’affichent par paquet vulnérable (nom@version). Pour savoir quel objet imbriqué le contient, utiliser la commande Équivalent sbom-generator scan --package du bouton CLI Commande (colonne OBJET).

8.3. Ligne de commande (bouton CLI Commande)

Le bouton CLI Commande, à côté du bouton d’analyse (commun aux trois onglets de scan), ouvre un popup avec les commandes correspondant au paramétrage courant de l’onglet, chacune avec un bouton Copier :

  • Commande exécutée par l’onglet — la ligne grype / osv-scanner / trivy exacte, avec toutes les options de l’onglet (construite par le même code que l’exécution). Avec l’option Par couche (voir Analyse par couche (source « Image de conteneur »)), la séquence réellement lancée : génération du jeu de SBOM par couche (sbom-generator --image … --per-layer), puis le scan de l’image (Rattachement) ou une boucle for f in …; do …; done sur les SBOM de couche (Chaque couche). Le répertoire temporaire de l’application est remplacé par /tmp/sbom-couches.

  • Équivalent sbom-generator scan — la commande du CLI du projet qui produit le même type d’analyse : cible (--sbom ou --image), --scanner, options par couche (--per-layer --layer-scan … --layer-mode …), filtre de date de l’onglet (--cve-after, --cve-before, --cve-date-field, --include-undated) et enrichissement hors-ligne (--no-enrich). Une remarque signale les options de l’onglet sans équivalent (template, --fail-on, --only-fixed, sévérités Trivy, fichiers de configuration…) et rappelle qu’avec --image, sbom-generator scan analyse le SBOM généré par syft et non l’image directement.

En source Paquet / archive, le popup affiche en plus la génération du SBOM (sbom-generator --input … --depth N, SBOM écrit dans /tmp/sbom-paquet/) avant la commande du scanner, et l’équivalent est sbom-generator scan --package … --depth N.

Tant que la cible n’est pas renseignée, elle apparaît sous la forme <sbom.cdx.json>, <image> ou <paquet>.

8.4. Analyse par couche (source « Image de conteneur »)

En mode Image de conteneur, la case Par couche (commune aux trois onglets de scan) attribue chaque vulnérabilité à la couche de l’image qui apporte le paquet vulnérable. L’application génère d’abord, via sbom-generator --image … --per-layer (backend syft), un SBOM global et un SBOM par couche dans un répertoire temporaire ; ce jeu est réutilisé par les trois onglets tant que l’image et le calcul ne changent pas.

Méthode Principe Ce qu’on voit

Rattachement (défaut)

Un seul scan de l’image, comme sans l’option ; chaque vulnérabilité est rattachée à la couche d’origine de son paquet. Trivy et OSV-Scanner indiquent eux-mêmes cette couche (Layer.DiffID, image_origin_details), utilisée en priorité ; sinon, le paquet est cherché dans le SBOM global.

Les CVE de l’image finale, par couche qui les a introduites.

Chaque couche

Le SBOM de chaque couche est scanné séparément (un scan par couche) ; les sorties sont fusionnées.

En plus, les CVE d’une version introduite par une couche puis remplacée plus haut (avec le calcul Rootfs). Une CVE peut apparaître dans plusieurs couches.

Le second sélecteur choisit le calcul des couches : Métadonnées (couche d’origine indiquée par syft — rapide, ajouts seulement) ou Rootfs (couches appliquées une à une et réanalysées — ajouts, modifications, suppressions ; plus lent). Pendant l’analyse, une ligne d’état indique l’étape en cours (préparation des SBOM, couche i/N…) ; le bouton Stop interrompt aussi la génération et les scans restants.

Dans la Vue Table (voir [sec-vue-table]) :

  • une colonne COUCHE affiche la ou les couches de chaque vulnérabilité (? si le paquet est absent du SBOM de l’image — un bandeau en indique le nombre) ; l’info-bulle rappelle le digest et l’instruction de build ;

  • le menu Toutes les couches / Couche N (n) filtre sur une couche ;

  • le bouton Grouper par couche (icône de couches) regroupe la liste sous un en-tête par couche — digest, instruction de build et compteurs par sévérité ;

  • les exports CSV et AsciiDoc + PDF ajoutent une colonne Couche(s) et, pour le PDF, une section Couches de l’image.

Le Tableau de bord reprend ces informations (voir Couches de l’image).

Note
 En mode Chaque couche, OSV-Scanner analyse des SBOM et non l’image : il trouve alors peu ou pas de CVE sur les paquets système (voir [sec-pourquoi-ecarts-scanners]) — préférer le Rattachement avec cet outil.

8.5. Options de scan

8.5.1. --platform linux

Force grype à considérer la plateforme cible comme Linux lors de la résolution des vulnérabilités, en mode Fichier SBOM uniquement. Recommandé pour les SBOM issus de listes de paquets RPM ou DEB.

Décochez cette option si vous analysez un SBOM issu d’un autre système (bibliothèques macOS…).

Note
 Cette case n’a aucun effet en mode Image de conteneur : elle est ignorée au profit du champ Plateforme décrit ci-dessus (linux seul, sans architecture, est d’ailleurs rejeté par grype sur une image multi-plateforme).

8.5.2. --add-cpes-if-none

Grype utilise les identifiants CPE (Common Platform Enumeration) pour faire correspondre les paquets aux entrées CVE. Si un paquet du SBOM ne possède pas de CPE déclaré, cette option demande à grype d’en générer un automatiquement depuis le nom et la version du paquet.

Recommandé : réduit les faux-négatifs sur des SBOM produits sans CPE (c’est le cas de la plupart des SBOM générés par sbom-generator).

8.5.3. --by-cve

Sans cette option, grype groupe les résultats par identifiant GHSA (GitHub Security Advisory) quand il est disponible. Avec cette option, chaque résultat est présenté sous son identifiant CVE principal, plus universel et reconnu par les outils de gestion des vulnérabilités.

Recommandé pour l’interopérabilité avec des outils de ticketing (Jira, défauts, etc.) ou des référentiels de vulnérabilités internes.

8.5.4. --distro rhel:<version>

Précise la distribution Linux cible. Sans cette option, grype tente de la déduire du SBOM, ce qui peut échouer ou produire des correspondances imprécises.

Versions RHEL disponibles dans le menu : 7, 8, 9, 10. Sélectionnez (aucune) pour laisser grype détecter automatiquement la distribution.

Note
 Choisir la mauvaise version peut engendrer des faux-positifs (vulnérabilités non applicables car déjà corrigées par le backport RHEL) ou des faux-négatifs. Vérifiez la version exacte de votre système avec cat /etc/redhat-release.

8.5.5. --fail-on <sévérité>

Contrôle le code de retour de grype. Avec cette option, grype retourne un code d’erreur (non nul) si au moins une vulnérabilité du niveau indiqué ou supérieur est détectée. Utile en CI/CD.

Exemple : --fail-on high fait échouer l’analyse si une vulnérabilité High ou Critical est trouvée.

La bannière de résultat dans l’UI reflète ce code de retour : fond rouge si grype a retourné une erreur, fond vert sinon.

8.5.6. --only-fixed

N’affiche que les vulnérabilités pour lesquelles une version corrigée est disponible. Permet de se concentrer sur les actions immédiatement réalisables.

8.6. Template de sortie (-t)

Le champ Template (-t) permet de générer une sortie personnalisée (CSV, HTML, texte) via un fichier template Go.

Le champ est pré-rempli avec ./grype_csv.tmpl. Si ce fichier n’existe pas au moment du lancement, la sortie template est ignorée sans erreur.

Exemple de template Go pour un CSV :

"CVE","Paquet","Version installée","Version corrigée","Sévérité"
{{- range .Matches}}
"{{.Vulnerability.ID}}","{{.Artifact.Name}}","{{.Artifact.Version}}","{{fixedIn .Vulnerability}}","{{.Vulnerability.Severity}}"
{{- end}}

La sortie produite est affichée dans l’onglet Template (voir vue Template) et peut être copiée dans le presse-papiers.

Note
 Grype est lancé en une seule passe qui produit simultanément la sortie JSON (pour la vue Table) et la sortie template (via un fichier temporaire).

8.7. Fichier de configuration (grype.yaml)

Chemin vers un fichier de configuration grype au format YAML. Permet de définir des règles d’ignorance, des bases de données personnalisées, des proxies, etc.

Ce paramètre est optionnel. Laissez le champ vide pour utiliser la configuration grype par défaut (~/.grype.yaml si elle existe).

Documentation officielle : https://github.com/anchore/grype#configuration

8.8. Lancer et arrêter l’analyse

Cliquez sur Analyser pour démarrer. Une barre de progression linéaire s’affiche pendant l’exécution. Le bouton devient Stop pour interrompre.

8.9.2. Vue Table

La vue Table affiche une barre d’outils de recherche/tri, les filtres par sévérité, puis la liste des vulnérabilités :

  [ Rechercher...                        ] [⬇]
  Filtre : [Critical (1)] [High (2)] [Medium (2)] [Low (0)]  [Tout voir]

  ┌────────────┬──────────────────┬──────────────────┬───────────────┬──────┐
  │ SÉVÉRITÉ ↕ │ PAQUET ↕         │ VERSION ↕        │ CVE/ID ↕      │ TYPE │
  ├────────────┼──────────────────┼──────────────────┼───────────────┼──────┤
  │ CRITICAL   │ openssl          │ 1.1.1k → 1.1.1l  │ CVE-2021-3711 │ rpm  │
  │ HIGH       │ bash             │ 5.0.17  (no fix) │ CVE-2021-3489 │ rpm  │
  │ MEDIUM     │ zlib             │ 1.2.11  → 1.2.12 │ CVE-2022-37434│ rpm  │
  └────────────┴──────────────────┴──────────────────┴───────────────┴──────┘

Fusion des doublons visuels : un même composant peut être détecté à plusieurs emplacements distincts dans l’image/le SBOM analysé — par exemple une bibliothèque présente à la fois en jar autonome et reshadée (embarquée) dans un autre jar — avec exactement la même sévérité, le même CVE, le même paquet et la même version. Grype et Trivy remontent alors, à raison, deux résultats distincts, mais visuellement identiques dans ce tableau (aucune colonne n’affiche le chemin du fichier). Ces lignes sont donc fusionnées en une seule, avec un badge ×N à côté de l’identifiant CVE — survolez-le pour voir le nombre d’emplacements réels. Cette fusion s’applique à la bannière de synthèse, aux compteurs de sévérité et aux exports (voir ci-dessous) ; seule la vue JSON (vue JSON) reste fidèle à la sortie complète et non fusionnée de l’outil.

Recherche : le champ de recherche filtre en temps réel sur le nom du paquet, l’identifiant CVE, la version ou le type.

Tri : cliquez sur l’en-tête d’une colonne (SÉVÉRITÉ, PAQUET, VERSION, CVE/ID) pour trier dans l’ordre croissant, cliquez à nouveau pour inverser. La flèche ↑↓ indique la colonne et le sens de tri actifs. Par défaut, les résultats sont triés par sévérité décroissante (Critical en premier).

Export CSV : le bouton ⬇ (téléchargement) exporte la liste filtrée en cours (tenant compte de la recherche, des filtres sévérité, et déjà fusionnée — voir ci-dessus) dans un fichier .csv au format RFC 4180. Colonnes : Sévérité, CVE/ID, Paquet, Version installée, Version corrigée, Type, Emplacements (nombre d’occurrences fusionnées, 1 si le composant n’est présent qu’à un seul endroit).

Export AsciiDoc + PDF : le bouton ⬥ (à côté de l’export CSV) exporte la liste filtrée dans un rapport soigné : page de garde (titre, date, cible analysée, version), résumé exécutif — un encart chiffré « Critiques / Élevées / CISA KEV / Total » et un verdict d’une phrase (« Action immédiate requise » si des CVE KEV sont présentes, etc.) — barre de répartition par sévérité, section Outils (versions détectées via <outil> --version au moment de l’export, donc toujours à jour), puis le tableau détaillé. Le fichier .adoc est ensuite converti en PDF via asciidoctor-pdf ; si l’outil est absent, le .adoc reste produit et un message l’indique. L’emplacement de sortie est choisi via une boîte de dialogue.

Le PDF utilise une mise en forme sobre : police sans-serif, palette bleu-ardoise, en-têtes de tableau foncés, badges de sévérité colorés (libellés français : CRITIQUE / ÉLEVÉE / MOYENNE / FAIBLE), pied de page avec titre du rapport et pagination « Page X / Y ». Le rapport du tableau de bord (bouton d’export de sa carte de synthèse) suit la même charte et ajoute une section « Détail des CVE ».

Filtres par sévérité : cliquez sur un ou plusieurs badges pour n’afficher que les vulnérabilités du niveau correspondant. Le bouton Tout voir efface les filtres actifs. Seuls les badges correspondant à des sévérités présentes dans les résultats sont affichés.

Filtre par date : une barre de filtrage temporel se trouve au-dessus de la table. Elle permet d’afficher uniquement les CVE publiées ou modifiées dans une plage de dates donnée :

  📅 Date CVE : [Publication] [Modification] [La plus récente]
     Après le : [2024-01-01 ×]   Avant le : [2024-12-31 ×]
     [✓] Sans date    [Propager aux autres onglets]

  • Champ de date : sélecteur à trois valeurs — Publication (date initiale de publication du CVE), Modification (dernière mise à jour), La plus récente (la plus tardive des deux dates disponibles).

  • Après le / Avant le : chips cliquables ouvrant un calendrier. Un × permet d’effacer chaque borne indépendamment.

  • Sans date : case à cocher pour inclure les CVE dont le champ de date sélectionné est absent ou non renseigné dans les données du scanner. Par défaut, ces CVE sont exclues lorsqu’un filtre est actif.

  • Propager aux autres onglets : copie le filtre en cours vers les deux autres onglets CVE (OSV-Scanner et Trivy). Les analyses elles-mêmes ne sont pas relancées ; seul l’affichage est filtré.

Note
 Le filtre par date s’applique en post-traitement sur le JSON retourné par Grype. Il est indépendant des options de ligne de commande Grype et cumulable avec les filtres par sévérité et par recherche textuelle.

Colonnes :

  • Badge de sévérité : libellé coloré (CRITICAL / HIGH / MEDIUM / LOW / NEGLIGIBLE)

  • Paquet : nom du paquet concerné en gras

  • Versions : version installée, et version corrigée si disponible (après →). La mention (won’t fix) indique que le mainteneur ne prévoit pas de correction.

  • CVE : identifiant de la vulnérabilité

  • Type : type de paquet (rpm, python, deb…)

Cliquer sur une ligne la déplie et affiche le détail complet de la CVE : paquet et versions, sévérité et dates telles que rapportées par le scanner, exploitabilité détaillée (KEV, EPSS, CVSS, PoC) et boutons de référence (NVD, CVE.org, osv.dev, CISA KEV). Le panneau de détail contient un bouton copier l’identifiant. Re-cliquer sur la ligne la referme.

8.9.3. Exploitabilité et exploitation active

Après chaque scan, l’application enrichit les CVE trouvées avec quatre signaux de priorisation, affichés sous forme de pastilles sous chaque ligne et de colonnes triables KEV / EPSS :

  • KEV (pastille rouge 🔥) — la CVE est au catalogue CISA Known Exploited Vulnerabilities : exploitation active confirmée dans la nature. Le survol indique la date d’ajout et l’éventuel usage par un rançongiciel.

  • EPSS — score Exploit Prediction Scoring System (FIRST.org), de 0 à 1 : probabilité d’exploitation dans les 30 jours, avec son percentile.

  • PoC — un exploit public est recensé (dépôts GitHub via poc-in-github, ou maturité E: du vecteur CVSS).

  • expl. — sous-score d’exploitabilité du vecteur CVSS (AV/AC/PR/UI), de 0 à 3,9, calculé localement.

Grype fournit déjà KEV, EPSS et le vecteur CVSS dans sa base : pour l’onglet Grype, seul le signal PoC nécessite une requête réseau. Pour OSV-Scanner et Trivy, l’enrichissement KEV/EPSS se fait en ligne. Les réponses sont mises en cache 24 h dans ~/.cache/sbom-generator/ (partagé avec la ligne de commande).

Filtre CISA KEV : une pastille CISA KEV (N) apparaît à côté des filtres de sévérité dès qu’une CVE exploitée est présente — cliquez dessus pour n’afficher que ces CVE. Le tri KEV place les CVE du catalogue en tête ; le tri EPSS ordonne par probabilité décroissante.

Basculer en ligne / hors-ligne : l’icône ☁ dans la barre d’outils de la table active ou coupe les requêtes réseau d’enrichissement. Le choix est mémorisé (comme le thème) et partagé par les trois onglets de scan. Hors-ligne, seules les données fournies par Grype et le cache local sont utilisées.

Les exports CSV et AsciiDoc/PDF gagnent les colonnes KEV, EPSS et PoC quand l’enrichissement a produit des résultats ; le tableau de bord marque les CVE KEV/EPSS élevé dans sa comparaison inter-scanners et les remonte en tête.

8.9.4. Vue JSON

Affiche la sortie JSON brute de grype, formatée et indentée. Utile pour inspecter le détail d’une vulnérabilité (CVSS, références, métadonnées…).

Le bouton 📋 en haut à droite copie l’intégralité du JSON dans le presse-papiers.

8.9.5. Vue Template

Affiche le résultat de la génération du fichier template (CSV ou autre format personnalisé). Visible uniquement si un fichier template a été configuré dans le champ Template (-t).

Un hint s’affiche si aucun template n’est configuré ou si l’analyse n’a pas encore été lancée.

Le bouton 📋 copie la sortie dans le presse-papiers.
